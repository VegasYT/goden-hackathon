# AGENTS.md - backend

Серверная часть системы мониторинга склада ресторана. Общий контекст проекта: [../AGENTS.md](../AGENTS.md), кейс: [../docs/Case.md](../docs/Case.md).

Архитектурные решения приняты в [../docs/ADR.md](../docs/ADR.md), состав системы и этапы - в [../docs/plan.md](../docs/plan.md). Код не должен им противоречить. Если задача требует отступить от ADR, сначала меняется ADR через OpenSpec change.

## Команды

Запускаются из `backend/`. Go 1.27 ставить не нужно: установленный Go 1.21+ сам скачает toolchain из `go.mod`.

- `go build ./...` - сборка
- `go test ./...` - unit-тесты, Docker не нужен
- `go test -tags=integration ./...` - все тесты, включая интеграционные; нужен запущенный Docker
- `GOTOOLCHAIN=go1.27.2 go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.14.0 run ./...` - линтер; `GOTOOLCHAIN` обязателен, иначе линтер соберётся более старым Go и откажется проверять модуль
- то же с `fmt` вместо `run` - форматирование `gofumpt`
- `DATABASE_URL=postgres://... go run ./cmd/migrate` - применить миграции; с `DEMO_COMPANY=true` после них создаётся демонстрационная компания (см. "Окружение разработки")
- `DATABASE_URL=postgres://... KAFKA_BROKERS=localhost:9092 go run ./cmd/api` - запустить API и SSE на `:8080`
- `DATABASE_URL=postgres://... go run ./cmd/worker` - запустить процесс фоновых задач, health на `:8081`; он выполняет проекции, контроль сроков и, при настройке Telegram, уведомления: без него списки и аналитика не обновляются, просроченные партии не отмечаются и сообщения не отправляются
- `go run ./cmd/generator` - запустить генератор событий, health на `:8082`; нужен запущенный API, база ему не нужна
- `GOTOOLCHAIN=go1.27.2 go run github.com/ogen-go/ogen/cmd/ogen@v1.24.0 --target internal/api/oas --package oas --clean api/openapi.yaml` - перегенерировать сервер и клиент после правки контракта; результат коммитится
- `GOTOOLCHAIN=go1.27.2 go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate` - перегенерировать код запросов после правки `queries.sql` или миграций; результат коммитится
- `UPDATE_GOLDEN=1 go test ./internal/...` - перезаписать эталонные JSON событий после намеренного изменения формата
- `GODEN_LOAD_ORDERS=2000 go test -tags=integration -v -run TestStockStaysConsistentUnderLoad ./internal/inventory/` - нагрузочный тест с увеличенным объёмом (по умолчанию 300 заказов); печатает число операций и скорость

Перед завершением задачи должны проходить сборка, все тесты и линтер.

Имя модуля - `goden/backend`, импорты внутри проекта начинаются с него. В имени нет точки, поэтому `goimports` в редакторе может переносить импорты проекта в группу стандартной библиотеки. Для VS Code добавь в настройки `"gopls": { "formatting.local": "goden" }`. В линтере это уже учтено настройкой `module-path`.

Переменные окружения: `DATABASE_URL` (обязательная), `DATABASE_MAX_CONNS` (по умолчанию 10), `LOG_LEVEL` (по умолчанию `info`), `HTTP_ADDR` (`:8080` у API, `:8081` у worker), `SHUTDOWN_TIMEOUT` (по умолчанию `15s`).

Redis-кеш API включается, только когда задан `REDIS_URL` (локально `redis://localhost:6379`). `REDIS_CACHE_TTL` по умолчанию `1m`, `REDIS_TIMEOUT` — `100ms`. Кешируются только списки поставок и заказов точки и статистика списаний, списаний по дням и дефицита точки (`/points/{pointId}/deliveries`, `/orders`, `/analytics/write-offs`, `/analytics/write-offs/days`, `/analytics/shortages`); точка входит в ключ вместе с остальными параметрами запроса; checkpoint соответствующей проекции входит в ключ. При ошибке Redis API читает PostgreSQL, а `/readyz` остаётся успешным. Метрики: `goden_read_cache_requests_total{result}` и `goden_read_cache_operation_duration_seconds{operation}`.

Переменные доступа к API: `OIDC_ISSUER` (адрес realm, локально `http://localhost:8180/realms/goden`; обязательна, если не задан `AUTH_DISABLED`), `OIDC_AUDIENCE` (по умолчанию `goden-api`), `AUTH_DISABLED` (по умолчанию `false`), `CORS_ALLOWED_ORIGINS` (по умолчанию `http://localhost:5173`, несколько адресов через запятую).

Переменные Kafka для API и worker: `KAFKA_BROKERS` (по умолчанию `localhost:9092`, несколько адресов через запятую) и `KAFKA_TOPIC_PREFIX` (по умолчанию `goden`). API использует их для SSE-reader, worker — для publisher. Producer и reader явно создают нужные топики, не полагаясь на broker auto-create.

Переменные worker: `EXPIRY_WARNING_PERIOD` (по умолчанию `24h`: за сколько до окончания срока годности выдаётся предупреждение по партии; период один для всех продуктов, поэтому он должен быть меньше самого короткого срока хранения в каталоге, иначе предупреждение придёт сразу при приёмке), `EXPIRY_CHECK_INTERVAL` (по умолчанию `1m`: как часто проверяются сроки).

Telegram worker включается, только когда одновременно заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (числовой ID личного чата, группы или канала). `TELEGRAM_CHAT_ID` - общий чат окружения: в него уходят только сообщения об ошибках обработчиков (`errors.v1`). Уведомления о сроках и автосписании уходят в чат точки, который задаёт владелец или управляющий (`PUT /points/{pointId}/telegram-chat`, право `notifications.manage`); точка без чата уведомлений не получает вовсе - в общий чат они не попадают, иначе там оказались бы данные точек чужих компаний. Чат определяется при постановке в очередь (`pointTarget` в `internal/notifications/domain.go`) и хранится в записи (`notification_deliveries.chat_id`, ноль - общий чат); текст называет точку. Если обе переменные пусты, worker запускается без уведомлений; если задана только одна или ID некорректен, запуск завершается ошибкой конфигурации. Токен не записывается в логи. Уведомления приходят для `BatchExpiryWarningIssued`, `BatchExpired` (партия просрочена и ждёт решения о списании) и записей `errors.v1`; списания уведомлений не создают. При создании отправитель к Telegram не обращается: недоступный Telegram или прокси не мешает запуску worker, а неверный токен или чат виден по ошибкам отправки (причина пишется в журнал и в `notification_deliveries.last_error`, токен в ней заменён на `***`). Событие старше часа (`maxEventAge` в `internal/notifications/domain.go`) уведомления не порождает, как и предупреждение о партии с уже истёкшим сроком: новая группа читает топики с начала, и без отсечки в чат уходила вся история. Следствие: за простой уведомлений дольше часа сообщения не придут. Между отправками в один чат диспетчер выдерживает паузу (`SendInterval`, 3 секунды: ограничение Telegram для групп), а при ответе "слишком часто" не шлёт в этот чат названное Telegram время. Паузы ведутся по чатам (`busyUntil` в `internal/notifications/dispatcher.go`, в памяти экземпляра): очередь пропускает записи занятых чатов, остальные точки не ждут. 

Очередь хранится в `notification_deliveries`: Kafka handler только ставит запись в очередь вместе с inbox, а Telegram dispatcher отправляет вне транзакции и повторяет временные ошибки. У записи есть конечное состояние `failed`: в него она попадает сразу, если Telegram отклонил сообщение окончательно (`notifications.UndeliverableError`: чат не найден, бот не состоит в чате, запрос отклонён), и после часа неудачных повторов (`Dispatcher.MaxAge`). Чат точки задаёт пользователь, и без этого записи с неверным чатом повторялись бы бесконечно и занимали диспетчер остальных точек. Неверный токен бота окончательным отказом не считается. Причина остаётся в `last_error`; исход `failed` есть в метрике попыток, а в число ожидающих такие записи не входят. Отправленные и недоставленные записи старше семи суток диспетчер удаляет раз в час (`Dispatcher.Retention`, `Queue.Prune`). Метрики worker: `goden_notification_delivery_attempts_total{kind,outcome}`, `goden_notification_deliveries_pending`, `goden_notification_error_reader_errors_total`.

Переменные генератора: `API_URL` (по умолчанию `http://localhost:8080/api/v1`), `HTTP_ADDR` (`:8082`), `GENERATOR_SEED` (по умолчанию `true`: наполнить пустой каталог демонстрационным набором), `GENERATOR_POLL_INTERVAL` (по умолчанию `2s`), `LOG_LEVEL`, а для работы с API, проверяющим токены, - `OIDC_ISSUER`, `GENERATOR_CLIENT_ID` (локально `goden-generator`) и `GENERATOR_CLIENT_SECRET`. Без `GENERATOR_CLIENT_ID` генератор ходит без токена: это работает только с API в режиме `AUTH_DISABLED=true`. `DATABASE_URL` он не читает.

Генератор включается на точке её владельцем; у точки без настроек он остановлен:

```bash
curl http://localhost:8080/api/v1/points/<точка>/generator
curl -X PUT http://localhost:8080/api/v1/points/<точка>/generator -H 'Content-Type: application/json' \
  -d '{"running":true,"deliveries_per_minute":6,"orders_per_minute":30}'
```

Процесс генератора раз в `GENERATOR_POLL_INTERVAL` запрашивает `GET /generator/points` - точки, на которых он включён, - и на каждой создаёт поставки и заказы с её интенсивностью. Своих компаний и точек он не создаёт. Каталог компании включённой точки наполняется демонстрационным набором (`GENERATOR_SEED`), если он пуст или набор в нём не закончен: это решает `seedNeeded` в `internal/generator/seed.go` по самому каталогу, поэтому перезапуск посреди наполнения его продолжает. Каталог, где есть продукт или блюдо не из набора, не меняется.

Аналитика точки доступна с правом `analytics.view` на ней: `GET /api/v1/points/{pointId}/analytics/write-offs?from=<date-time>&to=<date-time>`, `.../analytics/write-offs/days?from=<date-time>&to=<date-time>&time_zone=Europe/Moscow`, `.../analytics/shortages?from=<date-time>&to=<date-time>` и `.../analytics/stop-list-forecast`. Списания по дням разбиты по дню в часовом поясе клиента (`time_zone`, имя IANA; проверяет `time.LoadLocation` со встроенной `time/tzdata`, день считает PostgreSQL), продукту и причине. Первые три ответа читают асинхронную проекцию worker; прогноз использует её историю расхода и актуальные рецептуры и партии. После первого запуска дождись нулевого `goden_projection_lag_events{projection="analytics"}`.

## Окружение разработки

Внешние сервисы описаны в `infra/compose.yaml`. Команды выполняются из корня репозитория:

```bash
docker compose -f infra/compose.yaml up -d --wait   # поднять и дождаться готовности
docker compose -f infra/compose.yaml down           # остановить, данные PostgreSQL и Kafka остаются
docker compose -f infra/compose.yaml down -v        # остановить и стереть данные
```

| Сервис | Адрес с хоста | Переменная порта |
| --- | --- | --- |
| PostgreSQL 18 | `postgres://goden:goden@localhost:15432/goden?sslmode=disable` | `POSTGRES_PORT` |
| Kafka 4 | `localhost:9092` | `KAFKA_PORT` |
| Redis 8 | `localhost:6379` | `REDIS_PORT` |
| Keycloak 26 | `http://localhost:8180`, консоль: `admin` / `admin` | `KEYCLOAK_PORT` |
| Prometheus | `http://localhost:9090` | `PROMETHEUS_PORT` |
| Grafana | `http://localhost:3000`, вход без пароля, дашборд "Goden backend" открыт сразу | `GRAFANA_PORT` |

Порты открыты только на `127.0.0.1`. Если порт занят, задай переменную перед запуском: `KAFKA_PORT=19092 docker compose -f infra/compose.yaml up -d --wait`. PostgreSQL опубликован на 15432, а не на 5432: стандартный порт часто занят локальной установкой.

Запуск backend на окружении (из `backend/`):

```bash
export DATABASE_URL="postgres://goden:goden@localhost:15432/goden?sslmode=disable"
go run ./cmd/migrate
go run ./cmd/api
go run ./cmd/worker   # в отдельном терминале: проекции для списков
```

Prometheus опрашивает `/metrics` процессов backend на хосте по адресам по умолчанию (`:8080`, `:8081`, `:8082`); незапущенный процесс виден как недоступная цель. Дашборд и источник данных лежат в `infra/grafana/`, правки из интерфейса Grafana не сохраняются - меняй файл. История метрик не переживает пересоздание контейнера.

Процессы backend в compose не входят и запускаются с хоста. Интеграционные тесты от окружения не зависят: они поднимают свои контейнеры.

Keycloak, realm `goden` (`infra/keycloak/goden-realm.json`):

- в realm включена самостоятельная регистрация; локально подтверждения почты нет (нужен почтовый сервер); на сервере оно включается настройкой `KEYCLOAK_VERIFY_EMAIL` (см. `infra/README.md`). Пока оно выключено, адрес почты не доказывает, что он принадлежит человеку: до подтверждения почты назначать сотрудников по адресу можно только тем, кому владелец доверяет;
- `goden-api` - получатель токенов (`aud`). Прав пользователей в realm нет: их определяют владение компанией и назначения на точку (ADR-013). Client roles - `generator.run` и `migom.integration`.
- `goden-web` - публичный клиент frontend (вход с PKCE, адрес `http://localhost:5173`).
- `goden-generator` - сервисная учётная запись генератора, секрет `goden-generator-dev-secret`. В токене у неё одно право `generator.run`: по нему API отдаёт список точек с включённым генератором и добавляет права на этих точках.
- `migom-api` и `migom-backend` - клиенты сервиса доставки Мигом (отдельный репозиторий), который входит через этот realm. `migom-backend` (секрет `migom-backend-dev-secret`, на сервере - `MIGOM_BACKEND_SECRET`) входит по паролю пользователя и обновляет токен, а его сервисная учётная запись с ролями `manage-users`, `view-users`, `query-users` клиента `realm-management` заводит пользователей и меняет им пароль. Его токены несут `aud` `migom-api` и `goden-api`: Мигом ходит в API Goden от имени своего пользователя (его точки в `GET /me`, подключение заведения, меню точки) с правами этого пользователя по владению и назначениям, без дополнительных. Пользователи Мигома - обычные пользователи realm: войдя в веб Goden, они попадают на создание компании. Keycloak 26 не пускает пользователя без имени и фамилии ("Account is not fully set up"), поэтому их задаёт и Мигом.
- `migom-web` - публичный клиент кабинетов Мигома (владельца и модератора): вход перенаправлением с PKCE через тему Goden, адреса возврата `https://owner.<домен Мигома>`, `https://admin.<домен Мигома>` (выставляет `keycloak-config` по `MIGOM_DOMAIN`) и `http://localhost:5174`, `http://localhost:5175`. Токены несут `aud` `migom-api` и `goden-api`.
- `migom-integration` - сервисная учётная запись Мигома для API Goden, секрет `migom-integration-dev-secret` (на сервере - `MIGOM_INTEGRATION_SECRET`). В токене у неё одно право `migom.integration` и `aud` `goden-api`: по нему API отдаёт пары "точка - заведение" (`GET /migom/points`) и добавляет права на подключённых точках.
- Тестовые пользователи `admin`, `manager`, `approver`, `cook`, `waiter`, пароль совпадает с логином, почта `<логин>@goden.local`. Их идентификаторы заданы в файле realm и не меняются при пересоздании Keycloak: по ним их знает демонстрационная компания (`internal/demo`).

Демонстрационная компания: `DEMO_COMPANY=true go run ./cmd/migrate` создаёт компанию "Демо" с двумя точками. Владелец - `admin`; `manager`, `approver`, `cook` и `waiter` назначены на первую точку управляющим, приёмщиком, поваром и официантом; на первой точке включён генератор (каталог и склад появятся после запуска `cmd/generator`). `DEMO_TELEGRAM_CHAT_ID=<идентификатор>` задаёт первой точке чат Telegram. Повторный запуск ничего не добавляет и не отменяет изменений владельца: чат из настройки задаётся один раз и только точке без чата, уже известных пользователей запуск не трогает (`organization.Service.Register`). Сбой создания компании пишется в журнал и не останавливает `cmd/migrate`: на сервере его завершения ждут `api` и `worker`. Без настройки тестовые пользователи входят с пустым профилем и могут создать свои компании.

Пароли и секрет действуют только в локальном realm. Для любого другого окружения этот файл realm непригоден.

Получить токен:

```bash
# пользователь
curl -s http://localhost:8180/realms/goden/protocol/openid-connect/token \
  -d grant_type=password -d client_id=goden-web -d username=approver -d password=approver
# сервисная учётная запись генератора
curl -s http://localhost:8180/realms/goden/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=goden-generator -d client_secret=goden-generator-dev-secret
```

Keycloak не хранит данные между пересозданиями контейнера: realm создаётся из файла заново. Всё нужное вноси в файл realm, а не в консоль. Применить изменённый файл: `docker compose -f infra/compose.yaml up -d --force-recreate --wait keycloak`.

Keycloak окружения запускается из образа `goden-keycloak`: официальный Keycloak с темой страниц входа `goden`, которую `infra/keycloak/Dockerfile` собирает из `frontend/`. Поэтому первый `up` дольше: в сборке ставятся зависимости pnpm и Maven. Без `--build` образ не пересобирается, после изменения темы: `docker compose -f infra/compose.yaml up -d --build --wait keycloak`. Сами страницы удобнее править без Keycloak: `pnpm dev` во `frontend/` и адрес с параметром `?kcPage=<pageId>`, например `http://localhost:5173/?kcPage=login.ftl`.

Только PostgreSQL, без остального окружения: `docker run -d -e POSTGRES_PASSWORD=pw -p 127.0.0.1:55432:5432 postgres:18-alpine`.

Проверка: `curl http://localhost:8080/readyz`, `curl http://localhost:8080/api/v1/me`. Из консоли Windows тело запроса с кириллицей передавай из файла в UTF-8 (`curl --data-binary @body.json`): текст, набранный в командной строке, уходит в кодировке консоли, и API отклонит его как некорректный UTF-8.

Доступ к API. Каждый запрос к `/api/v1` несёт access token Keycloak: `Authorization: Bearer <токен>`. Без корректного токена ответ 401, без права на операцию - 403. Запуск с проверкой токенов (нужен Keycloak окружения):

```bash
export OIDC_ISSUER=http://localhost:8180/realms/goden
go run ./cmd/api
TOKEN=$(curl -s $OIDC_ISSUER/protocol/openid-connect/token -d grant_type=password -d client_id=goden-web \
  -d username=admin -d password=admin | python -c "import sys,json; print(json.load(sys.stdin)['access_token'])")
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/me
# генератор под сервисной учётной записью
GENERATOR_CLIENT_ID=goden-generator GENERATOR_CLIENT_SECRET=goden-generator-dev-secret go run ./cmd/generator
```

Access token живёт 15 минут, refresh token - 5 суток без обращений (`ssoSessionIdleTimeout`), сессия целиком - не дольше 30 суток (`ssoSessionMaxLifespan`); после этого нужен повторный вход. Без Keycloak: `AUTH_DISABLED=true go run ./cmd/api` - все запросы, в том числе без токена, выполняются от имени пользователя `dev`, сервер пишет об этом предупреждение при старте. Наружу такой сервер выставлять нельзя. Без `OIDC_ISSUER` и без `AUTH_DISABLED` API не запускается.

В режиме `AUTH_DISABLED` отключена только проверка токена. На операциях с точкой или компанией в адресе `dev` - обычный пользователь (`auth.DevUser`, почта `dev@goden.local`): он создаёт компанию и становится её владельцем, чужие ему закрыты. Исключение: генератор в этом режиме ходит без токена и тоже является `dev`, поэтому на точке с включённым генератором и в её компании `dev` получает права генератора, даже если компания не его.

Адрес издателя в токене фиксирован настройкой Keycloak (`http://localhost:8180/realms/goden`) и должен совпадать с `OIDC_ISSUER` буква в букву. При смене `KEYCLOAK_PORT` меняется и он.

Новая миграция - файл `migrations/<NNNNN>_<имя>.sql` с секциями `-- +goose Up` и `-- +goose Down`, где `NNNNN` - следующий по порядку номер из пяти цифр.

Правила для миграций:

- номера идут подряд, без пропусков и повторов; это проверяет `go test ./migrations/`;
- если две ветки создали миграцию с одним номером, перенумеровывает та ветка, которая сливается позже: её миграция получает следующий свободный номер. Git такого конфликта не покажет, имена файлов разные; его ловит тест;
- после перенумерации своей миграции локальную базу нужно пересоздать: в ней под старым номером уже записана другая миграция;
- миграцию, попавшую в `backend`, не переименовывают и не правят: исправление оформляется новой миграцией.

Таблицу `events` нельзя очистить: триггеры отклоняют `UPDATE`, `DELETE` и `TRUNCATE`. Чтобы начать с пустого склада, пересоздай базу целиком (удали базу или том контейнера) и примени миграции заново.

## Устройство доменного модуля

Образец - модуль `catalog`: в нём есть все части, кроме проекций.

Модуль - один Go-пакет в `internal/<модуль>/`. Файлы внутри:

- `events.go` - доменные события модуля и их версии схем;
- `<агрегат>.go` - агрегат и чистые функции принятия решений, без ввода-вывода;
- `service.go` - команды: загрузка состояния, решение, запись событий;
- `projection.go` - проекции модуля;
- `queries.sql` - SQL для sqlc, сгенерированный код лежит в подпакете `db/`;
- `http.go` - реализация обработчиков ogen для своей части API.

Границы модулей:

- модуль обращается к другому модулю только через его экспортируемые типы и интерфейсы;
- модуль не читает и не изменяет таблицы другого модуля напрямую;
- модуль реагирует на изменения в другом модуле через его доменные события;
- `platform` не импортирует доменные модули;
- циклические зависимости между модулями запрещены, общий тип выносится в модуль-владелец.

Границы проверяются линтером, а не только договорённостью. В конфиге golangci-lint настраивается `depguard`:

- подпакет `internal/<модуль>/db` импортирует только сам модуль;
- `internal/platform/...` не импортирует доменные модули.

Правила добавляются вместе с первым конфигом линтера и дополняются при появлении нового модуля. Нарушение границы исправляется в коде, а не исключением в конфиге.

## Проекции

Асинхронные read-модели строит движок `internal/platform/projection`. Проекция модуля лежит в его `projection.go` и описывается четырьмя полями:

```go
var stockLevels = projection.Projection{
    Name:    "stock-levels", // ключ позиции и метка метрик, уникален
    Version: 1,              // см. ниже
    Apply: func(ctx context.Context, tx pgx.Tx, e eventstore.Event) error {
        payload, err := eventstore.Decode(e.Type, e.SchemaVersion, e.Payload)
        if err != nil {
            return err
        }
        switch p := payload.(type) {
        case BatchReceived:
            // изменить таблицы проекции через tx
        }
        return nil // события, которые проекции не нужны, пропускаются
    },
    Reset: func(ctx context.Context, tx pgx.Tx) error {
        _, err := tx.Exec(ctx, `TRUNCATE stock_levels`)
        return err
    },
}
```

Что гарантирует движок: каждое событие приходит в `Apply` ровно один раз, в общем порядке чтения `(txid, position)`; события одного потока идут по версиям; сбой посреди порции откатывает и данные, и позицию; несколько экземпляров процесса не применяют событие дважды. Идемпотентность от `Apply` не требуется.

Правила:

- `Apply` меняет только таблицы своей проекции и только через переданную транзакцию; в сеть, Kafka и Redis не ходит: транзакция держит блокировку позиции;
- проекция не участвует в проверке инвариантов: решения команд принимаются по таблицам записи (ADR-002);
- `Apply` получает событие с конвертом: время события - `e.OccurredAt`, автор - в `e.Metadata`; текущее время в проекции не используется, иначе перестроение даст другой результат;
- ошибка `Apply` останавливает продвижение проекции: событие не пропускается, порция повторяется с паузой; это видно по `goden_projection_errors_total` и растущему `goden_projection_lag_events`;
- `Version` увеличивается при любом изменении логики `Apply` или схемы таблиц, после которого старые данные неверны; после выката движок сам вызывает `Reset` и применяет все события заново; пока идёт перестроение, данные проекции неполны;
- принудительно перестроить без смены версии: `DELETE FROM projection_checkpoints WHERE name = '<имя>'` и очистить таблицы проекции при остановленном worker;
- проекции независимы: у каждой своя позиция, сбой одной не останавливает остальные;
- все проекции перечислены в `internal/readmodel`: `cmd/worker` запускает каждую отдельной задачей, тесты берут тот же список; новая проекция добавляется туда и больше нигде. Проекции декодируют каждое событие, поэтому `readmodel` импортирует и модули, которых проекции не используют, но которые объявляют события (`recommendations`): тип, неизвестный worker, остановил бы проекции. Каталог событий (`internal/contract`) берётся через `readmodel` и это проверяет;
- список, у которого есть чтение по идентификатору, строится той же свёрткой: проекция поставок на каждое событие потока заново собирает состояние через `loadDelivery` и сохраняет его целиком в `jsonb`, отдельные столбцы - только для фильтров и сортировки; второй реализации правил в проекции нет;
- чтение по идентификатору (`GET /deliveries/{id}`, `GET /orders/{id}`) идёт по потоку событий и от проекций не зависит;
- проекция нужна не каждому чтению. Источник выбирается так: то, что уже лежит в синхронной таблице записи, читается из неё и не отстаёт (остатки `GET /stock`, партии); история одного объекта читается из его потока событий (история поставки, движения по продукту); проекция заводится только для списков и сводок по многим потокам, у которых нет таблицы (списки поставок и заказов);
- всё, что зависит от текущего времени (просрочена ли партия), проекцией хранить нельзя: оно считается при чтении по часам `runner.Now()`, тем же правилом, что в командах;
- история поставки - та же свёртка `foldDelivery`, остановленная на каждом событии; движение по продукту строится из события складского потока в `movementFromEvent`: новое складское событие должно получить там вид движения, иначе чтение движений вернёт ошибку (это проверяет `TestEveryStockEventIsAMovement`);
- стоп-лист и меню (`internal/stoplist`) не хранятся: число порций считается при каждом запросе чистой функцией `availability` по блюдам каталога и остаткам `inventory.Service.Stock`. Меню обязано совпадать с решением заказа: N порций в меню - заказ на N принимается, на N+1 отклоняется (`TestMenuAgreesWithOrders`). Правило доступного остатка в `stoplist` не повторяется, оно одно - в `inventory`;
- горячие предложения (`internal/recommendations/hot.go`) и рекомендации поставок (`supply.go`) - чистые функции, считаются при чтении. Приоритет блюда - сумма по продуктам под риском произведения `срочность * охват * значимость * исключительность`, каждый множитель от 0 до 1 и возвращается в ответе как объяснение; меняя формулу, сохраняй это свойство: рейтинг должен оставаться объяснимым. Срочность и значимость описывают партию с ближайшим сроком (она названа в объяснении), охват - всё количество под риском: среднее по партиям гасило бы срочность, когда рядом с истекающей партией лежит большая свежая. Поверх расчёта управляющий задаёт блюду режим на точке (`PUT /points/{pointId}/recommendations/dishes/{dishId}`, право `menu.manage`, событие `HotOfferChanged` в потоке `recommendations.HotOffersStream`, таблица записи `recommendations_hot_offers`, перестраивается `Rebuild` в `export_test.go`): `pinned` идёт первым в порядке добавления, пока блюдо можно приготовить, `hidden` скрывает его до конца дня в часовом поясе клиента (`hidden_until` записан в событии, истёкшая строка отбрасывается при чтении), `auto` удаляет строку. Объединяет расчёт с настройками чистая функция `withSettings` в `manual.go`;
- аналитика (`internal/analytics`) хранит нормализованные факты списаний, отказов и расхода и интервалы влияния продукта на блюда в проекции `analytics`, всё - по точкам; прогноз не хранится и считается при чтении с учётом FEFO и сроков партий. Интервал стоп-листа ведётся для тройки "точка, блюдо, продукт": точки компании проекция узнаёт из `organization.PointCreated`, выключенные блюда - из `catalog.DishAvailabilityChanged` (выключенное блюдо дефицита на точке не создаёт), отключение точки и компании - из `organization.PointDisabled` и `CompanyDisabled`: интервалы отключённой точки закрываются и больше не открываются. У новой точки остатков нет, поэтому блюда с рецептурой сразу оказываются в её стоп-листе;
- расход продукта - только события `StockConsumed` (`inventory.Service.Consumption`): списания и корректировки спросом не являются и в расход не входят;
- темп расхода в прогнозе стоп-листа (`internal/analytics/forecast.go`) - расход за окно, делённый на время, за которое есть данные (`observedPeriod`: от самого раннего расхода в окне, не меньше 10 минут и не больше окна), а не на всё окно: иначе на свежей системе темп занижается в десятки раз. Без расхода прогноз строится только по срокам годности партий. Прогноз блюда объясняется по ограничивающему продукту: годный остаток, количество на порцию, темп в час и причина (`ForecastCause`: `consumption` или `expiry`, её возвращает `productForecast` вместе с моментом). То же правило времени наблюдения - в рекомендациях поставок (`observedPeriod` в `internal/recommendations/supply.go`); продукт, которого не хватает на порцию хотя бы одного блюда, рекомендуется и без расхода;
- рейтинг дефицитных ингредиентов (`internal/analytics/service.go`) упорядочен по времени в стоп-листе, а не по числу отклонённых заказов: его накручивают заведомо завышенные заказы генератора. Незакрытый интервал стоп-листа считается до текущего момента, даже если конец периода в будущем;
- модуль не читает таблицы другого модуля и ради чтения: `GET /stock` берёт страницу продуктов у сервиса каталога и одним запросом досчитывает агрегаты по своей таблице партий;
- между записью события и появлением его в проекции проходит до 200 мс (период опроса) плюс время применения.

## Правила кода

Event Sourcing (подробно в ADR-002 и ADR-004):

- бизнес-состояние меняется только добавлением событий в Event Store; прямой `UPDATE` бизнес-данных в обход событий запрещён;
- событие после записи не изменяется; при изменении формата добавляется новая версия схемы, старая остаётся читаемой;
- позиция поставки содержит обязательный `expires_at`; просрочка определяется относительно времени фактической проверки;
- регистрация поставки не меняет остаток: партии создаются только из принятого количества после `DeliveryApproved`;
- для каждой позиции approval выполняется `declared = accepted + rejected + quarantined`; backend повторно проверяет `expires_at` внутри транзакции;
- approval неизменяем и содержит полный снимок позиций, результат проверки, `approved_by`, тип actor (`user` или `service`), время поставки и время приёмки;
- correction approval выполняется только командой `CorrectDeliveryApproval`: она сохраняет заявленное количество, не уменьшает принятое ниже уже израсходованного и атомарно добавляет `DeliveryApprovalCorrected` с `BatchReceived` либо `StockAdjusted`;
- просроченная позиция не принимается; повреждённая до приёмки позиция отклоняется или помещается в карантин;
- решение по карантину позиции - одна команда `ResolveQuarantine` на всё карантинное количество: она делит его на принятую часть (`QuarantinedDeliveryItemAccepted` и новая партия) и отклонённую (`QuarantinedDeliveryItemRejected`); после неё карантин позиции закрыт, повторное решение отклоняется;
- у позиции поставки может быть несколько партий: из приёмки, из карантина и по одной на каждое увеличение принятого количества корректировкой; уменьшение принятого количества снимается с партий позиции от последней созданной к первой и не может превысить их остаток;
- состояние поставки собирается из всех событий её потока; для каждой позиции после любого события выполняется `заявлено = принято + отклонено + карантин`; новое событие потока поставки обязано быть добавлено в свёртку, иначе чтение поставки вернёт ошибку;
- порча и просрочка после приёмки уменьшают остаток только событием `StockWrittenOff` с причиной, пользователем и комментарием; автоматического списания нет: просроченную партию списывает управляющий ручной операцией с причиной `expired`, отдельные события для этих случаев не вводятся;
- предупреждение о приближении срока оформляется командой `IssueBatchExpiryWarning` и событием `BatchExpiryWarningIssued`: один раз на партию, без изменения остатка; worker не публикует его в Kafka напрямую;
- `StockWrittenOff` - событие; команда списания одна - `WriteOffStock` (ручное, в том числе просрочки); она перечитывает партию под блокировкой и решает по актуальным сроку и остатку в синхронном write model;
- просрочку партии с остатком отмечает команда `MarkBatchExpired` событием `BatchExpired`: один раз на партию (`expired_noticed_at` в `inventory_batches`), без изменения остатка. Просроченный остаток не входит в доступный, в FEFO и меню, поэтому блюдо уходит в стоп-лист в момент просрочки и без списания; событие нужно, чтобы об этом узнали Telegram и экраны (категории склада в realtime). Просроченные партии копятся, пока их не спишут, поэтому кандидаты на отметку - только неотмеченные партии (`ListExpiredBatchIDs`);
- команды для worker (`MarkBatchExpired`, `IssueBatchExpiryWarning`) идемпотентны по состоянию партии, а не по ключу: если делать нечего, они ничего не пишут и возвращают `false` без ошибки; worker может повторять вызов после сбоя;
- контроль сроков (`inventory.ExpiryChecker`, задача `cmd/worker`) только находит кандидатов запросом и вызывает для каждой партии команду; решение принимает команда под блокировкой, поэтому несколько экземпляров worker и гонка с заказом безопасны без координации; ошибка по одной партии не прерывает проход; автор этих команд - `inventory.WorkerActor`;
- команда, пишущая в потоки `stock-*`, берёт advisory-блокировки по складским потокам (точка и продукт) в едином порядке и делает это до первой записи в транзакции;
- внутри транзакции с блокировками нет сетевых вызовов, обращений к Kafka и Redis;
- решение о списании принимается по синхронной таблице остатков, а не по асинхронной проекции;
- расход заказа берётся только из `StockConsumed`: вычислять его из рецептуры на момент события заказа нельзя - при одновременном изменении рецептуры событие `RecipeChanged` может стоять в общем порядке по другую сторону от заказа, чем состав, по которому заказ посчитан;
- оформление заказа отвечает 409, если рецептура блюда менялась во время заказа чаще, чем команда успевала повторяться; заказ при этом не оформлен, клиент повторяет запрос;
- бизнес-код не публикует сообщения в Kafka напрямую, это делает publisher;
- publisher пишет версионированный конверт в `goden.catalog.v1`, `goden.deliveries.v1`, `goden.stock.v1`, `goden.orders.v1` или `goden.expiry.v1` (префикс настраивается); постоянные ошибки consumers идут в `goden.errors.v1`;
- consumer выполняет изменение своей БД и запись `event_id` в inbox одной транзакцией; временная ошибка повторяется, постоянная помечается через `kafka.Permanent` и отправляется в поток ошибок;
- фоновая задача с Kafka не возвращает ошибку из `Run` при сбое Kafka или базы: задачи worker работают в одной группе, и вернувшаяся ошибка останавливает процесс вместе с проекциями и контролем сроков. Publisher, обработчик (`kafka.Consumer`) и читатель потока ошибок пишут ошибку в журнал и повторяют с паузой. У отправки записи есть срок (`produceTimeout`): без него сбой Kafka не доходил до метрик;
- одновременно публикует один publisher: экземпляр держит сессионную advisory-блокировку на отдельном соединении, остальные ждут. Обработчик повторяет событие не больше `MaxAttempts` раз (по умолчанию 10), затем отправляет его в поток ошибок;
- `notifications` читает `expiry.v1` и `errors.v1`, дедуплицирует источник в PostgreSQL и не делает сетевой вызов внутри inbox-транзакции; dispatcher захватывает запись через lease, отправляет её в Telegram и сохраняет retry с backoff при временной ошибке;
- проектор обновляет checkpoint в одной транзакции с данными проекции: это делает движок `platform/projection`, свои циклы чтения событий проекции не пишут;
- обработчики событий и consumers идемпотентны.

Команды записи:

- доменная команда запускается только через `command.Run`; прямой вызов `eventstore.Append` из доменного кода не используется;
- все складские потоки, в которые команда пишет, перечисляются в `Spec.Locks` как `inventory.StockStream(pointID, productID)`: без этого события потока могут дойти до проекций не по порядку версий. Точка входит в имя потока, поэтому команды разных точек друг друга не ждут;
- команда, которая пишет в поток не первое событие и принимает ключ идемпотентности, блокирует этот поток через `Spec.Locks` (пример - `ChangeRecipe` и `catalog.DishStream`): с ключом транзакция получает номер до чтения версии потока, и без блокировки события потока могут попасть в общий порядок чтения не по версиям;
- функция команды читает состояние и версии потоков внутри транзакции, после блокировок, а не до вызова `command.Run`;
- функция команды может быть вызвана повторно при конфликте версий, поэтому не имеет побочных эффектов вне переданной транзакции;
- результат команды - простая структура, которая сериализуется в JSON и обратно без потерь: он сохраняется для повторов с тем же ключом идемпотентности;
- время берётся из `tx.Now()`: оно одно на всю команду и стоит во всех её событиях;
- ключ идемпотентности приходит от клиента в запросе; для команд, вызываемых worker, ключ строится из идентификатора обрабатываемого объекта;
- ключ идемпотентности принадлежит автору: результат хранится по тройке "имя команды, автор, ключ" (`actorKey` в `internal/platform/command`). Один и тот же ключ у разных авторов - разные команды; чужой ключ нельзя ни занять, ни обнаружить по отказу.

Остатки:

- таблицу остатков `inventory_batches` читает и меняет только модуль `inventory`; команда другого модуля, которой нужно израсходовать продукты, передаёт потребность в `inventory.Service.ConsumeForOrder` в своей транзакции;
- правило FEFO и исключение просроченных партий записаны в одной чистой функции `planConsumption`; второй реализации выбора партий в проекте быть не должно;
- партия просрочена, если дата окончания срока годности не позже момента проверки; момент проверки - `tx.Now()`;
- отмена заказа (`orders.Service.CancelOrder`, `POST /points/{pointId}/orders/{orderId}/cancel`) возвращает в партии ровно то, что взяли под заказ: партии берутся из его событий `StockConsumed` (`inventory.Service.OrderConsumption`, частичный индекс по `order_id`), возврат - событие `StockReturned` (`ReturnForOrder`). Отменить можно только принятый заказ (`orders.ErrNotCancellable`, 409 `order-not-cancellable`). Возвращённое в истёкшую партию остаётся просроченным и ждёт ручного списания. Расход отменённого заказа - не спрос: проекция `analytics` удаляет его по `order_id`, `inventory.Service.Consumption` пропускает. Можно ли ещё вернуть продукты (заказ не начали готовить), решает вызывающий. Отмена требует права `orders.cancel` (владелец, управляющий, официант, Мигом на подключённой точке) и принимает необязательный комментарий (`OrderCancelled.comment`, до `orders.MaxCancelCommentLength` символов). Сервисная учётная запись отменяет только заказы, которые оформила сама (`Order.PlacedBy`, иначе 403): учётная запись Мигома одна на все его заведения. Заказ в ответе несёт `placed_by`, у отменённого - `cancelled_by` и `cancel_comment`: по ним фронт отличает заказы Мигома, а Мигом опросом `GET /points/{pointId}/orders/{orderId}` узнаёт об отмене сотрудником и её причине;
- состояние, от которого зависит набор блокировок (рецептуры для заказа), читается дважды: до транзакции, чтобы выбрать блокировки, и под блокировками через метод с переданным соединением (`catalog.Service.DishIn`), чтобы решать по актуальным данным; если набор вышел за блокировки, команда повторяется с новым набором.

Количество и время:

- количество хранится как `int64` в минимальной единице продукта; `float64` для количества запрещён;
- у количества есть верхняя граница `catalog.MaxQuantity` (10^12 минимальных единиц), у числа порций блюда в заказе - `orders.MaxPortions` (10000), у срока хранения - `catalog.MaxShelfLifeDays` (3650). Они записаны в контракте (`maximum`) и проверяются в домене. Без границ суммы остатков и потребность заказа переполняют `int64`: новое поле с количеством обязано получить обе проверки. В распределении приёмки каждая часть сравнивается с заявленным количеством до сложения;
- единиц измерения три: граммы (`g`), миллилитры (`ml`), штуки (`pcs`); единица задаётся у продукта и после появления первой партии не меняется;
- дробных количеств нет: продукт, который расходуется частями (пол-лимона, треть багета), учитывается в граммах, а не в штуках;
- поставки, рецептуры, остатки и API используют одну и ту же единицу продукта без пересчётов; перевод в килограммы и литры для отображения делает frontend;
- время хранится и передаётся в UTC;
- текущее время берётся только через `clock.Clock`, прямой вызов `time.Now()` в доменном коде запрещён: иначе логику сроков годности нельзя протестировать.

Общее:

- `context.Context` передаётся первым аргументом во все функции с вводом-выводом;
- ошибки оборачиваются через `fmt.Errorf("...: %w", err)`, доменные ошибки объявляются как типы или sentinel-значения и проверяются через `errors.Is` и `errors.As`;
- API отвечает ошибками в формате `application/problem+json` (RFC 9457);
- контроль доступа выполняется на backend для каждой защищённой операции;
- права (permissions) - набор роли на точке или владельца, в токене их нет: `catalog.view`, `deliveries.view`, `deliveries.register`, `deliveries.approve`, `orders.view`, `orders.accept`, `orders.cancel`, `inventory.view`, `inventory.edit`, `kitchen.view`, `products.manage`, `dishes.manage`, `analytics.view`, `recommendations.view`, `generator.manage`, `menu.manage`, `notifications.manage`, `staff.view`, `staff.manage`, `point.view`, `company.view`, `company.manage`. Наборы ролей - `rolePermissions` в `internal/organization/organization.go`; из токена берутся только `generator.run` и `migom.integration`, у ключа поставщика - `supplier.access`;
- генератор привозит партии с разным остатком срока годности (`remainingLife` в `internal/generator/simulator.go`): 10% позиций уже просрочены и отклоняются при приёмке, 5% истекают через 3-20 минут, у остальных остаток - от 15% до 100% срока хранения продукта. Без этого все партии были бы свежими, и на демо не работали бы горячие предложения и список истекающих и просроченных партий. Просроченные партии генератор не списывает: они копятся, пока их не спишут вручную. Часы при этом настоящие;
- поставка генератора - несколько запросов подряд, и сбой посреди оставил бы её без приёмки или с открытым карантином. Поэтому на точке, которая только что появилась у процесса, и после сорванной поставки симулятор вызывает `Resume`: читает непринятые поставки и поставки с открытым карантином, берёт свои по номеру (`generatedNumber`, "ГЕН-") и доводит до конца. Новый шаг поставки добавляется в `finish`, а не в `Deliver`;
- генератор - только клиент публичного API: симулятор в `internal/generator` зависит от сгенерированного клиента и не получает пул базы;
- генератор использует отдельную Keycloak service account с правом `generator.run`, всегда делает approval и закрывает созданный карантин до генерации заказов и не пишет в Event Store напрямую;
- права генератора - производная от настроек: для клиента с `generator.run` `authorize` добавляет на точке права `generator.Service.PointPermissions` (регистрация, чтение и приёмка поставок, заказы, чтение блюд точки: выключенные на точке блюда симулятор не заказывает), а в компании - `CompanyPermissions` (чтение и наполнение каталога), только пока генератор включён на точке или хотя бы на одной точке компании. Назначений в `organization` для него нет, выключение отзывает права сразу. На отключённой точке и в отключённой компании генератор не работает, даже если его настройки остались включёнными: такая точка не попадает в `GET /generator/points`, а права не добавляются (`generatorOnPoint`, `generatorInCompany` в `internal/api/security.go`). Выключить генератор можно и на отключённой точке, включить - только на работающей. Права генератора шире необходимого и это принято: приёмка открывает и поставки сотрудников, право на блюда - рецептуры всей компании. Генератор - демонстрационный инструмент, его включает владелец; при утечке секрета его меняют. Настройки (`generator_point_settings`) - техническое состояние без событий, строка на точку. Симулятор ведёт точки независимо (`running` в `simulator.go`): у каждой свои счётчики, выключенная точка накопленное забывает; ключи наполнения каталога включают идентификатор компании;
- права Мигома устроены так же, как права генератора: для клиента с `migom.integration` `authorize` добавляет на точке `migom.Service.PointPermissions` (меню, горячие предложения для покупателей, оформление, чтение и отмена своих заказов; отмена - право `orders.cancel`), только пока к точке подключено заведение Мигома, а точка и компания работают (`migomOnPoint` в `internal/api/security.go`). Прав в компании у Мигома нет. Подключение (`migom_points`, без событий) хранит номер заведения в Мигоме, `NULL` - отключено; меняет его владелец (`PUT /points/{pointId}/migom`). Учётная запись у Мигома одна на все заведения, поэтому привязка двусторонняя: Мигом работает с точкой для заведения, только если пара есть в `GET /migom/points`, а владелец заведения в Мигоме указал эту же точку. Одно заведение могут указать несколько точек, уникальности нет: иначе чужая точка, указав заведение первой, не дала бы подключить его настоящей;
- ключи поставщиков (ADR-014, `internal/suppliers`): владелец заводит поставщика с точками компании (`/companies/{companyId}/suppliers`, право `company.manage`), ключ `gdn_...` есть только в ответе на создание и выпуск (`POST .../{supplierId}/key`), в базе - SHA-256 (`suppliers.key_hash`, `NULL` - отозван, `DELETE .../key`). Ключ проверяет `suppliers.Service.Verifier` поверх проверки токена в `api.New`: токен с префиксом `gdn_` ищется по хешу, остальные уходят в Keycloak. Автор по ключу - `service` с идентификатором `supplier:<id>`, в токене одно право `supplier.access` (`GET /supplier`, `GET /supplier/products` - продукты без сведений о блюдах). На точке `authorize` добавляет поставщику только `deliveries.register`, если точка его и работает (`suppliers.Service.PointPermissions`); у отключённой компании поставщику недоступно ничего. Название поставщика в авторах ответов подставляет `organization.WithNames` через `SetServiceNames`;
- каждый процесс отдаёт метрики на `GET /metrics` рядом с `/healthz`, без токена; правила метрик:
  - имя начинается с `goden_` (`observability.MetricsNamespace`), счётчики заканчиваются на `_total`, время - в секундах;
  - в метках только значения из закрытых наборов (операция контракта, имя команды, тип события, причина, единица); идентификаторы, имена пользователей и названия продуктов метками не делают;
  - метрика объявляется рядом с кодом, который её меняет, и регистрируется через `observability.Register` в реестре процесса; у сервисов записи реестр даёт `runner.Registry()`; глобальный реестр и `promauto` не используем;
  - внутри команды счётчик увеличивают только через `tx.OnCommit`: функция команды может выполниться несколько раз или откатиться, а повтор по ключу идемпотентности её не вызывает вовсе;
  - бизнес-счётчики стороны записи - это `goden_events_appended_total{type}`: принятый заказ - событие `OrderAccepted`; отдельный счётчик заводят, только если нужна метка, которой нет в типе события (причина списания);
  - серии с закрытым набором меток создают при старте с нулём, иначе `increase()` не увидит первое срабатывание;
- трассировки нет: интеграция ogen с OpenTelemetry отключена в `ogen.yml`, запросы связывает correlation ID в логах;
- секреты, токены и персональные данные в логи не пишутся;
- каждый запрос и событие несут correlation ID, он попадает в логи;
- процессы завершаются корректно по `SIGTERM`: перестают принимать работу и дожидаются текущей.

## Контракт API

- Сначала меняется `api/openapi.yaml`, затем генерируется код, затем пишется реализация.
- Сгенерированный код не редактируется вручную и коммитится в репозиторий.
- Frontend получает типы из того же файла, поэтому несовместимое изменение контракта согласуется с фронтом.
- SSE-эндпоинт описывается в контракте для документации, но реализуется вручную.
- поток обновлений - операция точки: `GET /api/v1/points/{pointId}/events` требует тот же bearer token, что и REST, и право `point.view` на точке (владелец и любой сотрудник). Маршрут ручной, поэтому токен и право проверяет `pointStream` в `internal/api/security.go`, а не `authorize`. Категория `deliveries` - регистрация, приёмка, решение по карантину и исправление; складские события её не несут, иначе поставки перечитывал бы каждый заказ. Сигнал `deliveries` может на доли секунды опередить проекцию списка: чтение поставки по идентификатору не отстаёт, список и сводка могут. Каждое соединение сначала получает `sync` со всеми категориями, затем `update` из локального hub и keepalive-комментарии. Сигналы, пришедшие подряд в пределах `defaultMerge` (четверть секунды), обработчик потока склеивает в один (`collect` в `internal/realtime/http.go`): заказ на пять ингредиентов даёт клиенту один перезапрос. Hub отдаёт сигнал подписчикам точки события (`point_id` в событии склада) или всех точек компании события (`company_id` в событии каталога); сигнал без адресата не получает никто. В JSON сигнала адресация не попадает. Новое событие, которое должно будить клиентов, обязано нести `point_id` или `company_id`;
- при остановке API `cmd/api` вызывает `Hub.Close`: открытые потоки закрываются сразу, иначе сервер ждал бы их до истечения срока остановки. На запись события в поток действует срок 10 секунд (`writeTimeout`), заголовок `Last-Event-ID` разрешён в CORS;
- список партий продукта (`GET /products/{productId}/batches`) отдаётся страницами (`limit`, `offset`, `total`), параметр `in_stock=true` оставляет партии с остатком; неизвестный продукт даёт 404;
- Каждый экземпляр API без consumer group читает с конца `catalog.v1`, `deliveries.v1`, `stock.v1`, `orders.v1`, `expiry.v1` (принятый и отклонённый заказ дают категорию `orders`, складские категории принятому заказу дают его события `StockConsumed`): сигнал содержит только категории для повторного REST-запроса, а не бизнес-данные. Выключение блюда на точке (`DishAvailabilityChanged`) и все события каталога публикуются в `catalog.v1`; каждое событие каталога даёт категорию `catalog`, изменение продукта дополнительно будит склад, стоп-лист, рекомендации, поставки и заказы, переименование блюда - стоп-лист, рекомендации и заказы (`FromEnvelope` в `internal/realtime/event.go`). Ошибка Kafka не меняет `/readyz`; reader логирует её и повторяет подключение.

Выбор ogen проверен 2026-10-10 на эндпоинтах продуктов (тело запроса, пагинация, ошибки) и закреплён: ogen v1.24.0 остаётся генератором, перехода на oapi-codegen нет. Что подтверждено:

- все операции ссылаются на один ответ `default`, поэтому ogen включает режим "convenient errors": метод операции возвращает результат и `error`, а ошибку в ответ превращает один метод `NewError`;
- ответ ошибки уходит с типом содержимого `application/problem+json`;
- ошибки разбора запроса и проверки по контракту обрабатывает настраиваемый `ErrorHandler`;
- значения по умолчанию параметров запроса подставляет сгенерированный код;
- интеграция с OpenTelemetry отключена в `ogen.yml`: трассировки в проекте нет.

Спецификацию держим в пределах конструкций, которые ogen принял. Если новая конструкция не генерируется, сначала ищем более простую запись.

Соглашения API, общие для всех эндпоинтов:

- **Префикс** `/api/v1`. `/healthz` и `/readyz` лежат вне его.
- **Ошибки** - только `application/problem+json` (RFC 9457): `type`, `title`, `status`, `detail`, `correlation_id`, для валидации `errors[]` с полем и сообщением. Статусы: 400 - запрос не по контракту, 404 - не найдено, 409 - конфликт с текущим состоянием, 422 - нарушено правило предметной области, 500 - внутренняя ошибка без подробностей. У конфликтов, которые клиент обрабатывает по-разному, свой `type`: `delivery-already-approved`, `delivery-not-approved`, `quarantine-closed`, `version-conflict` (запрос можно повторить); остальные 409 - `conflict` (`namedConflict` в `internal/api/errors.go`). Элемент `errors[]` может нести `code` и `limit`: их отдаёт необязательный метод `FieldDetail` ошибки валидации модуля (`expired`, `stock-consumed` в `inventory`).
- **Пагинация**: параметры `limit` (1..200, по умолчанию 50) и `offset`, ответ `{items, total}`. Берутся ссылками на `components/parameters`.
- **Идемпотентность**: заголовок `Idempotency-Key` на операциях записи, тоже ссылкой на `components/parameters`.
- **Correlation ID**: заголовок `X-Correlation-Id`; middleware кладёт его в контекст, оттуда он попадает в логи и события.
- **Ограничения в схемах** - только те, что не зависят от нормализации данных: перечисления, `minimum`, обязательность. Пустоту строки после обрезки пробелов проверяет домен и возвращает 422.

Устройство слоя API:

- позиция поставки в ответе несёт название, единицу и категорию продукта, текущий остаток партий позиции (`in_stock_quantity`) и имена авторов, позиция заказа - название блюда, недостающий продукт отказа - продукт (`withProducts`): их подставляет обработчик при ответе (`named` в `inventory/http.go` и `orders/http.go`), в событиях их нет. Названия при этом всегда текущие: переименование продукта или блюда (`ProductChanged`, `DishRenamed`) сразу видно в старых поставках и заказах, проекции перестраивать не нужно. Новая операция, которая возвращает поставку или заказ, обязана пройти через `deliveryOut` или `orderOut`. Остаток в истории поставки - тоже текущий, а не на момент события;
- партия в ответе несёт номер поставки (`delivery_number`), изменение в движении по продукту - номер поставки своей партии: их подставляют `numbered` в `inventory/http.go` и `numberedChanges` в `inventory/http_reads.go`. Номер читается из первого события потока поставки (`inventory.Service.DeliveryNumbers`, `eventstore.ReadFirst`), а не из проекции списка: она асинхронна. Новая операция, которая возвращает партию, обязана пройти через `batchOut` или `numbered`;
- остатки с поиском, категорией, статусом и сортировкой (`GET /points/{pointId}/stock`) и сводка по статусам (`/stock/summary`) читает `inventory.Service.StockView` и `StockSummary`: каталог отдаёт все продукты компании под название и категорию (`catalog.Service.ProductsMatching`), статус и порядок считаются в памяти чистыми функциями `StockLevel.Is` и `sortStock` в `inventory/stock_view.go`. Статусы не исключают друг друга. `inventory.Service.Stock` без фильтров остаётся для стоп-листа и рекомендаций;
- доступность блюда (`/menu`, `/stop-list`) несёт всю рецептуру с остатками (`ingredients`) и отдельно ограничивающие продукты (`limiting`); обе считает `availability` в `internal/stoplist`;
- остальное для экранов приёмки считает свёртка `foldDelivery` из событий потока: время открытия карантина (`quarantined_at`: приёмка или исправление, назначившее карантин позиции без него), решения по карантину (`quarantine_resolutions`: два события одной команды с одним временем склеиваются в одну запись), распределение на момент приёмки (`approved`) и время последнего исправления. Список получает их через проекцию; изменение свёртки, меняющее сохранённое состояние, требует новой версии `DeliveriesProjection`;
- имя автора (`Actor.name`) в события не записывается: таблица событий не допускает изменений, и имя осталось бы там навсегда. В событии автор - логин; `organization_users.login` заполняется при `GET /me` и `POST /companies`, имя по логину находит `organization.Service.Names`, подставляет `withNames` в `inventory/http.go`. У пользователя, не запрашивавшего профиль после появления столбца, и у сервисной учётной записи имени нет;
- причины отклонения и карантина в запросах - перечисление `WriteOffReason`, его проверяет разбор запроса; в событиях и ответах причина остаётся строкой, потому что у прежних поставок там свободный текст. Закрытым перечислением в событии её делать нельзя: старые события перестанут читаться;
- сводка `GET /points/{pointId}/deliveries/summary` читает ту же проекцию, что и список; число позиций в открытом карантине - столбец `open_quarantine_items`. Поиск по номеру - по началу, без учёта регистра (`starts_with`, знаки шаблона не действуют);
- обработчик модуля (`internal/<модуль>/http.go`) - тонкая обёртка: разбирает запрос, берёт автора из `httpx.Actor(ctx)`, вызывает сервис, собирает ответ, ошибку сервиса возвращает как есть; правил предметной области в нём нет;
- `internal/api` объединяет обработчики встраиванием в один `Handler`; операция, которая есть в контракте, но ещё не реализована, отвечает 501;
- право операции записано в контракте: `security: - bearerAuth: [<право>]` у операции. `internal/api/security.go` проверяет токен через `auth.Verifier`, сверяет право и кладёт автора из токена в контекст; обработчики модулей о правах не знают. Операция без права в контракте закрыта для всех, кроме перечисленных в `authenticatedOnly`;
- у операции с `pointId` или `companyId` в адресе право определяет не токен, а `organization.Service`: `PointPermissions` и `CompanyPermissions` (ADR-013). Владелец компании получает все права, сотрудник - права роли из `rolePermissions` в `internal/organization/organization.go`, остальные - никаких. Сверяет их `authorize` в `internal/api/security.go` - middleware сгенерированного сервера: ему нужны параметры пути, поэтому проверка права идёт после разбора запроса. Права читаются из базы при каждом запросе, кеша нет: снятое назначение действует сразу. По ролям токена проверяются только операции без точки и компании в адресе: сейчас это списки точек генератора (`generator.run`) и Мигома (`migom.integration`) и операции поставщика по ключу (`supplier.access`);
- владелец передаёт компанию командой `TransferCompany` (`PUT /companies/{companyId}/owner`, получатель - почта зарегистрированного пользователя, событие `CompanyOwnerChanged`). Владелец - одно поле `owner_id`, права считаются по нему при каждом запросе, поэтому передача действует сразу. Команда перепроверяет владельца под блокировкой потока компании. Прежний владелец не получает назначений; назначения нового владельца на точках компании остаются и не действуют, пока он владелец. Повтор успешной передачи с тем же ключом отвечает 403: право проверяется раньше поиска результата;
- `company.manage` есть только у владельца: им закрыты компания и её точки. Правило "управляющий не назначает и не снимает управляющих" зависит от ролей в запросе и проверяется в домене (`mayManage`), а не правом операции;
- каталог принадлежит компании (`company_id` в `ProductCreated` и `DishCreated`), адреса - `/companies/{companyId}/products` и `/companies/{companyId}/dishes`. Право в компании проверяет `authorize`, а обработчик обязан второй проверкой убедиться, что объект по идентификатору принадлежит компании из адреса: `catalog.Service.ProductOf` и `DishOf` отвечают `ErrNotFound` для чужого. Без неё владелец своей компании менял бы чужую рецептуру по идентификатору блюда. То же правило - для любой будущей операции с идентификатором объекта внутри компании или точки;
- в каталоге вместо удаления - архив (`ProductArchived`, `ProductRestored`, `DishArchived`, `DishRestored`, столбец `archived`), события не удаляются, название архивного остаётся занятым (`catalog.NameTakenError{Archived}`, в ответе 409 поле `name` с `code` `taken_by_archived`). Архивный продукт не берётся в новые поставки (`catalog.Service.ActiveProductOf`) и рецептуры (`ArchivedProductError`, 422), не входит в рекомендации поставок (`Stock` отдаёт только неархивные продукты), на складе виден, только пока у него есть партии; продукт из рецептуры неархивного блюда в архив не уходит (`ProductInUseError`, 409 `product-in-use`). Архивное блюдо пропадает из `DishesOnPoint`, `DisabledOnPoint` считает его не продающимся, выключение на точках при архиве не трогается. Списки каталога без `status` отдают только неархивные;
- единица продукта меняется (`ChangeProduct`), пока он не использовался: нет в рецептуре любого блюда и в поставках любого статуса. Поставки каталог узнаёт через интерфейс `catalog.ProductUsage`, его реализует `inventory.Service.DeliveredProducts` по таблице записи `inventory_delivered_products` (её заполняет регистрация поставки), подключается в `internal/api/api.go` через `SetProductUsage`; так `catalog` не импортирует `inventory`. Иначе 409 `unit-locked`;
- в компании сотрудник любой её работающей точки получает `company.view` и `catalog.view` (`staffCompanyPermissions`); менять каталог (`products.manage`, `dishes.manage`) может только владелец;
- блюдо компании продаётся на каждой точке, пока его не выключили: `PUT /points/{pointId}/dishes/{dishId}` (право `menu.manage`: управляющий и владелец), событие `DishAvailabilityChanged` в потоке `catalog.MenuStream(pointID)`, таблица `catalog_disabled_dishes` хранит только выключенные пары. Меню, стоп-лист, рекомендации и прогноз строятся по `catalog.Service.DishesOnPoint` - блюдам компании без выключенных на точке; заказ с выключенным блюдом отклоняется (`orders.DishNotSoldError`, 422) без события заказа;
- склад принадлежит точке (ADR-013): `point_id` есть в `DeliveryRegistered`, `BatchReceived`, `StockConsumed`, `StockAdjusted`, `StockWrittenOff`, `BatchExpiryWarningIssued`, `OrderAccepted`, `OrderRejected`, складской поток - `inventory.StockStream(pointID, productID)`. Операции поставок, склада, заказов, меню, рекомендаций и аналитики лежат под `/points/{pointId}`. Чистые функции правил (FEFO, сроки, стоп-лист, формулы) точку не знают: меняется только отбор данных;
- сервис, которому нужны и склад точки, и каталог её компании, принимает `organization.Point`; обработчик получает её у `organization.Service`: `Point` для чтения, `WorkingPoint` для записи (отключённая точка или компания - `ErrDisabled`, 409), для записи в каталог компании - `WorkingCompany`. Модули таблицы `organization` не читают. Контроль сроков (worker) работает и на отключённой точке. Работающая точка и выключенное блюдо читаются без общей блокировки с командой отключения: запись может зафиксироваться в пределах миллисекунд после отключения, это принято - блокировка выстроила бы в очередь все заказы точки;
- проверка, которая стоит раньше `command.Run` (работающая точка в обработчике, блюда заказа до транзакции), выполняется раньше поиска результата по ключу идемпотентности. Оформление заказа поэтому сначала читает сохранённый результат через `command.Stored` (`orders.Service.Placed`): повтор принятого заказа возвращает его, даже если блюдо уже выключили или точку отключили. У складских операций такого чтения нет: повтор после отключения точки отвечает 409;
- объект с собственным идентификатором сверяется с точкой из адреса: `inventory.Service.DeliveryAt`, `BatchAt`, `orders.Service.OrderAt` отвечают `ErrNotFound` для объекта другой точки. Обработчик вызывает их до команды или чтения (в `inventory/http.go` - `deliveryWritable`, `batchWritable`); точка объекта не меняется, поэтому проверка не устаревает. Новая операция с идентификатором объекта обязана получить такую сверку и строку в `TestObjectsOfAnotherPointAreNotFound`;
- контроль сроков (`ExpiryChecker`) обходит партии всех точек одним запросом, команда узнаёт точку из партии. Уведомление уходит в чат точки партии;
- личность клиента обработчик берёт из `auth.UserFrom(ctx)`. Пользователь попадает в `organization_users` при `GET /me` и `POST /companies` (`HTTP.known`): назначить на точку можно только того, кто уже обращался. Таблица пользователей - отражение Keycloak, а не события: из Event Store она не перестраивается;
- автор команды берётся только из токена: пользователь - `{user, <имя пользователя>}`, сервисная учётная запись - `{service, <идентификатор клиента>}`. Он попадает в события, поэтому Event Store служит журналом аудита; отказы 401 и 403 пишутся в лог с операцией и автором;
- ошибки предметной области превращаются в статусы в одной функции `problemFor` в `internal/api/errors.go`; новую sentinel-ошибку модуля нужно добавить туда, иначе клиент получит 500;
- `ValidationError` модуля реализует метод `InvalidField`: по нему слой API распознаёт ошибку валидации без перечисления типов;
- тело запроса проверяется на корректный UTF-8 и размер до разбора: JSON-разбор кодировку не проверяет.

Операция на точке: путь начинается с `/points/{pointId}` (параметр берётся ссылкой на `components/parameters/PointId`), право - из набора роли; больше ничего для проверки доступа делать не нужно. Имя параметра менять нельзя: по нему `authorize` узнаёт точку.

Порядок добавления эндпоинта: операция в `api/openapi.yaml` вместе с её правом (`security`), генерация, запрос операции в `operations` в тестах `internal/api` (без него не пройдёт `TestEveryOperationHasARequest`, а матрица прав не проверит операцию), метод в `http.go` модуля, при первом эндпоинте модуля - встраивание его обработчика в `api.Handler`, интеграционный тест через `apitest`.

- Обязательные сценарии перечислены в разделе 11 [../docs/plan.md](../docs/plan.md): обязательный `expires_at`, частичная приёмка, оба выхода из карантина, correction approval, единый `StockWrittenOff`, сквозной сценарий генератора, FEFO, permissions Keycloak, параллельные заказы, полный replay и отсутствие пропусков событий у проектора.
- Табличные тесты - стиль по умолчанию.
- Интеграционные тесты лежат в файлах `*_integration_test.go` с тегом сборки `//go:build integration`.
- `apitest.New(t)` поднимает весь API на отдельной базе тем же конструктором, что и `cmd/api`, и возвращает сгенерированный клиент. Тесты эндпоинтов ходят через клиент; сырые запросы нужны только для того, что клиент отправить не позволит.
- Клиент `apitest` действует от имени пользователя `dev`, токены проверяет подделка. `apitest.New` создаёт ему компанию и точку (`s.CompanyID`, `s.PointID`), на них он владелец. Сотрудник точки с правами роли: `s.Staff(t, "approver", oas.RoleApprover)`; токен для сырого запроса: `s.Hire(t, actor, роль)`. Права из токена (`s.As`, `s.TokenFor(actor, права...)`) действуют только на операции списка точек генератора; клиент его учётной записи - `s.As(t, service, "generator.run")`. У пользователя `dev` в токене есть все права, включая это. Разбор настоящих токенов Keycloak покрыт интеграционным тестом пакета `auth`: он поднимает Keycloak с файлом realm из `infra/keycloak/` и добавляет к прогону около 40 секунд.
- Пользователь без прав в токене, которого можно назначить на точку: `s.Login(t, "cook")` - клиент с почтой `cook@goden.local`, первое обращение уже выполнено. Матрица прав проверяет операции организации на чужой точке: токен со всеми правами получает 403.
- Каталог в тестах создаётся в компании `dev` (`oas.CreateProductParams{CompanyId: s.CompanyID}`), склад ведётся на его точке (`oas.GetStockParams{PointId: s.PointID}`); сырые адреса - `companyPath(s)+"/products"` и `pointPath(s)+"/stock"`. В тестах сервисов без API точка и компания - любые (`organization.Point{ID: ..., CompanyID: ...}`): их существование склад и каталог не проверяют.
- Значение метрики в тесте: через API - `s.Metric(t, "goden_commands_total", "command", "PlaceOrder", "outcome", "ok")` (читает `/metrics` тестового сервера), по реестру - `metricstest.Value(t, registry, имя, метки...)`. У каждого `apitest.New` свой реестр, тесты не влияют друг на друга.
- Перед запуском контейнера testcontainers вне `pgtest` вызывай `dockertest.Setup()`: без него контейнеры не стартуют на Windows.
- `pgtest.NewDB(t)` даёт пул к отдельной базе PostgreSQL с применёнными миграциями. База создаётся на один тест, контейнер один на пакет.
- `estest.Append(t, pool, stream, events...)` кладёт готовые события в Event Store без команд: так тесты проекций получают входные данные. `estest.AppendAt` делает то же с заданным временем события: оно нужно, когда проекция считает что-то по времени расхода или списания. Пример - `internal/inventory/events_integration_test.go`.
- `estest.Golden(t, event)` сверяет JSON события с эталоном в `testdata/`. Формат события - контракт: эталон меняется только вместе с согласованным изменением события.
- Тест списка через API: после записи и перед чтением вызови `s.Sync(t)` - он применяет к проекциям все записанные события. Фоновых проекторов в `apitest` нет, без `Sync` список пуст. Образец - `internal/api/lists_integration_test.go`.
- Тест проекции: записать события (`estest.Append` или командами), вызвать `engine.CatchUp(ctx, projection)`, проверить таблицы. `CatchUp` дожидается и событий, которые зафиксированы, но ещё не читаются из-за чужой незавершённой транзакции в кластере, поэтому результат не зависит от соседних тестов. Образец тестовой проекции и приёмов - `internal/platform/projection/projection_integration_test.go`.
- Таблицы записи (`inventory_batches`, `catalog_*`) обязаны восстанавливаться из событий. Это проверяют тесты replay: `Rebuild` в `export_test.go` модуля перестраивает таблицу теми же функциями `apply*`. Новое событие модуля добавляется в `Replayers` там же (с `nil`, если таблицу не меняет), иначе тест `TestRebuildKnowsEveryEventOfTheModule` не пройдёт. Команда не меняет таблицу записи иначе как через `apply*` своего события.
- Нагрузочный тест `TestStockStaysConsistentUnderLoad` проверяет свойства, а не числа: остаток каждой партии равен пересчитанному по событиям отдельным запросом, заказы израсходовали по рецептуре, версии потоков идут подряд. Его помощники `requireStockMatchesEvents`, `requireOrdersConsumedByRecipe` и `requireStockReplays` годятся для любого теста через `apitest` в пакете `inventory_test`.
- Не запускай через `t.Parallel` тесты, читающие события через `eventstore.ReadAll`: незавершённая транзакция в любой базе контейнера задерживает такое чтение.

## Скиллы

- Скиллы backend лежат в `backend/.agents/skills/`; `backend/.claude/skills` - симлинк на неё. Общие правила по скиллам - в корневом [AGENTS.md](../AGENTS.md).
- Свои скиллы называем с префиксом `backend-` (например, `backend-eventstore`, `backend-api`).
- Перед работой над backend запускай агента из папки `backend/`.
