# План разработки системы

Система предназначена для учёта складских остатков ресторана, контроля сроков годности, обработки заказов, формирования стоп-листа и рекомендаций блюд.

## 1. Общая архитектура

Основные компоненты:

- backend на Go;
- frontend на React;
- PostgreSQL как хранилище Event Store и read-моделей;
- Redis для кеша и хранения короткоживущих данных;
- Kafka для доставки интеграционных событий;
- Keycloak для авторизации и управления ролями;
- SSE для обновления данных на frontend в реальном времени;
- Prometheus и Grafana для мониторинга;
- Promtail и Loki для сбора и просмотра логов;
- Telegram-бот для уведомлений о просроченных продуктах.

Система рассчитана на несколько компаний и точек (ADR-013): владелец создаёт компанию, в ней точки, на каждой точке свой склад и своя кухня. Каталог (продукты, блюда, рецептуры) общий на компанию; поставки, остатки, заказы, стоп-лист, рекомендации и аналитика ведутся отдельно по каждой точке. Разделы ниже описывают работу одной точки, если не сказано иное.

Backend реализуется как модульное приложение. На начальном этапе нет необходимости разделять его на микросервисы: домены отделяются внутри кода, чтобы при необходимости их можно было выделить позднее.

```text
React frontend
       |
   REST + SSE
       |
   Go backend
       |
       +-- PostgreSQL Event Store + projections
       +-- Redis
       +-- Kafka
       +-- Keycloak
       |
 Background workers
       |
       +-- контроль сроков годности
       +-- Telegram-уведомления
       +-- рекомендации и аналитика
```

## 2. Event Store и read-модели

Система использует Event Sourcing. Источником истины является append-only Event Store в PostgreSQL, а текущее состояние строится проекциями из событий.

Основные потоки событий относятся к:

- продуктам, блюдам и рецептурам;
- поставкам и партиям;
- складским остаткам;
- заказам;
- списаниям и корректировкам;
- действиям пользователей, требующим аудита.

Примеры доменных событий: `DeliveryRegistered`, `DeliveryApproved`, `DeliveryApprovalCorrected`, `QuarantinedDeliveryItemAccepted`, `QuarantinedDeliveryItemRejected`, `BatchReceived`, `StockWrittenOff`, `BatchExpiryWarningIssued`, `OrderAccepted`, `OrderRejected`, `StockConsumed` и `StockAdjusted`.

Каждое событие содержит уникальный идентификатор, глобальный номер `position`, идентификатор транзакции `txid`, stream ID, версию потока, тип, версию схемы, payload, metadata, время, correlation ID и causation ID. События после записи не изменяются и не удаляются.

Отдельные read-модели хранят:

- актуальные остатки по продуктам и партиям;
- поставки, результаты приёмки и approvals;
- доступность блюд и стоп-лист;
- историю заказов и поставок;
- истекающие партии;
- рекомендации и аналитические показатели.

Основные требования:

- остатки ведутся в потоке на продукт точки `stock-<pointId>-<productId>`, партии входят в поток своего продукта;
- команды, меняющие несколько потоков остатков, берут блокировки по продуктам точки в едином порядке;
- запись событий использует optimistic concurrency по версии потока;
- связанные события команды добавляются атомарно в одной транзакции PostgreSQL;
- повторная команда не создаёт события второй раз;
- количество хранится с фиксированной точностью, даты — в UTC;
- схемы событий версионируются и остаются обратно совместимыми;
- проекции имеют checkpoints, обрабатывают события идемпотентно и могут быть полностью перестроены;
- проекторы и publisher читают события в порядке `(txid, position)` и только ниже границы `pg_snapshot_xmin`, чтобы не пропускать события параллельных транзакций; checkpoint хранит пару `(txid, position)`; подробнее: ADR-002 в [ADR.md](ADR.md);
- структура Event Store и read-моделей изменяется через миграции.

## 3. Backend

### Продукты, блюда и рецептуры

- управление продуктами и единицами измерения;
- управление блюдами;
- настройка состава блюда и количества ингредиентов на порцию;
- проверка корректности рецептуры.

### Поставки и склад

- регистрация поставок и создание партий только после приёмки;
- предварительный просмотр состава поставки до приёмки;
- разделение позиций на просроченные и непросроченные;
- полная или частичная приёмка поставки уполномоченным сотрудником;
- отбраковка или помещение в карантин повреждённых продуктов;
- принятие или окончательное отклонение позиции после карантина;
- валидация `expires_at` и его согласованности с датой изготовления и сроком хранения;
- просмотр общих остатков и остатков по партиям;
- ручная корректировка с указанием причины;
- история всех складских событий.

Каждая позиция поставки содержит обязательный `expires_at`. `manufactured_at` может передаваться дополнительно; при наличии срока хранения backend проверяет согласованность дат. Статус просрочки определяется сравнением `expires_at` со временем проверки поставки, а не выводится только из срока хранения.

До approval поставка не увеличивает доступный остаток. При приёмке по каждой позиции фиксируются заявленное, принятое, отклонённое и помещённое в карантин количество, причина отклонения и комментарий. Для каждой позиции должно выполняться равенство `заявлено = принято + отклонено + карантин`. Backend повторно проверяет `expires_at` в момент записи approval, даже если UI ранее показал позицию непросроченной. Для принятого количества создаются складские партии; просроченные и отклонённые продукты в доступный остаток не попадают.

Карантинная позиция остаётся вне доступного остатка до отдельного решения пользователя с `deliveries.approve`. Команда разрешения карантина решает судьбу всего карантинного количества позиции сразу: делит его на принятую часть, для которой создаётся партия через `QuarantinedDeliveryItemAccepted` и `BatchReceived`, и отклонённую часть, которая фиксируется через `QuarantinedDeliveryItemRejected`. Любая из частей может быть нулевой. После команды карантин позиции закрыт, повторное решение запрещено.

Approval неизменяем и содержит снимок всех позиций поставки, результат проверки каждой позиции, `approved_by` с типом actor (`user` или `service`), дату и время поставки, а также дату и время приёмки. При UI-приёмке actor — менеджер; автоматический approval генератора явно помечается как service account.

Ошибка исправляется командой `CorrectDeliveryApproval`. Она требует ссылку на исходный approval, построчные изменения, причину, пользователя и время. Correction сохраняет исходное заявленное количество и меняет только распределение между принятым, отклонённым и карантинным количеством. Команда атомарно добавляет `DeliveryApprovalCorrected` и результирующие события склада: `BatchReceived` при увеличении принятого количества либо `StockAdjusted` при его уменьшении. Уменьшить принятое количество можно только в пределах ещё доступного остатка соответствующей партии. Исходный approval не изменяется; проекция показывает оригинал и историю corrections.

Регистрация поставки и approval остаются разными командами. Внутри команды approval событие `DeliveryApproved` в потоке поставки и события `BatchReceived` в потоках продуктов записываются атомарно; при ошибке не добавляется ни одно из них.

### Заказы

При создании заказа backend:

1. рассчитывает общую потребность в ингредиентах;
2. в одной транзакции берёт advisory-блокировки на затронутые продукты в порядке возрастания идентификатора;
3. читает партии этих продуктов из синхронной таблицы остатков (write model) и версии потоков `stock-<pointId>-<productId>`;
4. проверяет доступные непросроченные остатки;
5. выбирает партии по FEFO — сначала с ближайшим сроком годности;
6. атомарно добавляет события заказа и списания с проверкой версий потоков и обновляет таблицу остатков.

Если хотя бы одного продукта недостаточно, события списания не добавляются. Блокировки по продуктам выстраивают в очередь заказы с общими ингредиентами, проверка версии потока остаётся страховкой: при конфликте команда повторяется ограниченное число раз. Асинхронные read-модели в проверке бизнес-инвариантов не участвуют. Подробнее: ADR-002 в [ADR.md](ADR.md).

### Стоп-лист

Для каждого блюда рассчитываются:

- доступность;
- возможное количество порций;
- недостающие или ограничивающие ингредиенты;
- причина попадания в стоп-лист.

Стоп-лист не хранится: он рассчитывается при каждом запросе по синхронным таблицам рецептур и партий, тем же правилом доступного остатка, что и оформление заказа. Так он не отстаёт от записи и учитывает просрочку, которая наступает без события. Эти таблицы полностью перестраиваются из Event Store. Подробнее: ADR-002 в [ADR.md](ADR.md).

### Сроки годности

- поиск истекающих и просроченных партий;
- настраиваемый период предупреждения;
- однократное предупреждение по партии событием `BatchExpiryWarningIssued`;
- отметка о просрочке партии событием `BatchExpired` без изменения остатка; просрочку списывает управляющий вручную через `StockWrittenOff` с причиной `expired` (автоматического списания нет с 2026-10-15);
- ручное списание с причиной;
- регистрация досрочной порчи из-за перевозки, хранения или повреждения;
- статистика списаний;
- добавление единого события `StockWrittenOff` для любого уменьшения остатка из-за порчи или истечения срока.

Фоновый обработчик использует проекцию истекающих партий для поиска кандидатов, но перед `BatchExpired` повторно проверяет актуальный остаток и срок в синхронном write model. Повторная обработка не должна создавать дублирующие уведомления или отметки.

Предупреждение о приближении срока оформляется так же: worker находит партию по проекции и вызывает команду `IssueBatchExpiryWarning`, которая повторно проверяет партию в write model и добавляет `BatchExpiryWarningIssued`. Событие не меняет остаток и выдаётся один раз на партию. Telegram-уведомление и SSE-обновление получают его через publisher и Kafka; напрямую в Kafka worker не пишет. Подробнее: ADR-008 в [ADR.md](ADR.md).

Порча после приёмки оформляется ручной операцией: сотрудник выбирает партию и количество, указывает причину и комментарий. Единственное событие `StockWrittenOff` уменьшает доступный остаток и содержит причину `expired`, `transport_damage`, `storage_violation`, `physical_damage`, `quality_issue` или `other`, время, исходную партию и actor. Actor — всегда пользователь, комментарий обязателен: просрочку тоже списывает человек. Отдельные события сообщения о порче и отдельного просроченного списания не вводятся. Физическое удаление или ручное изменение остатка без события запрещено.

### Горячие предложения и поставки

Рекомендации блюд учитывают:

- близость срока годности ингредиентов;
- количество продукта под риском списания;
- расход продукта на порцию;
- доступность остальных ингредиентов.

Результат содержит рейтинг и понятное объяснение рекомендации. Отдельный расчёт предлагает поставки для продуктов, остаток которых опустился ниже заданного уровня. Уровень задаётся запасом по времени: остатка хватит меньше чем на заданное число часов при расходе под заказы за последний период; рекомендуемое количество доводит запас до целевого. Оба расчёта выполняются при чтении по текущим остаткам и времени.

### Аналитика и прогнозы

Показатели строятся проекциями по доменным событиям склада и заказов и могут быть перестроены из Event Store.

Статистика дефицитных ингредиентов:

- сколько раз продукт стал причиной отклонения заказа (по событиям `OrderRejected`);
- сколько раз и как долго продукт держал блюда в стоп-листе;
- рейтинг продуктов по этим показателям за выбранный период.

Прогноз момента стоп-листа:

- скорость расхода продукта считается по событиям `StockConsumed` за последний период;
- время до исчерпания продукта равно доступному остатку, делённому на скорость расхода;
- доступный остаток учитывает истечение сроков годности партий внутри горизонта прогноза;
- прогноз для блюда равен минимальному времени среди его ингредиентов;
- результат содержит ожидаемое время попадания в стоп-лист и ограничивающий ингредиент;
- если расхода за период не было, прогноз не выдаётся.

### Генератор событий

Отдельный процесс эмулирует работу ресторана: создаёт поставки, выполняет их approval и создаёт заказы через публичный REST API. Речь о внешних командах, а не о доменных событиях: в Event Store генератор не пишет.

Генератор аутентифицируется в Keycloak через отдельную service account. Владелец включает его на своей точке и задаёт интенсивность; генератор создаёт поставки и заказы на каждой точке, где он включён, по каталогу её компании, и наполняет этот каталог демонстрационным набором, если он пуст. Настройки точки:

- запуск и остановка;
- настройка интенсивности поставок и заказов;
- набор продуктов, блюд и сроков хранения берётся из справочников системы;
- каждая позиция получает корректный `expires_at`; часть тестовых поставок намеренно содержит уже просроченные или карантинные позиции;
- после регистрации генератор выполняет approval, принимая только допустимые позиции; созданный им карантин он затем явно принимает или отклоняет;
- часть заказов намеренно превышает остатки, чтобы проверялись отказ и стоп-лист;
- генератор не обращается к базе данных напрямую и не обходит проверки backend.

## 4. API и события

Backend предоставляет REST API для:

- продуктов, блюд и рецептур;
- поставок, проверки, approval и партий;
- складских остатков и истории событий;
- отбраковки, карантина и досрочного списания;
- заказов;
- стоп-листа;
- истекающих продуктов и списаний;
- рекомендаций блюд и поставок;
- аналитики: списания, дефицитные ингредиенты, прогноз стоп-листа;
- управления генератором событий.

API должно иметь единый формат ошибок, пагинацию, фильтрацию и документацию OpenAPI.

Доменные события сначала сохраняются в Event Store. После успешного commit необходимые интеграционные события надёжно публикуются в Kafka отдельным publisher-процессом. Kafka используется для распространения событий:

- зарегистрирована поставка;
- поставка проверена, принята полностью или частично;
- позиция поставки отклонена или помещена в карантин;
- карантинная позиция принята или окончательно отклонена;
- approval скорректирован отдельной операцией;
- изменился остаток;
- оформлен или отклонён заказ;
- партия скоро истечёт;
- партия просрочена и списана;
- требуется пересчитать рекомендации.

Event Store в PostgreSQL остаётся источником истины. Kafka используется для асинхронной доставки и не является журналом доменных событий. Повторная публикация и повторная доставка безопасны благодаря идентификатору события и идемпотентным consumers.

## 5. Realtime: SSE вместо WebSocket

Поток открывается для точки (`/points/{pointId}/events`) и несёт сигналы только её событий и каталога её компании. Для проекта предпочтительнее SSE, потому что основные realtime-сценарии однонаправленные: сервер сообщает frontend об изменении остатков, стоп-листа, сроков годности и рекомендаций. Команды пользователя отправляются через REST.

Преимущества SSE в этом случае:

- проще реализация и сопровождение;
- работает поверх обычного HTTP;
- встроенное переподключение клиента;
- достаточно для серверных уведомлений;
- проще использовать через прокси и балансировщик.

WebSocket стоит рассматривать только при появлении постоянного двустороннего обмена, например совместного редактирования или интерактивного потока команд. Если SSE недоступен, frontend не опрашивает REST по таймеру: он показывает, на какое время актуальны данные, переподключается и после переподключения перечитывает данные точки.

## 6. Frontend

### Экран приёмки поставки

Экран показывает номер и время поставки, а также все поступившие продукты: название, заявленное количество, срок годности и статус `не просрочен` или `просрочен`.

Перед approval менеджер по каждой позиции указывает принятое количество и при необходимости отклонённое или карантинное количество с причиной. Допускается частичная приёмка. Просроченные позиции нельзя принять в доступный остаток.

После подтверждения экран показывает неизменяемый approval со снимком состава поставки, результатом по каждой позиции, принявшим actor, временем поставки и временем приёмки. Для обычной UI-приёмки показывается менеджер; синтетическая приёмка генератора помечается как автоматическая. Отдельный список показывает открытые карантинные позиции и позволяет пользователю с `deliveries.approve` принять либо окончательно отклонить их. Ошибочная приёмка исправляется действием `CorrectDeliveryApproval` с тем же permission и обязательной причиной; редактирование сохранённого approval запрещено.

### Экран складского учёта

Экран содержит таблицу продуктов и партий с фильтрами по названию, категории, статусу, сроку годности, наличию, поставке и партии. Пользователь может перейти к истории событий партии.

Сотрудник с правом редактирования может оформить досрочную порчу продукта из-за неправильного хранения или повреждения: выбрать партию и количество, указать причину и комментарий. После подтверждения остаток пересчитывается, а операция появляется в истории и аудите.

### Экран повара

Экран содержит:

- список блюд и рецептов с ингредиентами;
- актуальный стоп-лист;
- доступное количество порций;
- причины недоступности блюда.

Повар видит только разрешённые ему данные и не получает права редактирования склада автоматически.

### Остальные экраны

- сводка состояния склада;
- история заказов;
- истекающие и просроченные партии;
- горячие предложения;
- рекомендации поставок;
- аналитика списаний;
- статистика дефицитных ингредиентов;
- прогноз попадания блюд в стоп-лист;
- управление генератором событий;
- управление доступом через Keycloak.

Основные требования:

- адаптивная работа на компьютере и планшете;
- фильтрация, сортировка и пагинация;
- понятные статусы сроков годности;
- подтверждение списаний и других критичных действий;
- отдельное подтверждение approval поставки с итогами принятия и отбраковки;
- отображение причин ошибок и отказа заказа;
- автоматическое обновление данных через SSE;
- повторная загрузка актуального состояния после восстановления соединения.

## 7. Авторизация

Keycloak отвечает за вход и самостоятельную регистрацию пользователей и подтверждает личность. Права в токене не передаются: их определяют назначения сотрудников на точки (ADR-013).

- владелец компании имеет все права на всех её точках;
- сотрудник получает права роли на той точке, куда назначен: управляющий, приёмщик, повар или официант;
- каталог компании меняет только владелец;
- сотрудников добавляют владелец и управляющий точки, по точному адресу почты зарегистрированного пользователя.

Backend проверяет право для каждой операции на точке или в компании из адреса запроса.

Базовые permissions:

- `catalog.view` — смотреть продукты, блюда и рецептуры;
- `deliveries.view` — смотреть поставки, approvals и карантин;
- `deliveries.register` — регистрировать поставки;
- `deliveries.approve` — принимать поставки;
- `orders.view` — смотреть историю заказов;
- `orders.accept` — принимать заказы;
- `inventory.view` — смотреть товары и партии на складе;
- `inventory.edit` — корректировать остатки, оформлять порчу и списания;
- `kitchen.view` — смотреть экран повара, рецепты и стоп-лист;
- `products.manage` — создавать и изменять продукты;
- `dishes.manage` — создавать и изменять блюда и рецептуры;
- `analytics.view` — смотреть аналитику;
- `recommendations.view` — смотреть горячие предложения и рекомендации поставок;
- `generator.manage` — включать, останавливать и настраивать генератор на точке (только владелец);
- `menu.manage` — выключать и включать блюда на точке;
- `staff.view`, `staff.manage` — смотреть и менять сотрудников точки;
- `notifications.manage` — задавать точке чат Telegram;
- `point.view`, `company.view`, `company.manage` — смотреть точку и компанию, менять компанию и её точки (только владелец).

Роли точки собираются из permissions: управляющий, приёмщик, повар и официант. Каталог компании (`products.manage`, `dishes.manage`) меняет только владелец; в компании сотрудник любой её точки читает каталог. Сервисная учётная запись генератора получает права на точке (регистрация и приёмка поставок, заказы) и в её компании (чтение и наполнение пустого каталога), только пока генератор на точке включён; в токене у неё единственное право `generator.run`. Назначениями управляют владелец и управляющий точки. Остальные комбинации следуют принципу минимальных прав.

Критичные действия — approval поставки, отбраковка, изменение рецептур, корректировка остатков и списание — записываются в журнал аудита.

## 8. Redis и масштабирование

Redis используется для:

- кеширования списков поставок, истории заказов, аналитики списаний и статистики дефицита;
- хранения готового ответа под ключом с checkpoint проекции и параметрами запроса.

Меню, стоп-лист, текущие остатки, партии и рекомендации через Redis не кешируются: они должны учитывать синхронное состояние склада или текущее время. Rate limiting и ускорение защиты от повторной обработки остаются возможным развитием, но в текущую реализацию не входят.

Backend не хранит пользовательское состояние в памяти и при необходимости запускается в нескольких экземплярах за балансировщиком. Фоновые обработчики также можно масштабировать, используя Kafka consumer groups.

Кеш включается непустым `REDIS_URL`; TTL задаётся `REDIS_CACHE_TTL`, timeout операций — `REDIS_TIMEOUT`. Корректность складских операций и readiness не зависят от Redis: при его недоступности система читает PostgreSQL и работает медленнее.

## 9. Мониторинг и логи

Prometheus собирает технические и бизнес-метрики:

- время ответа и количество ошибок API;
- количество успешных и отклонённых заказов;
- число истекающих и просроченных партий;
- объём списаний;
- задержку обработки Kafka;
- задержку проекций относительно Event Store;
- ошибки добавления событий и конфликты версий потоков;
- состояние PostgreSQL, Redis и фоновых обработчиков.

Grafana отображает дашборды и правила оповещений. Приложение пишет структурированные логи. Promtail собирает их и отправляет в Loki, а просмотр выполняется через Grafana.

Telegram используется для прикладных уведомлений:

- продукт скоро станет просроченным;
- партия просрочена и ждёт решения о списании;
- обработчик уведомлений не смог выполнить задачу.

Сообщение содержит продукт, номер партии, остаток, срок годности и ссылку на соответствующий экран системы.

## 10. Надёжность и безопасность

- атомарное добавление связанных событий поставок, заказов и списаний;
- optimistic concurrency по версии потока;
- идемпотентность внешних запросов и Kafka-обработчиков;
- резервное копирование Event Store в PostgreSQL;
- возможность перестроить все проекции из событий;
- повтор обработки временно неуспешных сообщений;
- отдельная очередь для сообщений, которые не удалось обработать;
- health checks для backend и workers;
- защищённое хранение секретов;
- TLS и ограничение доступа по ролям;
- валидация входных данных и ограничение частоты запросов.

- тесты REST API;
- end-to-end тесты основных пользовательских сценариев;

- тесты обязательного `expires_at` и классификации позиции на момент проверки;
- тесты обоих выходов из карантина и запрета повторного решения;
- тесты `CorrectDeliveryApproval` и атомарного изменения складского состояния;
- тесты единого `StockWrittenOff` для просрочки и досрочной порчи;

Критичные сценарии: частичная приёмка поставки, классификация по `expires_at`, оба выхода из карантина, correction approval, единое списание просрочки и порчи, сквозной сценарий генератора, FEFO по нескольким партиям, отсутствие событий списания при отклонённом заказе, защита от повторной команды, конфликт параллельных заказов, replay Event Store и актуальное обновление стоп-листа.
