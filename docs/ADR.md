# Architecture Decision Record

- **Статус:** принято
- **Дата:** 2026-10-10
- **Основание:** [Case.md](Case.md), [plan.md](plan.md)

Документ фиксирует основные архитектурные решения проекта. При изменении решения соответствующий раздел должен получить новый статус и ссылку на заменяющий ADR или OpenSpec change.

## ADR-001: модульное приложение вместо микросервисов

### Контекст

Система включает склад, поставки, заказы, стоп-лист, мониторинг сроков годности и рекомендации. Эти области связаны общими транзакциями и данными, а независимое масштабирование каждой из них пока не требуется.

### Решение

Backend реализуется на Go как модульное приложение с разделением доменов внутри кодовой базы. Frontend реализуется отдельно на React. Фоновые задачи запускаются отдельными worker-процессами, использующими те же доменные правила.

### Последствия

- проще разработка, тестирование и развёртывание;
- транзакционные сценарии не требуют распределённых транзакций;
- границы модулей должны исключать произвольные прямые зависимости;
- при подтверждённой необходимости отдельный модуль можно выделить в сервис.

## ADR-002: Event Sourcing и Event Store в PostgreSQL

### Контекст

Заказы и складские операции требуют атомарности, защиты от конкурентного списания, полного аудита и возможности восстановить состояние на любой момент времени.

### Решение

Система использует Event Sourcing. Append-only Event Store в PostgreSQL является единственным источником истины. Изменение бизнес-состояния фиксируется доменными событиями; текущее состояние и представления для чтения строятся проекциями. Отдельный продукт EventStoreDB на этом этапе не вводится.

Событие содержит event ID, глобальный номер `position`, идентификатор транзакции `txid`, stream ID, версию потока, тип и версию схемы, payload, metadata, время, correlation ID и causation ID. События после записи не изменяются и не удаляются.

Связанные события одной команды добавляются атомарно. Конкурентные изменения защищаются optimistic concurrency по ожидаемой версии потока. Списание идёт по FEFO: сначала используется непросроченная партия с ближайшим сроком годности.

#### Границы потоков

С ADR-013 склад ведётся по точке: складской поток - `stock-<pointId>-<productId>`, блокировки берутся по паре "точка, продукт". Ниже в этом ADR "продукт" в описании потока и блокировок читается как "продукт на точке".

- `stock-<productId>`: складской поток продукта. Содержит все события остатков этого продукта по всем его партиям: приход, списание по заказу, корректировку, истечение срока, списание просрочки. Партия не является отдельным потоком.
- `order-<orderId>`: поток заказа.
- `delivery-<deliveryId>`: поток поставки.
- отдельные потоки справочников: продукт, блюдо с рецептурой.

Поток остатков заведён на продукт, потому что инвариант "доступного количества хватает" и выбор партий по FEFO относятся к продукту целиком: для решения нужны все его партии сразу.

#### Команды, затрагивающие несколько потоков

Заказ и поставка меняют несколько потоков `stock-*` одновременно. Такая команда выполняется в одной транзакции PostgreSQL:

1. берёт транзакционные advisory-блокировки (`pg_advisory_xact_lock`) на все затронутые продукты, в порядке возрастания идентификатора продукта;
2. читает текущее состояние партий этих продуктов и версии их потоков;
3. принимает решение: проверяет остатки и выбирает партии по FEFO;
4. добавляет события во все потоки с проверкой ожидаемой версии каждого;
5. в той же транзакции обновляет таблицу текущих остатков партий.

Блокировки выстраивают в очередь только команды с общими продуктами; команды по разным продуктам идут параллельно. Единый порядок взятия блокировок исключает взаимные блокировки. Проверка версии потока остаётся страховкой: при конфликте команда повторяется ограниченное число раз, затем возвращает ошибку.

Все команды, пишущие в `stock-*`, идут через этот путь, включая фоновое списание просрочки и ручную корректировку.

#### Состояние для принятия решений

Таблица текущих остатков партий является write model: она обновляется синхронно, в одной транзакции с добавлением событий, поэтому не отстаёт от Event Store. Решения о списании принимаются по ней, а не по replay потока на каждый заказ. Таблица не является источником истины и полностью перестраивается из событий.

Остальные проекции (списки поставок и заказов, истекающие партии, рекомендации, аналитика) обновляются асинхронно и в проверке инвариантов не участвуют.

Стоп-лист и число возможных порций не хранятся как проекция: они рассчитываются при чтении по таблице текущих остатков и таблицам рецептур. Доступность продукта зависит от текущего времени - партия перестаёт быть доступной в момент истечения срока, без события, - поэтому хранимый стоп-лист расходился бы с решением заказа. Расчёт при чтении использует те же таблицы и то же правило, что команда заказа, и совпадает с ней по построению. В проверке инвариантов стоп-лист по-прежнему не участвует: решение принимает только команда.

#### Чтение событий проекторами и publisher

Глобальный номер события выдаётся при вставке, а видимым событие становится при commit. Параллельные транзакции могут завершиться не в порядке номеров, поэтому чтение по условию "номер больше checkpoint" способно навсегда пропустить событие.

Чтобы этого не происходило:

- каждое событие хранит глобальный номер `position` и идентификатор транзакции `txid` типа `xid8` со значением по умолчанию `pg_current_xact_id()`;
- читатель выбирает только события с `txid < pg_snapshot_xmin(pg_current_snapshot())`, то есть записанные транзакциями старше самой старой ещё не завершённой;
- события читаются в порядке `(txid, position)`, checkpoint хранит эту пару;
- по `(txid, position)` создаётся индекс.

Ниже границы `pg_snapshot_xmin` новые события появиться не могут, поэтому читатель не пропускает события и не требует сериализации писателей.

Блокировки по продуктам берутся до первой записи в транзакции. Тогда транзакция получает `txid` после завершения предыдущей команды по тем же продуктам, и порядок `(txid, position)` совпадает с порядком версий внутри потока `stock-*`.

Проекция в PostgreSQL обновляет свой checkpoint в одной транзакции с записью данных проекции. Publisher сдвигает checkpoint после подтверждения от Kafka.

### Последствия

- параллельные заказы с общим ингредиентом выполняются последовательно, без лавины повторов по конфликту версий;
- время удержания блокировки равно времени одной транзакции, поэтому внутри неё нет сетевых вызовов и обращений к Kafka или Redis;
- расхождение таблицы остатков с Event Store является дефектом и проверяется тестом полного replay;
- проекторы и publisher не пропускают события при параллельной записи;
- любая долгая транзакция в базе задерживает всех читателей событий, поэтому транзакции должны быть короткими, а отставание читателей выводится в метрики;
- требуется PostgreSQL 13 или новее (тип `xid8`);
- отсутствие пропусков проверяется тестом с параллельными писателями и задержкой перед commit;
- остаток партии не может стать отрицательным;
- при нехватке ингредиента события списания не добавляются;
- решение о списании не принимается только по потенциально отстающей read-модели;
- каждое изменение остатка представлено отдельным доменным событием;
- схемы событий версионируются и сохраняют обратную совместимость;
- проекции имеют checkpoints, обрабатывают события идемпотентно и полностью перестраиваются;
- snapshots допускаются как оптимизация длинных потоков, но не заменяют события;
- резервное копирование Event Store важнее резервного копирования пересоздаваемых проекций.

## ADR-003: Redis только для ускорения

### Контекст

Некоторые справочники и рассчитанные представления читаются часто, но потеря кеша не должна нарушать складской учёт.

### Решение

Redis используется для кеширования read-моделей, rate limiting, короткоживущего технического состояния и ускорения защиты от повторной обработки. Критичные остатки и бизнес-состояние в Redis не хранятся как единственная копия.

Первая реализация кеширует только готовые ответы асинхронных проекций:

- список поставок (`GET /deliveries`, проекция `inventory-deliveries`);
- историю заказов (`GET /orders`, проекция `orders-history`);
- аналитику списаний и дефицита (`GET /analytics/write-offs`, `GET /analytics/shortages`, проекция `analytics`).

Ключ содержит версию формата, имя, версию и позицию checkpoint проекции, операцию и хеш всех параметров запроса. Данные проекции и checkpoint обновляются в одной транзакции PostgreSQL: после продвижения проекции следующий запрос получает новый ключ. Старые значения удаляются по TTL; массовая инвалидация через Kafka не требуется.

Меню, стоп-лист, текущие остатки, партии и рекомендации не кешируются. Они участвуют в проверке актуальной доступности либо зависят от текущего времени и могут измениться без нового события.

Кеш работает в режиме fail-open: пустой `REDIS_URL` отключает его, а ошибка Redis приводит к чтению PostgreSQL. Redis не входит в readiness API. Rate limiting и перенос идемпотентности или Kafka inbox в Redis этой реализацией не вводятся.

### Последствия

- при недоступности Redis система может работать медленнее, но остаётся корректной;
- данные кеша можно восстановить из проекций, а проекции — из Event Store;
- checkpoint в ключе обеспечивает инвалидацию при изменении проекции, TTL ограничивает хранение старых ключей;
- каждый запрос к кешируемому представлению всё ещё читает одну строку checkpoint из PostgreSQL.

## ADR-004: разделение доменных событий и Kafka

### Контекст

Доменные события должны надёжно фиксировать состояние системы, а изменение склада запускает независимые действия: пересчёт рекомендаций, realtime-обновления, мониторинг и Telegram-уведомления. Эти действия не должны замедлять команду заказа или поставки.

### Решение

Доменные события сначала сохраняются в Event Store. После commit publisher читает новые события по checkpoint и публикует необходимые интеграционные события в Kafka, включая:

- регистрацию поставки;
- полную или частичную приёмку поставки;
- отклонение, карантин или досрочную порчу продукта;
- изменение остатка;
- оформление или отклонение заказа;
- приближение срока годности (доменное событие `BatchExpiryWarningIssued`);
- списание просроченной партии;
- запрос на пересчёт рекомендаций.

Consumers работают идемпотентно и масштабируются через consumer groups. Временно неуспешные сообщения повторяются, необрабатываемые направляются в отдельный поток ошибок.

### Последствия

- Event Store, а не Kafka, является журналом доменных событий и источником истины;
- недоступность Kafka не должна препятствовать фиксации корректной бизнес-операции в Event Store;
- после восстановления publisher продолжает работу с сохранённого checkpoint;
- отставание publisher от Event Store выводится в метрики;
- Kafka допускает повторную доставку, поэтому consumers используют event ID для идемпотентности;
- интеграционные контракты могут отличаться от внутренних схем доменных событий и версионируются отдельно.

## ADR-005: REST для команд, SSE для realtime

### Контекст

Frontend отправляет обычные команды и получает односторонние обновления остатков, стоп-листа, сроков годности и рекомендаций. Постоянный двусторонний канал не требуется.

### Решение

Команды и запросы выполняются через REST API. Обновления от backend к frontend передаются через Server-Sent Events.

SSE выбран вместо WebSocket, поскольку он проще для одностороннего потока, работает поверх HTTP и поддерживает автоматическое переподключение. После восстановления соединения клиент повторно загружает актуальное состояние. Периодического REST polling на время недоступности SSE нет (изменено 2026-10-14): пока связи нет, веб-клиент показывает, на какое время актуальны данные, и переподключается, а после переподключения перечитывает данные точки.

### Последствия

- API документируется через OpenAPI;
- требуется единый формат ошибок, фильтрация и пагинация;
- SSE не является источником состояния и может пропускать промежуточные события;
- при долгом обрыве данные на экране устаревают до переподключения, и пользователь видит время, на которое они актуальны;
- переход на WebSocket рассматривается только при появлении постоянного двустороннего обмена.

## ADR-006: Keycloak для авторизации

- **Статус:** частично заменено ADR-013 (внедрено 2026-10-12): Keycloak остаётся провайдером входа и самостоятельной регистрации, а прав пользователей в токене нет - их определяют владение компанией и назначения сотрудников на точки. Список permissions ниже сохраняется как права ролей на точке; сведения о client roles и составных ролях в тексте решения описывают прежнее устройство. Единственное право из токена - `generator.run` у сервисной учётной записи генератора. Дополнено [ADR-014](#adr-014-сервисные-ключи-поставщиков): кроме токенов Keycloak API принимает ключи поставщиков, которые выпускает сам backend.

### Контекст

Права на просмотр, оформление заказов, изменение рецептур и корректировку склада различаются. Самостоятельная реализация identity-провайдера не относится к предметной области проекта.

### Решение

Keycloak выполняет аутентификацию, выдаёт токены и управляет ролями. Права представлены client roles/claims, а не произвольными attributes как единственным источником авторизации. Backend проверяет токен и необходимое право для каждой защищённой операции. Frontend использует Keycloak для входа и управления сессией.

Базовые permissions:

- `catalog.view`;
- `deliveries.view`;
- `deliveries.register`;
- `deliveries.approve`;
- `orders.view`;
- `orders.accept`;
- `inventory.view`;
- `inventory.edit`;
- `kitchen.view`;
- `products.manage`;
- `dishes.manage`;
- `analytics.view`;
- `recommendations.view`;
- `generator.manage`.

Роль менеджера включает `inventory.view`. Роль approver включает `deliveries.view`, `deliveries.approve` и `inventory.view`. Service account генератора включает `catalog.view`, `deliveries.register`, `deliveries.approve` и `orders.accept`. Для наполнения пустого каталога демонстрационным набором ей дополнительно выдаются `products.manage` и `dishes.manage`; там, где каталог ведут люди, эти два права не выдают и наполнение отключают. Изменение настроек генератора требует `generator.manage`; читать их может любой аутентифицированный клиент, в том числе сам генератор. Остальные роли собираются из permissions по принципу минимальных прав.

С ADR-013 этот абзац не действует: ролей и прав в токене нет, в том числе у сервисной учётной записи генератора. В токене у неё одно право `generator.run`, остальные она получает на точке, пока на ней включён генератор; наборы ролей - в ADR-013.

### Последствия

- контроль доступа всегда выполняется на backend;
- скрытие элемента frontend не считается контролем доступа;
- approval поставки, отбраковка, изменение рецептур, корректировка остатков и списание записываются в аудит;
- секреты и токены не попадают в репозиторий и логи.

## ADR-007: наблюдаемость через Prometheus, Grafana и Loki

### Контекст

Для диагностики нужны как технические показатели, так и бизнес-метрики: ошибки API, отклонённые заказы, истекающие партии и списания.

### Решение

- Prometheus собирает метрики backend, workers, Kafka, PostgreSQL, Redis, скорости append и задержки проекций.
- Grafana отображает дашборды и правила оповещений.
- Приложения пишут структурированные логи в stdout.
- Promtail доставляет логи в Loki.
- Grafana используется для поиска и просмотра логов.

### Последствия

- запросы и события получают correlation ID;
- запрещено логировать секреты, токены и лишние персональные данные;
- новые критичные фоновые процессы должны предоставлять метрики состояния и ошибок;
- алерты должны покрывать остановку проектора, рост projection lag и конфликты версий потоков.

## ADR-008: Telegram для прикладных уведомлений

- **Дополнено ADR-013 (2026-10-11):** чат для уведомлений задаётся у точки, уведомление уходит в чат точки, на которой произошло событие.

### Контекст

Ответственные сотрудники должны оперативно узнавать о риске порчи продуктов без постоянного просмотра интерфейса.

### Решение

Фоновый обработчик отправляет Telegram-сообщения, когда:

- срок годности партии скоро истекает;
- партия просрочена и ждёт решения о списании;
- обработчик уведомлений завершился ошибкой.

Сообщение содержит продукт, партию, остаток, срок годности и ссылку на соответствующий экран, если она доступна.

Каждое уведомление порождается доменным событием из Event Store: предупреждение о сроке - `BatchExpiryWarningIssued`, просрочка - `BatchExpired`. Обработчик уведомлений получает их из Kafka от publisher, как и остальные consumers.

Приближение и наступление срока годности происходят по времени, а не в результате действия пользователя, поэтому для них вводятся отдельные события. Worker находит кандидатов по проекции истекающих партий и вызывает команду `IssueBatchExpiryWarning`. Команда идёт тем же путём, что и остальные записи в `stock-*`: берёт блокировку по продукту, повторно проверяет срок и остаток партии в синхронном write model и добавляет `BatchExpiryWarningIssued` с партией, остатком, `expires_at` и действовавшим периодом предупреждения. Остаток событие не меняет.

Изменено 2026-10-15 (change `expiry-manual-write-off`): автоматического списания просрочки нет, решение о списании принимает управляющий. Когда срок партии с остатком истёк, worker вызывает команду `MarkBatchExpired`, она тем же путём добавляет `BatchExpired` один раз на партию и остаток не меняет. Просроченный остаток не участвует в заказах и меню, пока его не спишут вручную. Это отказ от пункта кейса "Автоматическое списание просроченной продукции", принятый командой осознанно.

Предупреждение выдаётся один раз на партию: факт выдачи хранится в синхронной таблице остатков партий. Для списанной, израсходованной или уже просроченной партии событие не создаётся.

### Последствия

- отправка выполняется асинхронно и не блокирует складские операции;
- повторная обработка события не должна создавать дублирующее сообщение;
- worker не публикует сообщения в Kafka напрямую: правило "в Kafka пишет только publisher" сохраняется без исключений;
- история предупреждений восстанавливается из Event Store и доступна проекциям и аналитике;
- изменение периода предупреждения не приводит к повторным предупреждениям по уже предупреждённым партиям;
- ошибка Telegram сохраняется для повторной обработки и мониторинга.

## ADR-009: горизонтальное масштабирование без усложнения домена

### Контекст

Система должна допускать рост нагрузки, но преждевременное распределение доменной логики увеличит сложность.

### Решение

Backend остаётся stateless и может запускаться в нескольких экземплярах за балансировщиком. Workers масштабируются через Kafka consumer groups. Event Store в PostgreSQL обеспечивает сохранность истории и проверку версий потоков, read-модели обслуживают запросы, а Redis ускоряет чтение. Масштабирование не должно менять бизнес-инварианты.

### Последствия

- пользовательское состояние не хранится в памяти экземпляра backend;
- фоновые обработчики обязаны быть идемпотентными;
- несколько проекторов могут работать параллельно только с безопасным разделением потоков и checkpoints;
- health checks нужны для backend и workers;
- резервное копирование Event Store и проверка восстановления обязательны;
- базовые нагрузочные, конкурентные и replay-тесты входят в проверку системы.

## ADR-010: approval и частичная приёмка поставки

### Контекст

Фактически доставленное количество и состояние продуктов могут отличаться от заявки. В одной поставке одновременно могут быть нормальные, просроченные и повреждённые позиции. Необходимо сохранить юридически и операционно значимый факт приёмки конкретным менеджером.

### Решение

Регистрация поставки и её приёмка являются разными действиями. До approval продукты не увеличивают доступный складской остаток.

Каждая позиция поставки содержит обязательный `expires_at`. Опциональный `manufactured_at` используется для трассировки; при наличии срока хранения backend проверяет согласованность дат. Просрочка определяется сравнением `expires_at` со временем фактической проверки поставки.

При приёмке каждая позиция разделяется на:

- принятое количество;
- отклонённое количество;
- количество в карантине для дополнительной проверки.

Для каждой позиции выполняется инвариант `заявлено = принято + отклонено + карантин`. Backend проверяет `expires_at` повторно в транзакции approval: классификация, ранее показанная UI, не считается достаточной.

Для отклонения и карантина обязательны причина и комментарий. Просроченное количество нельзя принять в доступный остаток. `DeliveryApproved` в потоке поставки и `BatchReceived` для принятого количества в потоках продуктов добавляются атомарно в одной транзакции.

Карантин имеет обязательный конечный переход. Пользователь с `deliveries.approve` либо принимает количество через `QuarantinedDeliveryItemAccepted` и `BatchReceived`, либо окончательно отклоняет его через `QuarantinedDeliveryItemRejected`. До этого решения количество недоступно. Повторно разрешить закрытый карантин нельзя.

Решение по карантину позиции принимается одной командой на всё карантинное количество сразу. Команда делит его на принятую и отклонённую части; любая из частей может быть нулевой, а их сумма равна карантинному количеству позиции. Для ненулевой принятой части создаются `QuarantinedDeliveryItemAccepted` и `BatchReceived`, для ненулевой отклонённой - `QuarantinedDeliveryItemRejected`; все события записываются атомарно. После команды карантин позиции закрыт. Так проверка может закончиться результатом "часть годна, часть нет", но у позиции не остаётся нерешённого остатка, о котором можно забыть. Позиция, срок годности которой истёк к моменту решения, в принятую часть не попадает. Карантин позиции может открыться снова только через `CorrectDeliveryApproval`, если корректировка назначит ей карантинное количество; тогда по нему принимается новое решение. Тот же permission требуется для `CorrectDeliveryApproval`.

Approval сохраняется одним событием `DeliveryApproved` и доступен через проекцию. Событие содержит полный снимок позиций и результатов проверки, `approved_by`, тип actor (`user` или `service`), время поставки и время приёмки. В обычном UI actor является менеджером, а approval генератора явно отмечается как автоматический. Отдельные события осмотра, отклонения и помещения в карантин не создаются: эти решения уже входят в снимок approval. Сохранённый approval неизменяем.

Ошибка исправляется командой `CorrectDeliveryApproval`. Она содержит ссылку на исходный approval, построчные изменения, причину, пользователя и время. Correction не меняет исходное заявленное количество, а перераспределяет его между принятым, отклонённым и карантинным. Команда атомарно добавляет `DeliveryApprovalCorrected` и события изменения склада: `BatchReceived` при увеличении принятого количества либо `StockAdjusted` при уменьшении. Уменьшение ограничено ещё доступным остатком партии. Проекция показывает исходный approval и всю историю corrections.

### Последствия

- поддерживается частичная приёмка без потери информации об отклонённом товаре;
- повреждённый товар не смешивается с доступным остатком;
- невозможно создать позицию поставки без даты окончания срока годности;
- карантин не может остаться без определённого дальнейшего действия;
- approval полностью восстанавливается из Event Store;
- повторная команда approval идемпотентна;
- correction не переписывает историю и согласован со складскими событиями;
- frontend обязан показать итог приёмки до подтверждения.

## ADR-011: досрочная порча и ручное списание

### Контекст

Продукт может испортиться до даты истечения срока из-за неправильной перевозки, хранения на кухне или физического повреждения. Изменение срока годности задним числом или ручная правка остатка уничтожили бы историю.

### Решение

До approval повреждённый товар отклоняется либо помещается в карантин в рамках приёмки. После approval уполномоченный сотрудник оформляет операцию досрочной порчи для конкретной партии и количества.

Операция требует причину (`expired`, `transport_damage`, `storage_violation`, `physical_damage`, `quality_issue` или `other`) и actor. Списание всегда ручное: actor — пользователь, комментарий обязателен; просрочку тоже списывает пользователь (изменено 2026-10-15, автоматического списания нет, см. ADR-008). Единое событие `StockWrittenOff` одновременно фиксирует причину и уменьшает доступный остаток. Отдельные события сообщения о порче и просроченного списания не вводятся.

### Последствия

- физическое удаление партии и редактирование остатка без события запрещены;
- сохраняются автор, время, причина, количество и исходная партия;
- повторная команда не создаёт повторное списание;
- только `StockWrittenOff` уменьшает остаток при порче или истечении срока;
- аналитика различает истечение срока и досрочную порчу;
- право на операцию контролируется permission `inventory.edit`.

## ADR-012: генератор работает через публичный workflow

### Контекст

После разделения регистрации и approval зарегистрированная поставка не создаёт доступный остаток. Если генератор только регистрирует поставки, склад остаётся пустым и сгенерированные заказы отклоняются.

### Решение

Генератор использует публичный REST API и отдельную Keycloak service account с permissions `catalog.view`, `deliveries.register`, `deliveries.approve` и `orders.accept`. Для наполнения пустого каталога демонстрационным набором ей дополнительно выдаются `products.manage` и `dishes.manage`; там, где каталог ведут люди, эти два права не выдают и наполнение отключают.

С ADR-013 этот абзац не действует: ролей и прав в токене нет, в том числе у сервисной учётной записи генератора. В токене у неё одно право `generator.run`, остальные она получает на точке, пока на ней включён генератор; наборы ролей - в ADR-013.

Для каждой поставки генератор:

1. формирует позиции с обязательным `expires_at`;
2. регистрирует поставку;
3. выполняет approval, принимая допустимые позиции и отклоняя либо помещая в карантин тестовые проблемные позиции;
4. явно принимает или окончательно отклоняет созданные им карантинные позиции;
5. только после успешного approval продолжает генерацию заказов.

Пользовательское управление запуском, остановкой и интенсивностью генератора требует отдельного permission `generator.manage`. С ADR-013 генератор включается и настраивается на каждой точке отдельно её владельцем, а его сервисная учётная запись получает права на точке, только пока он на ней включён.

### Последствия

- генератор проверяет тот же workflow и авторизацию, что реальные клиенты;
- генератор не пишет напрямую в Event Store или read-модели;
- тестовый сценарий обязан подтверждать появление остатка после approval и успешное оформление хотя бы одного заказа;
- секрет service account хранится только в конфигурации окружения.

## ADR-013: компании, точки и права по назначениям

- **Статус:** принято и внедрено (2026-10-12) пятью изменениями OpenSpec: `organization-and-access`, `catalog-per-company`, `stock-per-point`, `point-background`, `demo-company-and-realm`
- **Дата:** 2026-10-11
- **Основание:** уточнение кейсодателя о поддержке нескольких складов ([Case.md](Case.md), раздел "Уточнения кейсодателя")
- **Заменяет:** ADR-006 в части хранения и проверки прав

### Контекст

Система строилась под один ресторан с одним складом: остаток считался по продукту, роль пользователя лежала в токене и действовала на всю систему. Кейсодатель уточнил, что складов должно быть несколько. Склад в ресторане неотделим от кухни и персонала, поэтому "несколько складов" означает несколько точек, а с ними - несколько владельцев и разграничение доступа между ними.

### Решение

Вводятся три понятия:

- **компания** - сеть точек одного владельца. Владелец - пользователь, создавший компанию; компаний у него может быть несколько. Владелец может передать компанию другому зарегистрированному пользователю: тот получает все права сразу, прежний владелец теряет их;
- **точка** - место, где есть и склад, и кухня. Принадлежит одной компании;
- **назначение** - сотрудник на точке с ролью: тройка "пользователь, точка, роль". У сотрудника может быть несколько назначений на разных точках с разными ролями, в том числе в компаниях разных владельцев.

Границы данных:

| Уровень компании | Уровень точки |
| --- | --- |
| продукты, блюда, рецептуры | поставки, партии, остатки |
| точки и назначения | заказы |
| | стоп-лист и меню, выключенные на точке блюда |
| | горячие предложения, рекомендации поставок |
| | аналитика, уведомления, настройки генератора |

Правила расчёта (FEFO, сроки годности, стоп-лист, формулы рекомендаций) не меняются: они применяются в границах точки.

Доступ:

- Keycloak выполняет вход и самостоятельную регистрацию и подтверждает личность. Ролей и прав в токене нет;
- права определяет назначение. Роли на точке: управляющий, приёмщик, повар, официант; каждая роль - набор permissions: к перечню ADR-006 добавлены `company.view`, `company.manage`, `point.view`, `staff.view`, `staff.manage`, `menu.manage`, `notifications.manage`; наборы ролей - в таблице ниже;
- владелец имеет все права на всех точках своих компаний без назначений;
- каталог компании меняет только владелец;
- сотрудников на точку добавляют владелец (на любую точку компании) и управляющий (на свою точку); управляющий не назначает управляющих. Назначить можно только зарегистрированного пользователя, поиск - по точному адресу почты;
- точка и компания передаются в адресе запроса: `/points/{pointId}/...` и `/companies/{companyId}/...`. Backend для каждой операции проверяет право вызывающего на этой точке или в этой компании;
- сервисная учётная запись генератора работает на точке, пока владелец включил на ней генератор: права она получает от настроек генератора, а не назначением;
- объект с собственным идентификатором (поставка, партия, заказ, продукт, блюдо) в адресе сверяется с точкой или компанией из адреса: чужой объект отвечает как несуществующий.

Права ролей на точке. Владелец компании имеет все права, включая те, которых нет ни у одной роли: `products.manage`, `dishes.manage`, `generator.manage`, `company.manage`. В компании сотрудник любой её работающей точки получает `company.view` и `catalog.view`.

| Право | Управляющий | Приёмщик | Повар | Официант |
| --- | --- | --- | --- | --- |
| `point.view`, `staff.view`, `catalog.view` | да | да | да | да |
| `staff.manage`, `menu.manage`, `notifications.manage` | да | | | |
| `deliveries.view`, `inventory.view` | да | да | | |
| `deliveries.register`, `inventory.edit`, `analytics.view` | да | | | |
| `deliveries.approve` | да | да | | |
| `kitchen.view` | да | | да | да |
| `orders.view`, `recommendations.view` | да | | | да |
| `orders.accept` | | | | да |
| `orders.cancel` | да | | | да |

Хранение:

- компании, точки и назначения - бизнес-состояние: меняются событиями в Event Store, как каталог (ADR-002). История "кто кого и когда назначил" получается без отдельного журнала;
- складской поток точки: `stock-<точка>-<продукт>`; advisory-блокировки берутся по тому же имени, поэтому точки не мешают друг другу;
- в событиях поставки, заказа и склада появляется точка, в событиях каталога - компания;
- пользователь записывается в таблицу системы при первом входе (идентификатор Keycloak, почта, имя): так назначение не требует обращений к служебному API Keycloak;
- компании, точки и назначения не удаляются, а отключаются.

Не делается: перемещение продуктов между точками, разные цены и рецептуры по точкам, подтверждение передачи компании получателем, разбивка метрик Prometheus по точкам.

### Последствия

- контракт API меняется целиком: у складских операций в адресе появляется точка, у операций каталога - компания;
- записанные события не содержат компании и точки, а события неизменяемы: данные существующих окружений пересоздаются;
- проверка прав выполняется по базе на каждой операции; при необходимости назначения кешируются, но решение о доступе не может опираться только на кеш (ADR-003);
- токен, выданный до отзыва назначения, прав не сохраняет: права читаются из назначений, а не из токена;
- уведомления Telegram уходят в чат точки; чат задаётся в настройках точки. Точка без чата уведомлений не получает: общий чат окружения остаётся только для ошибок обработчиков, иначе в него попадали бы данные чужих компаний;
- поток обновлений открывается для точки и несёт сигналы только её событий и каталога её компании;
- у блюда, выключенного на точке, нет ни меню, ни стоп-листа, ни рекомендаций на этой точке;
- дашборд Grafana показывает систему в целом; состояние точки смотрят в приложении;
- режим без Keycloak (`AUTH_DISABLED`) отключает только проверку токена: пользователь `dev` получает права по тем же правилам, что и остальные;
- для показа и проверки ролей есть демонстрационная компания "Демо": её создаёт запуск миграций по настройке окружения, тестовые пользователи realm имеют постоянные идентификаторы;
- Keycloak на сервере хранит данные в томе: на идентификаторы самостоятельно зарегистрированных пользователей ссылаются компании и назначения;
- подтверждения почты при регистрации нет, поэтому назначение по адресу почты годится для показа, но не для настоящей работы;
- изолированность компаний проверяется тестами: пользователь без назначения не читает и не меняет данные чужой точки.


## ADR-014: сервисные ключи поставщиков

- **Статус:** принято (2026-10-15), изменение OpenSpec `supplier-api-keys`
- **Дата:** 2026-10-15
- **Дополняет:** ADR-006 и ADR-013 в части аутентификации внешних систем

### Контекст

Поставщик может сам отправлять поставки из своей учётной системы, а приёмщик - проверять и принимать их. Поставщиков у компании много, заводит и отключает их владелец. Сервисная учётная запись Keycloak на каждого поставщика потребовала бы прав администратора realm у backend.

### Решение

- поставщик - техническая настройка компании: название и точки, на которые он возит. Хранится в таблицах без событий, как подключение Мигома и настройки генератора; не удаляется, чтобы его название оставалось в истории поставок;
- ключ поставщика выпускает backend: `gdn_` и 32 случайных байта. Ключ показывается владельцу один раз, в базе хранится только SHA-256. Перевыпуск и отзыв действуют сразу;
- API принимает ключ в `Authorization: Bearer` наравне с токеном Keycloak. Автор действий по ключу - `service` с идентификатором `supplier:<поставщик>`;
- по ключу поставщик читает сведения о себе и продукты своей компании без блюд и рецептур, а на своих работающих точках получает только `deliveries.register`. Приёмка остаётся за сотрудниками точки.

### Последствия

- Keycloak остаётся единственным провайдером входа пользователей; ключи - только для систем поставщиков;
- ключ ищется в базе на каждом запросе: отзыв не ждёт истечения срока, как у токенов;
- поставщик сопоставляет свои товары с продуктами компании сам, по их идентификаторам;
- ограничения частоты запросов нет: перебор 256-битного ключа нереален, поток запросов поставщика мал.
