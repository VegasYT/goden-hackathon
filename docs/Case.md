# Мониторинг остатков, сроков годности и стоп-листов

(кейс компании "Флагман", flagman-it.ru).

## Проблема

Ресторан ежедневно работает с большим количеством продуктов, которые поступают разными партиями, имеют ограниченный срок хранения и используются при приготовлении различных блюд.

При отсутствии актуальной информации об остатках ресторан рискует принимать заказы на блюда, для которых уже недостаточно ингредиентов. Одновременно продукты с истекающим сроком годности могут оставаться незамеченными и списываться.

Автоматизированный контроль товародвижения позволяет сократить количество списаний, своевременно обновлять доступность блюд и эффективнее использовать складские остатки.

## Задача

Реализовать систему учета движения продуктов, контроля их количества и сроков годности, формирования стоп-листа блюд и рекомендаций по приоритетной продаже продукции.

## Требования к решению

### 1. Поставки

- Система должна принимать информацию о поступающих в ресторан поставках.
- Каждая поставка содержит дату создания, уникальный идентификатор, номер поставки и список поступивших продуктов.
- Для каждого продукта необходимо хранить его идентификатор, название, количество и срок хранения.
- Продукты одного типа могут поступать в разных поставках и иметь разные сроки годности.

Базовый функционал поставок:

- Получение новой поставки
- Регистрация партий продуктов
- Учет количества продукции
- Расчет срока годности каждой партии
- Просмотр текущих складских остатков

### 2. Заказы

- Система должна обрабатывать поступающие заказы.
- Заказ содержит одно или несколько блюд.
- Для каждого блюда заранее известен его состав - список необходимых продуктов и их количество.
- При создании заказа система должна проверить наличие требуемого количества ингредиентов на складе.
- После успешного оформления заказа соответствующие продукты должны быть списаны из складских остатков.

Базовый функционал заказов:

- Получение нового заказа
- Проверка доступности ингредиентов
- Списание продуктов со склада
- Отказ в создании заказа при нехватке продуктов
- Автоматическое формирование стоп-листа блюд

### 3. Мониторинг сроков годности

- Система должна контролировать сроки хранения продуктов с учетом конкретных партий поставки.
- Для каждой партии необходимо определять оставшееся время хранения и выделять продукты, срок годности которых подходит к концу.
- При списании продуктов рекомендуется в первую очередь использовать партии с наиболее ранним сроком годности.

Базовый функционал мониторинга:

- Просмотр актуальных складских остатков
- Просмотр остатков по партиям
- Отображение оставшегося срока хранения
- Выявление продуктов с истекающим сроком годности
- Сигнализация истечения срока годности по партиям
- Анализ и предложение необходимых поставок

## Дополнительно можно реализовать

### Горячие предложения

- Система может автоматически формировать список блюд, продажу которых рекомендуется стимулировать.
- Приоритет блюда должен зависеть от ингредиентов, использующихся для его приготовления: чем меньше времени осталось до окончания срока годности продукта, тем выше приоритет блюда, в котором этот продукт может быть использован.
- При расчете также можно учитывать количество продукта на складе, количество продукта в составе блюда и возможность его использования в нескольких блюдах.

Базовый функционал горячих предложений:

- Расчет приоритета блюд
- Формирование списка рекомендуемых блюд
- Объяснение причины рекомендации
- Автоматическое обновление списка при изменении остатков

### Прочее

- Автоматическое списание просроченной продукции
- Аналитика количества списанных продуктов
- Статистика наиболее дефицитных ингредиентов
- Прогноз момента возникновения стоп-листа
- WebSocket/SSE для обновления остатков в реальном времени
- API или генератор событий, эмулирующий поступление поставок и заказов
- Дашборд состояния склада, например используя Grafana
- Все ваши идеи по улучшению UX, повышению безопасности проекта и оптимизации алгоритмов работы в рамках задачи и разумных пределах

## Платформы для реализации

Web-сервис, desktop-приложение или иной интерфейс на усмотрение команды.

## Рекомендуемые технологии разработки

- **Backend:** C# .net/asp.net, Java, Go
- **Frontend:** Нативный Js или Ts + scss, React, Chakra

Для имитации внешних событий можно реализовать генератор поставок и заказов либо отдельный сервис.

Это лишь рекомендации, выбор языков остается за участником.

## Критерии оценки

- Корректная работа со сроками годности и партиями
- Работа стоп-листа при недостатке ингредиентов
- Качество алгоритма формирования горячих предложений
- Стабильность и качество реализации
- Приятная верстка и дизайн
- Приветствуется, если:
  - Код решения расположен на github
  - Решение задеплоено и можно посмотреть его по ссылке или установив apk

## Уточнения кейсодателя

Раздел не входит в исходный текст кейса: здесь записаны ответы кейсодателя на вопросы команды.

**2026-10-11. Несколько складов.** Система должна поддерживать несколько складов. Команда приняла такую трактовку:

- пользователь регистрируется и создаёт компанию (сеть точек); у одного владельца может быть несколько компаний;
- у компании есть точки; на точке находятся и склад, и кухня;
- владелец добавляет на точку зарегистрированных сотрудников с ролью;
- один сотрудник может работать на нескольких точках с разными ролями;
- меню общее на компанию, отдельные блюда на точке могут не продаваться.

Требования разделов 1-3 и блока "Дополнительно" действуют в границах точки: поставки, партии, остатки, заказы, стоп-лист, сроки годности, рекомендации и аналитика у каждой точки свои. Решение описано в ADR-013 ([ADR.md](ADR.md)).
