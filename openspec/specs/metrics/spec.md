# metrics Specification

## Purpose
Метрики дают числовую картину работы backend: нагрузку и ошибки API, исходы команд и ключевые бизнес-показатели стороны записи - в формате, который собирает Prometheus.

## Requirements

### Requirement: Эндпоинт метрик
Каждый процесс backend SHALL отдавать метрики в текстовом формате Prometheus по `GET /metrics` на том же адресе, что и проверки состояния. Эндпоинт SHALL быть доступен без токена и SHALL NOT находиться под префиксом API. Ответ SHALL включать стандартные метрики процесса и среды выполнения Go.

#### Scenario: Метрики API
- **WHEN** запрашивают `/metrics` процесса API без токена
- **THEN** возвращается статус 200 и текст в формате Prometheus с метриками процесса

#### Scenario: Метрики остальных процессов
- **WHEN** запрашивают `/metrics` процессов worker и generator
- **THEN** каждый отвечает статусом 200 в том же формате

#### Scenario: Запросы за метриками не искажают метрики API
- **WHEN** `/metrics` и `/healthz` запрашивают много раз
- **THEN** счётчик запросов API от этого не растёт

### Requirement: Метрики запросов API
API SHALL считать запросы и измерять время ответа с метками: операция контракта и статус ответа. Меткой операции SHALL быть имя операции из контракта, а не путь запроса: идентификаторы из пути SHALL NOT попадать в метки. Запрос, не соответствующий ни одной операции, SHALL учитываться под одной общей меткой.

#### Scenario: Успешный запрос
- **WHEN** выполняют операцию создания продукта
- **THEN** счётчик запросов с меткой этой операции и статусом 201 увеличивается на единицу, а в гистограмме времени ответа появляется наблюдение

#### Scenario: Отказ в доступе
- **WHEN** операцию вызывают без токена
- **THEN** увеличивается счётчик с меткой этой операции и статусом 401

#### Scenario: Идентификаторы не попадают в метки
- **WHEN** читают сто разных продуктов по идентификатору
- **THEN** у метрики запросов одна серия для операции чтения продукта, а не сто

#### Scenario: Неизвестный путь
- **WHEN** запрашивают путь, которого нет в контракте
- **THEN** запрос учтён под общей меткой неизвестной операции

### Requirement: Метрики команд
Система SHALL считать выполнение команд записи с метками: имя команды и исход. Исходы SHALL различать успех, ошибку предметной области, ответ из сохранённого результата по ключу идемпотентности и отказ после исчерпания повторов. Повторы команды из-за конфликта версий или взаимной блокировки SHALL считаться отдельным счётчиком с именем команды.

#### Scenario: Успешная команда
- **WHEN** команда выполнена
- **THEN** счётчик команд с её именем и исходом "успех" увеличивается на единицу

#### Scenario: Повтор по ключу идемпотентности
- **WHEN** запрос повторяют с тем же ключом идемпотентности
- **THEN** увеличивается счётчик с исходом "сохранённый результат", а счётчик успехов не меняется

#### Scenario: Конфликт версий
- **WHEN** команда повторяется из-за конфликта версий и затем выполняется
- **THEN** счётчик повторов с её именем увеличивается на число повторов, счётчик успехов - на единицу

#### Scenario: Ошибка предметной области
- **WHEN** команда отклонена правилом предметной области
- **THEN** увеличивается счётчик с исходом "ошибка"

### Requirement: Бизнес-метрики стороны записи
Система SHALL считать записанные доменные события с меткой типа события: по нему определяются принятые и отклонённые заказы, зарегистрированные и принятые поставки. Система SHALL считать число списаний с меткой причины и списанное количество с метками причины и единицы измерения продукта. Бизнес-счётчик SHALL увеличиваться только после фиксации события: откатившаяся команда и повтор запроса с тем же ключом идемпотентности SHALL NOT увеличивать его.

#### Scenario: Принятый и отклонённый заказы
- **WHEN** оформлены один принятый и один отклонённый заказ
- **THEN** счётчик событий принятого заказа и счётчик событий отклонённого заказа увеличились на единицу каждый

#### Scenario: Повтор заказа с ключом
- **WHEN** заказ оформлен с ключом идемпотентности, а затем запрос повторён с тем же ключом
- **THEN** счётчик событий принятого заказа увеличился на единицу, а не на две

#### Scenario: Списание
- **WHEN** списывают 30 миллилитров по причине повреждения
- **THEN** счётчик списанного количества с этой причиной и единицей "ml" увеличивается на 30

### Requirement: Состояние пула соединений
Процессы, работающие с PostgreSQL, SHALL отдавать состояние пула соединений: предел, занятые и свободные соединения, число ожиданий свободного соединения.

#### Scenario: Пул в метриках
- **WHEN** запрашивают `/metrics` процесса API
- **THEN** в ответе есть предел пула, равный настроенному, и текущее число занятых соединений

### Requirement: Метрики генератора
Генератор SHALL считать выполненные действия с метками: вид действия (поставка, заказ) и исход (выполнено, ошибка), а для заказов - число принятых и отклонённых.

#### Scenario: Работа генератора
- **WHEN** генератор создал поставку и оформил заказ
- **THEN** счётчики действий обоих видов с исходом "выполнено" увеличились

#### Scenario: API недоступен
- **WHEN** действие генератора завершилось ошибкой
- **THEN** увеличился счётчик действий с исходом "ошибка"
