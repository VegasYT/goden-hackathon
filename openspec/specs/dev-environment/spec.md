# dev-environment Specification

## Purpose
Локальное окружение разработки даёт всем участникам одинаковый набор внешних сервисов - PostgreSQL, Kafka, Redis и Keycloak с готовым realm - одной командой, без ручной настройки.

## Requirements

### Requirement: Запуск окружения одной командой
Репозиторий SHALL содержать описание окружения в папке `infra/`, которое одной командой `docker compose -f infra/compose.yaml up -d` из корня поднимает PostgreSQL 18, Kafka 4 в режиме KRaft, Redis 8, Keycloak 26, Prometheus, Loki, Promtail и Grafana. Каждый сервис SHALL иметь проверку готовности, а версии образов SHALL быть закреплены. Порты сервисов SHALL публиковаться только на `127.0.0.1` и SHALL переопределяться переменными окружения.

#### Scenario: Чистый запуск
- **WHEN** на машине с Docker выполняют `docker compose -f infra/compose.yaml up -d --wait` в свежем клоне репозитория
- **THEN** команда завершается успешно, все сервисы находятся в состоянии healthy

#### Scenario: Повторный запуск сохраняет данные
- **WHEN** окружение останавливают командой `down` и запускают снова
- **THEN** данные PostgreSQL и Kafka сохранены

#### Scenario: Полный сброс
- **WHEN** выполняют `down -v` и запускают окружение снова
- **THEN** PostgreSQL и Kafka пусты, а realm Keycloak создан заново из файла

#### Scenario: Занятый порт
- **WHEN** порт сервиса на хосте занят и его переопределяют переменной окружения
- **THEN** сервис публикуется на новом порту без правки файлов репозитория

### Requirement: Backend работает с окружением
Процессы backend, запущенные с хоста, SHALL подключаться к сервисам окружения по адресам, записанным в `backend/AGENTS.md`. Порт Keycloak на хосте SHALL NOT совпадать с портами процессов backend.

#### Scenario: Миграции и API
- **WHEN** на запущенном окружении выполняют `cmd/migrate` и запускают `cmd/api` с адресом базы из документации
- **THEN** миграции применяются, `/readyz` отвечает 200

#### Scenario: Генератор
- **WHEN** на том же окружении запускают `cmd/generator` и включают его через API
- **THEN** в базе появляются события поставок и заказов

#### Scenario: Kafka и Redis доступны с хоста
- **WHEN** с хоста отправляют сообщение в Kafka и читают его, а в Redis записывают и читают ключ
- **THEN** обе операции проходят по адресам из документации

### Requirement: Realm Keycloak
Keycloak SHALL при старте импортировать realm `goden`. Realm SHALL содержать клиент `goden-api`, публичный клиент `goden-web` для frontend и клиент `goden-generator` с сервисной учётной записью. Клиент `goden-api` SHALL иметь единственную client role `generator.run`, выданную только сервисной учётной записи генератора. В realm SHALL быть включена самостоятельная регистрация. Прав пользователей realm SHALL NOT содержать: их определяют назначения в системе.

#### Scenario: Realm доступен после запуска
- **WHEN** после запуска окружения запрашивают документ обнаружения OpenID Connect realm `goden`
- **THEN** он возвращается со статусом 200

#### Scenario: Все permissions существуют
- **WHEN** перечисляют client roles клиента `goden-api`
- **THEN** роль одна: `generator.run`

#### Scenario: Сервисная учётная запись генератора
- **WHEN** клиент `goden-generator` получает токен по client credentials
- **THEN** в `resource_access.goden-api.roles` находится ровно `generator.run`

#### Scenario: Пользователь
- **WHEN** тестовый пользователь получает токен
- **THEN** в токене нет прав клиента `goden-api`, а есть идентификатор, почта и имя пользователя

### Requirement: Роли и тестовые пользователи
Realm SHALL содержать тестовых пользователей `admin`, `manager`, `approver`, `cook` и `waiter` с постоянными идентификаторами, не меняющимися при пересоздании realm. Ролей с правами у них в realm SHALL NOT быть: `admin` является владельцем демонстрационной компании, остальные получают роль назначением на её точку.

#### Scenario: Постоянный идентификатор
- **WHEN** realm пересоздают и тестовый пользователь получает токен
- **THEN** идентификатор пользователя в токене тот же, что до пересоздания

#### Scenario: Токен приёмщика
- **WHEN** тестовый пользователь `approver` получает токен
- **THEN** в токене нет прав клиента `goden-api`; право принимать поставки он получает назначением на точку

#### Scenario: Токен администратора
- **WHEN** тестовый пользователь `admin` получает токен
- **THEN** в токене нет прав клиента `goden-api`; все права в демонстрационной компании у него есть как у владельца

#### Scenario: Управление генератором
- **WHEN** получают токены всех тестовых пользователей
- **THEN** ни в одном нет `generator.manage` и `generator.run`; настройки генератора меняет владелец точки

### Requirement: Просмотр метрик
Prometheus окружения SHALL опрашивать `/metrics` процессов backend, запущенных с хоста на адресах по умолчанию. Grafana SHALL запускаться с настроенным источником данных Prometheus и готовым дашбордом backend, без ручной настройки. Процесс backend, который не запущен, SHALL отображаться в Prometheus как недоступная цель и SHALL NOT мешать опросу остальных.

#### Scenario: Цели Prometheus
- **WHEN** окружение запущено и на хосте работают API и генератор
- **THEN** Prometheus показывает их цели доступными, а цель незапущенного worker - недоступной

#### Scenario: Дашборд без настройки
- **WHEN** после запуска окружения открывают Grafana
- **THEN** в ней есть дашборд backend, и его графики показывают данные работающего API

#### Scenario: Метрики под генератором
- **WHEN** генератор включён и создаёт поставки и заказы
- **THEN** на дашборде растут число запросов, принятые и отклонённые заказы

### Requirement: Пароли realm задаются снаружи
Файл realm SHALL принимать пароли тестовых пользователей и секрет сервисной учётной записи генератора из переменных окружения контейнера Keycloak. Без этих переменных SHALL действовать значения локального окружения: пароль пользователя равен логину, секрет генератора прежний.

#### Scenario: Локальный запуск без переменных
- **WHEN** локальное окружение поднимают как раньше, не задавая переменных
- **THEN** вход пользователем `approver` с паролем `approver` и получение токена генератора с прежним секретом работают

#### Scenario: Заданный пароль
- **WHEN** Keycloak запущен с переменной пароля пользователя `admin`
- **THEN** вход с заданным паролем проходит, а с паролем `admin` отклонён

### Requirement: Демонстрационная компания
При запуске миграций с включённой настройкой демонстрационной компании система SHALL создать компанию "Демо" с двумя точками, владельцем которой является тестовый пользователь `admin`, и назначить тестовых пользователей `manager`, `approver`, `cook` и `waiter` на первую точку с ролями управляющего, приёмщика, повара и официанта. На первой точке SHALL быть включён генератор. Если задан чат Telegram демонстрационной точки, он SHALL быть задан первой точке один раз, пока у неё нет своего чата: чат, который владелец задал или снял в приложении, запуск SHALL NOT менять. Тестовых пользователей, которые уже обращались к системе, запуск SHALL NOT изменять. Повторный запуск SHALL NOT создавать дубликаты и SHALL NOT менять то, что владелец изменил после создания. Без настройки демонстрационная компания SHALL NOT создаваться.

#### Scenario: Первый запуск
- **WHEN** миграции запускают с настройкой демонстрационной компании на пустой базе и тестовый пользователь `cook` входит в систему
- **THEN** в его профиле первая точка компании "Демо" с ролью повара

#### Scenario: Владелец
- **WHEN** после создания входит тестовый пользователь `admin`
- **THEN** в его профиле компания "Демо" и обе её точки, на которых он владелец

#### Scenario: Генератор
- **WHEN** после создания запускают генератор
- **THEN** на первой точке появляются поставки и заказы, а каталог компании "Демо" наполнен

#### Scenario: Повторный запуск
- **WHEN** миграции с настройкой запускают второй раз
- **THEN** новых событий нет

#### Scenario: Без настройки
- **WHEN** миграции запускают без настройки демонстрационной компании
- **THEN** компаний в системе нет

#### Scenario: Чат задан владельцем
- **WHEN** владелец задал первой точке свой чат, а миграции запускают с другим чатом в настройке
- **THEN** чат точки остаётся тем, что задал владелец

#### Scenario: Имя тестового пользователя
- **WHEN** тестовый пользователь уже входил и его имя взято из Keycloak, а миграции запускают снова
- **THEN** его имя не меняется

### Requirement: Тема страниц входа в окружении
Keycloak окружения разработки SHALL отдавать страницы входа темы `goden`, собранной из текущего кода репозитория. Для запуска SHALL хватать Docker: Java, Maven и Node.js на машине разработчика SHALL NOT требоваться. Изменения страниц темы SHALL применяться пересборкой Keycloak окружения одной командой, записанной в документации.

#### Scenario: Запуск окружения
- **WHEN** на машине с Docker выполняют `docker compose -f infra/compose.yaml up -d --wait` в свежем клоне репозитория
- **THEN** страница входа realm `goden` открывается в оформлении Goden

#### Scenario: Изменение страницы
- **WHEN** разработчик меняет страницу темы и выполняет команду пересборки Keycloak из документации
- **THEN** страница входа показывает изменение
