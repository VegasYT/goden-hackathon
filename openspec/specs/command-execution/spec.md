# command-execution Specification

## Purpose
Выполнение команд записи даёт доменным модулям единый корректный способ изменить состояние системы: атомарно, без гонок между командами по одним продуктам, без повторной обработки одного запроса и с одинаково заполненными служебными полями событий.

## Requirements

### Requirement: Атомарное выполнение команды
Команда SHALL выполняться в одной транзакции базы данных. Все события, добавленные командой в любые потоки, и все изменения таблиц, сделанные ею, SHALL фиксироваться вместе при успешном завершении и не оставлять следов при ошибке или аварийном завершении.

#### Scenario: Успешная команда
- **WHEN** команда добавляет события в два потока, изменяет таблицу и завершается без ошибки
- **THEN** события обоих потоков и изменение таблицы видны после её завершения

#### Scenario: Ошибка бизнес-логики
- **WHEN** команда добавляет событие в поток, а затем её логика возвращает ошибку
- **THEN** событие не записано, вызывающая сторона получает исходную ошибку

#### Scenario: Аварийное завершение
- **WHEN** логика команды завершается паникой после добавления события
- **THEN** событие не записано, соединение с базой возвращено в пул

### Requirement: Очередь команд с общими потоками
Команда SHALL объявлять потоки, по которым ей нужна исключительная работа. Две команды, объявившие хотя бы один общий поток, SHALL выполняться строго по очереди: вторая начинает бизнес-логику только после завершения первой и видит её результат. Команды без общих объявленных потоков SHALL выполняться параллельно. Порядок, в котором команда перечислила потоки, SHALL NOT приводить к взаимной блокировке команд.

#### Scenario: Две команды по одному продукту
- **WHEN** две команды одновременно объявляют один и тот же складской поток, читают его версию и добавляют в него событие
- **THEN** обе завершаются успешно без конфликта версий, логика каждой выполнена ровно один раз, в потоке два события

#### Scenario: Команды по разным продуктам не ждут друг друга
- **WHEN** первая команда объявила поток A и ещё выполняется, а вторая объявляет поток B
- **THEN** вторая команда завершается, не дожидаясь первой

#### Scenario: Потоки перечислены в разном порядке
- **WHEN** множество команд одновременно объявляют потоки A и B, половина в порядке "A, B", половина в порядке "B, A"
- **THEN** все команды завершаются успешно, взаимных блокировок нет

#### Scenario: Порядок чтения совпадает с порядком версий
- **WHEN** много команд параллельно добавляют события в один объявленный поток, а затем все события читаются в общем порядке
- **THEN** события этого потока идут по возрастанию версии

### Requirement: Идемпотентность по ключу запроса
Команда, вызванная с ключом идемпотентности, SHALL выполняться не более одного раза для тройки "имя команды, автор, ключ". Повторный вызов с тем же ключом и тем же содержимым запроса SHALL возвращать результат первого выполнения, не выполняя бизнес-логику и не создавая событий. Вызов с тем же ключом и другим содержимым запроса SHALL отклоняться ошибкой повторного использования ключа. Команда, завершившаяся ошибкой, SHALL NOT занимать ключ: её можно повторить с тем же ключом. Команда без ключа SHALL выполняться при каждом вызове.

#### Scenario: Повтор успешной команды
- **WHEN** команду с ключом K вызывают дважды с одинаковым запросом
- **THEN** бизнес-логика выполнена один раз, события записаны один раз, оба вызова возвращают одинаковый результат

#### Scenario: Одновременные вызовы с одним ключом
- **WHEN** два вызова команды с ключом K и одинаковым запросом приходят одновременно
- **THEN** бизнес-логика выполнена один раз, оба вызова возвращают одинаковый результат

#### Scenario: Тот же ключ, другой запрос
- **WHEN** команду с ключом K успешно выполнили, а затем вызывают с тем же ключом и другим содержимым запроса
- **THEN** возвращается ошибка повторного использования ключа, новые события не создаются

#### Scenario: Повтор после ошибки
- **WHEN** команда с ключом K завершилась ошибкой, а затем её вызывают снова с тем же ключом
- **THEN** бизнес-логика выполняется заново

#### Scenario: Один ключ у разных команд
- **WHEN** две команды с разными именами вызывают с одним и тем же ключом
- **THEN** обе выполняются независимо

### Requirement: Повтор при конфликте
Если выполнение команды завершилось конфликтом версий потока или взаимной блокировкой в базе данных, команда SHALL быть выполнена заново целиком, с новым чтением состояния. Число попыток SHALL быть ограничено; после исчерпания попыток вызывающая сторона SHALL получить ошибку, по которой конфликт можно отличить от прочих ошибок. Другие ошибки SHALL возвращаться сразу, без повтора.

#### Scenario: Конфликт на первой попытке
- **WHEN** первая попытка команды завершается конфликтом версий, а вторая проходит
- **THEN** команда завершается успешно, события записаны один раз

#### Scenario: Конфликт не исчезает
- **WHEN** каждая попытка команды завершается конфликтом версий
- **THEN** после ограниченного числа попыток возвращается ошибка конфликта версий, события не записаны

#### Scenario: Ошибка бизнес-логики не повторяется
- **WHEN** логика команды возвращает ошибку, не связанную с конфликтом
- **THEN** логика выполнена ровно один раз, ошибка возвращена вызывающей стороне

### Requirement: Служебные поля событий команды
События, добавленные командой, SHALL получать служебные поля единообразно: уникальный идентификатор события; время возникновения из общего источника времени, одинаковое для всех событий команды; correlation ID из контекста вызова, а при его отсутствии созданный для этой команды; causation ID, равный идентификатору команды и одинаковый у всех её событий; метаданные с автором действия и именем команды.

#### Scenario: События одной команды связаны
- **WHEN** команда добавляет три события в два потока
- **THEN** у всех трёх одинаковые causation ID, correlation ID и время возникновения, а идентификаторы событий различны

#### Scenario: Correlation ID из контекста
- **WHEN** команду вызывают в контексте с заданным correlation ID
- **THEN** все её события содержат этот correlation ID

#### Scenario: Время из управляемых часов
- **WHEN** команду выполняют с управляемыми часами, установленными на заданный момент
- **THEN** время возникновения её событий равно этому моменту

#### Scenario: Автор и команда в метаданных
- **WHEN** команду с именем "RegisterDelivery" выполняет пользователь с идентификатором U
- **THEN** метаданные её событий содержат автора типа `user` с идентификатором U и имя команды "RegisterDelivery"

### Requirement: Проверка описания команды
Команда с некорректным описанием SHALL отклоняться до обращения к базе данных: без имени, без автора или с пустым идентификатором потока среди объявленных.

#### Scenario: Команда без имени
- **WHEN** запускают команду с пустым именем
- **THEN** возвращается ошибка валидации, бизнес-логика не выполняется

### Requirement: Ключ идемпотентности принадлежит автору
Ключ идемпотентности SHALL действовать в границах автора: повтором считается запрос с тем же ключом, тем же содержимым и от того же автора. Запрос с тем же ключом от другого автора SHALL выполняться как независимая команда: он не получает сохранённый результат первого автора и не получает отказ, по которому можно узнать о чужом ключе.

#### Scenario: Тот же ключ от другого автора
- **WHEN** один пользователь выполнил команду с ключом, а другой отправляет ту же команду с тем же ключом и тем же содержимым
- **THEN** команда второго пользователя выполняется, её события записаны, результат первого ему не возвращается

#### Scenario: Повтор тем же автором
- **WHEN** автор повторяет свой запрос с тем же ключом и содержимым
- **THEN** возвращается сохранённый результат, команда повторно не выполняется
