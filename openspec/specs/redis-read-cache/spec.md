# redis-read-cache Specification

## Purpose

Кеш чтения ускоряет повторные запросы к асинхронным представлениям, не превращая Redis в источник истины и не меняя корректность складских операций.

## Requirements

### Requirement: Кешируемые представления

Система SHALL кешировать ответы списков поставок, истории заказов, аналитики списаний и статистики дефицита. Система SHALL NOT кешировать меню, стоп-лист, текущие остатки, партии и рекомендации.

#### Scenario: Повторный запрос
- **WHEN** один и тот же запрос к кешируемому представлению выполняют повторно при неизменившейся проекции
- **THEN** система может вернуть сохранённый результат без повторного чтения данных представления

#### Scenario: Критичное представление
- **WHEN** запрашивают меню, стоп-лист, текущие остатки, партии или рекомендации
- **THEN** система рассчитывает ответ без использования Redis-кеша результата

### Requirement: Свежесть относительно проекции

Кешированный ответ SHALL использоваться только для той позиции проекции, на которой он был рассчитан. Изменение позиции или параметров запроса SHALL приводить к чтению нового результата.

#### Scenario: Проекция не изменилась
- **WHEN** позиция проекции и параметры повторного запроса совпадают с сохранённым результатом
- **THEN** система возвращает эквивалентный кешированный ответ

#### Scenario: Проекция продвинулась
- **WHEN** worker применил новое событие и позиция проекции изменилась
- **THEN** следующий запрос не использует результат предыдущей позиции

#### Scenario: Другие параметры
- **WHEN** меняется фильтр, период или страница запроса
- **THEN** результат запроса с прежними параметрами не используется

### Requirement: Redis не влияет на доступность API

При отключённом или недоступном Redis система SHALL обслуживать кешируемые запросы из PostgreSQL. Ошибка Redis SHALL NOT изменять успешный ответ и SHALL NOT делать API неготовым.

#### Scenario: Кеш отключён
- **WHEN** подключение к Redis не настроено
- **THEN** API запускается и читает все представления из PostgreSQL

#### Scenario: Redis недоступен
- **WHEN** Redis не отвечает во время чтения или записи кеша
- **THEN** запрос получает результат из PostgreSQL, если PostgreSQL доступен

#### Scenario: Проверка готовности
- **WHEN** PostgreSQL доступен, а Redis недоступен
- **THEN** `/readyz` API отвечает статусом 200

### Requirement: Ограниченное хранение

Каждый кешированный ответ SHALL иметь ограниченный срок хранения. Истечение срока SHALL приводить к повторному чтению представления, даже если его позиция не изменилась.

#### Scenario: Срок хранения истёк
- **WHEN** срок хранения сохранённого ответа истёк
- **THEN** следующий запрос читает представление из PostgreSQL и может сохранить новый ответ

### Requirement: Наблюдаемость кеша

Система SHALL учитывать попадания, промахи, ошибки и обход кеша в метриках с конечным набором меток.

#### Scenario: Попадание в кеш
- **WHEN** запрос обслужен сохранённым результатом
- **THEN** счётчик попаданий увеличивается

#### Scenario: Ошибка Redis
- **WHEN** операция Redis завершается ошибкой и запрос обслуживается из PostgreSQL
- **THEN** счётчик ошибок кеша увеличивается без идентификаторов запроса или пользователя в метках

### Requirement: Значение неожиданной формы в кеше
Если значение в кеше является корректным JSON, но не соответствует ожидаемому ответу, запрос SHALL обслуживаться из базы данных, а не завершаться ошибкой.

#### Scenario: Значение от другой версии кода
- **WHEN** под ключом ответа лежит JSON другой формы
- **THEN** клиент получает корректный ответ, прочитанный из базы

### Requirement: Общая загрузка не зависит от первого клиента
Когда несколько запросов одновременно ждут загрузки одного ключа, отключение клиента, начавшего загрузку, SHALL NOT приводить к ошибке у остальных.

#### Scenario: Первый клиент отключился
- **WHEN** два запроса ждут одну загрузку и клиент первого разрывает соединение
- **THEN** второй запрос получает результат
