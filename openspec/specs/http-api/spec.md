# http-api Specification

## Purpose
HTTP API - единый способ для frontend, генератора и внешних клиентов работать с системой. Общие правила задают одинаковое поведение всех эндпоинтов: как сообщаются ошибки, как читаются длинные списки, как безопасно повторять запросы и как связать запрос с его следами в логах и событиях.

## Requirements

### Requirement: Контракт API
HTTP API SHALL быть описан одним документом OpenAPI, из которого генерируется код сервера и клиента. Все эндпоинты API SHALL находиться под префиксом `/api/v1`. Запрос, не соответствующий контракту, SHALL отклоняться до выполнения бизнес-логики.

#### Scenario: Запрос с телом не по контракту
- **WHEN** на эндпоинт создания отправляют JSON без обязательного поля
- **THEN** возвращается статус 400 с описанием проблемы, бизнес-логика не выполняется

#### Scenario: Неизвестный путь
- **WHEN** запрашивают путь, которого нет в контракте
- **THEN** возвращается статус 404

### Requirement: Формат ошибок
Любой ответ с ошибкой SHALL иметь тип содержимого `application/problem+json` и поля `type`, `title`, `status` и `detail`. Ошибка валидации SHALL дополнительно содержать список некорректных полей с названием поля и сообщением. Все человекочитаемые значения `title`, `detail` и `errors[].message` SHALL быть на русском языке, а машинные значения `type`, имена полей и HTTP-статусы SHALL сохранять прежнюю семантику. Ответ с ошибкой SHALL содержать correlation ID запроса. Внутренние подробности сбоя SHALL NOT попадать в ответ со статусом 500.

Статусы SHALL назначаться единообразно: 400 - запрос не соответствует контракту; 404 - объект не найден; 409 - конфликт с текущим состоянием; 422 - запрос корректен по форме, но нарушает правило предметной области; 500 - внутренняя ошибка.

#### Scenario: Ошибка валидации
- **WHEN** создают продукт с пустым названием
- **THEN** возвращается статус 422, тип содержимого `application/problem+json`, поле `name` и русские значения `title`, `detail` и `errors[].message`

#### Scenario: Запрос не соответствует контракту
- **WHEN** отправляют запрос с некорректным значением параметра или тела
- **THEN** возвращается статус 400 с русскими значениями `title` и `detail`, а машинный `type` остаётся кодом ошибки

#### Scenario: Объект не найден
- **WHEN** запрашивают продукт по идентификатору, которого нет
- **THEN** возвращается статус 404 в формате `application/problem+json` с русскими значениями `title` и `detail`

#### Scenario: Конфликт
- **WHEN** создают продукт с уже занятым названием
- **THEN** возвращается статус 409 в формате `application/problem+json` с русскими значениями `title` и `detail`

#### Scenario: Внутренняя ошибка
- **WHEN** при обработке запроса происходит непредвиденный сбой
- **THEN** возвращается статус 500 с общим русским сообщением без текста исходной ошибки, а сама ошибка записана в лог с correlation ID

### Requirement: Пагинация списков
Эндпоинты списков SHALL принимать параметры `limit` и `offset` и возвращать элементы страницы вместе с общим числом элементов. Значение `limit` по умолчанию SHALL быть 50, максимальное - 200. Некорректные значения параметров SHALL отклоняться со статусом 400.

#### Scenario: Первая страница по умолчанию
- **WHEN** запрашивают список без параметров при 120 элементах
- **THEN** возвращаются первые 50 элементов и общее число 120

#### Scenario: Следующая страница
- **WHEN** запрашивают список с `limit=50` и `offset=100` при 120 элементах
- **THEN** возвращаются последние 20 элементов и общее число 120

#### Scenario: Слишком большой limit
- **WHEN** запрашивают список с `limit=1000`
- **THEN** возвращается статус 400

### Requirement: Идемпотентность запросов на запись
Запросы на запись SHALL принимать необязательный заголовок `Idempotency-Key`. Повторный запрос с тем же ключом и тем же телом SHALL возвращать тот же результат, что и первый, без повторного выполнения. Запрос с тем же ключом и другим телом SHALL отклоняться со статусом 422.

#### Scenario: Повтор запроса
- **WHEN** запрос создания продукта отправляют дважды с одним `Idempotency-Key`
- **THEN** оба ответа содержат один и тот же идентификатор продукта, продукт создан один раз

#### Scenario: Ключ с другим телом
- **WHEN** запрос создания отправляют с уже использованным `Idempotency-Key` и другим телом
- **THEN** возвращается статус 422 в формате `application/problem+json`

### Requirement: Correlation ID
Каждый запрос SHALL иметь correlation ID: значение заголовка `X-Correlation-Id`, если клиент прислал корректный UUID, иначе созданное сервером. Сервер SHALL возвращать его в заголовке ответа `X-Correlation-Id`, записывать в логи запроса и проставлять в события, созданные при обработке запроса.

#### Scenario: Клиент прислал correlation ID
- **WHEN** запрос создания продукта отправлен с заголовком `X-Correlation-Id`
- **THEN** ответ содержит тот же идентификатор в заголовке, и событие `ProductCreated` записано с этим correlation ID

#### Scenario: Клиент не прислал correlation ID
- **WHEN** запрос отправлен без заголовка `X-Correlation-Id`
- **THEN** ответ содержит заголовок с новым идентификатором

### Requirement: Проверка состояния процесса
Процесс SHALL отвечать на `GET /healthz` статусом 200, пока он работает, и на `GET /readyz` статусом 200, только когда он готов обслуживать запросы, включая доступность базы данных; иначе `/readyz` SHALL отвечать статусом 503. Эти эндпоинты SHALL NOT требовать авторизации и не входят в префикс `/api/v1`.

#### Scenario: Процесс готов
- **WHEN** процесс запущен и база данных доступна
- **THEN** `/healthz` и `/readyz` отвечают статусом 200

#### Scenario: База данных недоступна
- **WHEN** процесс работает, а база данных недоступна
- **THEN** `/healthz` отвечает статусом 200, `/readyz` отвечает статусом 503

### Requirement: Кросс-доменные запросы
API SHALL отвечать на кросс-доменные запросы браузера с адресов из настраиваемого списка разрешённых источников: разрешать методы контракта и заголовки `Authorization`, `Content-Type`, `Idempotency-Key`, `X-Correlation-Id`. Предварительный запрос `OPTIONS` SHALL обслуживаться без токена. Запрос с источника не из списка SHALL NOT получать разрешающих заголовков.

#### Scenario: Предварительный запрос с разрешённого источника
- **WHEN** браузер отправляет `OPTIONS` с разрешённым `Origin` и запрашивает метод `POST` с заголовком `Authorization`
- **THEN** ответ успешен без токена и содержит разрешение для этого источника, метода и заголовка

#### Scenario: Запрос с разрешённого источника
- **WHEN** операцию вызывают с разрешённым `Origin` и корректным токеном
- **THEN** ответ содержит заголовок, разрешающий этот источник

#### Scenario: Чужой источник
- **WHEN** запрос приходит с `Origin`, которого нет в списке
- **THEN** в ответе нет разрешающих заголовков

### Requirement: Нулевой символ в теле запроса
Запрос, тело которого содержит нулевой символ, в том числе в экранированном виде, SHALL отклоняться как некорректный до обработки, а не завершаться внутренней ошибкой.

#### Scenario: Название с нулевым символом
- **WHEN** создают продукт с названием, содержащим экранированный нулевой символ
- **THEN** ответ - 400, продукт не создан

### Requirement: Ответ на конфликт версий без подробностей движка
Ответ 409, вызванный конфликтом версий потока, SHALL NOT содержать имя команды, имя потока и номера версий.

#### Scenario: Повторы исчерпаны
- **WHEN** команда не выполнена из-за конфликта версий после всех повторов
- **THEN** клиент получает 409 с общим пояснением, что объект изменён одновременным запросом

### Requirement: Разрыв соединения клиентом
Запрос, прерванный разрывом соединения со стороны клиента, SHALL NOT учитываться как внутренняя ошибка: статус ответа в метриках - 499, запись уровня ошибки в журнал не делается.

#### Scenario: Клиент отключился во время запроса
- **WHEN** клиент разрывает соединение до завершения обработки
- **THEN** запрос учтён со статусом 499, а не 500

### Requirement: Длина строк в запросах
Строки в запросах SHALL иметь предельную длину, заданную контрактом: названия продукта, категории, блюда и номер поставки - 200 символов, причины и комментарии - 1000. Запрос с более длинной строкой SHALL отклоняться как не соответствующий контракту.

#### Scenario: Слишком длинное название
- **WHEN** создают продукт с названием из 201 символа
- **THEN** ответ - 400, продукт не создан

#### Scenario: Название предельной длины
- **WHEN** создают продукт с названием из 200 символов кириллицы
- **THEN** продукт создан

### Requirement: Паника обработчика в журнале и метриках
Запрос, обработка которого завершилась паникой, SHALL получать ответ 500 и SHALL учитываться в журнале запросов и в счётчике запросов со статусом 500.

#### Scenario: Паника в обработчике
- **WHEN** обработчик запроса завершается паникой
- **THEN** клиент получает 500, в журнале запросов есть запись с этим статусом

### Requirement: Адреса операций точки
Операции поставок, партий, остатков, заказов, меню, стоп-листа, рекомендаций и аналитики SHALL располагаться под `/api/v1/points/{pointId}` и действовать в границах этой точки. Адреса этих операций в сценариях других возможностей, записанные без точки (например `/api/v1/deliveries`), SHALL читаться относительно `/api/v1/points/{pointId}`. Объект, указанный в адресе идентификатором (поставка, партия, заказ, продукт), SHALL принадлежать точке или её компании, иначе ответ - 404.

#### Scenario: Операция на точке
- **WHEN** отправляют `GET /api/v1/points/{pointId}/stock`
- **THEN** возвращаются остатки этой точки

#### Scenario: Объект другой точки
- **WHEN** отправляют `GET /api/v1/points/{pointId}/deliveries/{id}` с идентификатором поставки другой точки, на которой у вызывающего тоже есть права
- **THEN** возвращается статус 404

#### Scenario: Прежний адрес
- **WHEN** отправляют `GET /api/v1/stock`
- **THEN** возвращается статус 404

### Requirement: Различимые конфликты
Ответ 409 SHALL различать по полю `type`:
- `delivery-already-approved` — поставка уже принята;
- `delivery-not-approved` — поставка ещё не принята;
- `quarantine-closed` — у позиции нет открытого карантина;
- `version-conflict` — объект изменён одновременным запросом, запрос можно повторить;
- `product-in-use` — продукт есть в рецептурах неархивных блюд, `detail` называет их;
- `unit-locked` — единицу продукта уже нельзя менять;
- `archived-ingredients` — в рецептуре восстанавливаемого блюда есть архивные продукты, `detail` называет их.

Остальные конфликты SHALL иметь `type` `conflict`.

#### Scenario: Повторная приёмка
- **WHEN** принятую поставку принимают ещё раз
- **THEN** возвращается статус 409 с `type` `delivery-already-approved`

#### Scenario: Закрытый карантин
- **WHEN** решение отправляют по позиции, карантин которой уже решён
- **THEN** возвращается статус 409 с `type` `quarantine-closed`

#### Scenario: Занятое название
- **WHEN** создают продукт с уже занятым названием
- **THEN** возвращается статус 409 с `type` `conflict`

#### Scenario: Продукт в рецептуре
- **WHEN** в архив отправляют продукт из рецептуры блюда "Омлет"
- **THEN** возвращается статус 409 с `type` `product-in-use`, `detail` называет "Омлет"

### Requirement: Код и предел в ошибке поля
Элемент `errors` ответа об ошибке валидации MAY нести машиночитаемый код и числовой предел. Ошибка, вид которой не различается, SHALL приходить без кода.

#### Scenario: Ошибка без кода
- **WHEN** приёмка отклонена, потому что сумма количеств не равна заявленному
- **THEN** ошибка поля содержит поле и сообщение, кода нет

### Requirement: Поле в ошибке названия и почты
Ошибка SHALL указывать поле запроса, к которому относится, чтобы форма показала её у поля:
- занятое название продукта, блюда, точки или компании — 409 с `errors` из одного элемента: поле `name` и `code`;
  - `taken` — название занято;
  - `taken_by_archived` — название занято архивным продуктом или блюдом;
- незарегистрированная почта при назначении сотрудника и передаче компании — 422 с элементом: поле `email`, `code` `unknown`.

Статусы и `type` прежних ответов SHALL NOT меняться.

#### Scenario: Занятое название точки
- **WHEN** создают точку с названием, которое уже есть в компании
- **THEN** возвращается статус 409, в `errors` поле `name` с `code` `taken`

#### Scenario: Название архивного продукта
- **WHEN** создают продукт с названием архивного продукта
- **THEN** возвращается статус 409, в `errors` поле `name` с `code` `taken_by_archived`

#### Scenario: Незарегистрированная почта сотрудника
- **WHEN** на точку добавляют сотрудника по почте, с которой никто не входил
- **THEN** возвращается статус 422, в `errors` поле `email` с `code` `unknown`
