# Spec Delta

## Purpose

Event Store хранит доменные события в PostgreSQL как единственный источник истины. Он гарантирует порядок событий внутри потока, неизменяемость записанного и чтение всех событий без пропусков при параллельной записи.

## ADDED Requirements

### Requirement: Добавление событий в поток с проверкой версии
Система SHALL добавлять одно или несколько событий в поток только тогда, когда текущая версия потока равна ожидаемой версии, переданной вызывающей стороной. Версии событий в потоке SHALL идти подряд, начиная с 1, без пропусков. При несовпадении версий система SHALL вернуть ошибку конфликта версий и не записать ни одного события.

#### Scenario: Первое событие нового потока
- **WHEN** в несуществующий поток добавляют два события с ожидаемой версией 0
- **THEN** события записаны с версиями 1 и 2, вызывающая сторона получает новую версию потока 2

#### Scenario: Продолжение существующего потока
- **WHEN** в поток с текущей версией 2 добавляют событие с ожидаемой версией 2
- **THEN** событие записано с версией 3

#### Scenario: Устаревшая ожидаемая версия
- **WHEN** в поток с текущей версией 3 добавляют событие с ожидаемой версией 2
- **THEN** возвращается ошибка конфликта версий, поток остаётся на версии 3

#### Scenario: Ожидаемая версия больше текущей
- **WHEN** в поток с текущей версией 3 добавляют событие с ожидаемой версией 5
- **THEN** возвращается ошибка конфликта версий, в потоке не появляется пропуск версий

#### Scenario: Две параллельные записи с одной ожидаемой версией
- **WHEN** две транзакции одновременно добавляют событие в один поток с одинаковой ожидаемой версией
- **THEN** ровно одна транзакция завершается успешно, вторая получает ошибку конфликта версий

### Requirement: Атомарная запись в несколько потоков
Система SHALL записывать события в несколько потоков в рамках одной транзакции вызывающей стороны по принципу "всё или ничего". Вместе с событиями в той же транзакции SHALL можно изменять другие таблицы.

#### Scenario: Ошибка во втором потоке отменяет запись в первый
- **WHEN** в одной транзакции событие добавлено в поток A, а добавление в поток B завершилось конфликтом версий
- **THEN** после завершения транзакции ни в потоке A, ни в потоке B нет новых событий

#### Scenario: Успешная запись в два потока
- **WHEN** в одной транзакции события добавлены в потоки A и B и транзакция зафиксирована
- **THEN** события обоих потоков доступны для чтения

### Requirement: Состав записанного события
Каждое записанное событие SHALL содержать: уникальный идентификатор события, идентификатор потока, версию в потоке, тип, версию схемы, содержимое, метаданные, время возникновения в UTC, correlation ID и causation ID. Система SHALL сама назначать событию глобальный номер и идентификатор записавшей транзакции. Система SHALL отклонять событие с идентификатором, который уже есть в хранилище.

#### Scenario: Прочитанное событие совпадает с записанным
- **WHEN** событие записано и затем прочитано из потока
- **THEN** идентификатор, тип, версия схемы, содержимое, метаданные, время, correlation ID и causation ID совпадают с переданными при записи, а глобальный номер и идентификатор транзакции заполнены

#### Scenario: Повторный идентификатор события
- **WHEN** добавляют событие с идентификатором уже записанного события
- **THEN** запись отклоняется с ошибкой, новых событий не появляется

#### Scenario: Некорректные входные данные
- **WHEN** добавляют пустой список событий, событие без типа или указывают пустой идентификатор потока
- **THEN** возвращается ошибка валидации, обращения к хранилищу на запись не происходит

### Requirement: Неизменяемость событий
Записанные события SHALL NOT изменяться и удаляться. Запрет SHALL действовать на уровне базы данных, независимо от кода приложения.

#### Scenario: Попытка изменить событие
- **WHEN** к таблице событий выполняют запрос на изменение строки
- **THEN** база данных отклоняет запрос с ошибкой, событие остаётся прежним

#### Scenario: Попытка удалить событие
- **WHEN** к таблице событий выполняют запрос на удаление строки или очистку таблицы
- **THEN** база данных отклоняет запрос с ошибкой, события остаются на месте

### Requirement: Чтение потока
Система SHALL возвращать события одного потока в порядке возрастания версии, начиная с указанной версии. Для несуществующего потока система SHALL возвращать пустой результат без ошибки.

#### Scenario: Чтение потока целиком
- **WHEN** читают поток из трёх событий, начиная с версии 1
- **THEN** возвращаются три события с версиями 1, 2, 3 в этом порядке

#### Scenario: Чтение с середины
- **WHEN** читают поток из трёх событий, начиная с версии 3
- **THEN** возвращается одно событие с версией 3

#### Scenario: Несуществующий поток
- **WHEN** читают поток, в который никогда не писали
- **THEN** возвращается пустой список и нулевая версия потока

### Requirement: Чтение всех событий без пропусков
Система SHALL возвращать события всех потоков порциями в едином порядке, продолжая с позиции, переданной вызывающей стороной. Событие, однажды оставшееся позади позиции читателя, SHALL NOT появиться позже: параллельные транзакции записи не должны приводить к пропуску событий. События одного потока SHALL возвращаться в порядке версий при условии, что записи в этот поток не выполняются параллельно.

#### Scenario: Последовательное чтение порциями
- **WHEN** в хранилище пять событий и читатель запрашивает порции по два события, каждый раз передавая позицию последнего полученного
- **THEN** он получает порции из 2, 2 и 1 события, все пять событий ровно по одному разу, затем пустую порцию

#### Scenario: Незавершённая более ранняя транзакция
- **WHEN** транзакция A записала событие и ещё не завершена, а начавшаяся позже транзакция B записала событие и завершилась
- **THEN** чтение не возвращает событие транзакции B, пока A не завершится

#### Scenario: Обе транзакции завершены
- **WHEN** транзакции A и B из предыдущего сценария обе завершены и читатель повторяет запрос с прежней позиции
- **THEN** он получает оба события, сначала событие A, затем событие B

#### Scenario: Отменённая транзакция
- **WHEN** транзакция записала событие и была отменена
- **THEN** это событие не возвращается ни одним чтением и не задерживает чтение последующих событий
