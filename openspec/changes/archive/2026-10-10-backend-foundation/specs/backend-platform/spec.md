# Spec Delta

## Purpose

Платформа backend даёт всем серверным процессам общую основу: конфигурацию из окружения, управляемое время, структурированные логи, транзакции и миграции базы данных. Доменные модули опираются на неё и не решают эти задачи каждый по-своему.

## ADDED Requirements

### Requirement: Конфигурация из переменных окружения
Процесс SHALL получать настройки только из переменных окружения. При отсутствии обязательной переменной или некорректном значении процесс SHALL завершаться при старте с ошибкой, в которой названа проблемная переменная. Значения секретов SHALL NOT попадать в текст ошибки и в логи.

#### Scenario: Все обязательные переменные заданы
- **WHEN** процесс запускают с заданной строкой подключения к базе данных
- **THEN** конфигурация загружается, необязательные параметры получают значения по умолчанию

#### Scenario: Обязательная переменная отсутствует
- **WHEN** процесс запускают без строки подключения к базе данных
- **THEN** процесс завершается с ненулевым кодом и сообщением, в котором названа отсутствующая переменная

#### Scenario: Некорректное значение
- **WHEN** процесс запускают с нечисловым значением числового параметра
- **THEN** процесс завершается с ненулевым кодом и сообщением, в котором названа переменная, но не её значение

### Requirement: Управляемые часы
Код, которому нужно текущее время, SHALL получать его через общий интерфейс часов. Система SHALL предоставлять реализацию с системным временем в UTC и управляемую реализацию для тестов, время которой задаётся и сдвигается явно.

#### Scenario: Системные часы возвращают UTC
- **WHEN** у системных часов запрашивают текущее время
- **THEN** возвращается момент в часовом поясе UTC

#### Scenario: Сдвиг управляемых часов
- **WHEN** управляемые часы установлены на заданный момент и сдвинуты на 48 часов
- **THEN** они возвращают момент ровно на 48 часов позже заданного и не меняются сами по себе

### Requirement: Структурированные логи
Процесс SHALL писать логи в стандартный вывод в формате JSON, по одной записи на строку, с временем, уровнем и сообщением. Минимальный уровень SHALL задаваться конфигурацией. Запись, сделанная в рамках запроса или обработки события с correlation ID, SHALL содержать этот идентификатор.

#### Scenario: Запись с correlation ID
- **WHEN** код пишет лог в контексте, в который помещён correlation ID
- **THEN** строка лога является корректным JSON и содержит поле с этим идентификатором

#### Scenario: Фильтрация по уровню
- **WHEN** минимальный уровень задан как `warn` и код пишет записи уровней `info` и `error`
- **THEN** в выводе есть только запись уровня `error`

### Requirement: Транзакции базы данных
Платформа SHALL предоставлять единый способ выполнить набор операций в одной транзакции PostgreSQL: транзакция фиксируется, если операции завершились без ошибки, и отменяется при ошибке или аварийном завершении операции.

#### Scenario: Успешная транзакция
- **WHEN** операции внутри транзакции завершаются без ошибки
- **THEN** изменения зафиксированы и видны другим соединениям

#### Scenario: Ошибка внутри транзакции
- **WHEN** одна из операций внутри транзакции возвращает ошибку
- **THEN** все изменения транзакции отменены, вызывающая сторона получает исходную ошибку

#### Scenario: Аварийное завершение внутри транзакции
- **WHEN** операция внутри транзакции завершается паникой
- **THEN** изменения отменены, соединение возвращено в пул

### Requirement: Миграции схемы базы данных
Схема базы данных SHALL изменяться только версионируемыми миграциями, которые хранятся вместе с кодом. Применение миграций SHALL быть идемпотентным: повторный запуск на актуальной базе ничего не меняет. Система SHALL предоставлять команду, которая применяет миграции к базе из конфигурации окружения.

#### Scenario: Применение к пустой базе
- **WHEN** команду применения миграций запускают на пустой базе
- **THEN** создаются все объекты схемы, команда завершается с нулевым кодом и логирует применённые миграции

#### Scenario: Повторное применение
- **WHEN** команду применения миграций запускают повторно на той же базе
- **THEN** схема не меняется, команда завершается с нулевым кодом

#### Scenario: База недоступна
- **WHEN** команду применения миграций запускают с адресом недоступной базы
- **THEN** команда завершается с ненулевым кодом и понятным сообщением об ошибке подключения
