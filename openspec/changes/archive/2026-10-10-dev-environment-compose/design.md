# Design

## Context

Мотивация и границы - в proposal.md. Что есть сейчас:

- Backend запускается с хоста: `cmd/api` на `:8080`, `cmd/worker` на `:8081`, `cmd/generator` на `:8082`. Конфигурация - только переменные окружения.
- Интеграционные тесты поднимают свои контейнеры через testcontainers и от compose не зависят.
- Frontend работает на Vite (порт 5173) и знает только `VITE_API_URL=http://localhost:8080`.
- Keycloak в коде не используется. ADR-006 задаёт 14 permissions как client roles и три явных правила о составе ролей; остальной состав оставлен "по принципу минимальных прав".
- Папки `infra/` в репозитории нет, в корневом `AGENTS.md` она помечена как планируемая; это изменение её создаёт.

## Goals / Non-Goals

**Goals:**

- Одна команда из корня поднимает всё, что нужно backend и frontend снаружи.
- Realm воспроизводим: он лежит в репозитории и создаётся из файла.
- Задача A7 получает готовые клиентов, роли и пользователей и не меняет realm, а только проверяет токены.

**Non-Goals:**

- Процессы backend и frontend в контейнерах, образы приложений.
- Наблюдаемость: Prometheus, Grafana, Loki.
- Пригодность для деплоя: это окружение разработки с известными паролями.

## Decisions

### 1. Всё окружение лежит в infra/

`infra/compose.yaml` и файлы, которые монтируются в контейнеры (`infra/keycloak/`), лежат вместе. Окружение принадлежит системе целиком, а не backend или frontend: Keycloak нужен обоим, позже сюда же придут Prometheus и Grafana. В `backend/` и `frontend/` останутся только их собственные `Dockerfile`, когда они появятся.

Имя проекта compose задано в файле (`goden`), иначе оно получилось бы из имени папки.

*Альтернатива:* `compose.yaml` в корне. Отклонена: команда короче, но конфигурация оказалась бы разнесена между корнем и `infra/`. Команду всё равно берут из `AGENTS.md`.

### 2. Сервисы

| Сервис | Образ | Порт на хосте | Переменная порта |
| --- | --- | --- | --- |
| PostgreSQL | `postgres:18-alpine` | 15432 | `POSTGRES_PORT` |
| Kafka | `apache/kafka` 4.x | 9092 | `KAFKA_PORT` |
| Redis | `redis:8-alpine` | 6379 | `REDIS_PORT` |
| Keycloak | `quay.io/keycloak/keycloak` 26.x | 8180 | `KEYCLOAK_PORT` |

Теги закреплены до патч-версии по состоянию на 2026-10-10: `postgres:18.6-alpine`, `apache/kafka:4.3.1`, `redis:8.8.3-alpine`, `quay.io/keycloak/keycloak:26.8.0`.

Все порты публикуются на `127.0.0.1`: API без авторизации и сервисы с известными паролями не должны быть видны из сети.

- **PostgreSQL:** база, пользователь и пароль `goden`; данные в именованном томе. Адрес для backend: `postgres://goden:goden@localhost:15432/goden?sslmode=disable`. Порт на хосте - 15432, а не 5432 (изменено при реализации: на машине разработчика 5432 оказался занят локальным PostgreSQL, и окружение не поднялось).
- **Kafka:** один узел в совмещённой роли broker и controller. Два listener: для хоста (`localhost:9092`) и внутренний для будущих контейнеров (`kafka:19092`). Автосоздание тем включено: тему создаёт первый publisher. Данные в именованном томе: publisher запоминает в PostgreSQL, что уже отправил, поэтому Kafka не должна терять сообщения раньше базы.
- **Redis:** без пароля и без сохранения на диск: по ADR-003 он только ускоряет, его данные можно терять.
- **Keycloak:** режим `start-dev` с флагом импорта realm; администратор `admin` / `admin`.

### 3. Keycloak не хранит данные между пересозданиями контейнера

Keycloak в режиме разработки использует встроенную файловую базу внутри контейнера, без тома. Realm создаётся из файла при каждом создании контейнера.

*Альтернативы:* том для встроенной базы или отдельная база в PostgreSQL проекта. Отклонены: всё содержимое realm описано файлом, а сохранённое состояние мешало бы применять его изменения - импорт пропускает уже существующий realm.

Изменено при реализации: сначала предполагался том. Следствия выбранного варианта: изменённый файл realm применяется пересозданием контейнера Keycloak; пользователи и настройки, заведённые вручную в консоли, теряются при `down`.

### 4. Realm goden

**Клиенты:**

- `goden-api` - владелец прав: 14 client roles с именами permissions. Сам токены не запрашивает.
- `goden-web` - публичный клиент frontend: вход с перенаправлением и PKCE, адреса `http://localhost:5173/*`. Для него включена и выдача токена по логину и паролю: так токен тестового пользователя получают из `curl` и из будущих тестов A7. Это допустимо только в локальном realm.
- `goden-generator` - закрытый клиент с сервисной учётной записью и фиксированным секретом для разработки.

**Права в токене.** Стандартный набор утверждений Keycloak кладёт client roles в `resource_access.<клиент>.roles`. Чтобы backend мог проверять получателя токена, клиентам `goden-web` и `goden-generator` добавляется преобразователь, который вписывает `goden-api` в `aud`.

**Составные роли** (realm roles, собранные из client roles `goden-api`):

| Роль | Permissions |
| --- | --- |
| `admin` | все 14 |
| `manager` | `catalog.view`, `deliveries.view`, `deliveries.register`, `orders.view`, `inventory.view`, `inventory.edit`, `products.manage`, `dishes.manage`, `analytics.view`, `recommendations.view` |
| `approver` | `deliveries.view`, `deliveries.approve`, `inventory.view` |
| `cook` | `kitchen.view`, `catalog.view` |
| `waiter` | `orders.accept`, `orders.view`, `kitchen.view`, `catalog.view` |

`approver` и `inventory.view` у `manager` заданы ADR-006. Остальное - предложение этого изменения по принципу минимальных прав: менеджер ведёт каталог и склад, но не принимает поставки и не оформляет заказы; приёмка отделена от регистрации; `generator.manage` только у администратора.

**Пользователи:** `admin`, `manager`, `approver`, `cook`, `waiter` - по одной роли, пароль совпадает с логином.

Сервисная учётная запись `goden-generator` получает четыре client roles напрямую, без составной роли.

### 5. Документация

В `backend/AGENTS.md` раздел "Локальный запуск без `docker compose`" заменяется разделом о запуске окружения: команды запуска, остановки и сброса, адреса сервисов, значение `DATABASE_URL`, клиенты и тестовые пользователи Keycloak, пример получения токена. Одиночный `docker run` для PostgreSQL остаётся одной строкой как запасной вариант.

## Risks / Trade-offs

- [Известные пароли и секрет клиента в репозитории] → расходится с буквой ADR-006 "секреты не попадают в репозиторий". Это учётные данные локального realm, а не секреты окружений; они помечены в файле и в документации. Для деплоя realm с такими данными использовать нельзя.
- [Состав ролей `manager`, `cook`, `waiter` не задан ADR] → предложен здесь; если команда решит иначе, меняется один файл realm.
- [Сделанное вручную в консоли Keycloak теряется при `down`] → всё нужное вносится в файл realm; записано в документации.
- [Выдача токена по паролю у публичного клиента] → небезопасно вне разработки; только локальный realm.
- [Kafka на одном узле, Redis без сохранения] → достаточно для разработки и демо на одной машине.
- [Порт сервиса на хосте может быть занят] → каждый порт переопределяется переменной; для PostgreSQL по умолчанию выбран нестандартный 15432.
- [Процессы backend вне compose] → демо запускается несколькими командами. Контейнеры приложений - отдельная задача ближе к защите.
