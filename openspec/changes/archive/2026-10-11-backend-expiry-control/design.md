# Design

## Context

Команды `inventory.Service.IssueBatchExpiryWarning` и `WriteOffExpiredBatch` готовы и идемпотентны по состоянию партии: если делать нечего, они ничего не пишут и возвращают `false`. Обе перечитывают партию под блокировкой и решают по `tx.Now()`. `cmd/worker` выполняет задачи из функции `tasks` и уже запускает проекции.

## Decisions

### 1. Проверка сроков - задача worker поверх готовых команд

`inventory.ExpiryChecker` раз в период находит кандидатов двумя запросами к таблице партий и для каждой партии вызывает команду. Решение принимает команда, а не запрос: запрос только сужает список. Поэтому гонка двух экземпляров worker и гонка с заказом безопасны без дополнительной координации - это свойство команд из A5.

Порядок в проходе: сначала списание просрочки, затем предупреждения. Ошибка по партии пишется в журнал и в счётчик, проход продолжается.

Автор команд - `{service, worker}`. Сервисной учётной записи Keycloak worker не нужен: он вызывает сервисы напрямую, а не через API.

*Альтернатива:* планировать действие на точный момент истечения каждой партии. Отклонена: опрос раз в минуту проще и переживает перезапуск без сохранения расписания; минута задержки для сроков годности несущественна.

### 2. Список читается из таблицы партий

Решение выведено из правила `backend/AGENTS.md` "зависящее от текущего времени проекцией не хранят", а не задано пользователем. Запрос выбирает партии с остатком и сроком не позже `сейчас + горизонт`; признак "просрочена" - то же правило, что у заказа. Продукты для страницы берутся у каталога одним запросом по списку идентификаторов: таблицы каталога модуль `inventory` не читает.

### 3. Настройки

Переменные worker: `EXPIRY_WARNING_PERIOD` (по умолчанию `24h`), `EXPIRY_CHECK_INTERVAL` (по умолчанию `1m`). Параметр запроса списка `within_hours` по умолчанию 72: это горизонт просмотра, он не связан с периодом предупреждения, и API не знает настроек worker.

Изменено при реализации: период предупреждения по умолчанию был 72 часа. В демонстрационном каталоге генератора хлеб хранится 3 дня, поэтому предупреждение по нему выдавалось бы в момент приёмки. Период один для всех продуктов; делать его долей срока хранения продукта - отдельное решение, оно понадобится до уведомлений в Telegram (B9), если короткие и длинные сроки должны предупреждаться по-разному.

### 4. Метрики

`goden_batches_expiring` и `goden_batches_expired` - датчики, выставляются после каждого прохода по результатам тех же запросов; `goden_expiry_checks_total` с меткой `outcome` (`ok`, `error`) - счётчик проходов. Число выданных предупреждений и списаний уже видно в `goden_events_appended_total`.

## Risks / Trade-offs

- [Без запущенного worker просрочка не списывается] → заказ её всё равно не расходует, а стоп-лист и остатки учитывают просрочку при чтении; страдает только учёт списаний.
- [За время демо партии не успеют истечь: сроки хранения в днях] → автосписание проверяется тестами со сдвигом часов; показать его вживую можно, только добавив в генератор позиции с коротким сроком - это вне изменения.
