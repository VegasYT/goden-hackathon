# Design

## Context

Мотивация и границы - в proposal.md. Изменение повторяет на трёх разделах то, что сделано для каталога:

- `api/openapi.yaml` с общими параметрами и ответом `Error`; ogen с режимом "convenient errors";
- `api.Handler` собирает обработчики модулей встраиванием; `api.New` сейчас создаёт только сервис каталога;
- `problemFor` уже содержит все ошибки `inventory` и `orders`: `ValidationError`, `ErrNotFound`, `ErrAlreadyApproved`, `ErrNotApproved`, `ErrQuarantineClosed`, `UnknownDishError`, `DishWithoutRecipeError`, `catalog.UnknownProductError`;
- сервисы `inventory.Service` и `orders.Service` со всеми командами и чтением;
- `catalog/http.go` как образец тонкого обработчика.

## Goals / Non-Goals

**Goals:**

- Главные сценарии кейса проходят через API целиком: каталог, поставка, приёмка, заказ с FEFO, отказ, списание.
- Ни одного нового правила предметной области и ни одного нового соглашения API.

**Non-Goals:**

- Эндпоинты списков и агрегатов (все поставки, все заказы, остатки по складу, стоп-лист): проекции разработчика B.
- Публикация команд worker. `WriteOffExpiredBatch` и `IssueBatchExpiryWarning` вызываются внутри процесса; наружу они дали бы любому клиенту возможность списывать партии от имени сервиса.

## Decisions

### 1. Операции

| Раздел | Операция | Метод и путь | Ответ |
| --- | --- | --- | --- |
| deliveries | `registerDelivery` | `POST /deliveries` | 201, `Delivery` |
| deliveries | `getDelivery` | `GET /deliveries/{deliveryId}` | 200, `Delivery` |
| deliveries | `approveDelivery` | `POST /deliveries/{deliveryId}/approval` | 200, `Delivery` |
| deliveries | `resolveQuarantine` | `POST /deliveries/{deliveryId}/items/{itemId}/quarantine-resolution` | 200, `Delivery` |
| deliveries | `correctDeliveryApproval` | `POST /deliveries/{deliveryId}/corrections` | 200, `Delivery` |
| stock | `listProductBatches` | `GET /products/{productId}/batches` | 200, `BatchList` |
| stock | `getBatch` | `GET /batches/{batchId}` | 200, `Batch` |
| stock | `writeOffStock` | `POST /batches/{batchId}/write-offs` | 200, `Batch` |
| stock | `adjustStock` | `POST /batches/{batchId}/adjustments` | 200, `Batch` |
| orders | `placeOrder` | `POST /orders` | 201, `Order` |
| orders | `getOrder` | `GET /orders/{orderId}` | 200, `Order` |

Все операции записи принимают `Idempotency-Key`.

Приёмка, решение по карантину, корректировка, списание и корректировка остатка - действия над существующим объектом, поэтому отвечают 200 и новым состоянием объекта, а не 201. Регистрация поставки и оформление заказа создают объект и отвечают 201.

Партии продукта возвращаются списком без пагинации: у продукта их единицы или десятки, а порядок FEFO важен целиком. Ответ - объект с полем `items`, чтобы позже добавить поля без смены формата.

### 2. Отказ в заказе - успешный ответ

`POST /orders` отвечает 201 и для принятого, и для отклонённого заказа; различает их поле `status`. Отклонённый заказ записан событием, имеет идентификатор и читается через `GET /orders/{id}`: это созданный объект, а не ошибка клиента. Статус 4xx означал бы "запрос был неверным", что для корректного заказа при пустом складе неправда, и заставил бы клиента разбирать тело ошибки ради бизнес-результата.

### 3. Схемы

Схемы повторяют типы сервисов; имена полей - `snake_case`, как в событиях и в уже существующих схемах.

- Время - `string` с `format: date-time`; количество - `integer` с `format: int64`.
- Закрытые наборы - перечисления: статус поставки, статус заказа, причина списания, тип автора.
- Ограничения только те, что не зависят от нормализации: `minItems: 1` для позиций поставки, решений, блюд заказа и позиций корректировки; `minimum: 1` для заявленного количества, количества списания и числа порций; `minimum: 0` для количеств в решениях. Сумма количеств, обязательность причин и комментариев, просрочка - правила предметной области с ответом 422.
- `Shortage` в ответе заказа: `product_id`, `required_quantity`, `available_quantity`.

Обязательная дата окончания срока годности позиции поставки задана в схеме (`required`). Так требование ADR-010 "невозможно создать позицию без даты окончания срока годности" выполняется уже на уровне контракта.

### 4. Сборка

`api.New` создаёт сервисы каталога, склада и заказов на одном `command.Runner` и встраивает в `Handler` три обработчика: `*catalog.HTTP`, `*inventory.HTTP`, `*orders.HTTP`. Имена методов между модулями не пересекаются, потому что `operationId` в контракте уникальны.

### 5. Обработчики

`inventory/http.go` и `orders/http.go` содержат методы операций и функции преобразования между типами модуля и сгенерированными типами. Преобразование поставки и партии в ответ - по одной функции на тип: они нужны нескольким операциям.

### 6. Проверка

Кроме тестов по разделам добавляется сквозной сценарий через сгенерированный клиент, повторяющий точки сверки С2 и С3 из плана: продукты, блюдо с рецептурой, поставка с частичной приёмкой и карантином, решение по карантину, заказ с FEFO из двух партий, отклонённый заказ, списание, корректировка. Он же служит образцом последовательности вызовов для генератора.

## Risks / Trade-offs

- [Большой прирост контракта и сгенерированного кода за одно изменение] → операции однотипны; ревью контракта проще делать целиком, чем тремя частями с общими схемами.
- [201 для отклонённого заказа] → клиент обязан смотреть поле `status`, а не только код ответа. Записано в описании операции в контракте.
- [Нет эндпоинтов списков] → до задач разработчика B frontend может показать поставку или заказ только по известному идентификатору. Это ожидаемое разделение работ.
- [Операции без авторизации] → до A7 любой клиент может принять поставку или списать партию от имени `dev`. Ограничение уже записано в `AGENTS.md`.
