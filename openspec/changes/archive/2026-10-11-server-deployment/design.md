## Context

`infra/compose.yaml` поднимает только внешние сервисы, процессы backend запускаются с хоста. Сервер один: Linux, `194.154.24.234`, репозиторий склонирован в `/home/root/goden`. У домена `goden.pro` записей A пока нет. Frontend - оболочка без обращений к API.

## Goals / Non-Goals

**Goals:** рабочая ссылка для жюри; выкладка без ручных шагов после первого запуска; локальное окружение не меняется.

**Non-Goals:** отказоустойчивость, масштабирование, выкладка без простоя.

## Decisions

**Отдельный файл `infra/compose.prod.yaml`, а не надстройка над `compose.yaml`.** У сервера другие порты, пароли, режим Keycloak и цели Prometheus; надстройка переопределяла бы почти каждый сервис и читалась бы хуже двух независимых файлов. Цена - версии образов записаны в двух местах.

**Caddy как обратный прокси.** Сам получает и продлевает сертификаты, конфигурация на все адреса - около 30 строк. Альтернатива nginx с certbot требует отдельного контейнера и задания на продление.

**Frontend - свой образ со статикой, прокси - отдельный сервис.** Образ frontend содержит сборку и Caddy, который только раздаёт файлы по HTTP и отдаёт `index.html` на неизвестный путь. Внешний прокси - стандартный образ Caddy с `infra/caddy/Caddyfile`. Так образ frontend не знает о доменах и сертификатах, а правка адресов не требует пересборки.

**API на том же домене, что и frontend (`/api/v1`).** Запросы из браузера идут на свой источник, CORS не участвует. Решение пользователя.

**Один образ backend с четырьмя программами.** `api`, `worker`, `generator`, `migrate` собираются из одного модуля; сервис выбирает программу командой запуска. Четыре образа пересобирали бы один и тот же код четыре раза.

**Миграции - разовый сервис compose.** `api` и `worker` ждут его успешного завершения (`service_completed_successfully`).

**Образы собираются на сервере.** `docker compose up -d --build` после `git pull`. Реестр образов и сборка в GitHub дали бы быстрый откат и разгрузили сервер, но требуют настройки реестра и токенов. Риск: сборка на слабом сервере может быть долгой; ресурсы сервера пока не проверены (доступа нет).

**Keycloak без постоянного хранилища, realm из файла.** Как локально: любое изменение вносится в файл realm. Запускается командой `start` за прокси (`KC_PROXY_HEADERS=xforwarded`, `KC_HOSTNAME=https://auth.goden.pro`). Отдельная база для Keycloak не нужна, пока пользователи заданы файлом.

**Секреты через подстановки в файле realm.** Keycloak заменяет `${ИМЯ:значение по умолчанию}` при импорте. Значения по умолчанию - нынешние, поэтому локальное окружение и тесты не меняются. На сервере переменные обязательны: compose останавливает запуск записью `${ИМЯ:?сообщение}`. Демонстрационные пользователи остаются: жюри нужны логины всех ролей; их пароли на сервере другие и передаются жюри отдельно.

**Grafana на сервере со входом по паролю.** Локально вход анонимный; в интернете это открыло бы редактирование дашбордов любому.

**Выкладка по SSH из GitHub Actions.** Отдельный ключ только для выкладки, закрытая часть хранится в секретах репозитория. Задание выполняет на сервере `infra/deploy.sh`: скрипт приводит рабочую копию к коммиту и запускает compose. Шаги выкладки лежат в репозитории, а не в workflow, поэтому их можно выполнить на сервере вручную.

**API обращается к Keycloak по внешнему адресу через прокси.** Адрес издателя в токене и адрес, по которому API читает ключи, должны совпадать. Прокси получает в сети compose имя `auth.<домен>`, поэтому запрос не выходит наружу. Следствие: прокси стартует без зависимостей, а API перезапускается, пока Keycloak не станет доступен через него. Интеграционные тесты идут на стандартной машине GitHub: Docker на ней есть, testcontainers работает без настройки.

**Проверки и выкладка запускаются только при попадании коммита в `main`.** Решение пользователя. Один workflow: проверки backend и frontend, затем выкладка, если обе прошли. Фильтра по путям нет: слияния в `main` редки, а выкладка должна зависеть от обеих проверок. Следствие: до слияния `develop` в `main` выкладывать нечего, в `main` сейчас только описание кейса.

## Risks / Trade-offs

- Записей A у домена нет → до их появления Caddy не получит сертификаты; первый запуск возможен только после настройки DNS.
- Publisher Kafka не создаёт топики (`backend/review.md`, находка 2) → worker на сервере пишет ошибки публикации в лог; API, проекции и интерфейс работают. Исправляется отдельно.
- Сборка на сервере и перезапуск дают простой в десятки секунд при каждой выкладке → для демо приемлемо.
- Демонстрационные данные пишет генератор; любой, кто знает пароль пользователя, может их менять → пароли не публикуются, базу можно пересоздать.
- Лимит запросов Let's Encrypt: частое пересоздание тома Caddy с сертификатами может упереться в лимит → том сертификатов сохраняется между выкладками.
