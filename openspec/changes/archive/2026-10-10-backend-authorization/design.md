# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- `httpx.FixedActor(httpx.DevActor)` кладёт в контекст одного автора для всех запросов; обработчики модулей берут его через `httpx.Actor(ctx)` и передают в команды. Менять обработчики и сервисы не нужно: достаточно положить в контекст настоящего автора.
- Контракт из 20 операций; ни одна не объявляет безопасность. ogen генерирует и сервер, и клиент.
- `apitest.New` поднимает API и возвращает клиент; на нём около сотни интеграционных тестов, которые не знают о токенах.
- Генератор создаёт клиент `oas.NewClient(url)` и ходит без токена.
- Realm `goden`: права в `resource_access.goden-api.roles`, `goden-api` в `aud`; файл realm лежит в `infra/keycloak/`.
- CORS в backend нет.

## Goals / Non-Goals

**Goals:**

- Право проверяется в одном месте для всех операций; забыть защитить новую операцию нельзя.
- Доменные модули и их обработчики не меняются.
- Существующие тесты API продолжают работать без правок в каждом тесте.
- Проверка настоящих токенов Keycloak покрыта тестом, а не только подделкой.

**Non-Goals:**

- Собственные пользователи, роли и вход: всё это в Keycloak.
- Права на уровне объектов (например, "только свои поставки").
- Отзыв токена до истечения срока: полагаемся на короткий срок жизни access token.

## Decisions

### 1. Безопасность объявляется в контракте, проверяет её обработчик ogen

В `openapi.yaml` добавляется схема `bearerAuth` и глобальное требование безопасности. ogen генерирует для сервера интерфейс обработчика безопасности, который получает токен и имя операции, а для клиента - источник токена. Обработчик в `internal/api`:

1. проверяет токен через `auth.Verifier` и получает `auth.Principal` (автор и набор прав);
2. находит право операции в таблице;
3. кладёт автора в контекст через `httpx.WithActor`.

*Альтернатива:* HTTP-middleware перед сервером ogen. Отклонена: middleware не знает, какая операция вызвана, и пришлось бы дублировать маршрутизацию. Если при реализации окажется, что обработчик безопасности ogen не позволяет вернуть 401 и 403 в нужном формате, запасной вариант - middleware с определением операции через сгенерированный поиск маршрута.

Права операций записаны в контракте, а не в коде (изменено при реализации): `security: - bearerAuth: [<право>]` у каждой операции. ogen передаёт обработчику безопасности список прав операции, поэтому отдельная таблица в Go не нужна, а право видно в контракте и frontend. Операции, доступные любому аутентифицированному клиенту, перечислены в `authenticatedOnly`; остальные операции без права отклоняются. Тест сверяет список операций контракта со списком запросов матрицы прав.

Формально OpenAPI 3.0 разрешает непустой список только для схем OAuth2 и OpenID Connect, а для `http bearer` - начиная с 3.1. ogen принимает его и в 3.0; если инструмент frontend на этом споткнётся, контракт переводится на 3.1.

Режим без авторизации: сгенерированный сервер требует сам заголовок `Authorization`, поэтому в этом режиме запросу без токена подставляется токен-заглушка, а `auth.Disabled` принимает любой.

### 2. Пакет platform/auth

```go
type Principal struct {
    Actor       eventstore.Actor
    Permissions map[string]struct{}
}

type Verifier interface {
    Verify(ctx context.Context, token string) (Principal, error)
}
```

- `auth.NewOIDC(ctx, issuer, audience)` - проверка через `go-oidc`: ключи подписи берутся у издателя и кешируются библиотекой; проверяются подпись, издатель, получатель и срок.
- `auth.Disabled()` - любой запрос, в том числе без токена, получает пользователя `dev` со всеми правами.

Права читаются из `resource_access.<audience>.roles`.

### 3. Автор из токена

- Сервисная учётная запись: в токене есть утверждение `client_id`; автор - `{service, <client_id>}`. Выяснилось при реализации: при импорте realm из файла Keycloak это утверждение не добавляет (консоль добавляет его сама), поэтому оно описано в файле realm явно.
- Пользователь: автор - `{user, <preferred_username>}`.

*Альтернатива:* идентификатор `sub`. Отклонена: Keycloak окружения не хранит данные, и после пересоздания контейнера у тех же пользователей новые `sub` - события ссылались бы на несуществующие идентификаторы. Имя пользователя стабильно, читается в журнале и совпадает с тем, что видит оператор. Цена: если пользователя удалить и завести другого с тем же именем, в событиях их не различить. Смена имени пользователя в realm запрещена настройкой по умолчанию.

### 4. Ошибки

- 401: тип `unauthorized`, заголовок `WWW-Authenticate: Bearer`. Подробность проверки (просрочен, чужой ключ) пишется в журнал, но не в ответ.
- 403: тип `forbidden`, в `detail` - какое право требуется.

Оба отказа пишутся в журнал уровнем `warn` с операцией и автором, если он определён.

### 5. Конфигурация API

- `AUTH_DISABLED` (по умолчанию `false`);
- `OIDC_ISSUER` - адрес realm, например `http://localhost:8180/realms/goden`; обязателен, если авторизация включена;
- `OIDC_AUDIENCE` (по умолчанию `goden-api`);
- `CORS_ALLOWED_ORIGINS` (по умолчанию `http://localhost:5173`).

При старте API обращается к издателю за конфигурацией. Если Keycloak недоступен, процесс завершается с ошибкой: без ключей он не может проверить ни один токен. `api.New` получает `auth.Verifier` аргументом.

### 6. CORS

Небольшой middleware в `httpx` на стандартной библиотеке: сравнивает `Origin` со списком, отвечает на `OPTIONS` до проверки токена, добавляет `Vary: Origin`. Учётные данные в cookie не используются, поэтому `Access-Control-Allow-Credentials` не выставляется. Сторонняя библиотека не нужна.

### 7. Тесты

- **`apitest`** получает поддельный `Verifier`: токен - строка, заранее зарегистрированная вместе с автором и правами. `apitest.New` по умолчанию даёт клиент с токеном пользователя `dev` со всеми правами, поэтому существующие тесты не меняются. `Server.As(actor, permissions...)` возвращает клиент с другим набором прав.
- **Матрица прав** - один табличный тест: для каждой операции вызов без токена (401), без прав (403), со всеми правами, кроме нужного (403), и только с нужным (не 401 и не 403).
- **Настоящий Keycloak** - интеграционный тест пакета `auth`: контейнер Keycloak с файлом realm из `infra/keycloak/`, токены тестовых пользователей и сервисной учётной записи проверяются `auth.NewOIDC`; отдельно - просроченный токен, чужой получатель, чужая подпись.
- **Сквозной тест** на окружении вручную: API с включённой авторизацией, генератор с учётной записью, запросы `curl` с токенами `approver` и `cook`.

Тест с Keycloak добавляет около 30-40 секунд к прогону пакета `auth`.

### 8. Генератор

Переменные: `OIDC_ISSUER`, `GENERATOR_CLIENT_ID`, `GENERATOR_CLIENT_SECRET`. Если `GENERATOR_CLIENT_ID` пуст, клиент работает без токена. Иначе источник токена - `clientcredentials` из `golang.org/x/oauth2`: он сам кеширует токен и обновляет его перед истечением. Адрес выдачи токенов берётся из конфигурации издателя.

Ошибка получения токена - обычная ошибка действия: цикл продолжается, `/readyz` отвечает 503.

### 9. Права учётной записи генератора

Учётная запись получает `products.manage` и `dishes.manage` в дополнение к четырём правам ADR-012. ADR-006, ADR-012, `docs/plan.md` и `backend/AGENTS.md` правятся в этом же изменении.

*Альтернатива:* вынести наполнение каталога из генератора в отдельную команду `cmd/seed` с прямым доступом к базе. Отклонена: наполнение через API уже реализовано и проверено, а отдельная команда обходила бы авторизацию и дублировала сборку сервисов. Цена выбранного варианта: учётная запись шире минимально необходимого для самой симуляции; в окружении, где каталог ведут люди, эти два права учётной записи не выдают и запускают генератор с `GENERATOR_SEED=false`.

Чтение настроек (`GET /generator`) открыто любому аутентифицированному клиенту: это не секрет, а отдельное право ради одного запроса потребовало бы менять список permissions в ADR-006.

### 10. Фиксированный адрес издателя

Добавлено при реализации. Keycloak в режиме разработки пишет в токен тот адрес, по которому к нему обратились: токен, полученный через `127.0.0.1:8180`, имел издателя `http://127.0.0.1:8180/...`, и API с `OIDC_ISSUER` на `localhost` его бы отклонил. В `infra/compose.yaml` задан `KC_HOSTNAME=http://localhost:8180`; проверено, что издатель одинаков при обращении по `localhost`, по `127.0.0.1` и из сети compose. Когда процессы backend поедут в контейнеры, им понадобится обращаться к Keycloak по имени сервиса при издателе `localhost`: `go-oidc` это умеет, но потребует отдельной настройки.

### 11. Общая настройка Docker для тестов

Обход особенностей Docker Desktop на Windows вынесен из `pgtest` в пакет `platform/dockertest`: он нужен и тесту с контейнером Keycloak.

## Risks / Trade-offs

- [Frontend перестанет работать с API без токена] → режим `AUTH_DISABLED=true`; предупреждение при старте; в документации сказано, что такой сервер нельзя выставлять наружу.
- [`AUTH_DISABLED` включат там, где нельзя] → значение по умолчанию `false`; предупреждение в журнале при каждом старте.
- [API не стартует без Keycloak] → осознанно; локально Keycloak поднимается тем же compose.
- [Автор по имени пользователя, а не по `sub`] → см. решение 3.
- [Отозванный токен действует до истечения срока] → срок жизни access token в realm по умолчанию 5 минут.
- [Учётная запись генератора шире ADR-012] → ADR меняется явно; см. решение 9.
- [Поддельный `Verifier` в тестах API не проверяет разбор токена] → разбор покрыт тестом с настоящим Keycloak.
- [Обработчик безопасности ogen может не дать нужный формат ошибок] → запасной вариант в решении 1; проверяется первой задачей.
