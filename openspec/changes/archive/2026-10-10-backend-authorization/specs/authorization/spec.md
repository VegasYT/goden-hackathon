# Spec Delta

## Purpose

Авторизация определяет, кто обращается к API и что ему разрешено: backend проверяет токен Keycloak и право на каждую операцию и записывает автора действия в события.

## ADDED Requirements

### Requirement: Аутентификация запросов
API SHALL принимать запросы к операциям `/api/v1` только с access token Keycloak в заголовке `Authorization: Bearer`. Токен SHALL проверяться по подписи, издателю, получателю `goden-api` и сроку действия. Запрос без токена или с токеном, не прошедшим проверку, SHALL отклоняться со статусом 401 в формате ошибок API и заголовком `WWW-Authenticate: Bearer`, а причина отказа SHALL NOT раскрываться в ответе. Эндпоинты `/healthz` и `/readyz` SHALL оставаться доступными без токена.

#### Scenario: Запрос без токена
- **WHEN** операцию вызывают без заголовка `Authorization`
- **THEN** возвращается статус 401, команда не выполняется

#### Scenario: Корректный токен
- **WHEN** операцию вызывают с токеном пользователя, выданным Keycloak, и у пользователя есть нужное право
- **THEN** операция выполняется

#### Scenario: Просроченный токен
- **WHEN** операцию вызывают с токеном, срок действия которого истёк
- **THEN** возвращается статус 401

#### Scenario: Токен для другого получателя
- **WHEN** операцию вызывают с корректно подписанным токеном, в `aud` которого нет `goden-api`
- **THEN** возвращается статус 401

#### Scenario: Подделанный токен
- **WHEN** операцию вызывают с токеном, подписанным чужим ключом
- **THEN** возвращается статус 401

#### Scenario: Проверка состояния без токена
- **WHEN** `/readyz` запрашивают без токена
- **THEN** возвращается статус 200

### Requirement: Права операций
Каждая операция контракта SHALL требовать ровно одно право из ADR-006 либо быть явно помечена как доступная любому аутентифицированному клиенту. Права клиента SHALL браться из `resource_access.goden-api.roles` токена. Запрос аутентифицированного клиента без нужного права SHALL отклоняться со статусом 403, и команда SHALL NOT выполняться. Право операции SHALL быть записано в контракте API; операция, у которой оно не записано, SHALL отклоняться для всех клиентов.

Соответствие операций и прав:

| Операции | Право |
| --- | --- |
| чтение продуктов и блюд | `catalog.view` |
| создание продукта | `products.manage` |
| создание блюда, изменение рецептуры | `dishes.manage` |
| регистрация поставки | `deliveries.register` |
| чтение поставки | `deliveries.view` |
| приёмка, решение по карантину, корректировка приёмки | `deliveries.approve` |
| чтение партий | `inventory.view` |
| списание, корректировка остатка | `inventory.edit` |
| оформление заказа | `orders.accept` |
| чтение заказа | `orders.view` |
| изменение настроек генератора | `generator.manage` |
| чтение настроек генератора | любой аутентифицированный клиент |

#### Scenario: Право есть
- **WHEN** клиент с правом `deliveries.approve` принимает поставку
- **THEN** приёмка выполняется

#### Scenario: Права нет
- **WHEN** клиент без права `deliveries.approve` пытается принять поставку
- **THEN** возвращается статус 403, поставка остаётся непринятой, событий не появляется

#### Scenario: Каждая операция защищена
- **WHEN** каждую операцию контракта, требующую права, вызывают с токеном без единого права
- **THEN** каждая отвечает статусом 403

#### Scenario: Каждое право открывает только свои операции
- **WHEN** каждую операцию контракта вызывают с токеном, в котором есть все права, кроме требуемого этой операцией
- **THEN** она отвечает статусом 403

#### Scenario: Новая операция без записи о праве
- **WHEN** в контракте появляется операция без записанного права или без запроса в матрице прав
- **THEN** тесты проекта сообщают об этом

### Requirement: Автор действия
Автор команды SHALL определяться по токену. Для пользователя автор SHALL иметь тип `user` и идентификатор, равный имени пользователя; для сервисной учётной записи - тип `service` и идентификатор клиента. Автор SHALL попадать в метаданные и поля событий, которые порождает команда. Клиент SHALL NOT иметь возможности указать автора в запросе.

#### Scenario: Действие пользователя
- **WHEN** пользователь `approver` принимает поставку
- **THEN** в событии приёмки и в ответе автором указан пользователь `approver`

#### Scenario: Действие сервисной учётной записи
- **WHEN** сервисная учётная запись `goden-generator` регистрирует поставку
- **THEN** в событии автором указана сервисная учётная запись `goden-generator`

### Requirement: Аудит критичных действий
Приёмка поставки, отбраковка, решение по карантину, корректировка приёмки, изменение рецептуры, корректировка остатка и списание SHALL оставлять в Event Store событие с автором, временем и идентификатором запроса. Отклонённые запросы (401 и 403) SHALL записываться в журнал процесса с операцией и, если он известен, автором.

#### Scenario: Критичное действие
- **WHEN** пользователь `manager` списывает часть партии
- **THEN** в Event Store есть событие списания с автором `manager`, временем и correlation ID запроса

#### Scenario: Отказ в доступе
- **WHEN** пользователь `cook` пытается списать партию
- **THEN** в журнале процесса есть запись об отказе с операцией и автором `cook`, событий не появляется

### Requirement: Режим без авторизации
API SHALL иметь режим без авторизации для локальной разработки, включаемый только явной настройкой окружения. В этом режиме запросы SHALL выполняться от имени пользователя `dev` со всеми правами, а процесс SHALL писать предупреждение при старте. Без этой настройки и без адреса издателя токенов процесс SHALL NOT запускаться.

#### Scenario: Режим включён
- **WHEN** API запускают с настройкой режима без авторизации и вызывают операцию без токена
- **THEN** операция выполняется от имени пользователя `dev`

#### Scenario: Настройки нет
- **WHEN** API запускают без режима без авторизации и без адреса издателя
- **THEN** процесс завершается с ошибкой конфигурации
