# Proposal

## Why

Сейчас любой, кто достучался до API, может принять поставку, списать остаток или изменить рецептуру, а во всех событиях автором стоит выдуманный пользователь `dev`. ADR-006 требует проверять право на backend для каждой операции и записывать, кто выполнил критичное действие. Keycloak с realm, ролями и тестовыми пользователями уже есть (задача 0.4). Это задача A7 из [backend/plan.md](../../../backend/plan.md).

## What Changes

- API проверяет access token Keycloak в каждом запросе к `/api/v1`: подпись, издатель, получатель, срок действия. Без корректного токена ответ 401.
- Каждая операция контракта требует одно право из ADR-006; без него ответ 403. Соответствие операций и прав записано в одной таблице.
- Автор команды берётся из токена: пользователь или сервисная учётная запись. Он попадает в события, поэтому Event Store остаётся журналом аудита критичных действий; отдельной таблицы аудита нет.
- Контракт объявляет схему безопасности; сгенерированный клиент передаёт токен.
- Генератор получает токен по client credentials своей сервисной учётной записи.
- Появляется явный режим без авторизации для локальной разработки: `AUTH_DISABLED=true`. Без этой переменной API не запустится без адреса Keycloak.
- API отвечает на кросс-доменные запросы с разрешённых адресов frontend (CORS): без этого браузер не отправит запрос с токеном.
- **BREAKING** для клиентов API: запросы без токена отклоняются. Frontend до реализации входа и разработчик B могут работать с `AUTH_DISABLED=true`.

**Изменение ADR-012 и ADR-006:** сервисная учётная запись генератора дополнительно получает `products.manage` и `dishes.manage`. Они нужны только для наполнения пустого каталога демонстрационным набором: с четырьмя правами из ADR генератор не может создать ни продукт, ни блюдо. Альтернатива - вынести наполнение из генератора в отдельную команду с доступом к базе; она отклонена в design.

**Чтение настроек генератора** (`GET /generator`) доступно любому аутентифицированному клиенту: генератор должен их читать, а права `generator.manage` у его учётной записи нет и быть не должно. Изменение настроек требует `generator.manage`.

Вне изменения: эндпоинт чтения журнала аудита (сторона чтения, разработчик B); авторизация SSE (эндпоинта ещё нет); права `kitchen.view`, `analytics.view`, `recommendations.view` - операций под них в контракте пока нет, они появятся с эндпоинтами разработчика B; учётная запись worker.

## Capabilities

### New Capabilities

- `authorization`: проверка токена, права операций, автор действия, режим без авторизации.

### Modified Capabilities

- `http-api`: кросс-доменные запросы.
- `event-generator`: генератор аутентифицируется сервисной учётной записью.
- `dev-environment`: состав прав сервисной учётной записи генератора.

## Impact

- **Код:** новый пакет `internal/platform/auth`; `internal/api` (обработчик безопасности, таблица прав, ошибки 401 и 403); `httpx` (CORS, удаление `FixedActor`); `api/openapi.yaml` и перегенерированный `oas`; `cmd/api`, `cmd/generator`; `apitest` и существующие тесты API (клиент с токеном).
- **Зависимости:** `github.com/coreos/go-oidc/v3` и `golang.org/x/oauth2` (оба уже в стеке `backend/AGENTS.md`).
- **Окружение:** `infra/keycloak/goden-realm.json` - два права сервисной учётной записи.
- **Документы:** `docs/ADR.md` (ADR-006, ADR-012), `docs/plan.md`, `backend/AGENTS.md`, `backend/plan.md`.
- **Frontend:** должен входить через Keycloak и передавать токен; получает CORS. До этого работает с API в режиме `AUTH_DISABLED=true`.
- **Разработчик B:** новые операции чтения обязаны получить строку в таблице прав, иначе тест не пройдёт; интеграционные тесты через `apitest` продолжают работать без изменений.
