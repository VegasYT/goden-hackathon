# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- `internal/inventory/events.go`: все события поставок и склада с эталонными JSON, функции `DeliveryStream` и `StockStream`.
- `command.Run`: транзакция, блокировки по потокам через `Spec.Locks`, идемпотентность, повтор при конфликте версий, `Tx.Now()`.
- `catalog.Service.Product`: чтение продукта с единицей и сроком хранения. Продукты не удаляются и не меняются.
- Модуль `catalog` как образец: правила в чистых функциях, команды в `service.go`, запись в таблицы через функции применения событий, sqlc.
- Правило ADR-002: команда, пишущая в `stock-*`, объявляет эти потоки в блокировках.

## Goals / Non-Goals

**Goals:**

- После приёмки на складе есть партии, пригодные для FEFO-списания в A4.
- Правила приёмки проверяются unit-тестами без базы данных.
- Состояние поставки не дублируется: его единственный источник - события потока поставки.

**Non-Goals:**

- Выход из карантина и корректировка приёмки: задача A3.1. Модель состояния позиции проектируется так, чтобы они добавились без переделки (см. решение 2).
- Списки поставок, поиск и фильтры: проекции разработчика B.
- Уникальность номера поставки. В ADR её нет; от случайного дубля защищает ключ идемпотентности.

## Decisions

### 1. Состояние поставки восстанавливается из её потока

Поставка - агрегат Event Sourcing в чистом виде: команда читает поток `delivery-<id>`, сворачивает события в структуру состояния и решает по ней. Синхронной таблицы для поставок нет.

Причины: поток короткий (регистрация, приёмка, позже несколько решений по карантину и корректировок), решение нужно только самой поставке, а таблицы для чтения списков всё равно строит разработчик B как проекции. Вторая таблица на стороне записи дублировала бы их.

Версия потока, прочитанная при загрузке, передаётся в `tx.Append` как ожидаемая. Две одновременные приёмки поэтому дают конфликт версий у второй; `command.Run` повторяет её, она видит уже принятую поставку и возвращает "уже принята".

*Альтернатива:* синхронная таблица поставок по образцу каталога. Отклонена по причинам выше; в каталоге таблица нужна для проверки уникальности названий и для чужих модулей, у поставки таких потребителей нет.

### 2. Модель состояния

```go
type Delivery struct {
    ID          uuid.UUID
    Number      string
    DeliveredAt time.Time
    Status      DeliveryStatus // "registered" | "approved"
    ApprovedAt  *time.Time
    ApprovedBy  *eventstore.Actor
    Items       []DeliveryItemState
}

type DeliveryItemState struct {
    ID, ProductID        uuid.UUID
    DeclaredQuantity     int64
    ExpiresAt            time.Time
    ManufacturedAt       *time.Time
    AcceptedQuantity     int64
    RejectedQuantity     int64
    QuarantinedQuantity  int64      // ещё не решённый карантин
    Expired              bool       // на момент приёмки
    BatchID              *uuid.UUID
    RejectReason, QuarantineReason, Comment string
}
```

Для принятой поставки у каждой позиции всегда `заявлено = принято + отклонено + карантин`. В A3.1 выход из карантина переносит количество из "карантин" в "принято" или "отклонено", а корректировка перераспределяет три числа; равенство сохраняется, модель не меняется.

Эта же структура возвращается командами и чтением и сохраняется как результат для повторов с ключом идемпотентности.

### 3. Чистые функции решений

Файл `delivery.go`, без ввода-вывода:

- `planRegistration(in NewDelivery, products map[uuid.UUID]catalog.Product) (DeliveryRegistered, error)` - проверка входных данных и согласованности дат;
- `(d Delivery) planApproval(decisions []ItemDecision, actor, now) (DeliveryApproved, []BatchReceived, error)` - проверка статуса, покрытия позиций, сумм, причин и просрочки; формирование снимка и событий партий;
- `foldDelivery(events []eventstore.Payload) (Delivery, error)` - свёртка событий в состояние.

Идентификаторы позиций и партий создаются внутри этих функций как UUIDv7. Время приходит аргументом: в командах это `tx.Now()`, в тестах - заданное значение.

Позиция считается просроченной, если дата окончания срока годности не позже момента приёмки.

Согласованность дат при регистрации: дата изготовления не позже даты окончания срока; если у продукта задан срок хранения и указана дата изготовления, интервал между датами не превышает срок хранения. Без даты изготовления или без срока хранения проверка не выполняется.

### 4. Ход команд

**RegisterDelivery.** До транзакции: чтение продуктов позиций через `catalog.Service` (неизвестный продукт - ошибка с его идентификатором), вызов `planRegistration`. В транзакции: `tx.Append(DeliveryStream(id), 0, event)`. Блокировок нет: складские потоки не затрагиваются.

**ApproveDelivery.**

1. До транзакции: чтение потока поставки, чтобы узнать продукты позиций. Поставки нет - "не найдено".
2. `Spec.Locks` - складские потоки всех продуктов поставки. Состав позиций после регистрации не меняется, поэтому набор блокировок не может устареть.
3. В транзакции: повторная загрузка состояния с версией потока, `planApproval` с `tx.Now()`.
4. Запись событий партий: по одному вызову `tx.Append` на складской поток продукта, со всеми партиями этого продукта и ожидаемой версией, прочитанной под блокировкой.
5. Применение каждого `BatchReceived` к таблице остатков.
6. Запись `DeliveryApproved` в поток поставки с ожидаемой версией из шага 3.

Блокируются потоки всех продуктов поставки, а не только тех, по которым есть принятое количество: набор известен до чтения решений, а лишняя блокировка на время одной транзакции безвредна.

### 5. Таблица остатков партий

```sql
CREATE TABLE inventory_batches (
    id                uuid PRIMARY KEY,
    product_id        uuid        NOT NULL,
    delivery_id       uuid        NOT NULL,
    item_id           uuid        NOT NULL,
    received_quantity bigint      NOT NULL CHECK (received_quantity > 0),
    quantity          bigint      NOT NULL CHECK (quantity >= 0),
    expires_at        timestamptz NOT NULL,
    received_at       timestamptz NOT NULL
);
CREATE INDEX inventory_batches_fefo_idx ON inventory_batches (product_id, expires_at, received_at);
```

Это write model из ADR-002: обновляется в транзакции команды, по ней A4 будет проверять остатки и выбирать партии. `CHECK (quantity >= 0)` - последняя линия защиты инварианта "остаток не уходит в минус". Индекс совпадает с порядком FEFO.

Строки добавляет только функция `applyBatchReceived`. Таблица - функция от событий складских потоков; её перестроение и сверка с Event Store относятся к задаче A9.

Внешнего ключа на `catalog_products` нет: это таблица другого модуля. Существование продукта гарантирует регистрация поставки.

### 6. Интерфейс модуля

```go
type Service struct{ /* runner, pool, catalog */ }
func NewService(runner *command.Runner, pool *pgxpool.Pool, products *catalog.Service) *Service

func (s *Service) RegisterDelivery(ctx, actor, key string, in NewDelivery) (Delivery, error)
func (s *Service) ApproveDelivery(ctx, actor, key string, deliveryID uuid.UUID, decisions []ItemDecision) (Delivery, error)
func (s *Service) Delivery(ctx, id uuid.UUID) (Delivery, error)
func (s *Service) Batches(ctx, productID uuid.UUID) ([]Batch, error)

var ErrNotFound, ErrAlreadyApproved error
type ValidationError struct{ Field, Message string }
```

Неизвестный продукт возвращается как `*catalog.UnknownProductError`: тип уже есть в API каталога, заводить второй такой же незачем.

`inventory` получает `*catalog.Service` напрямую, без промежуточного интерфейса: реализация одна, а тесты используют настоящий каталог на тестовой базе.

### 7. sqlc

В `sqlc.yaml` добавляется второй элемент списка с теми же настройками: запросы `internal/inventory/queries.sql`, результат в `internal/inventory/db`. Запросы: вставка партии и чтение партий продукта в порядке FEFO.

## Risks / Trade-offs

- [Карантин без выхода до A3.1] → количество в карантине недоступно и решения по нему нет. Принято на время между двумя изменениями; A3.1 идёт сразу за заказами или перед ними по решению команды.
- [Чтение потока поставки на каждую команду и каждое чтение] → для потока из нескольких событий это один запрос по индексу. Если потоки поставок станут длинными, вводится снимок; сейчас причин нет.
- [Просрочка определяется по времени приёмки с точностью до момента] → позиция, срок которой истекает через минуту, формально годна. Это следует из ADR-010; период предупреждения о скором истечении относится к мониторингу (B4).
- [Проверка согласованности дат зависит от необязательных полей] → без даты изготовления или срока хранения ошибка в сроке годности не ловится. Это ограничение исходных данных, а не реализации.
- [Блокировка всех продуктов поставки] → большая поставка на время приёмки задерживает заказы по своим продуктам. Время удержания - одна транзакция без сетевых вызовов.

## Open Questions

Нет. Вопрос о решении по карантину закрыт дополнением ADR-010: одна команда на всё карантинное количество позиции, с делением на принятую и отклонённую части. Реализация - в A3.1; модель состояния из решения 2 её поддерживает.
