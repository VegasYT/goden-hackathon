# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде после изменения `backend-foundation`:

- `eventstore.Append(ctx, tx, streamID, expectedVersion, events...)` пишет в переданной транзакции и возвращает `ErrVersionConflict` при несовпадении версии; после нарушения уникальности транзакция непригодна.
- `eventstore.StreamVersion`, `ReadStream`, `Encode`, тип `Actor`.
- `postgres.InTx`, `clock.Clock`, `observability.CorrelationID`.
- `ReadAll` отдаёт события в порядке `(txid, position)`. По ADR-002 этот порядок совпадает с порядком версий потока, только если блокировка взята до первой записи в транзакции: `txid` назначается при первой записи.

## Goals / Non-Goals

**Goals:**

- Доменная команда описывается декларативно, а её корректность по ADR-002 не зависит от аккуратности автора команды.
- Порядок шагов "блокировки, затем первая запись" обеспечен конструкцией, а не правилом в документации.
- Пакет не знает о доменных понятиях: продукт, поставка, заказ.

**Non-Goals:**

- Загрузка агрегатов и синхронные таблицы: каждая команда A2-A5 сама читает нужное состояние внутри функции.
- Метрики и трассировка: A8. Здесь только запись в лог о повторе.
- Очистка таблицы результатов команд. Объём за время проекта мал, срок хранения можно ввести позже без изменения поведения.
- Redis как ускоритель идемпотентности (ADR-003): источник истины всё равно PostgreSQL, ускорение добавляется при измеренной необходимости.

## Decisions

### 1. Интерфейс пакета

```go
package command

type Spec struct {
    Name           string           // имя команды: "RegisterDelivery"
    Actor          eventstore.Actor
    Locks          []string         // идентификаторы потоков, по которым нужна очередь
    IdempotencyKey string           // пусто - команда выполняется при каждом вызове
    Request        any              // содержимое запроса, сравнивается при повторе ключа
}

type Runner struct{ /* pool, clock, logger, maxAttempts */ }
func NewRunner(pool *pgxpool.Pool, clk clock.Clock, logger *slog.Logger) *Runner

func Run[T any](ctx context.Context, r *Runner, spec Spec,
    fn func(ctx context.Context, tx *Tx) (T, error)) (T, error)

type Tx struct{ pgx.Tx /* ... */ }
func (tx *Tx) Append(ctx, streamID string, expectedVersion int64, payloads ...eventstore.Payload) (int64, error)
func (tx *Tx) Now() time.Time
func (tx *Tx) Locked(streamID string) bool

var ErrKeyReused, ErrInvalidSpec error
```

- `Run` - функция, а не метод: методы Go не бывают обобщёнными, а типизированный результат нужен, чтобы сохранить и вернуть его при повторе.
- `Tx` встраивает `pgx.Tx`: команда той же транзакцией читает и меняет свои синхронные таблицы.
- `Tx.Append` принимает доменные события (`eventstore.Payload`), сам сериализует их и заполняет конверт. Прямой вызов `eventstore.Append` из доменного кода остаётся возможным, но не нужен.
- `Tx.Now()` возвращает время, зафиксированное в начале попытки. Одно время на всю команду делает события согласованными и упрощает тесты сроков годности.
- `Tx.Locked` позволяет модулю проверить, что поток, в который он пишет, действительно объявлен. Проверку для `stock-*` добавит inventory в A3.

*Альтернатива:* блокировки по идентификаторам продуктов (`LockProducts []uuid.UUID`). Отклонена: платформа узнала бы о продуктах. Идентификатор потока - понятие Event Store, а `inventory.StockStream(productID)` и есть складской поток из ADR-002.

### 2. Порядок шагов одной попытки

1. Открыть транзакцию.
2. Взять блокировки на объявленные потоки.
3. Если есть ключ идемпотентности: занять его или вернуть сохранённый результат.
4. Выполнить функцию команды.
5. Если есть ключ: сохранить результат.
6. Зафиксировать транзакцию.

Блокировки идут до шага 3 намеренно. Занятие ключа - запись в таблицу, она назначает транзакции `txid`. Если бы ключ занимался до блокировки, транзакция с меньшим `txid` могла бы дождаться блокировки позже соперницы и записать более позднюю версию потока: порядок `(txid, position)` разошёлся бы с порядком версий, и проекции разработчика B получили бы события потока не по порядку. Взятие advisory-блокировки и чтение `txid` не назначают.

### 3. Блокировки

`pg_advisory_xact_lock(hashtextextended($1, 0))` для каждого потока. Потоки перед взятием приводятся к множеству и сортируются как строки; запросы отправляются одним `pgx.Batch`, который выполняется в порядке очереди. Единый порядок исключает взаимные блокировки между командами. Блокировки снимаются автоматически при завершении транзакции.

Совпадение хешей двух разных потоков возможно, но безвредно: такие команды просто встанут в общую очередь.

### 4. Идемпотентность

```sql
CREATE TABLE command_results (
    command_name    text        NOT NULL,
    idempotency_key text        NOT NULL,
    request_hash    text        NOT NULL,
    command_id      uuid        NOT NULL,
    result          jsonb,                 -- NULL, пока команда не завершена
    created_at      timestamptz NOT NULL,
    PRIMARY KEY (command_name, idempotency_key)
);
```

Шаг 3: `INSERT ... ON CONFLICT DO NOTHING`.

- Строка вставлена: ключ свободен, команда выполняется. На шаге 5 в ту же строку записывается результат. Строка и события фиксируются одной транзакцией, поэтому "результат сохранён, а событий нет" невозможно.
- Строка не вставлена: ключ занят завершённой командой. Читается сохранённая строка. Если `request_hash` совпадает, результат десериализуется и возвращается без вызова функции; если нет - `ErrKeyReused`.
- Одновременный вызов с тем же ключом ждёт на первичном ключе, пока первая транзакция не завершится. Если та зафиксирована, срабатывает ветка "ключ занят"; если отменена, вставка проходит и команда выполняется.

`request_hash` - SHA-256 от JSON поля `Spec.Request`. Результат `T` хранится как JSON, поэтому тип результата должен сериализоваться в JSON и обратно без потерь.

Таблица - техническое состояние стороны записи, а не проекция: из событий она не восстанавливается и в replay не участвует. Это не противоречит ADR-002: бизнес-состояния в ней нет.

*Альтернатива:* хранить ключ в метаданных события и искать по нему. Отклонена: команда может не создать ни одного события (отказ в заказе создаёт, а проверка без изменений - нет), и поиск по `jsonb` потребовал бы отдельного индекса.

### 5. Повтор

Попытка повторяется, если ошибка - `eventstore.ErrVersionConflict` или код PostgreSQL `40P01` (взаимная блокировка) или `40001` (сбой сериализации). Попыток три, между ними нет паузы: блокировки уже упорядочивают команды по складским потокам, а для остальных потоков (поставка, заказ) повторное чтение обычно сразу приводит к доменной ошибке вида "уже принято".

Идентификатор команды создаётся один раз на вызов `Run` и не меняется между попытками. После исчерпания попыток возвращается последняя ошибка с обёрткой, сохраняющей `errors.Is(err, eventstore.ErrVersionConflict)`. Каждый повтор пишется в лог уровнем `warn` с именем команды и номером попытки.

### 6. Конверт события

| Поле | Значение |
| --- | --- |
| `ID` | новый UUIDv7 |
| `OccurredAt` | `Tx.Now()`, время начала попытки из `clock.Clock` |
| `CorrelationID` | из контекста через `observability.CorrelationID`; если нет, создаётся один на вызов `Run` |
| `CausationID` | идентификатор команды |
| `Metadata` | `{"actor": {"type": ..., "id": ...}, "command": "<имя>"}` |

Автор действия дублируется в метаданных, хотя часть событий уже несёт его в содержимом. В содержимом автор - часть бизнес-факта ("кто принял поставку"), в метаданных - единый для всех событий след для аудита, которому не нужно знать структуру каждого типа.

### 7. Размещение и границы

Пакет лежит в `internal/platform/command` и импортирует только `eventstore`, `clock`, `observability`. Правило `depguard` для `platform` уже запрещает ему доменные модули. Таблица `command_results` принадлежит пакету; доменные модули к ней не обращаются.

## Risks / Trade-offs

- [Команда пишет в складской поток, не объявив его] → порядок событий потока для читателей может нарушиться. Платформа этого не видит: она не знает, какие потоки складские. Смягчение: `Tx.Locked` и проверка в inventory (A3), правило в `AGENTS.md`.
- [Набор потоков нужно знать до начала транзакции] → для заказа он зависит от рецептур, которые могут измениться между чтением и блокировкой. Смягчение в A4: функция команды перечитывает рецептуры внутри транзакции и, если набор продуктов вышел за объявленный, возвращает конфликт, который приводит к повтору с новым набором. Механизм повтора для этого уже есть.
- [Долгая функция команды держит блокировку] → очередь по популярному продукту растёт. Смягчение: правило из ADR-002 "внутри транзакции нет сетевых вызовов"; время ожидания ограничено контекстом вызова.
- [Таблица `command_results` растёт без очистки] → принято, см. Non-Goals.
- [Результат команды должен переживать JSON] → структуры результата проектируются как простые DTO; тест идемпотентности сравнивает результат повтора с исходным.
