# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- `httpx.Health` собирает `ServeMux` с `/healthz` и `/readyz`; им пользуются все три процесса. `httpx.AccessLog` уже измеряет время запроса и пишет путь.
- Сервер ogen умеет найти операцию по методу и пути (сгенерированный поиск маршрута) и даёт имя операции в свои middleware.
- `command.Run` - единственная точка выполнения команд: в ней повторы, идемпотентность и исход.
- Бизнес-события пишут три сервиса: `orders.PlaceOrder`, `inventory` (поставки, списания), `catalog`.
- Генератор выполняет действия в `Simulator.act`.
- Интеграция ogen с OpenTelemetry отключена в `ogen.yml` с пометкой "до A8".
- Проекций, publisher и контроля сроков ещё нет.

## Goals / Non-Goals

**Goals:**

- Метрики объявляются рядом с кодом, который их меняет, и не требуют прокидывать зависимости через все конструкторы.
- Число серий ограничено: в метках только значения из закрытых наборов.
- Тесты проверяют значения метрик, не завися друг от друга.

**Non-Goals:**

- Трассировка и OpenTelemetry.
- Метрики стороны чтения и Kafka.
- Оповещения и сбор логов.

## Decisions

### 1. client_golang и один реестр процесса

Метрики объявляются через `client_golang`. Реестр - не глобальный по умолчанию, а собственный, создаваемый в `observability.NewMetrics()`; в него же добавляются стандартные сборщики процесса и Go. Модули получают реестр в конструкторе и регистрируют в нём свои метрики.

*Альтернатива:* глобальный реестр и `promauto`. Отклонена: интеграционные тесты поднимают несколько экземпляров API в одном процессе, и повторная регистрация одной метрики в глобальном реестре завершается паникой; со своим реестром у каждого экземпляра свои счётчики, и тест читает значения без влияния соседних тестов.

*Альтернатива:* OpenTelemetry с экспортом в Prometheus, включив интеграцию ogen. Отклонена: тянет заметный набор зависимостей ради метрик HTTP, а бизнес-счётчики всё равно пришлось бы объявлять отдельно. Пометка в `ogen.yml` меняется: интеграция остаётся отключённой осознанно.

Чтобы не менять сигнатуры конструкторов, реестр создаёт сам `command.Runner` и отдаёт методом `Registry()`: он уже есть у каждого сервиса записи, а в процессе один. Сервис в конструкторе регистрирует свои метрики; `internal/api` добавляет метрики HTTP и пула и отдаёт этот же реестр на `/metrics`. Процессы без команд (`generator`, пока и `worker`) создают реестр сами.

### 2. Имена и метки

Префикс `goden_`. Имена по соглашениям Prometheus: счётчики с `_total`, время в секундах.

| Метрика | Тип | Метки |
| --- | --- | --- |
| `goden_http_requests_total` | счётчик | `operation`, `status` |
| `goden_http_request_duration_seconds` | гистограмма | `operation` |
| `goden_commands_total` | счётчик | `command`, `outcome` (`ok`, `replayed`, `error`, `exhausted`) |
| `goden_command_retries_total` | счётчик | `command` |
| `goden_events_appended_total` | счётчик | `type` |
| `goden_stock_written_off_quantity_total` | счётчик | `reason`, `unit` |
| `goden_stock_write_offs_total` | счётчик | `reason` |
| `goden_db_pool_connections` | датчик | `state` (`max`, `acquired`, `idle`) |
| `goden_db_pool_waits_total` | счётчик | - |
| `goden_generator_actions_total` | счётчик | `action`, `outcome` |
| `goden_generator_orders_total` | счётчик | `status` |

Исходы команды: `ok` - выполнена; `replayed` - возвращён сохранённый результат по ключу идемпотентности; `error` - завершилась ошибкой без повторов (как правило, отклонена правилом предметной области); `exhausted` - повторы после конфликтов исчерпаны.

Изменено при реализации: отдельных счётчиков заказов и поставок нет. Их заменяет один счётчик записанных событий по типу: принятый заказ - это событие `OrderAccepted`, отклонённый - `OrderRejected`, поставки - `DeliveryRegistered` и `DeliveryApproved`. Он считается в одном месте (`Tx.Append`) без кода в модулях, набор меток закрыт реестром событий, и он же даёт скорость записи в Event Store, которую требует ADR-007. Отдельные счётчики остались только у списаний: причина и единица продукта в тип события не входят.

Количество списаний считается в единицах продукта, поэтому единица - метка: складывать граммы со штуками нельзя. Продукт меткой не делается: число серий росло бы с каталогом.

### 3. Метрики HTTP

Middleware в `internal/api`, а не в `httpx`: имя операции знает только сгенерированный сервер. Middleware до вызова обработчика находит операцию по методу и пути; если операция не найдена, метка - `unknown`. Статус берётся тем же приёмом, что в `AccessLog`. Запросы к `/metrics`, `/healthz`, `/readyz` в метрики API не попадают: middleware стоит только на префиксе API.

Границы гистограммы - от 5 мс до 5 с: команды под блокировками обычно укладываются в десятки миллисекунд.

### 4. Метрики команд и бизнес-счётчики

`command.Run` увеличивает `goden_commands_total` один раз на вызов и `goden_command_retries_total` на каждый повтор.

Счётчики, зависящие от результата команды, увеличиваются через `tx.OnCommit`: отложенное действие выполняется после успешной фиксации транзакции. Попытка, которая откатилась или повторилась, и ответ из сохранённого результата его не вызывают. Существующие вызовы `command.Run` не меняются.

*Альтернатива:* считать в функции команды внутри транзакции. Отклонена: функция может выполняться несколько раз при повторах, а транзакция - откатиться.

*Альтернатива:* выводить бизнес-метрики из событий в проекторе. Это правильнее для показателей вроде "истекающие партии", но движка проекций нет; счётчики стороны записи не требуют его.

Счётчики теряются при перезапуске процесса, как любые счётчики Prometheus: графики строятся по скорости роста, а не по абсолютному значению.

### 5. Пул соединений

Собственный сборщик в `observability`, читающий `pgxpool.Pool.Stat()` при каждом опросе. Готовая библиотека не подключается: это два десятка строк.

### 6. Эндпоинт

`httpx.Health` получает необязательный обработчик метрик и вешает его на `GET /metrics`. Процесс без реестра эндпоинт не отдаёт. `worker` пока отдаёт только метрики процесса и пула.

### 7. Окружение

В `infra/compose.yaml` добавляются:

- **Prometheus** (порт 9090, `PROMETHEUS_PORT`): конфигурация в `infra/prometheus/prometheus.yml`, цели - `host.docker.internal:8080`, `:8081`, `:8082`, опрос раз в 5 секунд. Для Linux добавляется `extra_hosts: host.docker.internal:host-gateway`.
- **Grafana** (порт 3000, `GRAFANA_PORT`): источник данных и дашборд подключаются файлами из `infra/grafana/`; вход без пароля с правами просмотра и редактирования, только локально.

Дашборд "Goden backend": запросы в секунду по операциям, доля ошибок, время ответа (p50, p95), заказы принятые и отклонённые, поставки, списания по причинам, повторы команд, пул соединений, действия генератора.

Данные Prometheus и Grafana не сохраняются между пересозданиями контейнеров: всё нужное лежит в файлах репозитория.

Теги образов закрепляются при реализации по доступным на тот момент.

### 8. Серии с нулём

Выяснилось при проверке на окружении: `increase()` в Prometheus не видит прироста, если серия впервые появилась уже со значением 1, и панель списаний показывала ноль после первого списания. Серии счётчика списаний по причинам создаются при старте с нулём. У счётчика событий по типам серии не создаются заранее: теряется только первое событие каждого типа после запуска процесса, на графиках скорости это незаметно.

## Risks / Trade-offs

- [`/metrics` открыт без токена] → как `/healthz`; в метках нет идентификаторов. Наружу порт процесса не выставляется.
- [Счётчики бизнес-событий живут в памяти процесса] → после перезапуска начинаются с нуля; точные числа за период даст аналитика по событиям (задача B8).
- [Несколько экземпляров API дают каждый свои счётчики] → Prometheus суммирует по цели; дашборд агрегирует.
- [Prometheus в контейнере не достанет процесс, слушающий только `127.0.0.1`] → процессы backend по умолчанию слушают все интерфейсы; в документации это оговаривается.
- [Порт 3000 может быть занят] → `GRAFANA_PORT`.
- [Метрик стороны чтения нет] → появятся с задачами B1, B4, B6; ADR-007 по ним пока не выполнен, в `backend/plan.md` это записано.
