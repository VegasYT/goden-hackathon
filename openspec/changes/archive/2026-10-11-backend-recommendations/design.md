# Design

## Context

Готово и используется как есть: `stoplist.Service.Menu` (блюда с рецептурами и числом порций), `inventory.Service.ExpiringBatches` (партии с остатком по сроку), `inventory.Service.Stock` (доступный остаток продукта). Заказ списывает партии по FEFO, поэтому проданная порция расходует именно ближайшую по сроку партию. Папка `internal/recommendations` заведена и пуста.

## Decisions

### 1. Расчёт при чтении, без проекций

Обе рекомендации зависят от текущего времени (сколько осталось до срока, расход за последние часы), поэтому считаются при запросе. Решение выведено из правила `backend/AGENTS.md`, а не задано пользователем.

### 2. Формула горячих предложений

Продукт под риском - продукт, у которого есть партии с остатком, истекающие в пределах горизонта `H`. Для него:

- `R` - количество под риском: сумма остатков таких партий;
- `срочность` - средневзвешенная по количеству величина `1 - осталось / H` по этим партиям: 0 у партии на границе горизонта, 1 у партии, истекающей сейчас.

Вклад продукта в приоритет блюда, у которого на порцию идёт `q` продукта и можно приготовить `P` порций:

```text
вклад = срочность * охват * значимость * исключительность

охват            = min(1, P * q / R)      какую долю риска блюдо способно израсходовать
значимость       = min(1, R / q)          риск меньше одной порции - вклад ниже
исключительность = (1 + 1 / n) / 2        n - сколько доступных блюд используют продукт
```

Приоритет блюда - сумма вкладов его продуктов под риском, умноженная на 100 и округлённая. Число порций к продаже - наибольшее по продуктам `min(P, ceil(R / q))`.

Почему так:

- все множители лежат в `[0, 1]` и не зависят от единицы измерения, поэтому граммы, миллилитры и штуки сравнимы;
- сумма, а не максимум: блюдо, спасающее два продукта, полезнее;
- исключительность не обнуляет вклад при большом `n`: продукт, который используется в пяти блюдах, всё ещё нужно продавать, просто каждое из них менее критично;
- каждый множитель назван и возвращается в причине, так что рейтинг объясним.

*Альтернатива:* машинно подобранные веса или денежная оценка потерь. Отклонена: цен в системе нет, а объяснимость формулы для повара и официанта важнее точности.

Функция расчёта чистая: принимает меню, партии под риском, текущее время и горизонт.

### 3. Рекомендации поставок: запас по времени

Расход продукта за период `W` считается суммой по событиям `StockConsumed`; списания и корректировки в расход не входят - это не спрос. `скорость = расход / W`, `хватит на = доступно / скорость`.

Продукт рекомендуется, если `хватит на < запас`, либо если доступного остатка нет, а продукт есть в рецептуре. Количество: `скорость * целевой запас - доступно`; для продукта без расхода за период - количество на 10 порций самого "жадного" блюда, в котором он используется. Это число - ориентир, а не расчёт: без истории спроса точнее не посчитать.

*Альтернатива:* фиксированный минимальный остаток у продукта в каталоге. Отклонена в proposal: требует нового события каталога и ручной настройки каждого продукта.

### 4. Расход читается из Event Store запросом

`inventory.Service.Consumption(ctx, since)` - один агрегирующий запрос по событиям `StockConsumed` за период. Таблицу событий читает модуль-владелец события.

*Альтернатива:* проекция расхода по часам. Отложена: на учебном объёме запрос по событиям дёшев, а проекция понадобится аналитике (B8) - тогда рекомендации перейдут на неё. В коде место отмечено как известный предел: запрос просматривает все события периода.

### 5. Контракт

- `listDishRecommendations`: `GET /recommendations/dishes`, параметры `horizon_hours` (72), `limit`, `offset`.
- `listDeliveryRecommendations`: `GET /recommendations/deliveries`, параметры `window_hours` (24), `cover_hours` (24), `target_hours` (72), `limit`, `offset`.

Целевой запас меньше запаса - ошибка предметной области (422): границы каждого параметра проверяет контракт, а их соотношение - сервис.

## Risks / Trade-offs

- [Формула эвристическая] → все множители возвращаются в ответе; веса не подбирались по данным.
- [Сразу после запуска расход за период мал или равен нулю] → рекомендации поставок опираются на отсутствие остатка; оценка "хватит на" появляется по мере накопления заказов.
- [Количество под риском делится между блюдами не строго] → каждое блюдо считает, что может израсходовать весь риск; сумма рекомендованных порций по блюдам может превышать необходимое. Множитель исключительности смягчает это, резервирования нет.
