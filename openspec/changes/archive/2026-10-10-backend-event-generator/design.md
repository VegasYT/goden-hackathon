# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- Контракт из 18 операций и сгенерированный клиент `oas.Client`: все действия генератора покрыты операциями каталога, поставок и заказов.
- Сквозной тест `TestScenarioFromCatalogToOrders` - образец последовательности вызовов.
- `cmd/worker` - образец процесса с health-эндпоинтами и корректным завершением; `httpx.Serve`, `httpx.Health`, `config.Load`.
- `apitest.New` поднимает API на тестовой базе и возвращает клиент.
- Правило `backend/AGENTS.md`: новый модуль получает правило `depguard` для подпакета `db` и запись в `sqlc.yaml`.
- Авторизации нет: все запросы идут от имени пользователя `dev`.

## Goals / Non-Goals

**Goals:**

- Генератор - обычный клиент API: он не импортирует ни одного доменного модуля, кроме своего, и не имеет доступа к базе.
- Поведение симуляции воспроизводимо в тестах: источник случайности и часы передаются снаружи.
- Управление генератором идёт через тот же API, что и всё остальное: у frontend один адрес и одна будущая авторизация.

**Non-Goals:**

- Реалистичная модель спроса. Достаточно правдоподобного потока с известными долями проблемных случаев.
- Статистика и история работы генератора в API. Что он сделал, видно по событиям системы.
- Несколько экземпляров генератора с распределением нагрузки.

## Decisions

### 1. Настройки хранит API, генератор их опрашивает

Настройки лежат в базе и доступны через две операции контракта. Процесс генератора раз в период опроса (по умолчанию 2 секунды) читает их через клиент и подстраивается.

*Альтернатива:* собственный HTTP-интерфейс управления у процесса генератора. Отклонена: frontend пришлось бы ходить на второй адрес с отдельным CORS и отдельной авторизацией, а состояние "запущен" терялось бы при перезапуске процесса. При выбранном варианте право `generator.manage` из ADR-012 позже навешивается на обычную операцию API.

Операции: `getGeneratorSettings` (`GET /generator`) и `updateGeneratorSettings` (`PUT /generator`). Схема `GeneratorSettings`: `running`, `deliveries_per_minute`, `orders_per_minute` (оба 0..600), `updated_at` только для чтения.

### 2. Модуль generator

```text
internal/generator/
  settings.go     тип Settings, сервис чтения и изменения настроек
  http.go         обработчики двух операций настроек
  queries.sql     чтение и изменение единственной строки; код sqlc в db/
  simulator.go    сценарии: поставка, заказ; цикл Run
  seed.go         демонстрационный каталог
```

Модуль используется двумя процессами: `cmd/api` берёт из него настройки и обработчики, `cmd/generator` - симулятор. Симулятор зависит только от сгенерированного клиента; сервис настроек - только от пула. Друг о друге они не знают.

Таблица настроек - одна строка с ограничением, не позволяющим создать вторую. Это техническое состояние, а не бизнес-данные: событий для него нет, как и для таблицы результатов команд.

### 3. Симулятор

```go
type API interface { /* методы oas.Client, которые нужны симулятору */ }

type Simulator struct{ /* api API, clock clock.Clock, rng *rand.Rand, logger */ }

func (s *Simulator) Seed(ctx) error               // наполнить пустой каталог
func (s *Simulator) Deliver(ctx) error            // одна поставка по полному пути
func (s *Simulator) Order(ctx) error              // один заказ
func (s *Simulator) Run(ctx, poll, tick time.Duration) error
```

`API` - интерфейс из нужных методов клиента: в рабочем процессе его реализует `*oas.Client`, а в тесте недоступности - обёртка, возвращающая ошибки.

`Deliver` и `Order` - по одному действию за вызов: тесты вызывают их напрямую и проверяют результат в системе, без ожидания таймеров.

**Поставка.** От одной до трёх позиций разных продуктов. Количество зависит от единицы измерения: для граммов и миллилитров - тысячи, для штук - десятки. Срок годности: текущее время плюс срок хранения продукта из каталога (если он не задан, 7 дней). Проблемные позиции:

- с вероятностью 10% позиция уже просрочена: срок годности в прошлом; при приёмке она отклоняется целиком с причиной `expired`;
- с вероятностью 15% пятая часть годной позиции уходит в карантин; сразу после приёмки генератор принимает по нему решение: в половине случаев принимает всё, в половине - отклоняет всё.

Дата изготовления не передаётся: проверка согласованности дат со сроком хранения отклонила бы намеренно просроченные позиции ещё на регистрации.

**Заказ.** Одно или два блюда с рецептурой, от одной до трёх порций. С вероятностью 10% число порций завышается до сотен: такой заказ система отклоняет.

Доли вынесены в константы пакета. Настройками API они не управляются: это свойства сценария, а не режим работы.

**Цикл `Run`.** Раз в `poll` читаются настройки, раз в `tick` (по умолчанию 1 секунда) выполняются накопившиеся действия. Сколько действий выполнить, считает накопитель: за каждый тик к нему прибавляется `интенсивность в минуту * tick / минута`, целая часть выполняется, дробная переносится. Так 12 поставок в минуту дают одну поставку каждые пять тиков без дрейфа. За один тик выполняется не больше ограниченного числа действий, чтобы после долгой недоступности API генератор не выстрелил всем накопленным сразу.

Действия выполняются последовательно в одном потоке. Параллельная нагрузка для проверки блокировок - задача A9.

### 4. Наполнение каталога

`Seed` запрашивает список продуктов с `limit=1`. Если общее число больше нуля, ничего не делает. Иначе создаёт набор: около десяти продуктов с единицами и сроками хранения и пять блюд с рецептурами.

Запросы наполнения несут постоянные ключи идемпотентности вида `seed-product-<номер>` (имя в ключ не годится: формат ключа - латиница и цифры). Если запрос наполнения завершился ошибкой, процесс повторяет наполнение при следующем опросе: признак "наполнение начато" он держит в памяти, а постоянные ключи не дают создать дубликаты. Имена демонстрационных продуктов на русском: это данные интерфейса.

Изменено при реализации: первоначально предполагалось продолжать наполнение и после перезапуска процесса, по признаку "продукты есть, блюд с рецептурой нет". Это противоречит требованию не менять непустой каталог: так выглядит и каталог, в который пользователь завёл только продукты. Поэтому после падения процесса посреди наполнения каталог остаётся неполным; исправляется пересозданием базы.

### 5. Устойчивость

Каждое действие - отдельный вызов с собственным таймаутом. Ошибка действия пишется в лог уровнем `warn` и не прерывает цикл. Запросы на запись несут случайный ключ идемпотентности; повторов запросов внутри действия нет: следующее действие всё равно наступит через долю секунды.

Отклонённый заказ - успешный результат действия: он считается и логируется уровнем `debug`.

`/readyz` процесса отвечает 200, если последний опрос настроек прошёл успешно.

### 6. Процесс cmd/generator

Переменные окружения: `API_URL` (по умолчанию `http://localhost:8080/api/v1`), `HTTP_ADDR` для health (по умолчанию `:8082`), `GENERATOR_SEED` (по умолчанию `true`), `GENERATOR_POLL_INTERVAL` (по умолчанию `2s`), `LOG_LEVEL`. `DATABASE_URL` процессу не нужен и не читается: это и есть проверка требования "не обращается к базе данных".

### 7. Сборка и правила

- `api.New` создаёт сервис настроек и встраивает `*generator.HTTP` четвёртым обработчиком под псевдонимом.
- В `.golangci.yml` добавляется правило `depguard` для `internal/generator/db` и модуль в список запрещённых для `platform`.
- В `sqlc.yaml` добавляется пакет модуля.
- Миграция получает следующий по порядку номер.

## Risks / Trade-offs

- [Нет сервисной учётной записи и права `generator.manage`] → отступление от ADR-012 до задачи A7. Настройки генератора может менять любой клиент, как и всё остальное сейчас.
- [Сроки годности в днях] → за время демо партии генератора не успеют истечь сами; просрочку показывают только намеренно просроченные позиции, которые отклоняются при приёмке. Истечение партий на складе генератор не демонстрирует. Команда приняла это при обсуждении плана.
- [Последовательные действия] → генератор не создаёт конкурентной нагрузки; интенсивность ограничена временем ответа API. 600 действий в минуту - потолок настройки, а не гарантия.
- [Склад может опустеть или переполниться] → соотношение поставок и заказов задаёт оператор интенсивностями. Пустой склад даёт поток отказов, что тоже демонстрирует стоп-лист.
- [Случайность усложняет тесты] → источник случайности передаётся в конструктор; тесты проверяют инварианты (нет открытого карантина, просроченное не принято), а не конкретные значения.
- [Опрос настроек раз в 2 секунды] → задержка реакции на кнопку до двух секунд. Приемлемо для ручного управления.
