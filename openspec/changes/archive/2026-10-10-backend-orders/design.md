# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- `orders/events.go`: `OrderAccepted`, `OrderRejected` с `Shortage`, функция `OrderStream`.
- `inventory`: таблица `inventory_batches` с индексом FEFO, событие `StockConsumed`, `Service.Batches`, приём `receiveBatches` как образец записи в складские потоки под блокировкой с проверкой `tx.Locked`.
- `catalog.Service.Dish` читает блюдо с рецептурой через пул.
- `command.Run`: блокировки из `Spec.Locks` берутся до начала функции команды и на время одного вызова `Run` неизменны; при конфликте версий функция вызывается заново с теми же блокировками.
- Правило `depguard`: чужой модуль не импортирует `inventory/db` и `catalog/db`.

## Goals / Non-Goals

**Goals:**

- Алгоритм FEFO - чистая функция, проверяемая unit-тестами без базы данных.
- Таблицу остатков читает и меняет только модуль `inventory`.
- Заказ корректен при параллельной нагрузке генератора без повторов из-за конфликта версий.

**Non-Goals:**

- Резервирование продуктов без списания, отмена и изменение заказа: в кейсе и ADR заказ сразу списывает продукты.
- Частичное выполнение заказа: по ADR-002 при нехватке ингредиента заказ не меняет склад.
- Списки заказов и стоп-лист: проекции разработчика B.

## Decisions

### 1. Списание принадлежит складу

Заказ не читает партии сам. Он передаёт складу потребность и получает либо подтверждение списания, либо список нехваток:

```go
// inventory
type Need struct{ ProductID uuid.UUID; Quantity int64 }
type Shortage struct{ ProductID uuid.UUID; Required, Available int64 }

func (s *Service) ConsumeForOrder(ctx, tx *command.Tx, orderID uuid.UUID, needs []Need) ([]Shortage, error)
```

`ConsumeForOrder` работает в транзакции вызывающей команды: читает доступные партии всех продуктов, решает по каждому, и только если хватает всех, записывает события `StockConsumed` и уменьшает остатки. При нехватке возвращает непустой список и ничего не пишет. Для каждого продукта проверяется `tx.Locked(StockStream(id))`: вызов без блокировки - ошибка программиста, а не данных.

Так выбор партий, исключение просроченных и обновление таблицы остатков живут в одном модуле вместе с её схемой. Тем же методом позже сможет воспользоваться любая другая команда, расходующая продукты.

*Альтернатива:* заказ сам читает `inventory_batches` и пишет `StockConsumed`. Отклонена: нарушает границу модулей и размазывает правило FEFO по двум местам.

### 2. Чистая функция FEFO

```go
// inventory/stock.go
func planConsumption(batches []Batch, need int64, now time.Time) (taken []BatchQuantity, available int64)
```

На вход - партии продукта в порядке FEFO и потребность. Функция пропускает партии с нулевым остатком и просроченные (`expires_at` не позже `now`), считает доступный остаток и, если его хватает, набирает потребность по партиям подряд. Если не хватает, возвращает пустой список и доступное количество.

Порядок партий задаёт запрос: `ORDER BY product_id, expires_at, received_at, id`. Идентификатор в конце делает порядок полностью определённым при равных сроках и времени поступления.

### 3. Ход команды PlaceOrder

1. Проверка состава до транзакции: не пуст, порции положительны, блюда не повторяются.
2. Чтение блюд из каталога через пул. Нет блюда - `UnknownDishError`; нет рецептуры - `DishWithoutRecipeError`.
3. Расчёт потребности по продуктам; `Spec.Locks` - складские потоки этих продуктов.
4. В транзакции под блокировками: повторное чтение блюд в этой же транзакции и повторный расчёт потребности.
5. Если новый набор продуктов вышел за набор блокировок, функция возвращает внутреннюю ошибку "рецептуры изменились", транзакция откатывается, шаги 2-4 повторяются с новым набором. Попыток три.
6. `inventory.ConsumeForOrder`.
7. Нет нехваток: `tx.Append(OrderStream(id), 0, OrderAccepted{...})`. Есть: `tx.Append(OrderStream(id), 0, OrderRejected{...})` со списком нехваток. В обоих случаях транзакция фиксируется.

Шаги 4-5 закрывают ограничение из изменения `backend-command-execution`: набор блокировок нужно знать до транзакции, а рецептура может измениться между чтением и блокировкой. Повторное чтение под блокировкой гарантирует, что списание идёт по актуальной рецептуре и только по заблокированным потокам. Если рецептура изменилась, но набор продуктов остался в пределах блокировок, повтор не нужен: потребность просто считается по новой рецептуре.

Отказ - не ошибка: команда возвращает заказ со статусом "отклонён" и транзакция фиксируется. Иначе событие `OrderRejected` откатилось бы вместе с транзакцией, а по нему разработчик B считает статистику дефицита. Отсюда же следует, что результат отказа сохраняется под ключом идемпотентности, как и результат принятия.

### 4. Чтение каталога в транзакции

```go
// catalog
type Querier = db.DBTX
func (s *Service) DishIn(ctx context.Context, q Querier, id uuid.UUID) (Dish, error)
```

`Dish` становится обёрткой над `DishIn` с пулом. `Querier` - псевдоним интерфейса из сгенерированного пакета; ему удовлетворяют и пул, и `*command.Tx`. Подпакет `catalog/db` при этом наружу не выходит: `orders` импортирует только `catalog`.

### 5. Интерфейс модуля orders

```go
type Service struct{ /* runner, pool, catalog, stock */ }
func NewService(runner *command.Runner, pool *pgxpool.Pool, dishes *catalog.Service, stock *inventory.Service) *Service

func (s *Service) PlaceOrder(ctx, actor eventstore.Actor, key string, items []OrderItem) (Order, error)
func (s *Service) Order(ctx, id uuid.UUID) (Order, error)

type Order struct {
    ID        uuid.UUID
    Status    OrderStatus // "accepted" | "rejected"
    Items     []OrderItem
    Shortages []Shortage  // только у отклонённого
}

var ErrNotFound error
type ValidationError struct{ Field, Message string }
type UnknownDishError struct{ DishID uuid.UUID }
type DishWithoutRecipeError struct{ DishID uuid.UUID }
```

`OrderItem` и `Shortage` - типы из `events.go`: у результата и события одинаковые поля, второй набор типов не нужен.

Состояние заказа для `Order` собирается из его потока, как у поставки: в потоке ровно одно событие.

Файлы: `order.go` - типы, проверка состава, чистый расчёт потребности `requirements(dishes, items)`; `service.go` - команда и чтение. Таблиц и запросов у модуля нет, sqlc для него не настраивается.

### 6. Изменения в inventory

- `stock.go`: типы `Need`, `Shortage`, функция `planConsumption`.
- `service.go`: `ConsumeForOrder`, функция применения `applyStockConsumed`.
- `queries.sql`: чтение доступных партий набора продуктов в порядке FEFO, уменьшение остатка партии.

`applyStockConsumed` уменьшает остаток запросом `UPDATE ... SET quantity = quantity - $2`. Ограничение `CHECK (quantity >= 0)` остаётся последней линией защиты: при ошибке в расчёте транзакция упадёт, а не уведёт остаток в минус.

Запрос доступных партий фильтрует только `quantity > 0`. Просрочку отсекает `planConsumption`: правило "не позже момента проверки" записано в одном месте и покрыто unit-тестом.

## Risks / Trade-offs

- [Заказ с популярным продуктом задерживает другие заказы с ним] → очередь по продукту задана ADR-002. Время под блокировкой - одна транзакция: чтение партий, несколько вставок и обновлений.
- [Чтение блюд дважды: до транзакции и внутри] → два лишних запроса на блюдо. Без первого чтения неизвестен набор блокировок, без второго рецептура могла устареть.
- [Отклонённый заказ занимает ключ идемпотентности] → повтор с тем же ключом после пополнения склада вернёт прежний отказ. Это стандартная семантика ключа; клиент оформляет новый заказ с новым ключом. Записано в спецификации отдельным сценарием.
- [Рецептура меняется три раза подряд между чтением и блокировкой] → заказ возвращает ошибку конфликта. На практике недостижимо: рецептуры меняются редко.
- [Просроченная партия с остатком остаётся в таблице] → она не расходуется, но и не списывается: списание просрочки - задача A5 и B4.
- [Переполнение при умножении порций на количество] → не проверяется: значения ограничены здравым смыслом и валидацией API.
