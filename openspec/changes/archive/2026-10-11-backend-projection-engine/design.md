# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- `eventstore.ReadAll(ctx, q, after, limit)` читает события в порядке `(txid, position)` ниже `pg_snapshot_xmin`; принимает и пул, и транзакцию. `Event.Checkpoint()` даёт позицию.
- Таблицы записи (`inventory_batches`, `catalog_*`) обновляются синхронно в командах и проекциями не являются.
- `cmd/worker` - каркас: функция `tasks` возвращает фоновые задачи, сейчас их нет; у процесса есть `/metrics`.
- Метрики регистрируются через `observability.Register` в реестре процесса.
- Тестовые опоры: `pgtest.NewDB`, `estest.Append` и `estest.AppendAt` кладут события без команд.
- ADR-009: несколько проекторов могут работать параллельно только с безопасным разделением потоков и checkpoints.

## Goals / Non-Goals

**Goals:**

- Автор проекции пишет только "что сделать с событием" и "как очистить свои таблицы".
- Событие применяется ровно один раз без требований идемпотентности к автору проекции.
- Тесты проекций детерминированы: можно синхронно догнать до конца.

**Non-Goals:**

- Параллельное применение событий внутри одной проекции.
- Проекции вне PostgreSQL (Redis, поисковый индекс): у них нет общей транзакции с checkpoint.
- Доставка в Kafka.

## Decisions

### 1. Описание проекции

```go
type Projection struct {
    Name    string // ключ checkpoint и метка метрик
    Version int    // смена версии запускает перестроение
    // Apply применяет событие в транзакции движка. События, которые проекции не нужны, она пропускает сама.
    Apply func(ctx context.Context, tx pgx.Tx, e eventstore.Event) error
    // Reset очищает таблицы проекции перед перестроением.
    Reset func(ctx context.Context, tx pgx.Tx) error
}
```

Событие передаётся как записано, вместе с конвертом: проекциям нужны время события, автор и correlation ID. Декодирует содержимое сама проекция через `eventstore.Decode`.

*Альтернатива:* интерфейс с методами. Отклонена: структура с двумя функциями короче, а состояние проекции лежит в её таблицах, а не в объекте.

### 2. Порция

Одна итерация - одна транзакция:

1. заблокировать строку checkpoint проекции (`SELECT ... FOR UPDATE`);
2. если версия в строке отличается от версии в коде - вызвать `Reset`, обнулить позицию, записать новую версию;
3. прочитать порцию событий после позиции через `eventstore.ReadAll` в этой же транзакции;
4. применить каждое через `Apply`;
5. записать позицию последнего события;
6. зафиксировать.

Ошибка на любом шаге откатывает всё. Блокировка строки (шаг 1) делает второй экземпляр процесса безопасным: он ждёт на блокировке, а получив её, читает уже сдвинутую позицию. Это выполняет условие ADR-009 без распределения потоков между экземплярами.

*Альтернатива:* advisory-блокировка на всё время жизни процесса ("лидер"). Отклонена: при зависании лидера проекция останавливается до его перезапуска, а блокировка строки на время порции обходится без выбора лидера.

Чтение внутри той же транзакции безопасно: граница `pg_snapshot_xmin` вычисляется по снимку запроса, и события ниже неё уже неизменны.

Размер порции - 200 событий. При перестроении это ограничивает длину транзакции: перестроение идёт порциями, шаг 2 выполняется один раз, дальше обычные итерации.

### 3. Цикл

`Run(ctx)` повторяет порции. Если порция вернула меньше событий, чем её размер, движок ждёт период опроса (по умолчанию 200 мс) и повторяет. Ошибка порции пишется в журнал, счётчик ошибок растёт, следующая попытка - с нарастающей паузой до 5 секунд. Цикл завершается только по отмене контекста.

*Альтернатива:* `LISTEN/NOTIFY` вместо опроса. Отложена: задержка до 200 мс для экранов склада приемлема, а уведомления требуют отдельного соединения и не отменяют опрос как страховку.

`CatchUp(ctx)` выполняет порции, пока за позицией проекции не останется ни одного события, и возвращается. Им пользуются тесты, а в B2 - тестовая обвязка API, чтобы чтение после записи в тесте было детерминированным.

Уточнено при реализации: первая версия `CatchUp` возвращалась, как только очередная порция оказывалась неполной. Тесты от этого изредка падали: событие зафиксировано, но ещё не читается, потому что его задерживает чужая незавершённая транзакция в кластере (служебная или соседнего теста), и `CatchUp` уходил, ничего не применив. Теперь он ждёт, пока число событий за позицией не станет нулевым.

Перед порцией движок без транзакции проверяет, есть ли что читать. Иначе холостой опрос каждые 200 мс блокировал бы строку позиции и расходовал номера транзакций.

### 4. Хранение позиции

```sql
CREATE TABLE projection_checkpoints (
    name       text PRIMARY KEY,
    version    integer     NOT NULL,
    txid       xid8        NOT NULL DEFAULT '0',
    position   bigint      NOT NULL DEFAULT 0,
    updated_at timestamptz NOT NULL
);
```

Строка создаётся при первом запуске проекции (`INSERT ... ON CONFLICT DO NOTHING`) до шага 1. Время в `updated_at` берётся из `clock.Clock`.

### 5. Перестроение

Срабатывает по смене `Version`. Автор проекции, изменив логику или схему таблиц, увеличивает версию; после выката проекция собирается заново сама.

Пока идёт перестроение, читатели видят неполные данные проекции. Для учебного объёма событий это секунды. Перестроение "в стороне" с переключением таблиц не делается.

*Альтернатива:* команда или эндпоинт "перестроить". Отклонена: версия в коде не требует ручного шага и не может быть забыта при выкате. Принудительно перестроить без смены кода можно, удалив строку checkpoint и очистив таблицы; это записывается в документацию.

### 6. Метрики

| Метрика | Тип | Метки |
| --- | --- | --- |
| `goden_projection_lag_events` | датчик | `projection` |
| `goden_projection_events_total` | счётчик | `projection` |
| `goden_projection_errors_total` | счётчик | `projection` |
| `goden_projection_last_success_timestamp_seconds` | датчик | `projection` |

Отставание считается после каждой порции и во время ожидания: число событий после позиции проекции. Запрос идёт по индексу `(txid, position)`. В число входят и события выше границы `pg_snapshot_xmin`, которые ещё нельзя читать: так долгая транзакция, задерживающая читателей, видна как растущее отставание - именно это требует ADR-002.

Время последней успешной порции нужно для оповещения "проектор остановился": отставание в событиях не растёт, если никто не пишет.

### 7. Тесты

Проекция для тестов считает события по потокам в собственной таблице, создаваемой тестом, и хранит последнюю версию потока: по ней видны пропуски, повторы и нарушение порядка.

- параллельные писатели: каждый добавляет события в свои и общие потоки и держит транзакцию открытой случайное время до 50 мс; проектор работает всё это время;
- сбой посреди порции: `Apply` возвращает ошибку на заданном событии;
- два проектора одной проекции одновременно;
- перестроение по версии и совпадение с исходной;
- отставание и счётчики.

## Risks / Trade-offs

- [Задержка до периода опроса между записью и чтением] → клиент, записав поставку, может не увидеть её в списке в ту же долю секунды. Для frontend это решает SSE (B7); ожидание проекции в запросе чтения - отдельное решение в B2.
- [Событие, которое проекция не может применить, останавливает её] → осознанно: пропуск дал бы тихое расхождение. Видно по счётчику ошибок и растущему отставанию.
- [Долгая транзакция в базе задерживает все проекции] → свойство чтения ниже `pg_snapshot_xmin`; транзакции команд короткие, отставание в метриках.
- [Проекция одна на всех экземпляров, без параллелизма] → события применяются последовательно; при учебной нагрузке достаточно. Узкое место - самая медленная проекция, а не движок: проекции независимы.
- [Во время перестроения данные проекции неполны] → секунды на текущих объёмах; переключение таблиц не делается.
- [Движок без единой настоящей проекции] → B1 проверяется тестовой проекцией; первая настоящая и подключение к `cmd/worker` - в B2, сразу следом.
