# Proposal

## Why

Redis уже входит в инфраструктуру и ADR, но backend к нему не подключён: повторные запросы к асинхронным read-моделям каждый раз читают PostgreSQL. Нужен восстанавливаемый кеш, который ускоряет чтение и не ослабляет гарантии склада при сбое или потере Redis.

## What Changes

- Добавить необязательное подключение API к Redis и cache-aside для списков поставок, истории заказов, аналитики списаний и статистики дефицита.
- Включать в ключ имя проекции, её PostgreSQL checkpoint, параметры запроса и версию формата: после продвижения проекции старый результат автоматически перестаёт использоваться.
- При промахе или любой ошибке Redis читать PostgreSQL; доступность и readiness API не должны зависеть от Redis.
- Ограничить время обращения к Redis, задать TTL и защитить одновременное заполнение одного ключа внутри экземпляра API.
- Добавить метрики результатов кеша и интеграционные тесты попадания, смены checkpoint и отказа Redis.
- Уточнить ADR-003: зафиксировать выбранную область кеширования, версионирование ключей и исключения из кеша.

Вне изменения: меню и стоп-лист, текущие остатки и партии, горячие предложения и рекомендации поставок; rate limiting; идемпотентность команд и Kafka inbox; контракт HTTP API и frontend.

## Capabilities

### New Capabilities

- `redis-read-cache`: необязательное кеширование асинхронных read-моделей с сохранением PostgreSQL как источника истины и безопасным обходом Redis при сбоях.

### Modified Capabilities

Нет.

## Impact

- `backend/`: новый платформенный Redis-клиент, конфигурация API, обёртка кеширования выбранных чтений, метрики и тесты; новая зависимость `go-redis/v9`.
- `infra/`: существующий Redis используется без изменения HTTP-контракта.
- `docs/ADR.md`, `docs/plan.md`, `backend/AGENTS.md`: документация приводится в соответствие с фактической областью кеширования и настройками.
- `frontend/` и `backend/api/openapi.yaml` не затрагиваются.
