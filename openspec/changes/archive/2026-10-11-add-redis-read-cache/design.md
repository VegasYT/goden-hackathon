# Design

## Context

См. [proposal.md](proposal.md). Redis поднят в `infra/compose.yaml`, но клиента и конфигурации backend нет. `inventory-deliveries`, `orders-history` и `analytics` обновляют данные и строку `projection_checkpoints` в одной транзакции PostgreSQL. Меню, стоп-лист и рекомендации считаются при чтении и зависят от синхронного состояния либо текущего времени.

## Goals / Non-Goals

**Goals:**

- ускорить повторные чтения выбранных асинхронных проекций;
- сохранить PostgreSQL источником истины и fail-open поведение Redis;
- получить одинаковое поведение нескольких экземпляров API;
- сделать попадания и сбои кеша наблюдаемыми.

**Non-Goals:**

- не кешировать данные, участвующие в решении заказа, и вычисления, зависящие от текущего времени;
- не использовать Redis для идемпотентности, Kafka inbox или пользовательских сессий;
- не добавлять rate limiting в этот change.

## Decisions

### 1. Cache-aside над готовыми результатами чтения

API сначала определяет версию данных, затем читает готовый результат из Redis. При промахе обработчик загружает его штатным сервисом из PostgreSQL и сохраняет сериализованное значение с TTL. Кеш подключается к обработчикам поставок, заказов и двум операциям аналитики; доменная запись и проекторы о Redis не знают.

Альтернатива — кешировать строки репозиториев. Она сильнее связывает платформенный код с доменными типами и оставляет повторные вычисления и сборку ответа.

### 2. Checkpoint проекции входит в ключ

Формат ключа:

`goden:v1:<projection>:<version>:<txid>:<position>:<operation>:<sha256-params>`.

Перед Redis API читает checkpoint из PostgreSQL. Данные проекции и checkpoint меняются одной транзакцией, поэтому после её commit следующий запрос получает другой ключ. Параметры нормализуются из типизированного запроса; токен, actor и correlation ID в ключ не входят, поскольку ответы не содержат пользовательских данных.

Гонка, при которой checkpoint прочитан до commit проектора, а данные — после, безопасна: более новое значение попадёт под старый ключ, который следующие запросы уже не используют. При отсутствии checkpoint кеш обходится.

Альтернатива — удалять ключи по Kafka-событиям. Она зависит от доступности и задержки Kafka, требует удаления всех вариантов параметров и может вернуть устаревший ответ после пропущенной инвалидации.

### 3. Только асинхронные read-модели

Кешируются:

- `GET /deliveries` по checkpoint `inventory-deliveries`;
- `GET /orders` по checkpoint `orders-history`;
- `GET /analytics/write-offs` и `GET /analytics/shortages` по checkpoint `analytics`.

Меню, стоп-лист, остатки, партии и оба вида рекомендаций не кешируются. Это следует из ADR-002: стоп-лист должен совпадать с решением заказа, а сроки и горячие предложения меняются от времени без нового события.

### 4. Redis необязателен и работает fail-open

`REDIS_URL` включает кеш; пустое значение отключает его. `REDIS_CACHE_TTL` по умолчанию `1m`, timeout операций — `100ms`. Создание клиента не выполняет обязательный `PING`; ошибки `GET`/`SET` журналируются с ограничением шума, учитываются в метриках и трактуются как промах. `/readyz` продолжает зависеть только от PostgreSQL.

Альтернатива — считать Redis обязательным. Она противоречит ADR-003 и без причины снижает доступность API.

### 5. Ограничение одновременного заполнения

На одном экземпляре API одинаковые промахи объединяются через `singleflight`. После ожидания запрос получает тот же загруженный результат. Между экземплярами распределённая блокировка не вводится: кратковременное дублирование чтения дешевле новой точки отказа.

### 6. Наблюдаемость

API публикует счётчик `goden_read_cache_requests_total{result}` со значениями `hit`, `miss`, `error`, `bypass` и histogram `goden_read_cache_operation_duration_seconds{operation}` с закрытым набором операций `get`, `set`. Ключи и параметры запросов в метки и логи не попадают.

### 7. Уточнение ADR-003

ADR-003 дополняется выбранной первой областью применения, checkpoint-ключами, fail-open поведением и явным запретом кешировать критичные и зависящие от времени представления. Это уточняет принятое решение, а не заменяет его.

## Risks / Trade-offs

- [Каждый запрос всё ещё читает checkpoint PostgreSQL] → это дешёвое чтение одной индексированной строки вместо чтения и сборки всей страницы.
- [Redis недоступен и добавляет задержку] → короткий timeout, fail-open и возможность отключить кеш пустым `REDIS_URL`.
- [Старые ключи занимают память после продвижения проекции] → короткий TTL; явная массовая инвалидация не нужна.
- [Первый промах одновременно приходит на несколько API] → `singleflight` уменьшает нагрузку внутри экземпляра; межпроцессное дублирование допустимо.
- [Формат сериализации меняется после деплоя] → версия формата входит в префикс ключа.

## Migration Plan

1. Развернуть код без `REDIS_URL`: поведение остаётся прежним.
2. Запустить Redis и включить кеш на одном экземпляре API; проверить метрики hit/miss/error.
3. Включить настройку на остальных экземплярах.
4. Для отката удалить `REDIS_URL` или откатить приложение; данные Redis можно потерять без миграции.
