# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- `inventory/delivery.go`: состояние `Delivery` из свёртки потока; `apply` понимает `DeliveryRegistered` и `DeliveryApproved`, на остальные события возвращает ошибку.
- `inventory/events.go`: `QuarantinedDeliveryItemAccepted`, `QuarantinedDeliveryItemRejected`, `DeliveryApprovalCorrected` с `CorrectedItem`, `BatchReceived` с источниками `quarantine` и `correction`, `StockAdjusted` с `CorrectionID`.
- `inventory/service.go`: `ApproveDelivery` как образец - чтение потока до транзакции для выбора блокировок, повторная загрузка с версией под блокировкой, `receiveBatches`, запись в поток поставки с ожидаемой версией; `appendToStock`, `applyStockAdjusted`.
- ADR-010 с правилом: одно решение на всё карантинное количество позиции.

## Goals / Non-Goals

**Goals:**

- После любого события потока поставки для каждой позиции выполняется "заявлено = принято + отклонено + карантин".
- Обе команды используют тот же каркас, что и приёмка: новые механизмы не вводятся.

**Non-Goals:**

- Изменение заявленного количества, срока годности или продукта позиции: корректировка только перераспределяет заявленное.
- Причины по частям в корректировке. У события одна причина на корректировку.
- Отмена корректировки: ошибочная корректировка исправляется следующей.

## Decisions

### 1. Состояние позиции

`DeliveryItemState.BatchID *uuid.UUID` заменяется на `BatchIDs []uuid.UUID` в порядке создания партий. После выхода из карантина и корректировок у позиции может быть несколько партий: из приёмки, из карантина, по одной на каждое увеличение.

Свёртка новых событий:

| Событие | Изменение состояния позиции |
| --- | --- |
| `QuarantinedDeliveryItemAccepted` | принято += количество, карантин -= количество, партия добавлена в список |
| `QuarantinedDeliveryItemRejected` | отклонено += количество, карантин -= количество |
| `DeliveryApprovalCorrected` | три количества заменяются итоговыми из события; партия из события, если есть, добавлена в список |

Причины и комментарий в состоянии остаются из исходной приёмки: это поля снимка. Причины решений по карантину и корректировок есть в событиях, их показывает проекция истории у разработчика B.

Событие, которого свёртка не знает, по-прежнему даёт ошибку: молча пропущенное событие означало бы неверные количества.

### 2. Решение по карантину

```go
type QuarantineDecision struct {
    ItemID           uuid.UUID
    AcceptedQuantity int64
    RejectedQuantity int64
    RejectReason     string
    Comment          string
}

func (s *Service) ResolveQuarantine(ctx, actor, key string, deliveryID uuid.UUID, in QuarantineDecision) (Delivery, error)
```

Чистая функция `(d Delivery) planQuarantineResolution(in, actor, now)` возвращает события поставки (одно или два) и, при ненулевой принятой части, `BatchReceived` с источником `quarantine`.

Порядок проверок: поставка принята (иначе `ErrNotApproved`), позиция существует, у позиции есть открытый карантин (иначе `ErrQuarantineClosed`), количества неотрицательны и в сумме равны карантинному, для отклонённой части есть причина и комментарий, для принятой части позиция не просрочена на `now`.

Комментарий обязателен только для отклонённой части: так же, как при приёмке причина и комментарий обязательны для отклонённого.

Блокировка - складской поток продукта позиции. Она берётся и для решения "отклонить всё": набор блокировок выбирается до чтения решения, как в приёмке.

Два одновременных решения: второе получает конфликт версии потока поставки, `command.Run` повторяет его, свёртка показывает нулевой карантин, результат - `ErrQuarantineClosed`.

### 3. Корректировка приёмки

```go
type ApprovalCorrection struct {
    Reason string
    Items  []ItemCorrection
}
type ItemCorrection struct {
    ItemID              uuid.UUID
    AcceptedQuantity    int64
    RejectedQuantity    int64
    QuarantinedQuantity int64
}

func (s *Service) CorrectDeliveryApproval(ctx, actor, key string, deliveryID uuid.UUID, in ApprovalCorrection) (Delivery, error)
```

Чистая функция `(d Delivery) planCorrection(in, batches map[uuid.UUID][]Batch, actor, now)` получает текущие партии исправляемых позиций и возвращает `DeliveryApprovalCorrected`, список `BatchReceived` и список `StockAdjusted`.

Для каждой позиции считается разница принятого количества:

- больше нуля: позиция не должна быть просрочена на `now`; создаётся `BatchReceived` с источником `correction` на величину разницы; идентификатор новой партии записывается в `CorrectedItem.BatchID`;
- меньше нуля: величина снимается с партий позиции в порядке от последней созданной к первой, по `min(остаток, сколько осталось снять)`; на каждую затронутую партию - `StockAdjusted` с отрицательным изменением, причиной `approval_correction` и `CorrectionID`; если суммарного остатка не хватает - ошибка валидации;
- равна нулю: склад не затрагивается, меняется только распределение между отклонённым и карантинным.

Снятие начинается с последней партии, потому что она появилась из более позднего решения, которое с большей вероятностью и исправляется. Порядок записан в спецификации, чтобы проекции разработчика B могли на него опираться.

Позиция, для которой корректировка не меняет ни одно из трёх чисел, считается ошибкой, если таковы все позиции корректировки: событие без изменений засоряло бы историю. Если изменения есть хотя бы в одной позиции, неизменённые позиции в событие не попадают.

Корректировка может задать ненулевое карантинное количество и тем самым открыть карантин заново; закрывается он обычным решением по карантину.

Блокировки - складские потоки продуктов всех позиций поставки, как в приёмке. Партии позиций читаются из таблицы остатков под блокировкой новым запросом по `item_id`.

Порядок записи в транзакции: события склада (`BatchReceived`, `StockAdjusted`) с применением к таблице остатков, затем `DeliveryApprovalCorrected` в поток поставки с ожидаемой версией.

### 4. Ошибки

- `ErrNotApproved` - решение по карантину или корректировка для поставки, которая ещё не принята.
- `ErrQuarantineClosed` - у позиции нет открытого карантина.
- `ValidationError` - остальное, включая уменьшение больше остатка: вызывающей стороне нужно поле и сообщение с доступным количеством.

### 5. Запросы

Один новый запрос sqlc: партии позиции поставки, от последней созданной к первой (`ORDER BY received_at DESC, id DESC`). Идентификаторы партий - UUIDv7, поэтому порядок по ним при равном времени тоже соответствует порядку создания.

## Risks / Trade-offs

- [Изменение типа поля `BatchID` на список] → затрагивает тесты приёмки и сохранённые результаты идемпотентности. Сохранённых результатов вне тестовых баз нет: живой базы ни у кого нет.
- [Партии из корректировки дробят остаток позиции] → у одной позиции может быть несколько мелких партий с одним сроком. FEFO от этого не страдает: при равном сроке партии расходуются по времени поступления.
- [Корректировка снимает количество с партии, которую одновременно расходует заказ] → обе команды идут под блокировкой складского потока продукта, поэтому выполняются по очереди; проверка остатка делается под блокировкой.
- [Причина решения по карантину не видна в состоянии поставки] → она есть в событии; полную историю приёмки показывает проекция разработчика B (задача B2).
- [Снятие с последней партии может быть не тем, чего ждёт сотрудник] → если нужно снять с конкретной партии, для этого есть ручная корректировка остатка `AdjustStock` из A5.
