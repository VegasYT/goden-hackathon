# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- Таблицы записи меняются только функциями `apply*` модулей `inventory` и `catalog`; команды вызывают их сразу после добавления события. Общего места "событие → функция применения" нет: каждая команда вызывает свою функцию напрямую.
- Состояние поставки и заказа - свёртка событий потока, таблиц у них нет: их "replay" выполняется при каждом чтении.
- `eventstore.ReadAll` читает события в порядке `(txid, position)`.
- Тесты параллельности уже есть на уровне сервисов: заказы одного продукта, заказы разных продуктов, устаревший набор блокировок. Через API и в смеси с поставками, списаниями и изменением рецептур параллельная работа не проверялась.
- `generator.Simulator` умеет создавать поставки и заказы через API; `apitest` поднимает API на тестовой базе.
- Асинхронных проекций в проекте ещё нет.

## Goals / Non-Goals

**Goals:**

- Проверка replay не зависит от того, как команды применяют события: расхождение между "что сделала команда" и "что следует из события" должно стать видимым.
- Нагрузочный тест детерминирован по свойствам, а не по числам: он проверяет инварианты при любом исходе гонок.
- Тест укладывается в обычный прогон интеграционных тестов.

**Non-Goals:**

- Измерение производительности с порогами.
- Перестроение таблиц в работающей системе как операция администратора.
- Проверка проекций и publisher.

## Decisions

### 1. Перестроение - тестовая опора, а не рабочий код

Функции перестроения лежат в файлах `export_test.go` модулей `inventory` и `catalog`: они видят неэкспортируемые `apply*`, но в сборку процессов не попадают. Перестроение:

1. очищает таблицы модуля;
2. читает все события через `eventstore.ReadAll` страницами;
3. для событий своего модуля вызывает ту же функцию `apply*`, что и команда; события чужих модулей пропускает; неизвестное событие своего модуля - ошибка.

*Альтернатива:* экспортируемая функция в рабочем коде и команда `cmd/replay`. Отклонена: у неё нет пользователя, кроме теста, а перестроение таблицы остатков на работающей системе требует остановки записи - это отдельная операция со своими правилами.

Как отличить "своё неизвестное" от "чужого": модуль перечисляет типы своих событий, которые таблицу не меняют (события поставок и заказов), явно. Тип из реестра событий, зарегистрированный пакетом модуля и не попавший ни в один список, вызывает ошибку. Так новое складское событие нельзя забыть.

### 2. Сравнение таблиц

Тест выполняет перестроение в транзакции и откатывает её: исходная таблица остаётся нетронутой, а сравнение идёт по снимкам "до" и "после перестроения". Снимок - строки таблицы как JSON, отсортированные по ключу. Сравниваются все столбцы, включая отметку о предупреждении.

Тесты replay лежат во внешних тестовых пакетах (`inventory_test`, `catalog_test`): им нужен `apitest`, который импортирует эти модули.

### 3. Сценарий для replay остатков

Один сценарий через API, который порождает каждое складское событие хотя бы раз и содержит оба направления корректировки приёмки (увеличение создаёт партию, уменьшение - корректировку остатка). Предупреждение о сроке вызывается через сервис: в API этой команды нет, она для worker.

### 4. Нагрузочный тест

Тест лежит в `internal/inventory` (изменено при реализации: перестроение доступно только тестам своего модуля, а нагрузочному тесту оно нужно). Подготовка: каталог из демонстрационного набора генератора и начальные поставки. Затем параллельно работают:

- несколько клиентов-симуляторов, каждый со своим источником случайности: поставки и заказы;
- клиент, который списывает и корректирует случайные партии (ответ 422 для него ожидаем: партию мог опустошить заказ);
- клиент, который меняет рецептуру блюда между двумя вариантами: это заставляет оформление заказа перечитывать рецептуры и повторяться с новым набором блокировок.

Часы теста - поддельные и стоят на месте: сроки годности не истекают во время нагрузки, и результат не зависит от скорости машины.

Любой ответ 5xx и любая ошибка транспорта - провал теста. После остановки клиентов проверяются свойства из спецификации:

- остатки по событиям считаются отдельным SQL-запросом по JSON событий, без функций `apply*`;
- для каждого принятого заказа расход сверяется с рецептурой, действовавшей на момент заказа: она восстанавливается по событиям `RecipeChanged`, предшествующим заказу в общем порядке чтения;
- порядок версий проверяется для всех потоков по `eventstore.ReadAll`.

Объём: по умолчанию 6 клиентов и около 300 заказов; переменная `GODEN_LOAD_ORDERS` увеличивает число заказов для ручного прогона. Тест пишет в журнал число операций, долю принятых заказов и операций в секунду.

### 5. Недоступное количество

Один тест через API с четырьмя шагами из спецификации. Правила уже покрыты по отдельности на уровне сервисов; здесь проверяется их совместная работа с контрактом: число "доступно" в ответе отклонённого заказа.

### 6. Что проверяет replay, а что - пересчёт по событиям

Уточнено при реализации. Перестроение вызывает те же функции `apply*`, что и команды, поэтому ошибку внутри самой функции оно не видит: и команда, и перестроение ошибутся одинаково. Replay ловит другое - изменение таблицы в обход событий, зависимость от порядка и от данных, которых нет в событии. Ошибку в функции применения ловит независимый пересчёт остатков по JSON событий в нагрузочном тесте. Обе проверки подтверждены мутациями: команда списания, меняющая таблицу мимо события, роняет replay; удвоенная корректировка роняет пересчёт.

### 7. Что нашли проверки

Дефектов учёта не найдено: на 2000 заказах под смешанной нагрузкой остатки сошлись с событиями, отрицательных остатков и внутренних ошибок не было. Найдены два свойства системы, которые стоит знать. Код ради них не менялся.

**Заказ может получить 409 при непрерывной смене рецептуры.** Если рецептура блюда меняется быстрее, чем заказ успевает взять блокировки под новый состав, команда исчерпывает повторы и отвечает 409 "recipes keep changing". В тесте рецептура менялась каждые 5 мс, и такой ответ получили 4 заказа из 2000. Заказ при этом не оформлен, повтор запроса проходит. В работе ресторана рецептуры так не меняют; это предел, а не дефект. Клиент должен трактовать 409 на оформлении заказа как "повторить".

**Порядок событий рецептуры и заказа может расходиться с тем, что видел заказ.** Заказ читает рецептуру в своей транзакции, а место в общем порядке чтения получает по номеру транзакции. Если рецептура меняется одновременно с заказом, событие `RecipeChanged` может стоять в общем порядке по другую сторону от заказа, чем состав, по которому заказ посчитан. В тесте так вышло у 102 принятых заказов из 1081 - при смене рецептуры каждые 5 мс. Остаток это не затрагивает: `StockConsumed` несёт фактически израсходованное количество. Следствие для проекций: расход заказа нельзя вычислять из рецептуры, действующей на момент события заказа, - только брать из `StockConsumed`. Устранить расхождение можно, блокируя поток блюда на время заказа или записывая потребность в событие заказа; первое сериализует заказы одного блюда, второе меняет формат события. Сейчас это не делается.

## Risks / Trade-offs

- [Перестроение дублирует знание "событие → функция применения"] → это цена независимости проверки; забытое событие даёт ошибку, а не тихий пропуск.
- [Сверка расхода с рецептурой на момент заказа] → из-за свойства из раздела 7 тест принимает расход и по текущей, и по соседней версии рецептуры; при расхождении с обеими печатает заказ и расход.
- [Нагрузочный тест зависит от планировщика и может не воспроизвести редкую гонку] → он проверяет свойства при любом исходе; узкие гонки покрыты отдельными тестами с управляемым порядком (`stale_locks`, тесты `command`).
- [Тест может быть медленным на слабой машине] → объём по умолчанию небольшой; ожидания по времени в нём нет.
- [Проверки не покрывают проекции] → их нет; образец replay передаётся разработчику B.
