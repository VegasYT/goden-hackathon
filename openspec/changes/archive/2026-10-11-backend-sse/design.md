# Design

## Context

См. [proposal.md](proposal.md). API сейчас обслуживает REST через сгенерированный ogen-handler, а точные маршруты вне него (`/healthz`, `/metrics`) собираются в `net/http.ServeMux`. Worker уже публикует доменные события из Event Store в Kafka; `stock.v1`, `orders.v1` и `expiry.v1` используют общий версионированный конверт. События каталога пока не публикуются. SSE по ADR-005 может терять промежуточные сообщения и после reconnect требует перечитать REST.

## Goals / Non-Goals

**Goals:**

- доставлять каждому экземпляру API сигналы из Kafka и раздавать их всем локальным SSE-клиентам;
- не связывать скорость одного клиента с Kafka-consumer и другими клиентами;
- сохранить REST работоспособным при временной недоступности Kafka;
- повторно использовать существующий конверт интеграционных событий.

**Non-Goals:**

- durable-очередь на клиента, replay по `Last-Event-ID` и согласованный снимок нескольких REST-ресурсов;
- передача payload доменных событий браузеру;
- изменение вычисления стоп-листа, сроков или рекомендаций.

## Decisions

### 1. Отдельный модуль realtime с hub, SSE-handler и преобразованием событий

Новый backend-модуль принимает Kafka envelope, преобразует тип события в набор категорий и публикует компактный сигнал в in-memory hub. Handler регистрируется точным маршрутом `GET /api/v1/events` раньше общего ogen-handler, выставляет `text/event-stream`, отключает кеширование, отправляет `retry`, затем `sync`, `update` и комментарии keepalive с обязательным flush.

Это решение следует существующему правилу `backend/AGENTS.md`: SSE описывается в OpenAPI, но реализуется вручную. Реализация через ogen отклонена, потому что генератор не управляет долгоживущим streaming-ответом.

### 2. Каждый экземпляр API читает Kafka независимо

API использует franz-go без общей consumer group и начинает чтение с конца топиков. Поэтому каждый экземпляр получает новые сообщения и может уведомить собственные соединения; старые сообщения не воспроизводятся, а начальный `sync` закрывает разрыв состояния. Durable inbox не используется: повтор `update` безопасен, а его пропуск компенсируется REST reload после reconnect.

Общая consumer group отклонена: она распределила бы сообщения между экземплярами API, и часть подключённых клиентов не получила бы сигнал. Чтение Event Store отдельным checkpoint отклонено как дублирование уже принятого publisher-пути.

### 3. События остаются сигналами инвалидирования

`update` содержит UUID и время исходного события и уникальный отсортированный список категорий. Складские изменения инвалидируют все четыре категории; события каталога — зависящие от них категории; предупреждение о сроке — `expiry`. Неподдерживаемые типы игнорируются. Payload и metadata Kafka в SSE не попадают.

Для `ProductCreated`, `DishCreated` и `RecipeChanged` publisher получает новый `catalog.v1`; формат envelope и остальные топики не меняются. Это выведено из существующего кода: без событий каталога изменение рецептуры не может обновить стоп-лист через Kafka.

### 4. Авторизация выполняется до перехода в streaming-режим

Ручной маршрут использует тот же `auth.Verifier`, режим `AUTH_DISABLED`, challenge и формат problem response, что REST. Операция доступна любому аутентифицированному клиенту: сигнал не содержит бизнес-данных, а фактические REST-чтения отдельно проверяют `inventory.view`, `kitchen.view` или `recommendations.view`. Передача токена ожидается в заголовке `Authorization`; frontend сможет использовать fetch-based SSE-клиент с управляемым reconnect.

Новый permission отклонён как лишнее изменение Keycloak и ролей для канала, который сам не раскрывает состояние.

### 5. Ограниченная очередь и отказоустойчивый lifecycle

У каждой подписки ограниченный канал. Если он заполнен, hub удаляет и закрывает только эту подписку; клиент переподключается и получает `sync`. Kafka-reader повторяет подключение после временных ошибок и не делает REST API неготовым. При остановке процесса reader и все SSE-соединения завершаются через общий context.

Producer перед первой записью, а reader перед чтением явно и идемпотентно создают нужные Kafka-топики с настройками broker по умолчанию. Реализация не зависит от `allow.auto.create.topics`; после ошибки topic provisioning повторяется, не влияя на readiness REST.

## Risks / Trade-offs

- [Одно складское действие создаёт несколько событий и REST может перечитываться несколько раз] → категории одного события объединяются; дальнейший debounce остаётся ответственностью клиента.
- [Событие может попасть между REST-чтением и установлением SSE] → `sync` отправляется после установки соединения, клиент перечитывает состояние после него.
- [Kafka недоступна, а SSE-соединение выглядит живым] → keepalive подтверждает только HTTP-соединение; reader логирует ошибки и повторяет чтение, после восстановления новые события снова доставляются, клиент может использовать предусмотренный polling fallback.
- [Ручной маршрут может разойтись с общими правилами API] → интеграционные тесты проверяют 401, correlation ID, CORS и формат ответа; OpenAPI остаётся документирующим источником.

## Migration Plan

1. Выпустить worker с публикацией `catalog.v1` и API с подпиской на все realtime-топики; миграции БД не нужны.
2. Старые worker/API совместимы: новый топик добавочный, формат существующих сообщений не меняется.
3. Для отката остановить использование SSE и вернуть предыдущие бинарники; REST и данные не требуют преобразования.
