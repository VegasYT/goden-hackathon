# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- `catalog.Service`: `CreateProduct`, `Product`, `Products` (весь список без пагинации); ошибки `ErrNotFound`, `ErrNameTaken`, `*ValidationError`.
- `command.ErrKeyReused`, `eventstore.ErrVersionConflict`; correlation ID в контексте через `observability.WithCorrelationID`, он попадает в логи и события.
- `config.Load`, `observability.NewLogger`, `postgres.NewPool`, `cmd/migrate` как образец исполняемого процесса.
- `backend/AGENTS.md`: выбор ogen должен быть проверен на первом эндпоинте с телом запроса, пагинацией и ошибками `application/problem+json`; запасной вариант - oapi-codegen v2.
- sqlc и линтер запускаются через `go run` с закреплённой версией.

Сведения об ogen из его документации: генератор запускается как `go run github.com/ogen-go/ogen/cmd/ogen --target <dir> --package <name> --clean <spec>`, настройки читает из `ogen.yml`; отдельные возможности, включая интеграцию с OpenTelemetry, отключаются через `generator.features.disable`; если все операции имеют одинаковый ответ `default`, включается режим "convenient errors" с методом `NewError`; ошибки разбора запроса идут в настраиваемый `ErrorHandler`.

## Goals / Non-Goals

**Goals:**

- Разработчик может запустить сервер локально и получить ответ на настоящий запрос.
- Соглашения API заданы один раз в контракте и в одном месте кода, а не в каждом обработчике.
- Обработчик модуля - тонкая обёртка: разбор запроса, вызов сервиса, сборка ответа.

**Non-Goals:**

- Авторизация. До A7 действует фиксированный пользователь разработки.
- Метрики и трассировка: A8. Интеграция ogen с OpenTelemetry отключается, чтобы не тянуть её зависимости раньше времени.
- Версионирование API сверх префикса `/api/v1`.
- Docker-образы и `docker compose`: задача 0.4.

## Decisions

### 1. Слои

```text
api/openapi.yaml                    контракт
internal/api/oas/                   сгенерированный ogen код, не редактируется
internal/api/                       сборка: общий Handler, преобразование ошибок, конструктор http.Handler
internal/<модуль>/http.go           обработчики модуля: методы интерфейса oas.Handler для своих операций
internal/platform/httpx/            middleware, запуск сервера, health; без знания о домене и контракте
cmd/api, cmd/worker                 сборка зависимостей и запуск
```

ogen генерирует один интерфейс `Handler` на все операции. Он собирается встраиванием: `api.Handler` включает `*catalog.HTTP`, позже `*inventory.HTTP` и другие, а также сгенерированный `oas.UnimplementedHandler` для операций, которых ещё нет. Модуль реализует только свои методы и не знает о чужих.

`internal/api` - не доменный модуль и не платформа: это слой сборки, которому разрешено импортировать доменные модули. Правило `depguard` для `platform` его не касается. Доменные модули импортируют только `internal/api/oas` ради типов запросов и ответов.

*Альтернатива:* общие типы ошибок и пагинации в `platform/httpx`, а обработчики без генератора. Отклонена: контракт перестал бы быть источником истины для frontend.

### 2. Контракт

- `servers` с базовым путём `/api/v1`; операции имеют `operationId` и `tags`, по тегам делится владение разделами между разработчиками.
- Схема `Problem`: `type`, `title`, `status`, `detail`, `correlation_id`, необязательный `errors[]` с `field` и `message`.
- Все операции ссылаются на один ответ `default` с `application/problem+json` и схемой `Problem`.
- Параметры `limit` (1..200, по умолчанию 50) и `offset` (от 0) в `components.parameters`; ответ списка - объект с `items` и `total`.
- Заголовок `Idempotency-Key` в `components.parameters`, необязательный, на операциях записи.
- Ограничения в схемах - только те, что не зависят от нормализации: перечисление единиц измерения, `minimum` для чисел, обязательность полей. Пустота строки после обрезки пробелов проверяется доменом и даёт 422.

Первые операции: `createProduct` (`POST /products`, 201), `listProducts` (`GET /products`), `getProduct` (`GET /products/{productId}`).

### 3. Проверка ogen и обработка ошибок

Порядок проверки:

1. Сгенерировать код для контракта из решения 2.
2. Убедиться, что режим "convenient errors" включился: в интерфейсе есть `NewError`, а методы операций возвращают результат и `error`.
3. Убедиться, что ответ ошибки уходит с `Content-Type: application/problem+json`.

Если шаги 2-3 проходят, ошибки обрабатываются так:

- обработчик модуля возвращает ошибку сервиса как есть;
- `api.Handler.NewError` превращает её в `Problem` и статус одной функцией преобразования;
- ошибки разбора и проверки запроса по контракту идут в `ErrorHandler` ogen, который пишет тот же `Problem` со статусом 400; он же обслуживает 404 и 405 маршрутизатора.

Если "convenient errors" не работает с `application/problem+json`, ответ `default` из операций убирается из генерации типизированных ответов, а все ошибки пишет один `ErrorHandler`. Контракт при этом по-прежнему документирует формат. Если не получается и так, выполняется переход на oapi-codegen v2 по правилу из `AGENTS.md`. Итог проверки записывается в `AGENTS.md` в любом случае.

Таблица преобразования ошибок в одной функции `internal/api`:

| Ошибка | Статус | `title` |
| --- | --- | --- |
| `*ValidationError` любого модуля | 422 | Validation failed, с `errors[]` |
| `*catalog.UnknownProductError`, аналогичные "неизвестная ссылка" | 422 | Unknown reference |
| `ErrNotFound` любого модуля | 404 | Not found |
| `catalog.ErrNameTaken` | 409 | Conflict |
| `command.ErrKeyReused` | 422 | Idempotency key reused |
| `eventstore.ErrVersionConflict` | 409 | Conflict, повторите запрос |
| остальное | 500 | Internal error, без текста ошибки; ошибка пишется в лог |

Чтобы функция не перечисляла типы ошибок всех модулей, ошибки валидации распознаются по небольшому интерфейсу с методами, возвращающими поле и сообщение; `ValidationError` модулей его реализуют. Ошибки "не найдено" распознаются через `errors.Is` с sentinel-значениями модулей.

### 4. Middleware и correlation ID

Цепочка в `platform/httpx`, от внешнего к внутреннему: восстановление после паники (500 в формате `Problem`), correlation ID, лог запроса.

Correlation ID: заголовок `X-Correlation-Id`, если он разбирается как UUID, иначе новый UUIDv7. Кладётся в контекст через `observability.WithCorrelationID`, поэтому без дополнительного кода попадает в логи и в события команд. Возвращается в заголовке ответа и в поле `correlation_id` тела ошибки.

Лог запроса: метод, путь, статус, длительность. Уровень `info`, для 5xx - `error`.

### 5. Автор запроса до A7

`httpx` определяет функцию получения автора из контекста. До A7 middleware кладёт в контекст фиксированного автора `{type: user, id: "dev"}`, а `cmd/api` при старте пишет предупреждение уровня `warn` о том, что авторизация отключена. A7 заменит middleware проверкой токена Keycloak; обработчики при этом не изменятся.

### 6. Пагинация каталога

`catalog.Service.Products` получает параметры страницы и возвращает элементы и общее число: один запрос со `LIMIT` и `OFFSET` и один запрос количества. Прежний вызов без параметров внутри проекта используется только в тестах; они переводятся на новую сигнатуру.

Пагинация по смещению выбрана за простоту для frontend: таблицы с номерами страниц. Списки системы невелики, цена `OFFSET` несущественна.

### 7. Процессы

`cmd/api`: конфигурация (`HTTP_ADDR`, по умолчанию `:8080`; `SHUTDOWN_TIMEOUT`, по умолчанию 15 секунд; части `Postgres` и `Log`), логгер, пул, сервисы, `http.Handler`, запуск. Миграции при старте не применяются: это делает `cmd/migrate`, иначе несколько экземпляров API применяли бы их одновременно.

`cmd/worker`: та же основа, HTTP-сервер только с `/healthz` и `/readyz` на `HTTP_ADDR` (по умолчанию `:8081`), пустой список фоновых задач и место, куда разработчик B их добавляет.

Общий запуск - `httpx.Serve(ctx, addr, handler, shutdownTimeout, logger)`: слушает адрес, по отмене контекста вызывает `Shutdown` с таймаутом. Контекст отменяется по `SIGINT` и `SIGTERM` через `signal.NotifyContext`.

`/readyz` проверяет базу запросом `Ping` с таймаутом в одну секунду.

### 8. Тестовая обвязка API

Пакет `internal/api/apitest`: `apitest.New(t)` поднимает `pgtest.NewDB`, собирает сервисы и `http.Handler` тем же конструктором, что и `cmd/api`, запускает `httptest.Server` и возвращает сгенерированный клиент ogen и базовый адрес. Тесты эндпоинтов ходят через клиент: так проверяются сразу сервер, клиент и контракт. Сырые запросы через `net/http` используются только там, где нужно отправить то, что клиент не позволит: тело не по контракту, произвольные заголовки.

### 9. Генерация

`go run github.com/ogen-go/ogen/cmd/ogen@<версия> --target internal/api/oas --package oas --clean api/openapi.yaml` с закреплённой версией, как sqlc. Настройки в `backend/ogen.yml`: отключение `ogen/otel`. Сгенерированный код коммитится и исключается из линтера.

Это уточняет фразу в `AGENTS.md` о подключении ogen директивой `tool`: все три генератора и линтер запускаются одинаково.

## Risks / Trade-offs

- [ogen не примет какую-то конструкцию контракта] → проверка на первом эндпоинте и есть цель изменения; запасные пути описаны в решении 3.
- [Авторизация отключена] → любой запрос выполняется от имени `dev`. Сервер пишет предупреждение при старте; до A7 его нельзя выставлять наружу. Записывается в `AGENTS.md`.
- [Один большой интерфейс `Handler`] → каждая новая операция в контракте до реализации отвечает 501 через `UnimplementedHandler`, а не ломает сборку. Конфликты имён методов между модулями исключены уникальностью `operationId`.
- [Два разработчика правят один `openapi.yaml`] → владение разделами по тегам уже записано в `plan.md`; сгенерированный код перегенерируется после слияния.
- [Объём сгенерированного кода в репозитории] → несколько тысяч строк на небольшой контракт. Принято: без него сборка требовала бы генерации на каждой машине.
- [Нет `docker compose`] → для локального запуска базу нужно поднять вручную одной командой `docker run`; команда записывается в `AGENTS.md`.
