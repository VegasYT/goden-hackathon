# Spec Delta

## Purpose

HTTP API - единый способ для frontend, генератора и внешних клиентов работать с системой. Общие правила задают одинаковое поведение всех эндпоинтов: как сообщаются ошибки, как читаются длинные списки, как безопасно повторять запросы и как связать запрос с его следами в логах и событиях.

## ADDED Requirements

### Requirement: Контракт API
HTTP API SHALL быть описан одним документом OpenAPI, из которого генерируется код сервера и клиента. Все эндпоинты API SHALL находиться под префиксом `/api/v1`. Запрос, не соответствующий контракту, SHALL отклоняться до выполнения бизнес-логики.

#### Scenario: Запрос с телом не по контракту
- **WHEN** на эндпоинт создания отправляют JSON без обязательного поля
- **THEN** возвращается статус 400 с описанием проблемы, бизнес-логика не выполняется

#### Scenario: Неизвестный путь
- **WHEN** запрашивают путь, которого нет в контракте
- **THEN** возвращается статус 404

### Requirement: Формат ошибок
Любой ответ с ошибкой SHALL иметь тип содержимого `application/problem+json` и поля `type`, `title`, `status` и `detail`. Ошибка валидации SHALL дополнительно содержать список некорректных полей с названием поля и сообщением. Ответ с ошибкой SHALL содержать correlation ID запроса. Внутренние подробности сбоя SHALL NOT попадать в ответ со статусом 500.

Статусы SHALL назначаться единообразно: 400 - запрос не соответствует контракту; 404 - объект не найден; 409 - конфликт с текущим состоянием; 422 - запрос корректен по форме, но нарушает правило предметной области; 500 - внутренняя ошибка.

#### Scenario: Ошибка валидации
- **WHEN** создают продукт с пустым названием
- **THEN** возвращается статус 422, тип содержимого `application/problem+json`, а в списке некорректных полей указано поле `name`

#### Scenario: Объект не найден
- **WHEN** запрашивают продукт по идентификатору, которого нет
- **THEN** возвращается статус 404 в формате `application/problem+json`

#### Scenario: Конфликт
- **WHEN** создают продукт с уже занятым названием
- **THEN** возвращается статус 409 в формате `application/problem+json`

#### Scenario: Внутренняя ошибка
- **WHEN** при обработке запроса происходит непредвиденный сбой
- **THEN** возвращается статус 500 с общим сообщением без текста исходной ошибки, а сама ошибка записана в лог с correlation ID

### Requirement: Пагинация списков
Эндпоинты списков SHALL принимать параметры `limit` и `offset` и возвращать элементы страницы вместе с общим числом элементов. Значение `limit` по умолчанию SHALL быть 50, максимальное - 200. Некорректные значения параметров SHALL отклоняться со статусом 400.

#### Scenario: Первая страница по умолчанию
- **WHEN** запрашивают список без параметров при 120 элементах
- **THEN** возвращаются первые 50 элементов и общее число 120

#### Scenario: Следующая страница
- **WHEN** запрашивают список с `limit=50` и `offset=100` при 120 элементах
- **THEN** возвращаются последние 20 элементов и общее число 120

#### Scenario: Слишком большой limit
- **WHEN** запрашивают список с `limit=1000`
- **THEN** возвращается статус 400

### Requirement: Идемпотентность запросов на запись
Запросы на запись SHALL принимать необязательный заголовок `Idempotency-Key`. Повторный запрос с тем же ключом и тем же телом SHALL возвращать тот же результат, что и первый, без повторного выполнения. Запрос с тем же ключом и другим телом SHALL отклоняться со статусом 422.

#### Scenario: Повтор запроса
- **WHEN** запрос создания продукта отправляют дважды с одним `Idempotency-Key`
- **THEN** оба ответа содержат один и тот же идентификатор продукта, продукт создан один раз

#### Scenario: Ключ с другим телом
- **WHEN** запрос создания отправляют с уже использованным `Idempotency-Key` и другим телом
- **THEN** возвращается статус 422 в формате `application/problem+json`

### Requirement: Correlation ID
Каждый запрос SHALL иметь correlation ID: значение заголовка `X-Correlation-Id`, если клиент прислал корректный UUID, иначе созданное сервером. Сервер SHALL возвращать его в заголовке ответа `X-Correlation-Id`, записывать в логи запроса и проставлять в события, созданные при обработке запроса.

#### Scenario: Клиент прислал correlation ID
- **WHEN** запрос создания продукта отправлен с заголовком `X-Correlation-Id`
- **THEN** ответ содержит тот же идентификатор в заголовке, и событие `ProductCreated` записано с этим correlation ID

#### Scenario: Клиент не прислал correlation ID
- **WHEN** запрос отправлен без заголовка `X-Correlation-Id`
- **THEN** ответ содержит заголовок с новым идентификатором

### Requirement: Проверка состояния процесса
Процесс SHALL отвечать на `GET /healthz` статусом 200, пока он работает, и на `GET /readyz` статусом 200, только когда он готов обслуживать запросы, включая доступность базы данных; иначе `/readyz` SHALL отвечать статусом 503. Эти эндпоинты SHALL NOT требовать авторизации и не входят в префикс `/api/v1`.

#### Scenario: Процесс готов
- **WHEN** процесс запущен и база данных доступна
- **THEN** `/healthz` и `/readyz` отвечают статусом 200

#### Scenario: База данных недоступна
- **WHEN** процесс работает, а база данных недоступна
- **THEN** `/healthz` отвечает статусом 200, `/readyz` отвечает статусом 503
