## Context

Права сейчас проверяет `internal/api/security.go`: право операции записано в контракте (`security: bearerAuth: [право]`), роли берутся из токена (`resource_access.goden-api.roles`), автор команды - имя пользователя из токена. Понятий компании и точки в системе нет. Решение о новой модели принято в ADR-013; здесь - как первый этап ложится на код.

## Goals / Non-Goals

**Goals:** хранить компании, точки и назначения; отвечать на вопрос "есть ли у пользователя право на этой точке"; дать интерфейсу профиль для выбора точки.

**Non-Goals:** перевод существующих операций на точки (этапы 2-4); настройки точки; экраны.

## Decisions

**Новый модуль `internal/organization`, устроенный как `catalog`.** Команды через `command.Run`, события в Event Store, синхронные таблицы записи меняются только функциями `apply*`. Потоки: `company-<id>` (создание, переименование, отключение компании) и `point-<id>` (точка и её назначения). Назначения в потоке точки: изменения состава одной точки выстраиваются по версии потока, и два одновременных назначения одного пользователя не создадут дубликат. Вывод из конвенций проекта и ADR-013; альтернатива - обычные таблицы без событий - проще, но теряет историю назначений и расходится с правилом "бизнес-состояние меняется событиями".

**Пользователь - строка таблицы, не событие.** `organization_users (id, email, name)` - отражение данных Keycloak, а не бизнес-состояние: обновляется при обращении, истории не требует. Идентификатор - `sub` токена: он не меняется при смене почты и имени. Запись выполняется при `GET /me` и `POST /companies`, а не на каждом запросе API: у остальных операций организации права есть только у того, кто уже записан. Почта принадлежит одному пользователю: если адрес занял другой, у прежнего он очищается.

**Автор в событиях остаётся именем пользователя.** Формат автора (`{user, имя}`) используется во всех существующих событиях и в аудите; менять его на идентификатор значило бы менять все события. Назначения и владение компанией ссылаются на идентификатор пользователя (`owner_id`, `user_id` в событиях); кто выполнил действие, записано в конверте события именем автора, как у всех событий.

**Право определяется одной функцией.** `organization.Service.Permissions(ctx, userID, pointID)` возвращает набор прав: все - для владельца компании точки, права роли - для назначенного сотрудника, пустой - для остальных. Роли и их права - таблица в коде (`roles.go`), перенесённая из составных ролей realm. К permissions ADR-006 добавляются `point.view` и `staff.view` (все роли точки), `staff.manage` (управляющий), `company.view` (сотрудник любой работающей точки компании) и `company.manage`. Последнего нет ни у одной роли: владелец получает полный список прав, поэтому "только владелец" выражается обычным правом операции, без отдельной проверки. Для компании есть парная функция `CompanyPermissions`. Из набора управляющего убраны `products.manage` и `dishes.manage`: каталог меняет только владелец.

**Проверка - в одном месте слоя API.** Право операции остаётся в контракте. Для операций с параметром `pointId` или `companyId` слой API читает параметр, вызывает функцию прав и сверяет право операции; обработчики модулей о правах по-прежнему не знают. Технически это middleware сгенерированного сервера (`authorize`): он получает имя операции и её параметры. Обработчик безопасности параметров не видит, поэтому он только проверяет токен, а сверка права целиком, включая прежнюю по ролям токена, перенесена в middleware. Следствие: отказ 403 теперь приходит после разбора запроса, и клиент без права на некорректный запрос получит 400, а не 403. Операции без точки и компании в адресе (`GET /me`, `POST /companies`) требуют только корректного токена. Отдельного списка компаний нет: их отдаёт профиль. Существующие операции до своего этапа проверяются по-старому, по ролям токена: оба способа сосуществуют, выбор - по наличию параметра точки или компании.

**Права читаются из базы на каждом запросе.** Два запроса по первичным ключам. Кеш не вводится: снятие назначения должно действовать сразу (требование спецификации), а нагрузки, которая оправдала бы инвалидацию кеша, нет.

**Отказ - 403 и для чужой точки, и для точки без права.** Существующую точку, к которой нет доступа, можно было бы скрывать ответом 404, но идентификаторы - UUIDv7, перебором их не найти, а единое правило "нет права - 403" уже действует во всём API. Несуществующая точка - 404.

**Самостоятельная регистрация - настройка realm.** Достаточно `registrationAllowed`: `sub`, `email` и `name` уже есть в токене клиента `goden-web`, вход по почте включён по умолчанию. Служебный API Keycloak не используется: назначить можно только того, кто уже обращался к системе.

**Режим без Keycloak.** `auth.Disabled()` возвращает пользователя `dev` с фиксированным идентификатором и почтой; дальше он обычный пользователь. Прежнее "все права" у `dev` остаётся только для ещё не переведённых операций.

**Статусы ошибок.** Назначение по неизвестной почте - 422 (`unknown-reference`), повторное назначение, занятое название точки и изменение отключённой точки или компании - 409, попытка управляющего распорядиться управляющим - 403.

**Отключение необратимо.** Команды включения обратно нет: спецификация её не требует. Сотрудники отключённой точки теряют на ней права и не видят её в профиле, владелец сохраняет чтение.

## Risks / Trade-offs

- Почта при регистрации не подтверждается (нет почтового сервера) → зарегистрировавшийся с чужим адресом будет найден по нему при назначении. До включения подтверждения почты это ограничение показа; запись есть в `backend/AGENTS.md`.

- Два способа проверки прав на время этапов 2-4 → правило выбора одно (есть ли в адресе точка или компания), тест матрицы прав проверяет оба; к этапу 5 старый способ удаляется.
- Запись пользователя при обращении добавляет запрос к базе → только на операциях профиля и организации.
- Работа идёт в долгой ветке: `develop` продолжает меняться → ветка регулярно подтягивает `develop`.
