## Что проверить вручную

Нужны окружение разработки с пересозданным Keycloak (`docker compose -f infra/compose.yaml up -d --force-recreate --wait keycloak`), применённые миграции и запущенный API. Запросы удобно выполнять в `/docs` или через `curl` с токеном.

- MUST На странице входа Keycloak есть ссылка регистрации; новый пользователь регистрируется сам, и `GET /api/v1/me` возвращает его почту и имя с пустыми списками компаний и точек.
- MUST Этот пользователь создаёт компанию (`POST /companies`) и точку (`POST /companies/{id}/points`); в `GET /me` появляются компания и точка с `owner: true`.
- MUST Владелец назначает второго зарегистрированного пользователя по почте (`POST /points/{id}/staff`); у того в `GET /me` появляется точка с ролью. Назначение по почте, с которой никто не входил, отклоняется со статусом 422.
- MUST Сотрудник с ролью повара получает 403 на `POST /points/{id}/staff` и на `GET /companies/{id}/points`; пользователь без назначения получает 403 на `GET /points/{id}`.
- MUST После снятия сотрудника (`DELETE /points/{id}/staff/{userId}`) его следующий запрос к точке получает 403 без повторного входа.
- MUST Прежние операции работают как раньше: тестовые пользователи `admin`, `manager`, `cook` входят и видят свои экраны.
- SHOULD Управляющий точки назначает повара, но получает 403 при назначении управляющего.
- SHOULD С `AUTH_DISABLED=true` запрос без токена создаёт компанию, а чужая компания отвечает 403.
- SHOULD Форма регистрации Keycloak выглядит приемлемо для показа (язык, поля).
