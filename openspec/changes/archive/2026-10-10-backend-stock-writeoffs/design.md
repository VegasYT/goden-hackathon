# Design

## Context

Мотивация и границы - в proposal.md. Что уже есть в коде:

- `inventory/events.go`: события `StockWrittenOff` с типом `WriteOffReason`, `StockAdjusted`, `BatchExpiryWarningIssued`.
- `inventory/service.go`: `ConsumeForOrder` как образец складской операции - проверка `tx.Locked`, чтение из таблицы остатков, запись события, функция применения `applyStockConsumed`.
- `inventory_batches`: остаток с `CHECK (quantity >= 0)`.
- `command.Run`: блокировки, идемпотентность, `tx.Now()`.
- Правило "партия просрочена, если дата окончания срока не позже момента проверки" в `planConsumption`.

## Goals / Non-Goals

**Goals:**

- Worker разработчика B может вызывать списание просрочки и предупреждение сколько угодно раз без ключей идемпотентности и без риска дублей.
- Правила каждой операции - чистые функции от состояния партии и времени.

**Non-Goals:**

- Поиск партий-кандидатов и расписание: worker читает свою проекцию истекающих партий (B4) и вызывает команды по одной партии.
- Отмена списания. Ошибочное списание исправляется корректировкой остатка с причиной.
- Закрытый набор причин корректировки. В ADR набор задан только для списания; причина корректировки - свободная строка.

## Decisions

### 1. Четыре команды, три события

| Команда | Событие | Кто вызывает |
| --- | --- | --- |
| `WriteOffStock` | `StockWrittenOff` | пользователь |
| `WriteOffExpiredBatch` | `StockWrittenOff` с причиной `expired` | worker |
| `AdjustStock` | `StockAdjusted` | пользователь |
| `IssueBatchExpiryWarning` | `BatchExpiryWarningIssued` | worker |

Списание просрочки вынесено в отдельную команду, а не сделано режимом ручного списания: у неё другой контракт. Ручное списание отклоняет некорректный запрос ошибкой, а автоматическое обязано молча ничего не делать, если списывать уже нечего. Событие при этом одно, как требует ADR-011.

В `backend/plan.md` и `backend/AGENTS.md` команда списания названа именем события `StockWrittenOff`. Это неточность формулировки: `StockWrittenOff` - событие, команды - `WriteOffStock` и `WriteOffExpiredBatch`. Оба документа уточняются.

### 2. Идемпотентность операций worker

`WriteOffExpiredBatch` и `IssueBatchExpiryWarning` идемпотентны по состоянию партии, а не по ключу: решение принимается по строке таблицы остатков, прочитанной под блокировкой.

- Списание просрочки: остаток 0 или срок не истёк - ничего не делать.
- Предупреждение: отметка о выданном предупреждении уже стоит - ничего не делать.

Обе возвращают булев результат "сделано или нет" и не возвращают ошибку в этих случаях. Worker может повторять вызов после сбоя, не храня ничего у себя. Несуществующая партия - единственный случай ошибки "не найдено".

Ручные команды принимают ключ идемпотентности, как остальные команды пользователя.

### 3. Блокировка и чтение партии

Продукт партии нужен до транзакции, чтобы объявить складской поток в `Spec.Locks`. Он читается из таблицы остатков через пул: продукт партии не меняется. Внутри транзакции партия перечитывается под блокировкой, и решение принимается по свежей строке. Так выполняется требование ADR-011: команда повторно проверяет актуальные срок и остаток в write model.

### 4. Чистые функции решений

Файл `stock.go`:

```go
func planWriteOff(b Batch, quantity int64, reason WriteOffReason, comment string, actor, now) (StockWrittenOff, error)
func planExpiredWriteOff(b Batch, actor, now) (StockWrittenOff, bool)
func planAdjustment(b Batch, delta int64, reason, comment string, actor) (StockAdjusted, error)
func planExpiryWarning(b Batch, period time.Duration, now) (BatchExpiryWarningIssued, bool)
```

Проверка просрочки вынесена в метод `Batch.expiredAt(now)` и используется во всех местах, включая `planConsumption`: правило записано один раз.

Условие предупреждения: срок не истёк, остаток больше нуля, отметки нет, и `expires_at - now <= period`.

Ручное списание с причиной `expired` требует, чтобы партия действительно была просрочена: иначе в аналитике разработчика B годная партия попала бы в потери от просрочки. Просроченную партию при этом можно списать и с другой причиной, например `physical_damage`.

### 5. Изменения в таблице и запросах

Миграция добавляет столбец `expiry_warned_at timestamptz` в `inventory_batches`. Тип `Batch` получает поле `ExpiryWarnedAt`.

Запросы:

- чтение одной партии по идентификатору;
- изменение остатка на величину со знаком - заменяет запрос уменьшения из `ConsumeForOrder`, чтобы списание, расход и корректировка шли через один запрос;
- установка отметки предупреждения.

Функции применения: `applyStockWrittenOff`, `applyStockAdjusted`, `applyBatchExpiryWarningIssued`. Вместе с уже существующими они покрывают все пять событий складского потока.

### 6. Интерфейс

```go
type WriteOff struct{ BatchID uuid.UUID; Quantity int64; Reason WriteOffReason; Comment string }
type Adjustment struct{ BatchID uuid.UUID; Delta int64; Reason, Comment string }

func (s *Service) WriteOffStock(ctx, actor, key string, in WriteOff) (Batch, error)
func (s *Service) WriteOffExpiredBatch(ctx, actor, batchID uuid.UUID) (writtenOff bool, err error)
func (s *Service) AdjustStock(ctx, actor, key string, in Adjustment) (Batch, error)
func (s *Service) IssueBatchExpiryWarning(ctx, actor, batchID uuid.UUID, period time.Duration) (issued bool, err error)
func (s *Service) Batch(ctx, id uuid.UUID) (Batch, error)
```

Ручные команды возвращают партию после операции. Автор передаётся явно и для команд worker: по ADR-011 это сервисная учётная запись.

## Risks / Trade-offs

- [Увеличение остатка корректировкой не ограничено сверху] → ошибка ввода может завысить остаток. Принято: пересчёт склада законно находит излишки, а корректировка записана событием с автором и причиной и видна в аудите.
- [Корректировка просроченной партии разрешена] → остаток просроченной партии можно изменить, хотя расходовать её нельзя. Это нужно, чтобы исправить расхождение перед списанием.
- [Предупреждение один раз, даже если период увеличили] → партия, предупреждённая за сутки, не получит второго предупреждения при периоде в двое суток. Так задано ADR-008, чтобы смена настройки не рассылала сообщения по всему складу.
- [Worker вызывает команды по одной партии] → при тысяче просроченных партий это тысяча транзакций. Для склада ресторана объём мал, а короткие транзакции не задерживают читателей событий.
- [Проекция кандидатов у worker может отставать] → команда решает по таблице остатков под блокировкой, поэтому устаревший кандидат даёт вызов без эффекта, а не ошибочное списание.
