# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- Движок `platform/projection`: проекция - имя, версия, `Apply`, `Reset`; `Run` и `CatchUp`.
- Состояние поставки - свёртка событий её потока: `loadDelivery(ctx, q, id)` читает поток и возвращает `Delivery` с позициями. Этим пользуются и команды, и `GET /deliveries/{id}`.
- Состояние заказа - свёртка потока из одного события; времени оформления в `Order` нет, хотя оно есть в конверте события.
- `cmd/worker`: функция `tasks` возвращает пустой список; у процесса есть пул, реестр метрик и `/metrics`.
- Контракт: `Delivery`, `Order`, параметры `Limit` и `Offset`, страницы `{items, total}`; право операции - в `security`.
- `apitest.New` поднимает API; тест `TestEveryOperationHasARequest` требует запрос в матрице прав для каждой операции.
- Правило плана: проекции склада лежат в модуле `inventory`, в файлах проекций.

## Goals / Non-Goals

**Goals:**

- Список не расходится с чтением по идентификатору: одно и то же состояние, одна логика его построения.
- Проекция остаётся маленькой: новая логика предметной области в ней не появляется.
- Тесты эндпоинтов списков детерминированы.

**Non-Goals:**

- Остатки по складу и истории (вторая часть B2).
- Произвольная сортировка и фильтры по датам, продукту, автору.
- Чтение своей записи без задержки.

## Decisions

### 1. Проекция поставок хранит готовое состояние

Таблица `inventory_deliveries`: идентификатор, номер, статус, дата поставки, признак открытого карантина и состояние поставки целиком в `jsonb`. Столбцы вне `jsonb` - только те, по которым идёт фильтр и сортировка.

`Apply` на любое событие потока поставки заново собирает состояние поставки существующей свёрткой `loadDelivery` в транзакции проекции и перезаписывает строку.

*Альтернатива:* отдельная логика применения каждого события к строкам проекции. Отклонена: это вторая реализация правил распределения количества по позициям, которая должна была бы в точности повторять свёртку. Корректировка приёмки и партии позиции делают её нетривиальной, а расхождение со чтением по идентификатору было бы дефектом.

Следствие выбранного варианта: свёртка читает поток до его текущего конца, поэтому строка может отражать события, до которых проекция ещё не дошла. Состояние в списке от этого только свежее; при обработке последующих событий того же потока строка перезаписывается тем же значением. При перестроении поток поставки читается столько раз, сколько в нём событий; потоки поставок короткие.

Признак открытого карантина: есть позиция с ненулевым карантинным количеством.

События, по которым проекция обновляет строку, определяются по потоку события (`delivery-<id>`), а не перечислением типов: новое событие поставки подхватится само, а если свёртка его не знает, она вернёт ошибку, и проекция остановится - это видно по метрикам.

### 2. Проекция истории заказов

Таблица `orders_history`: идентификатор, статус, время оформления и состояние заказа в `jsonb`. `Apply` на `OrderAccepted` и `OrderRejected` вставляет строку из содержимого события; время оформления - время события из конверта. Свёртка здесь не нужна: заказ - одно событие.

### 3. Время оформления заказа

`Order` получает поле `PlacedAt`. При чтении по идентификатору оно берётся из времени события потока, в истории - оттуда же при применении события. В контракте `Order` получает `placed_at`.

Результат команды оформления тоже содержит `placed_at` (время команды), поэтому ответ `POST /orders` и последующее чтение совпадают. Сохранённые результаты прежних команд этого поля не имеют; для новой базы это не важно, для существующей повтор старого запроса вернёт заказ без времени - допустимо, поле в контракте необязательное.

### 4. Запросы списков

Запросы sqlc в `queries.sql` модулей: выборка страницы и подсчёт общего числа с одинаковыми условиями. Необязательные фильтры - через `sqlc.narg`. Сортировка: поставки - по дате поставки и идентификатору по убыванию, заказы - по времени оформления и идентификатору по убыванию. Идентификаторы - UUIDv7, поэтому при равном времени порядок совпадает с порядком создания.

Состояние из `jsonb` раскодируется в те же типы `Delivery` и `Order`, из которых обработчики уже строят ответы.

Индексы: по `(status, delivered_at)` и частичный по открытому карантину для поставок; по `(status, placed_at)` для заказов.

### 5. Операции контракта

- `listDeliveries`: `GET /deliveries`, параметры `status` (перечисление), `quarantine` (перечисление из одного значения `open`), `limit`, `offset`; ответ `DeliveryPage`; право `deliveries.view`.
- `listOrders`: `GET /orders`, параметры `status`, `limit`, `offset`; ответ `OrderPage`; право `orders.view`.

Фильтр карантина - перечисление, а не булев параметр: позже к `open` можно добавить другие значения без смены контракта.

### 6. Список проекций и worker

Новый пакет `internal/readmodel` с функцией, возвращающей все проекции системы; ему нужны сервисы или пул, из которых проекции читают состояние. Его используют `cmd/worker` и `apitest`.

`cmd/worker` в `tasks` создаёт движок на реестре процесса и запускает `engine.Run` для каждой проекции как отдельную задачу. Ошибка проекции процесс не завершает: `Run` повторяет порцию сам.

*Альтернатива:* выполнять проекции внутри процесса API. Отклонена: API можно запустить в нескольких экземплярах, и фоновые задачи в нём мешают масштабированию и корректному завершению; `cmd/worker` для этого и заведён. Цена: для локальной работы нужно запускать ещё один процесс.

### 7. Тесты

`apitest.Server` получает метод `Sync(t)`: он вызывает `CatchUp` для всех проекций. Тесты списков вызывают его после записи и перед чтением. Фоновых проекторов в тестовой обвязке нет: тест сам решает, когда проекции догоняют.

Тест "worker выполняет проекции" запускает задачи worker на тестовой базе и ждёт появления записей в списках.

Тест соответствия: поставка проходит полный путь, после `Sync` элемент списка сравнивается с ответом чтения по идентификатору.

## Risks / Trade-offs

- [Списки отстают от записи] → до периода опроса проектора плюс время порции; чтение по идентификатору не отстаёт. Frontend после создания показывает ответ команды, а список обновляет позже или по SSE (B7).
- [Без запущенного worker списки пусты] → записывается в раздел запуска `backend/AGENTS.md`; на дашборде видно отставание проекций.
- [Состояние в `jsonb` дублирует события] → проекция пересоздаваема; при изменении формата состояния версия проекции увеличивается, и она перестраивается.
- [Строка поставки может опережать позицию проекции] → см. решение 1; на корректность списка не влияет.
- [Подсчёт общего числа при каждом запросе списка] → на учебных объёмах дёшево.
- [Старые сохранённые результаты заказов без времени оформления] → см. решение 3.
