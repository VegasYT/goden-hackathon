# Proposal

## Why

Поставку и заказ можно создать и прочитать по идентификатору, но нельзя получить их список: у приёмщика нет очереди поставок на приёмку и открытых карантинов, у менеджера - истории заказов. Поставка и заказ живут только как потоки событий, таблиц у них нет, поэтому список по ним - это асинхронная проекция. Движок проекций готов (B1). Это первая часть задачи B2 из [backend/plan.md](../../../backend/plan.md); разработчик B задерживается, задачу выполняет разработчик A.

## What Changes

- Появляются первые две проекции: поставки (в модуле `inventory`) и история заказов (в модуле `orders`).
- `GET /api/v1/deliveries` - список поставок с фильтрами по статусу и по наличию открытого карантина, с пагинацией. Каждый элемент - полное состояние поставки с позициями, как в `GET /deliveries/{id}`.
- `GET /api/v1/orders` - история заказов с фильтром по статусу и пагинацией. В заказе появляется время оформления.
- `cmd/worker` начинает выполнять проекции: теперь это рабочий процесс, без которого списки пусты.
- Тестовая обвязка API получает способ дождаться проекций, чтобы тесты чтения после записи были детерминированы.

Списки отстают от записи на доли секунды: запись идёт в Event Store, проекция догоняет его асинхронно. Чтение по идентификатору (`GET /deliveries/{id}`, `GET /orders/{id}`) по-прежнему строится по событиям потока и не отстаёт.

Вторая часть B2 - отдельным изменением: остатки по складу, история приёмки поставки и движения по продукту. Им проекции не нужны: остатки читаются из таблицы партий, истории - из потоков событий.

Вне изменения: ожидание проекции внутри запроса чтения; фильтры по датам и по продукту; SSE (B7).

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `deliveries`: список поставок.
- `orders`: история заказов, время оформления заказа.
- `projections`: процесс worker выполняет проекции.

## Impact

- **Код:** `internal/inventory/projection.go`, `internal/orders/projection.go`, запросы sqlc и обработчики чтения в обоих модулях; новый пакет со списком проекций процесса; `cmd/worker`; `api/openapi.yaml` и перегенерированный `oas`; `apitest`; миграция двух таблиц.
- **Запуск:** для работы списков нужен запущенный `cmd/worker`. В `backend/AGENTS.md` это записывается в раздел запуска.
- **Права:** `GET /deliveries` требует `deliveries.view`, `GET /orders` - `orders.view`.
- **Frontend:** получает списки для экранов приёмки и истории заказов; должен учитывать, что только что созданная запись появляется в списке с задержкой до нескольких сотен миллисекунд.
- **Документы:** `backend/AGENTS.md`, `backend/plan.md` (B2 выполняет разработчик A, первая часть готова).
