# Design

## Context

См. `proposal.md` — Why. Оба compose уже запускают Grafana с provisioned Prometheus; серверный compose держит API, worker и generator в контейнерах, а локальный обычно запускает backend на хосте. Backend использует `slog` JSON handler в stdout, добавляет `correlation_id` из контекста и читает минимальный уровень из `LOG_LEVEL` со значением `info` по умолчанию. ADR-007 закрепляет Promtail → Loki → Grafana.

Promtail достиг EOL 2 марта 2026 года. Это осознанное ограничение запроса и ADR, а не новая рекомендация стека.

## Goals / Non-Goals

**Goals:**

- один и тот же подход к контейнерным логам в dev и prod;
- единый управляемый порог `DEBUG`, `INFO`, `WARN` или `ERROR` для backend-контейнеров;
- поиск по стабильным labels и прикладным JSON-полям;
- ограниченное дисковое потребление на одном сервере;
- отказ логового конвейера не влияет на приложение.

**Non-Goals:**

- агент на хосте для локальных `go run` процессов;
- кластерный Loki, репликация и удалённое объектное хранилище;
- превращение прикладных полей в labels и алерты по логам.

## Decisions

### 1. Loki работает в single-binary режиме с локальным TSDB

Добавляется общий конфиг Loki со schema `v13`, TSDB и filesystem storage. В prod каталог данных монтируется в именованный том; compactor включает retention `168h`. Для хакатонного одноузлового сервера это проще объектного хранилища и соответствует текущему compose-развёртыванию.

Альтернатива — S3-совместимое хранилище — не выбрана: она добавляет сервис и секреты без требования к отказоустойчивости нескольких узлов.

### 2. Promtail обнаруживает только контейнеры своего compose-проекта

Promtail получает read-only доступ к Docker socket и каталогу json-file логов, использует Docker service discovery и фильтр по label `com.docker.compose.project`. Relabeling создаёт только `environment`, `compose_project`, `compose_service` и `stream`; технические discovery labels удаляются. Конфиг параметризуется именем проекта и окружением для `goden` и `goden-prod`.

Альтернатива — читать все файлы Docker по glob — не выбрана: она захватывает чужие проекты и не даёт устойчивого имени сервиса после пересоздания контейнера.

### 3. Порог применяется в backend, а JSON разбирается в LogQL

API, worker и generator получают `LOG_LEVEL` из окружения; compose использует `INFO`, если значение не задано. Backend формирует только записи не ниже порога, а Promtail не применяет собственную фильтрацию по уровню. Так единственным источником правила остаётся уже существующая конфигурация приложения.

Pipeline снимает только внешний Docker JSON envelope. Внутренний JSON backend остаётся строкой и разбирается запросом `| json`, например `{compose_service="api"} | json | level="ERROR"` или `{compose_service="api"} | json | correlation_id="..."`. `level`, `msg` и `correlation_id` не становятся Loki labels: особенно `correlation_id` создавал бы серию почти на каждый запрос.

Вывод остальных контейнеров остаётся обычным текстом и ищется по labels и содержимому.

### 4. Grafana получает отдельный provisioned datasource Loki

В существующем provisioning рядом с Prometheus добавляется datasource с постоянным UID `loki` и внутренним URL `http://loki:3100`. Prometheus остаётся datasource по умолчанию. Grafana ждёт готовность Loki, но недоступность Loki не входит в зависимости API, worker и generator.

### 5. Данные и позиции отделены от конфигурации

Конфиги Loki и Promtail монтируются read-only. Данные Loki и файл positions Promtail хранятся в отдельных именованных томах; обычный `down` и выкладка их сохраняют, `down -v` удаляет. В dev используется та же схема, хотя гарантия сохранения логов сформулирована только для prod.

### 6. Образы закрепляются без `latest`

Для Loki выбирается поддерживаемая совместимая версия. Для Promtail закрепляется последний доступный образ, совместимый с выбранным Loki, и проверяется его получение до фиксации compose. Автоматическое обновление Promtail запрещено из-за EOL; переход на Alloy требует отдельного change и обновления ADR-007.

## Risks / Trade-offs

- [Promtail больше не получает исправления] → закрепить образ, не публиковать его HTTP-порт, дать только необходимые mounts и запланировать отдельную миграцию на Alloy.
- [Docker socket раскрывает агенту метаданные и управление daemon API] → mount только внутри непубличного Promtail, read-only там, где поддерживается, и не добавлять агенту внешнюю сеть/порт; это остаётся известным риском Docker discovery.
- [Loki заполняет диск] → retention семь суток, данные в отдельном томе и команды контроля/очистки в `infra/README.md`.
- [Недоступный Loki теряет часть логов при длительном сбое или ротации Docker] → приложения не зависят от Loki; Promtail повторяет доставку, но конвейер не считается аудит-хранилищем.
- [Локальные backend-процессы не видны] → документация явно отделяет контейнерные логи от stdout процессов, запущенных на хосте.

## Migration Plan

1. Добавить конфиги, datasource и сервисы, проверить итоговый compose и закреплённые образы.
2. Поднять локальный набор, породить контейнерную запись и проверить запрос к Loki и Explore Grafana.
3. Выложить prod compose: новые тома создадутся автоматически, существующие сервисы продолжат запуск независимо от логового конвейера.
4. Для отката вернуть прежний compose и provisioning. Именованные тома Loki/Promtail оставить для возможного повторного включения либо удалить отдельной явно указанной командой; бизнес-данные это не затрагивает.
