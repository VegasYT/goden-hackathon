## Context

Номер поставки записан только в событии `DeliveryRegistered` её потока и в проекции списка поставок. Таблица партий `inventory_batches` хранит идентификатор поставки. Номер поставки после регистрации не меняется.

## Decisions

### Номер читается из первого события потока поставки

Обработчик собирает идентификаторы поставок страницы и одним запросом читает первые события их потоков (`stream_version = 1`, по уникальному индексу `stream_id, stream_version`). Для этого в `eventstore` добавляется чтение первых событий набора потоков.

Альтернативы:
- проекция `inventory_deliveries`: один запрос sqlc, но проекция асинхронна; во время перестроения обязательное поле осталось бы пустым. Отклонено;
- столбец номера в `inventory_batches`: таблица восстанавливается из `BatchReceived`, а номера в этом событии нет; записывать номер в события не нужно. Отклонено.

Выбор сделан по правилу проекта: чтение по идентификатору идёт по потоку событий и от проекций не зависит.

### Партия движения находится по таблице партий

Движение знает только идентификатор партии. Поставка партии берётся из `inventory_batches` одним запросом по идентификаторам страницы: строки пустых партий там остаются.

### Подстановка в обработчике

Как названия продуктов в позициях поставки (`named`): сервис отдаёт партии и движения без номера, обработчик дополняет ответ. Номер, который не удалось найти, остаётся пустой строкой: ответ склада из-за него не срывается. Для партий, созданных приёмкой, такого случая нет.

## Risks / Trade-offs

- Два дополнительных запроса на чтение движений и один на чтение партий. Страница ограничена 200 элементами, оба запроса идут по индексам.
- Клиент, который отправлял списание без поля `comment`, получит 400 вместо 422. Frontend сам попросил обязательное поле.
