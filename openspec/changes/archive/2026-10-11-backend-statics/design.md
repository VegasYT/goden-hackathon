# Design

## Context

См. `proposal.md` — Why. Event Store содержит все необходимые факты: `StockWrittenOff`, `OrderRejected`, `StockConsumed`, изменения рецептур и складских партий. Текущие стоп-лист и остатки считаются без задержки по write model, а аналитика по ADR-002 должна быть асинхронной и перестраиваемой. Общий движок проекций и регистрация в `readmodel.Projections()` уже существуют.

## Goals / Non-Goals

**Goals:**

- один воспроизводимый источник данных для трёх аналитических HTTP-отчётов;
- детерминированный расчёт интервалов стоп-листа и прогноза с управляемыми часами в тестах;
- согласованность доступности блюда с действующими правилами рецептур, непросроченных партий и FEFO.

**Non-Goals:**

- синхронное обновление аналитики в транзакции команды;
- статистические модели спроса, сезонность и хранение готовых прогнозов;
- отдельная пагинация небольших агрегированных отчётов B8.

## Decisions

### Одна проекция `analytics` с нормализованными фактами и своим состоянием

Новая проекция хранит факты списаний, дефицитов заказов и расхода с `event_id` как ключом идемпотентности. Для истории влияния на стоп-лист она поддерживает восстановимые из событий партии, рецептуры и открытые интервалы `(dish_id, product_id, started_at)`; закрытые интервалы получают `ended_at`.

Перед применением очередного события проекция учитывает истёкшие к его `occurred_at` партии, затем применяет событие и пересчитывает только блюда затронутого продукта либо изменённое блюдо. Отдельный интервал ведётся для каждого одновременно недостающего ингредиента: поэтому длительность отражает суммарное влияние продукта на блюда. `Reset` очищает все таблицы модуля, после чего общий движок воспроизводит их заново.

Это следует из существующей архитектуры проекций. Альтернатива — агрегировать запросами непосредственно по `events` — хуже отделяет read model и заставляет заново воспроизводить состояние склада и рецептур при каждом HTTP-запросе.

### Три read-only операции в OpenAPI

Контракт получает:

- `GET /analytics/write-offs?from=&to=`;
- `GET /analytics/shortages?from=&to=`;
- `GET /analytics/stop-list-forecast?window_hours=&horizon_hours=`.

Первые две операции агрегируют факты и интервалы в PostgreSQL. Для незакрытого интервала верхней границей служит `to`; число входов считает только `started_at` внутри периода. Период полуоткрытый, проверка `from < to` выполняется в модуле и отображается общей обработкой ошибок как 400. Все три операции защищены `analytics.view`.

Альтернатива — единый большой ответ — сильнее связывает независимые экраны и не позволяет обновлять дорогой прогноз отдельно.

### Прогноз рассчитывается при чтении

История `StockConsumed` даёт расход продукта за окно; скорость равна сумме количества, делённой на длительность окна. Текущие блюда, рецептуры и партии читаются из существующих сервисов. Для каждого продукта алгоритм моделирует равномерный расход по FEFO и дискретное истечение партий до конца горизонта; первый момент, когда остаток становится меньше количества на порцию, становится кандидатом ингредиента. Минимальный кандидат определяет прогноз блюда.

Готовый прогноз не хранится: он зависит от текущего времени и быстро устаревает. Альтернатива — простое `общий остаток / скорость` — не выполняет требование учитывать сроки отдельных партий.

### Имена и единицы берутся из текущего каталога

Факты связываются стабильными UUID, а API дополняет их актуальными названием и единицей продукта и названием блюда. Исторические переименования не моделируются: событий переименования в домене нет.

## Risks / Trade-offs

- [Проекция отстаёт от Event Store] → это разрешено спецификацией; lag уже наблюдается общими метриками проекций.
- [Истечение времени само не создаёт событие ровно в момент срока] → следующий обрабатываемый факт продвигает время проекции и открывает интервал с фактического `expires_at`; штатный expiry worker гарантирует последующее событие списания.
- [Равномерная скорость расхода — упрощение] → API возвращает прогноз, а не гарантию; окно настраивается, сезонность сознательно вне scope.
- [Пересчёт затронутых блюд может расти с каталогом] → индекс по `product_id` ограничивает пересчёт; объём хакатонного каталога мал, полное кеширование не вводится.

## Migration Plan

1. Применить миграцию аналитических таблиц.
2. Развернуть worker с новой проекцией и дождаться нулевого lag: она заполнит данные из Event Store.
3. Развернуть API с новыми операциями.
4. Для отката убрать операции и проекцию; таблицы удаляются down-миграцией, источник событий не затрагивается.
