# Design

## Context

- **Контракт.** В `develop` уже есть статус `cancelled`, `cancelled_at`, операция `POST /points/{pointId}/orders/{orderId}/cancel` с ключом идемпотентности, `GET` и `PUT /points/{pointId}/migom` (`MigomOnPoint{outlet_id | null}`, право `company.manage`, без ключа идемпотентности). Бэкенд добавляет:
  - обязательное `placed_by` у `Order`;
  - `cancelled_by` и `cancel_comment` у отменённого заказа;
  - необязательное тело отмены `{comment}`;
  - право `orders.cancel`.

  Названия полей взяты из ответа бэкендера, а не из `openapi.yaml`, поэтому сначала сверяемся с контрактом после выкладки.
- **Отменённый заказ уже показан** (b935616): фильтр «Отменённые», чип «отменён», движение `returned`. Спека заказов отстала, её правит этот change.
- **Автор движения на складе** — `movementActor` и `serviceLabels` в `pages/stock/model/history.ts`: фоновый процесс подписан «Система», генератор — «Генератор». В поставках свой `actorLabel` из `entities/delivery`: любая сервисная учётная запись там «автоматически».
- **Настройки точки** — `pages/point-settings`: карточки на `SettingsSection`, запись точки через `useStorePoint`, чат Telegram — образец поля номера (`model/chat-id.ts`).
- **Макеты** — страница холста «Мигом: отмена заказов и подключение», вариант А истории.

## Goals / Non-Goals

**Goals:**
- отмена в два действия: меню строки и подтверждение;
- одна подпись автора для склада и заказов.

**Non-Goals:**
- своя строка Мигома в `point-signals.ts`: подключение меняет только владелец со своей страницы;
- подписи сервисных учётных записей в поставках.

## Decisions

1. **Общая подпись автора.**
   - `movementActor` и `serviceLabels` переезжают в `src/shared/lib/actor` под именем `actorName(actor)`. В таблицу добавляется `'migom-integration': 'Мигом'`.
   - Там же `isMigom(actor)`: сервисная учётная запись с идентификатором `migom-integration`.
   - Склад, строка заказа, подробности отмены и подтверждение берут подпись отсюда.
   - `actorLabel` поставок не трогаем: там «автоматически» для фонового процесса задано спекой поставок. Решение выведено из кода.
2. **Запись отмены.**
   - `cancelOrder(pointId, orderId, comment, idempotencyKey)` живёт в `pages/orders/api/orders.ts`. Пустой комментарий не отправляется.
   - Хук `useCancelOrder(pointId)` получает ключ из `useIdempotencyKey` по `{orderId, comment}`.
   - После ответа хук заменяет заказ на всех закэшированных страницах истории (`setQueriesData` по `orderKeys.lists`), поэтому строка сразу отменённая. Затем `refreshAfterOrder`: меню и горячие предложения сразу, история с задержкой. Остатки склада перечитают сигналы склада от возврата.
   - При ошибке история перечитывается сразу, без задержки: заказ уже отменил кто-то другой, проекция его знает.
3. **Действие и диалог.**
   - Меню «⋮» (`OrderActions`) стоит в последнем столбце таблицы и в карточке. Показывается у принятого заказа при `mayWrite(profile, point, 'orders.cancel')`.
   - Пункт «Отменить заказ» открывает `CancelOrderDialog` на `ConfirmDialog`: `confirmColor='error'`, «Не отменять» и «Отменить заказ». Внутри состав, автор, плашка Мигома, поле комментария с `maxLength` 1000. Ошибку диалог показывает сам.
   - Состояние диалога и сообщения держит хук `useOrderCancel` по образцу `useHotOffers`: он отдаёт `open(order)` и элементы для страницы. Сообщение без кнопки, потому что отмену не откатить.
   - Время в заголовке и сообщении: у сегодняшнего заказа только время, у более старого — дата и время.
4. **Таблица.**
   - Столбцы: Оформлен | Оформил | Блюда | Статус | Подробности | действия.
   - Компонент `Reason` становится `Details`: у отклонённого — нехватка, у отменённого — «Отменил <кто>, <время> · «комментарий»», у принятого — прочерк.
   - Раскрытый отменённый заказ показывает справа блок отмены вместо таблицы нехватки.
   - Столбец действий есть только у пользователя, который может отменять. Так у остальных ширина таблицы не меняется.
5. **Мигом на точке.**
   - В `entities/organization` добавляются `migomQueryOptions(pointId)` под ключом `['points', pointId, 'migom']` и `setMigomOnPoint(pointId, outletId | null)`.
   - Хук `useSetMigom` в `pages/point-settings` кладёт ответ в кэш.
   - Запрос включён только при `can(point, 'company.manage')`. Право записи — `writeAccess`: на отключённой точке (`disabled`) остаётся только снятие.
   - Номер разбирает `parseOutletId` (целое больше нуля) рядом с `parseChatId`.
   - PUT по контракту без ключа идемпотентности: запись повторяемая сама по себе.
6. **Тестовые данные.**
   - `testOrder` получает `placed_by` официанта по умолчанию. Добавляются `migomActor` и заказ Мигома.
   - Права `orders.cancel` даются официанту и управляющему в `test-orders.ts`. По словам пользователя, роли те же, что у оформления, а бэкендер добавил к ним управляющего. Интерфейс читает право из профиля, так что от этого допущения зависят только тестовые данные.
   - `ordersApi` учится отвечать на `POST …/cancel`, или тест подменяет `apiClient.post` сам по образцу соседних тестов записи.

## Risks / Trade-offs

- **Контракт может прийти с другими именами.** Типы пересоздаются первой задачей. Расхождение с этим design видно в `pnpm typecheck` до остальной работы, и о нём сообщаем до реализации.
- **Фильтр «Принятые» после отмены.** Отменённая строка остаётся на странице до перечитывания с задержкой и потом пропадает. Это приемлемо: строка честно показывает «отменён».
