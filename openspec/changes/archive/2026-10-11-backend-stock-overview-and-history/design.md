# Design

## Context

Мотивация и границы - в proposal.md. Что есть в коде:

- Таблица `inventory_batches` - синхронная таблица записи: остаток, срок годности, продукт. Её читает только модуль `inventory`.
- Каталог: `catalog.Service.Products(ctx, page)` возвращает страницу продуктов по алфавиту и общее число; таблицы каталога читает только модуль `catalog`.
- `foldDelivery(events)` собирает состояние поставки из событий потока; ей пользуются команды, чтение по идентификатору и проекция списка.
- Складской поток продукта `stock-<id>` содержит `BatchReceived`, `StockConsumed`, `StockWrittenOff`, `StockAdjusted`, `BatchExpiryWarningIssued`. Автор команды лежит в метаданных каждого события.
- `eventstore.ReadStream(ctx, q, stream, fromVersion)` читает поток от версии до конца по возрастанию.
- Правило просрочки одно: партия просрочена, если срок годности не позже момента проверки. В командах момент проверки - `tx.Now()`; у сервиса `inventory` своих часов нет, они есть у `command.Runner`.

## Goals / Non-Goals

**Goals:**

- Числа на экране склада совпадают с тем, по чему команды принимают решения: тот же источник и то же правило просрочки.
- История не вводит второй реализации правил поставки.
- Границы модулей не нарушаются: `inventory` не читает таблицы каталога.

**Non-Goals:**

- Проекции и новые таблицы.
- Сводные показатели по складу в целом и по категориям.
- Поиск и произвольная сортировка.

## Decisions

### 1. Остатки: страница каталога плюс агрегат по партиям

`inventory.Service.Stock(ctx, page)`:

1. берёт страницу продуктов у `catalog.Service.Products` - отсюда порядок по названию, общее число и продукты без партий;
2. одним запросом к `inventory_batches` считает агрегаты для продуктов этой страницы: суммы остатков годных и просроченных партий, число партий с остатком, ближайший срок среди годных;
3. соединяет результаты в порядке страницы каталога.

Момент проверки просрочки передаётся в запрос параметром и берётся из часов `command.Runner`: ему добавляется метод, отдающий текущее время. Так правило и источник времени те же, что у команд, а в тестах время управляется поддельными часами.

*Альтернатива:* один запрос с соединением таблиц партий и каталога. Отклонена: `inventory` читал бы таблицу другого модуля, что запрещено правилами и линтером.

*Альтернатива:* проекция остатков. Отклонена: таблица партий уже содержит эти данные и не отстаёт; проекция дала бы те же числа с задержкой. Просрочка зависит от текущего времени, а не только от событий, поэтому проекция её вообще не может хранить.

### 2. История поставки: свёртка префиксов потока

Обработчик читает поток поставки и для каждого события строит запись: вид события, время и автор из конверта, состояние - `foldDelivery` от событий потока по это включительно. Причина корректировки берётся из события `DeliveryApprovalCorrected`.

Новой логики распределения количества нет: история - это та же свёртка, остановленная на каждом шаге. Потоки поставок короткие, квадратичная стоимость несущественна. Пагинации нет по той же причине.

Автор берётся из метаданных события (`actor`), а не из полей содержимого: он есть у каждого события одинаково.

Решение по карантину с двумя исходами (часть принята, часть отклонена) записано двумя событиями и даёт две записи истории подряд: принятие и отклонение. Состояние в первой из них промежуточное - оставшаяся часть ещё числится в карантине.

### 3. Движения по продукту

Запись строится из одного события складского потока:

| Событие | Вид движения | Изменения по партиям | Дополнительно |
| --- | --- | --- | --- |
| `BatchReceived` | `received` | `+количество` | поставка, срок годности |
| `StockConsumed` | `consumed` | по одному на партию, со знаком минус | заказ |
| `StockWrittenOff` | `written_off` | `-количество` | причина, комментарий |
| `StockAdjusted` | `adjusted` | `дельта` | причина, комментарий |
| `BatchExpiryWarningIssued` | `expiry_warning` | партия с нулевым изменением | срок годности |

Пагинация - по событиям потока: общее число равно версии потока, страница читается новой функцией `eventstore.ReadStreamBackward(ctx, q, stream, beforeVersion, limit)`. Смещение переводится в версию: `beforeVersion = версия потока - offset + 1`.

Событие, которое обработчик не знает, даёт ошибку, а не пропускается: новое складское событие должно получить вид движения. Существование продукта проверяется через каталог: для неизвестного продукта - 404, для известного без поставок - пустой список.

### 4. Контракт

- `getStock`: `GET /stock`, `limit`, `offset`; ответ `StockPage` из `StockLevel` (`product`, `available_quantity`, `expired_quantity`, `batches`, `nearest_expires_at`); право `inventory.view`.
- `getDeliveryHistory`: `GET /deliveries/{deliveryId}/history`; ответ `DeliveryHistory` со списком `DeliveryHistoryEntry` (`type`, `occurred_at`, `actor`, `reason`, `delivery`); право `deliveries.view`.
- `listProductMovements`: `GET /products/{productId}/movements`, `limit`, `offset`; ответ `MovementPage` из `Movement` (`id`, `type`, `occurred_at`, `actor`, `changes[]` с `batch_id` и `delta`, необязательные `order_id`, `delivery_id`, `reason`, `comment`, `expires_at`); право `inventory.view`. Источник партии (приёмка, карантин, корректировка) в движение не выведен: он виден по истории поставки.

В `StockLevel` продукт вложен целиком (схема `Product`): экрану склада нужны название, единица и категория, а отдельный запрос каталога на каждую строку был бы лишним.

### 5. Тесты

Через API, в `internal/api`. Для остатков - поддельные часы: партия становится просроченной сдвигом времени. Для движений - сверка суммы изменений по партии с её остатком. Для истории - сравнение последней записи с чтением по идентификатору. Новые операции добавляются в матрицу прав.

## Risks / Trade-offs

- [Остатки считаются запросом при каждом обращении] → агрегат по индексу продукта для одной страницы каталога; на учебных объёмах дёшево.
- [Два чтения в остатках - каталог и партии - не в одной транзакции] → между ними может появиться партия; строка покажет остаток на момент второго чтения. Для экрана склада несущественно.
- [История пересчитывает свёртку для каждого события] → потоки поставок короткие.
- [Пагинация движений по событиям, а не по изменениям партий] → страница может содержать больше изменений, чем её размер, если заказ затронул несколько партий; размер страницы - это число движений.
- [Движения показывают все события потока, включая предупреждения без изменения остатка] → у них пустой список изменений; вид движения позволяет их отфильтровать на экране.
