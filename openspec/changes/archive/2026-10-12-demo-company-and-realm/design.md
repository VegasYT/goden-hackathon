## Context

Тестовые пользователи realm (`admin`, `manager`, `approver`, `cook`, `waiter`) раньше получали права ролями в токене. Теперь права даёт назначение на точку, а пользователь появляется в системе при первом обращении, и назначить можно только того, кто уже обращался. Keycloak на сервере запущен без тома: realm создаётся из файла при каждом создании контейнера.

## Goals / Non-Goals

**Goals:** после запуска окружения тестовые пользователи входят и сразу работают в своих ролях; realm не содержит прав, которые ничего не значат; самостоятельно зарегистрированные пользователи не пропадают.

**Non-Goals:** подтверждение почты, frontend, архивация changes, действия на сервере.

## Decisions

**Постоянные идентификаторы тестовых пользователей.** В файле realm им задаётся `id`: Keycloak использует его как `sub` токена. Так демонстрационную компанию можно создать до первого входа пользователей: их записи создаются с известными идентификатором и почтой. Альтернатива - назначать при первом входе - требовала бы особой логики в обычном пути входа.

**Демонстрационная компания создаётся командами, а не вставками в таблицы.** Пакет `internal/demo` вызывает сервисы `organization` и `generator`: компания, точки и назначения появляются как события, как у любого владельца. Ключи идемпотентности постоянные, поэтому повторный запуск ничего не добавляет. Каталог не создаётся: его наполняет генератор, включённый на первой точке.

**Запускает её `cmd/migrate` по настройке `DEMO_COMPANY`.** Это разовая задача, которая уже выполняется перед API и worker и в разработке, и на сервере. Без настройки ничего не создаётся. Чат Telegram первой точки задаётся настройкой `DEMO_TELEGRAM_CHAT_ID`: так на стенде уведомления демонстрационной точки приходят в чат команды, а точки чужих компаний туда не пишут.

**Из realm убираются все права, кроме `generator.run`.** Составные роли и client roles с permissions удаляются; сервисная учётная запись генератора сохраняет только `generator.run`. Список permissions из ADR-006 остаётся в коде как права ролей на точке. Проверка по токену в слое API остаётся для единственной операции - списка точек генератора.

**Том для данных Keycloak на сервере.** Каталог данных Keycloak выносится в именованный том; файл realm по-прежнему монтируется для первого импорта. Следствие: после первого запуска изменения файла realm сами не применяются (импорт пропускает существующий realm) - их вносят через консоль администратора либо пересоздают том, теряя зарегистрированных пользователей. В окружении разработки том не добавляется: там важнее, чтобы файл realm применялся при каждом пересоздании, а постоянные идентификаторы тестовых пользователей сохраняют их компании.

## Risks / Trade-offs

- Самостоятельная регистрация без подтверждения почты → назначение по адресу небезопасно для настоящей работы; ограничение показа, записано в `backend/AGENTS.md`.
- Keycloak хранит данные во встроенной файловой базе и дописывает их при штатной остановке: проверка показала, что после принудительного завершения контейнера только что созданный пользователь теряется, а после штатной остановки сохраняется → контейнеру задан срок остановки 60 секунд; при аварийном отключении сервера последние регистрации могут пропасть. Внешняя база для Keycloak - отдельная задача.
- Изменения realm на сервере после первого запуска требуют ручных действий → описано в `infra/README.md`.
- Frontend мог опираться на роли в токене → после этапа их нет; профиль `GET /me` отдаёт роль и права по каждой точке.
- Пересоздание стенда стирает данные → выполняется отдельно и по явному решению.
