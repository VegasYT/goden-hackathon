# Design

## Context

См. `proposal.md` — Why. Publisher уже публикует `BatchExpiryWarningIssued` в `expiry.v1`, `StockWrittenOff` в `stock.v1`, а постоянные ошибки consumers — как `ErrorEnvelope` в `errors.v1`. Общий Kafka consumer устраняет повторы доменных событий через PostgreSQL inbox. Telegram — внешний сетевой эффект, который нельзя атомарно зафиксировать вместе с inbox.

Стабильного публичного URL и маршрута на карточку партии во frontend нет, поэтому B9 не добавляет ссылки. Это допущение не меняет контракт уведомлений.

## Goals / Non-Goals

**Goals:**

- отделить приём Kafka-события от сетевой отправки;
- переживать временную недоступность Telegram и перезапуск worker;
- тестировать форматирование и доставку без реального бота;
- сохранить явное создание Kafka-топиков и штатное завершение worker.

**Non-Goals:**

- строгая exactly-once доставка через границу Telegram API;
- управление подписчиками, командами бота и несколькими чатами;
- изменение доменных событий или HTTP API.

## Decisions

### 1. Durable-очередь между Kafka и Telegram

Новая миграция создаёт `notification_deliveries`: уникальный ключ исходного сообщения, тип, готовый русский текст, состояние, число попыток, время следующей попытки и lease. Обработчик доменного события вставляет запись в той же транзакции, что и inbox; конфликт уникального ключа ничего не меняет.

Dispatcher короткой транзакцией захватывает готовую запись с lease, отправляет её вне транзакции и затем отмечает доставленной. При ошибке запись возвращается в ожидание с ограниченным exponential backoff. `SKIP LOCKED` и lease позволяют нескольким worker не отправлять одну запись одновременно и восстанавливаться после падения.

Альтернатива — вызвать Telegram из Kafka handler. Она проще, но удерживает транзакцию на сетевом вызове и может повторно отправить сообщение до записи inbox, поэтому отвергнута.

### 2. Два входных формата Kafka

Для `expiry.v1` и `stock.v1` используется общий `platform/kafka.Consumer`; нерелевантные типы и ручные списания завершаются без создания доставки. Для `errors.v1` нужен небольшой reader модуля notifications, потому что поток содержит `ErrorEnvelope`, а не доменный `Envelope`. Его ключ идемпотентности — хеш байтов Kafka-записи; повтор той же записи приводит к конфликту уникального ключа.

Перед чтением consumer явно создаёт полные имена своих топиков через общий Kafka helper. Для этого общий consumer запоминает набор топиков и проверяет их в начале `Run`; зависимость от broker auto-create не появляется.

### 3. Формирование сообщения при постановке в очередь

Handler проверяет версию и payload события, читает название продукта и срок партии из существующих синхронных таблиц и сохраняет уже готовый текст. Для предупреждения срок берётся из события, для просроченного списания — из партии. Некорректный поддерживаемый payload считается постоянной ошибкой и идёт в `errors.v1`; неизвестный тип безопасно игнорируется.

`ErrorEnvelope` форматируется без поля `original`: исходный payload может содержать лишние данные. В текст попадают только consumer, топик, event type/id и описание ошибки.

### 4. Telegram-клиент за малым интерфейсом

Модуль использует `go-telegram/bot` за интерфейсом `Sender`. Production-адаптер отправляет plain-text в один `TELEGRAM_CHAT_ID`; тестовый sender хранит вызовы и возвращает управляемые ошибки. Токен читается из `TELEGRAM_BOT_TOKEN` и нигде не логируется.

Если обе переменные пусты, notifications не добавляются в задачи worker. Частичная конфигурация — ошибка старта. Это решение следует общей конвенции конфигурации backend и оставляет локальный запуск без Telegram рабочим.

### 5. Наблюдаемость

Worker публикует счётчики попыток по закрытым меткам `kind` и `outcome`, gauge ожидающих доставок и счётчик ошибок чтения. Логи содержат вид уведомления, event ID и retry delay, но не токен, исходный payload или текст Telegram API-ответа, способный раскрыть данные.

## Risks / Trade-offs

- [Падение после успешного Telegram API и до отметки `sent` может дать дубль] → lease и durable-очередь сужают окно; абсолютная exactly-once доставка невозможна без идемпотентного ключа у Telegram API. Гарантия B9 относится к повторной Kafka-доставке после зафиксированной успешной обработки.
- [Поток `errors.v1` может содержать ошибку самого notifications consumer] → reader не перепубликует ошибки декодирования обратно в тот же топик; он логирует их и учитывает метрикой, исключая цикл.
- [Большой поток ошибок засорит чат] → один consumer group и дедупликация ограничивают повторы; rate limiting и агрегация остаются вне B9.

## Migration Plan

1. Применить миграцию очереди уведомлений.
2. Развернуть worker без Telegram-переменных: новое поведение остаётся отключено.
3. Создать bot token и chat ID вне репозитория, задать обе переменные и перезапустить worker.
4. Для rollback убрать переменные и откатить код; сохранённые записи очереди не влияют на остальные процессы.
