## Context

- Проверено по контракту и коду бэкенда (изменения `stock-filters`, `batch-delivery-number` в `develop`):
  - `GET /points/{pointId}/stock`: `q` (начало названия), `category`, `status` (`in_stock`, `expiring`, `expired`, `out_of_stock`, пересекаются), `sort` (`name`, `nearest_expiry`, `available`, минус — обратный), `limit`, `offset`; `total` после фильтров. `GET /stock/summary` с теми же `q` и `category` отдаёт `total` и число по каждому статусу.
  - Партии: `GET /products/{productId}/batches?in_stock=true` в порядке FEFO, просроченные с остатком в нём есть, пока их не списал worker. У партии есть `delivery_id` и `delivery_number`.
  - Движения: `GET /products/{productId}/movements` от новых к старым, страницами; у изменения партии есть `delivery_number`; автор — `Actor`, фоновый процесс — сервис `worker`, генератор — сервис со своим идентификатором клиента.
  - `POST /batches/{batchId}/write-offs` (`quantity`, `reason`, обязательный `comment`) и `/adjustments` (`delta` не 0, обязательный `reason`, `comment`), оба с `Idempotency-Key`, право `inventory.edit`, ответ — партия. Причина `expired` для годной партии и количество больше остатка дают 422 по полю; кода и предела у ошибки остатка нет. Отключённая точка — 409.
  - Права: `inventory.view` — владелец, управляющий, приёмщик; `inventory.edit` — владелец и управляющий.
- Во фронте: роут `/points/$pointId/stock` — заглушка с `requireSection`. Образцы — список поставок (`pages/deliveries`: схема адреса на zod-mini, `TablePagination`, `SegmentedControl`, сводка для чисел), история поставки (`SidePanel`, панель в адресе), `useIdempotencyKey`, `UnitQuantityField`, причины списания `reasonLabel` в `entities/delivery`. Каталог компании — `catalogProductsQueryOptions`.
- Макеты: страница «Склад» холста, артборды `StockLaptop`, `StockTablet`, `StockStates`, `StockMovements`, `StockWriteOff`, `StockAdjust`.

## Goals / Non-Goals

**Goals:**
- Склад, который сам остаётся актуальным, пока его держат открытым на смене.

**Non-Goals:**
- Вкладки «Сроки» и «Пора заказать»: страница строится так, чтобы их можно было добавить, но панели вкладок в этом изменении нет.

## Decisions

### Слайсы

```
pages/stock
  api     stockKeys ['points', pointId, 'stock', ...], запросы остатков, сводки, партий,
          движений (infinite); writeOff, adjust
  model   схема адреса и перевод в параметры запроса; статусы и подписи;
          проверки списания и исправления; сборка ленты истории по дням
  ui      страница, фильтры, таблица и карточки, партии, панель истории,
          диалоги списания и исправления, уведомление
shared/ui/search-field   поле поиска с паузой ввода (перенос из pages/deliveries: второй потребитель)
shared/lib/quantity   показ на складе: малые количества в г и мл
app/routes/points.$pointId.stock.tsx   validateSearch, loader
```

Запросы склада пока нужны одной странице, поэтому лежат в `pages/stock`, а не в `entities` (правило проекта: в сущность переезжает при втором потребителе — им станут вкладка «Сроки» на той же странице или сводка). Причины списания остаются в `entities/delivery`; страница импортирует `reasonLabel` и порядок причин, для чего `writeOffReasons` добавляется в публичный API сущности.

### Адрес

Схема как у списка поставок: `q`, `category`, `status` (`all` по умолчанию), `sort` (`name`), `page`, `size` (10, от 5 до 50), `history` — идентификатор продукта открытой истории. Значения по умолчанию срезаются из адреса. Смена фильтра, поиска, категории, сортировки сбрасывает `page`. Поиск отправляется после паузы ввода, как в поставках. Раскрытые продукты в адрес не попадают: это локальное состояние строки.

### Категории

Список категорий берётся из каталога компании (`catalogProductsQueryOptions`, у всех, кому открыт склад, есть `catalog.view`): уникальные непустые категории по алфавиту. Отдельного запроса категорий в API нет. Выведено из контракта.

### Обновление

Остатки и сводка запрашиваются с `refetchInterval: 30_000` и с перечитыванием при фокусе (умолчание Query); пока идёт перечитывание, показываются прежние строки (`placeholderData`, как у поставок). Партии раскрытого продукта перечитываются с тем же интервалом, а после записи весь склад точки инвалидируется по общему префиксу ключа. Диалог хранит свои значения в собственном состоянии, перечитывание его не сбрасывает. Через SSE это заменится позже (раздел 8 чек-листа): ключи уже начинаются с `['points', pointId, 'stock']`.

### Количества

В `shared/lib/quantity` добавляются функции показа для склада, поставки их не используют:
- количество: меньше 1000 г или мл — целое в «г» или «мл», иначе кг или л с запятой, до трёх знаков без нулей в конце; штуки — «шт»;
- пара «остаток из принятого»: единица выбирается по принятому, остаток показывается в ней же;
- изменение со знаком «+» или «−».

Поля ввода — `UnitQuantityField` в кг, л и шт, как в поставках. Функции понадобятся и кухне для рецептур.

### Списание и исправление

- Оба диалога держат значения в состоянии компонента: полей мало, массивов и подписок по строкам нет, поэтому TanStack Form здесь лишний (отступление от первоначального плана, принято при реализации). Правила проверки — чистые функции модели (количество от 1 до остатка партии, комментарий не пустой после обрезки, причина `expired` только у истёкшей партии; фактическое количество не равно текущему, причина не пустая).
- Ключ идемпотентности — `useIdempotencyKey` по телу запроса.
- После успеха: ответ (партия) кладётся в кэш партий, инвалидируется весь префикс склада точки, показывается уведомление.
- Ошибка 422 по `quantity` или `delta` — признак, что остаток партии уменьшился: диалог перечитывает партии продукта и показывает «Сейчас в партии X, было Y». Если перечитанный остаток не меньше введённого, показывается текст ошибки сервера. Код ошибки сервер не отдаёт, поэтому различаем по полю.
- Причина «Истёк срок годности» неактивна, пока выбранная партия не просрочена по «сейчас», которое тикает раз в минуту (`useNow`).
- Исправление открывается из меню «…» партии; ссылка «поставке № N» в подсказке ведёт на карточку поставки, где есть «Исправить приёмку».

### Доступ к действиям

`mayEditStock(profile, point)` по образцу `mayApproveDeliveries`: право `inventory.edit` и работающая точка. Без него действий с партиями нет, вместо них пояснение. Отдельного адреса у диалогов нет, поэтому проверки роута не нужны.

### Авторы в истории

Пользователь — его имя; сервис `worker` — «Система»; любой другой сервис — «Генератор» (других сервисных учётных записей с записью на склад нет). Выведено из кода бэкенда: `inventory.WorkerActor` и учётная запись генератора.

### Планшет

Разметка выбирается по `useMediaQuery` от `lg`, как в поставках: от `lg` — таблица с вложенной таблицей партий, ниже — карточки. Диалог «Фильтры» содержит категорию и сортировку; поиск и чипы статуса остаются на экране.

## Risks / Trade-offs

- [Перечитывание раз в 30 секунд при открытой вкладке даёт 2 запроса в минуту на пользователя] → допустимо до SSE; при скрытой вкладке Query не перечитывает по таймеру.
- [Ошибку остатка отличаем по полю, а не по коду] → дополнительно сверяем с перечитанным остатком; если бэкенд добавит код и предел, проверка упростится.
- [Поиск только по началу названия: «черри» не найдёт «Томаты черри»] → так работает API, плейсхолдер «Название продукта».
