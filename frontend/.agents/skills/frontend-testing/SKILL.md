# Тесты

## Нужен ли тест

Тест нужен для значимых happy path, достижимых крайних случаев и реальных регрессий. Процент покрытия и число тестов не цель. Изменение кода само по себе не требует нового теста.

Перед тем как писать тест, найди существующие проверки, в том числе на более низком уровне, и ответь себе:

- Какое реальное поведение или какой реальный сбой ловит этот сценарий?
- Не покрывает ли его уже другой тест? Что нового найдёт эта проверка?
- На каком самом низком уровне это поведение можно проверить достоверно?

Нет отдельной пользы — не пиши тест, прогони подходящие существующие. Не дублируй через UI тест утилиты или стора, если связка компонентов не добавляет своего риска. Это рабочее решение агента: разрешения на него не спрашивают и отчёт по каждому тесту не пишут.

## Что проверять и чего не проверять

- Проверяй наблюдаемый результат и значимые инварианты нашего кода. Не переписывай реализацию в assertions и не фиксируй внутреннее устройство без причины в поведении.
- Крайний случай должен быть достижим при текущем контракте. Не придумывай невозможные состояния, ветки, которых нет в коде, будущие фичи и сценарии «на всякий случай».
- Опирайся на итоговые требования, а не на историю обсуждения. Если от варианта отказались, не пиши тест, что его нет. Отрицательная проверка нужна только для реального требования или регрессии: отмена не сохраняет правки, чужие данные не меняются.
- Не покрывай косметику: цвета, CSS-классы, отступы, радиусы. Вид проверяют витрина `/dev/ui` и глаза. Исключения — автотест контраста (WCAG AA — требование) и геометрия, от которой зависит работа интерфейса: видимость, перекрытие, прокрутка.
- Не тестируй гарантии библиотек: работу React, MUI, Base UI, TanStack Router и Query, zustand, браузерного API. Проверяй нашу логику и её подключение к библиотеке, когда в подключении есть свой риск.

## Границы тестового файла

Тест лежит рядом с модулем (`foo.tsx` → `foo.test.tsx`) и проверяет сценарии этого модуля. Тест стора или утилиты не монтирует UI ради проверки состояния. Проверку связки нескольких модулей клади к их владельцу: оболочки и сценарии через роутер — в `app/` (слои ниже не импортируют `test-router`), страницы — в её слайс.

Бери минимум зависимостей, нужный сценарию. Сначала используй существующие хелперы, не раздувай setup и моки ради простой проверки. Дополняй подходящую группу сценариев, если она остаётся сфокусированной; несвязанные сценарии в один файл не складывай.

Тексты `describe` и `it` пишутся по-русски и описывают поведение: «Escape закрывает диалог без действия», а не «вызывает onClose».

## Прогоны

Из `frontend/`:

```bash
pnpm exec vitest run <путь>   # тесты, относящиеся к изменению
pnpm exec eslint <пути>       # точечный линт изменённых файлов, без --quiet
pnpm typecheck                # vitest типы не проверяет: зелёный тест может не компилироваться
pnpm lint:fsd                 # если менялись импорты между слайсами или структура слайса
pnpm check                    # перед сообщением о готовности: типы, линтеры, формат, все тесты
```

Предупреждения линтера в своих строках разбирай, а не пропускай. Среди них бывают предупреждения React Compiler.

## Поиск элементов

- Элемент с понятной пользователю подписью ищи так же, как пользователь: `getByRole(роль, { name })`, поле формы — `getByLabelText`. Так запрос заодно проверяет, что у элемента есть роль и подпись.
- `data-testid` — только там, где роли и подписи нет и не должно быть: контейнер, область прокрутки. Имя описывает назначение, а не вид или позицию.
- Не выбирай элемент по номеру в списке (`getAllByRole(...)[1]`): соседний элемент незаметно подменит цель.
- Нет подписи у нового контрола — добавь её (`aria-label` у кнопки-иконки), а не testid. Роли и aria-атрибуты, не нужные пользователю, ради теста не навешивай.
- Существующие `data-testid` не удаляй и не переименовывай без согласования с пользователем.

## Хелперы

| Что | Где |
|---|---|
| Рендер компонента в теме приложения | `renderWithTheme` из `@shared/lib/test-utils` |
| Подмена `matchMedia` по запросу (ширина, `pointer: coarse`) | `mockMatchMedia(query => …)`; широкий экран от 1200px — `mockWideScreen()` |
| Системная тема со сменой на лету | `mockSystemColorScheme('dark').set('light')` |
| Дата в поле пикера, новый текст поля с уходом с него | `typeDate(label, value)`, `retype(input, value)` оттуда же |
| Имя с количеством для `getByRole`, тексты ячеек строки таблицы | `withUnits('Списать 500 г')`, `rowCells(row)` оттуда же |
| Поток точки в тестах | `FakeEventSource` оттуда же; подключение и сигнал — `connect()`, `signal(categories)` из `src/app/test-realtime.ts` |
| Продукт, поставка и позиция поставки | `testProduct`, `testDelivery`, `testDeliveryItem` из `@entities/product/index.testing` и `@entities/delivery/index.testing`; в `src/app` их же реэкспортируют `test-stock.ts` и `test-deliveries.ts` |
| Приложение целиком на адресе с профилем в кэше Query | `renderApp(path, { profile?, tree?, wide? })` из `src/app/test-router.tsx`: роутер с настройками приложения (`appRouterOptions`), по умолчанию владелец одной точки `lenina` со всеми правами на широком экране; планшетный тест передаёт `wide: false` |
| Профиль и точка для теста | `testProfile(points?, companies?)`, `testPoint(overrides?)`, точка из API организации — `testOrgPoint(overrides?)` оттуда же |
| Сотрудник с ролью | `testStaffPoint(role, overrides?)` с правами роли из `rolePermissions`; готовые `manager`, `approver`, `cook`, `waiter` оттуда же |
| Ответы `GET` к API | `mockGet((url, params) => …)` из `src/app/test-api.ts`; готовые ответы разделов — `stockApi`, `deliveriesApi`, `kitchenApi`, `ordersApi` из `src/app/test-*.ts` |
| Запросы к адресу и их параметры | `requestsTo(mock, '/stock' \| /regexp/)`, `paramsOf`, `lastParams`, `lastListParams` (без счётчиков вкладок с `limit: 1`), ключ записи — `idempotencyKeyOf(call)` оттуда же |

`vitest.setup.ts` после каждого теста возвращает настоящие таймеры, размонтирует компоненты и чистит `localStorage`, `unstubGlobals: true` снимает `vi.stubGlobal`, а `mockReset: true` перед каждым тестом сбрасывает все моки и шпионы. Свои `afterEach` и `mockReset()` для этого не заводи.

## Известные грабли

- **React Compiler работает и в тестах:** `vite.config.ts` подключает его для Vitest тоже. Компонент без изменившихся пропсов отдаёт запомненную разметку:
  - мок хука с данными делай реактивным — состояние в сторе zustand, тест меняет его через `act(() => store.setState(…))`; обычный объект, изменённый перед `rerender`, не сработает;
  - обёртка без пропсов (`Harness`) тоже запоминается, поэтому `rerender(<Harness />)` ничего не меняет.
- **`renderApp` берёт клиент запросов приложения** (`createQueryClient({ test: true })`): повторов после ошибки нет, данные свежи 15 секунд. Тест, который двигает время дальше, увидит перечитывание при монтировании.
- **Окружение — jsdom:** раскладки нет, размеры элементов нулевые, `window.scrollTo` не реализован и пишет предупреждение. Геометрию и прокрутку проверяй в браузере через Playwright, а не в unit-тесте.
- **Неактивная кнопка с `pointer-events: none`:** `userEvent.click` бросает ошибку. Если сценарий проверяет, что нажатие ничего не делает, используй `userEvent.setup({ pointerEventsCheck: 0 })`.
- **`ToggleButtonGroup`, а значит и `SegmentedControl`, использует roving tabindex:** Tab попадает только на выбранный вариант, дальше стрелки и Enter.
- **Файл вне `src`, например `index.html`, читай импортом `?raw`:** `import html from '../../index.html?raw'`. У `node:fs` в проекте нет типов.
- **Значение по умолчанию у параметра:** `fn(undefined)` проваливается в дефолт. Для «нет данных» передавай `null`.
- **Моки сбрасываются перед каждым тестом (`mockReset: true`):** `vi.fn()` снова возвращает `undefined`, `vi.fn(impl)` возвращается к `impl`, шпион `vi.spyOn` — к настоящей функции. Ответы, нужные всем тестам файла, задавай в `beforeEach`, а не на уровне модуля; `…Once` — только если тест гарантированно делает этот вызов.
