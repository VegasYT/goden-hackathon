# AGENTS.md — frontend

Веб-клиент системы мониторинга склада ресторана. Общий контекст проекта: [../AGENTS.md](../AGENTS.md), кейс: [../docs/Case.md](../docs/Case.md).

## Стек

- React 19, TypeScript (strict), Vite, React Compiler
- Material UI v9 — UI-библиотека и тема (светлая и тёмная)
- Base UI — только для специфический модификаций UI, например для `QuantityField`
- TanStack Router — роутинг
- TanStack Query — серверное состояние; Zustand — только клиентское состояние
- TanStack Form + zod-mini — формы и валидация
- Vitest — тестирование
- Линтеры — eslint, stylelint, steiger (FSD валидация), tsc прогоны для типизаций
- Prettier — форматирование
- axios — единый HTTP-клиент
- pnpm — пакетный менеджер

## Команды

Запускаются из `frontend/`:

- `pnpm install` — установить зависимости
- `pnpm dev` — dev-сервер
- `pnpm build` — проверка типов и production-сборка
- `pnpm test` / `pnpm test:watch` — тесты Vitest
- `pnpm lint`, `pnpm lint:styles`, `pnpm lint:fsd`, `pnpm typecheck` — отдельные проверки
- `pnpm format` — отформатировать код
- `pnpm api:types` — пересоздать типы контракта `src/shared/api/schema.gen.ts` из `../backend/api/openapi.yaml` после изменения контракта
- `pnpm check` — все проверки разом. Перед завершением задачи он должен проходить.

## Архитектура

Feature-Sliced Design (FSD). Правила слоёв, слайсов и импортов — в FSD-скилле в `.agents/skills/`.

- Код лежит в `src/` по слоям FSD. Алиасы строго по слоям: `@app/*`, `@pages/*`, `@widgets/*`, `@features/*`, `@entities/*`, `@shared/*` → `src/<слой>/*`. Общего алиаса `@/` нет.
- Роуты TanStack Router — файлы в `src/app/routes/`. `src/app/routeTree.gen.ts` генерируется плагином и коммитится: руками не правим.
- Сессия — `src/shared/auth`: вход через Keycloak, `useSession()` (идентификатор и имя), `logout()`. Прав в токене нет.
- Права — из профиля `GET /me` (`src/entities/profile`: `meQueryOptions`, `findPoint`, `can`, `roleLabel`). Профиль загружается в `src/app/main.tsx` до создания роутера и лежит в кэше Query. Он перечитывается при возврате на вкладку и по запросу, а не при открытии каждой страницы.
- Разделы живут на точке: `/points/$pointId/...`. Layout точки проверяет её через `requirePoint` и кладёт в контекст роута (`context.point`). Роут раздела проверяет право на точке через `requireSection(point, section)`, страница внутри раздела — через `requirePermission(point, permission, section)` (`src/app/point-access.ts`); право раздела задаётся в `nav-items.ts` оболочки. Контекст роута — снимок на момент перехода, поэтому страницы и layout'ы разделов берут профиль и точку через `usePoint(pointId)` из `src/entities/profile`, а контекст читают только `beforeLoad` и загрузчики. Роутер приложения и `renderApp` собираются одними `appRouterOptions` (`src/app/router.tsx`). Пользователь без точек попадает на `/welcome`.
- Клиент API — `apiClient` из `src/shared/api`: адрес `/api/v1`, токен добавляется сам, ошибки приходят как `ApiError` с готовым текстом `message` и `fieldErrors` (по полю — текст, а также `code` и `limit`, если сервер их прислал). Типы запросов и ответов — `components` и `paths` из `src/shared/api/schema.gen.ts` (генерируется `pnpm api:types`, коммитится, руками не правим).
- Ключи запросов данных точки строятся от `pointKey(pointId)` из `src/shared/lib/query` (`[...pointKey(pointId), <раздел>]`, образец — `deliveryKeys` в `src/entities/delivery`): так весь раздел точки сбрасывается одним префиксом. `queryFn` чтения — `getData(url, params)` из `src/shared/api`. Общий клиент запросов — `createQueryClient` (`src/app/query-client.ts`, его же берёт `renderApp`): свежесть по умолчанию `pointDataFreshMs` (15 с), повтор только при обрыве связи и ответе 5xx (`shouldRetry` из `src/shared/api`). Своя свежесть только у исключений: профиль `/me` и карточка карантина перед решением — 0, продукты и категории каталога — `catalogFreshMs`. Своя запись и сигналы потока помечают данные устаревшими через `invalidateKeys` из `src/shared/lib/query`: начатый запрос не обрывается. Список, который строится проекцией, после своей записи обновляется ответом и перечитывается с задержкой (`storeDelivery`). Меню и стоп-лист считаются при каждом запросе: «Кухня» и «Стоп-лист» читают один запрос меню из `src/entities/dish` (`dishKeys`, `menuQueryOptions`), после включения блюда меню перечитывается сразу, выключенное блюдо убирается из меню без запроса. Поиск по меню — `menuMatcher` (на «Кухне» с `byIngredients` и по продуктам рецептуры, в новом заказе только по названию), пустое меню — `EmptyMenuState`, оба из `src/entities/dish`.
- Каталог компании — `src/entities/product` и `src/entities/dish`: ключи под префиксом `catalogKey(companyId)` из `src/shared/lib/query` (`productKeys`, `dishCatalogKeys`), списки с фильтрами сервера (`productListQueryOptions`, `companyDishesQueryOptions`), категории (`productCategoriesQueryOptions`, из них же фильтр категорий склада), продукт и блюдо по идентификатору и записи (создание, изменение, рецептура, архив и восстановление). `catalogProductsQueryOptions` — первая страница до 200 продуктов, её читают генератор и история продукта на складе. Выбор продукта с поиском на сервере — `ProductPicker` из `src/entities/product` (новая поставка, рецептура, новое блюдо): `disabledReason` делает вариант недоступным с подписью, `onCreate` добавляет пункт «Новый продукт «<текст>»», `clearOnSelect` очищает поле после выбора. Фильтр по категории — `ProductCategorySelect` (склад и каталог). Количество на порцию в единице продукта — `formatPortion` и `baseUnitLabel` из `src/shared/lib/quantity` («120 г»). Даты вводятся через `DateField` и `DateTimeField` из `src/shared/ui/date-field` (пикеры MUI X; провайдер дат с русской локалью живёт внутри полей, чтобы `date-fns` грузился только со страницами, где есть даты); в тестах дату вводит `typeDate` из `@shared/lib/test-utils`.
- Количества приходят целыми в единице продукта (`g`, `ml`, `pcs`); показ и ввод в кг, л и шт — `src/shared/lib/quantity`. Поставки показывают количества через `formatQuantity` («4,0 кг»), склад, кухня и стоп-лист — через `formatAmount`, `formatAmountOf` и `formatAmountDelta`: меньше 1 кг или 1 л — в граммах и миллилитрах («180 г»). Сроки годности и «сейчас» с тиком раз в минуту — `src/shared/lib/expiry`, подпись срока — `ExpiryLabel` из `src/shared/ui/expiry-label` (`lead='date'` в поставках, `lead='remaining'` на складе, `withDate`, `inline`, `expiredLabel`, `expiredNote`), даты — `src/shared/lib/datetime` (время события `formatEventTime`: сегодня только время, иначе дата и время; `isSameDay`; `minuteMs`, `hourMs`, `dayMs`; окна «24 часа / 3 дня / 7 дней» — `hourWindows` и `hourWindowLabels`, их поле адреса — `hourWindowField` из `src/shared/lib/search-params`), подписи и выбор причин списания — `src/entities/delivery` (`reasonLabel`, `WriteOffReasonSelect`, `WriteOffCommentField`, `AutoExpiredReason`; распределение количества позиции — `allocationText` и `AllocationWarning`). Поле количества в единице продукта — `UnitQuantityField` из `src/shared/ui/quantity-field`: оно принимает и отдаёт целые граммы, миллилитры и штуки.
- Формы — на TanStack Form (образец — форма приёмки в `src/pages/delivery`): правила предметной области — чистые функции модели, форма их не дублирует. Селектор стора формы, который возвращает новый массив или объект, сравнивается `shallowEqual` из `src/shared/lib/shallow-equal` (`compare` у `useSelector`). Обязательное поле показывает подсказку серым сразу (`missing`), а красным становится после ухода с пустого поля (`field.state.meta.isBlurred`, образец — причина и комментарий приёмки). Состояние списков (фильтр, поиск, страница) и открытая боковая панель (`panel`) — в адресе через `validateSearch` со схемой zod-mini (`src/pages/deliveries/model/search.ts`). Открытие панели добавляет запись в историю браузера, поэтому «Назад» её закрывает.
- Запись с повтором после сбоя отправляется с ключом из `useIdempotencyKey` (`src/shared/lib/idempotency`): ключ тот же, пока тело запроса не изменилось. Запись — обычная функция API, которая принимает ключ и передаёт его через `idempotencyHeader` (`setDishOnPoint`, `writeOffBatch`), а хук страницы получает его из `keyFor` и обновляет кэш после ответа. Поле поиска списка с паузой в наборе — `SearchField` из `src/shared/ui/search-field`, заготовка строк загрузки — `SkeletonList` из `src/shared/ui/skeleton-list`, загрузка, ошибка с «Повторить» и данные запроса — `QueryState` и `LoadErrorState` (`query`), «Ничего не нашлось» со сбросом — `NoResultsState`, всё из `src/shared/ui/empty-state`, список карточек на планшете — `CardList` и `CardListItem` из `src/shared/ui/card-list`, параметры адреса — `withDefault`, `textField` и `pageFields` из `src/shared/lib/search-params`, раскрытые строки списка — `useToggleSet` из `src/shared/lib/toggle-set`. Право записи на работающей точке — `mayWrite(profile, point, permission)` из `src/entities/profile`, а почему записывать нельзя (точка отключена или нет права) — `writeAccess`; пояснение об этом на экране — `AccessNote` из `src/entities/profile` (свой текст для отключённой точки и для отсутствия права), пояснение с одним текстом — `ReadOnlyNote` из `src/shared/ui/read-only-note`, спокойное пояснение с «i» — `InfoNote` из `src/shared/ui/info-note`. Боковая панель (история, открытый карантин) — `SidePanel` из `src/shared/ui/side-panel`. Лента истории (склад, поставка) — `TimelineItem` из `src/shared/ui/timeline`. Плашка неудачной записи с «Повторить» — `RetryAlert` из `src/shared/ui/retry-alert`. Вопрос при уходе с несохранённой формы — `useLeaveConfirm` из `src/shared/ui/confirm-dialog`: `useBlocker` вне `shared` не используется. Сообщение после записи — `useNotice` из `src/shared/ui/notice` (свой `Snackbar` страницы не заводят). Значок раскрытия строки — `DisclosureIcon` из `src/shared/ui/icon`, прочерк на месте пустого значения — `EmptyValue` из `src/shared/ui/empty-value`. Панель итога страницы передаётся в `PageContent` слотом `actionBar`.
- Склад — `src/pages/stock`: фильтры, сортировку и страницы считает сервер (`GET /stock`, числа чипов — `/stock/summary`). Ключи склада `stockKeys`, истекающие партии `expiringBatchesQueryOptions`, окно срочных сроков `urgentExpiringHours` и подпись срока партии `BatchExpiryLabel` — `src/entities/stock`: их читает и «Сводка». Пагинация — `ListPagination` (линия сверху только над карточками) и `usePagedSearch` из `src/shared/ui/list-pagination`: смена фильтра открывает первую страницу, страница за концом списка заменяется последней. Заголовок колонки с сортировкой сервера — `SortableHeaderCell` из `src/shared/ui/sortable-header-cell`, `placeholderData` запросов точки — `keepPointData` из `src/shared/lib/query`; после записи в партию перечитываются истекающие партии, рекомендации поставок (`recommendationKeys`) и меню кухни. Вкладки склада — дочерние роуты `src/app/routes/points.$pointId.stock.*.tsx`: layout держит вкладки и панель истории (`?history=`), право отдельной вкладки проверяет её `beforeLoad` по точке из контекста роута, открытие истории — `useHistoryPanel`. Доступное количество продукта по его партиям считает `productStock` (`src/pages/stock/model/actions.ts`). Доступное количество в ячейке, с чипом «нет в наличии» при нуле, показывает `AvailableAmount` (`src/pages/stock/ui/parts.tsx`). Просроченные партии сами не списываются: их списывают вручную. В выбор партии для списания они входят (`stockedBatches`), заказы расходуют только годные (`usableBatches`), диалог для просроченной партии открывается с причиной «Истёк срок годности» и всем остатком (`initialWriteOff`). Диалоги «Списать порчу» и «Исправить остаток» — `FormDialog` на TanStack Form (`useWriteOffForm`, `useAdjustForm` в `src/pages/stock/model`), ошибки считаются в рендере по живому остатку партии, комментарий с этой причиной необязателен (`reasonNeedsComment` из `src/entities/delivery`), кнопка списания — `WriteOffButton`. Плашку просрочки над «Сроками» считает `/stock/summary` (`expired`), а не страница партий. Автор действия (сотрудник, «Система», «Генератор», «Мигом», другой сервис — «автоматически») — `actorName` из `src/entities/actor`, заказ или действие Мигома — `isMigom`; его берут поставки, горячие предложения, история продукта на складе и история заказов. Число рядом с подписью — `CountBadge` из `src/shared/ui/count-badge`. Адрес точки в API — `pointPath`, компании — `companyPath`, заголовок ключа идемпотентности — `idempotencyHeader` из `src/shared/api`. Подпись вкладки с числом — `TabLabel` из `src/shared/ui/count-badge`.
- Аналитика — `src/pages/analytics`: прогноз стоп-листа, дефицит и списания читаются четырьмя независимыми запросами под `['points', pointId, 'analytics']`, загрузчик роута начинает их через `prefetchAnalytics`. Период (`7d`, `30d`, свой по датам) и горизонт прогноза — в адресе; для 7 и 30 дней `from` считается с полуночи, а `to` не передаётся, чтобы ключ запроса не менялся в течение дня (`periodOf`, `toPeriodParams`). Списания приходят парами «продукт и причина», свёртки по продукту и по причине — `writeOffsByProduct`, `writeOffsByReason`. Название продукта со ссылкой на его историю на складе (с правом `inventory.view`) — `ProductHistoryLink` из `src/entities/product`: выглядит как текст и подчёркивается при наведении; на вкладках склада с `inPlace` история открывается поверх текущей вкладки. Шкала прогноза — вёрстка (`timelineShare`, `timelineTicks`), график списаний по дням — `BarChart` из `@mui/x-charts` с цветами темы через `themeVars`; дни считает сервер в часовом поясе браузера, столбцы за все дни периода собирает `dayBars`.
- Заказы — `src/pages/orders`: история входящих заказов (`orderKeys`, фильтр по статусу и страницы считает сервер), вкладка «Горячие предложения» (`hotDishKeys` и `hotDishesQueryOptions` из `src/entities/dish`, их вместе с рекомендациями поставок перечитывает сигнал `recommendations`; текст причины из множителей — `explainReason`). Управляющий (`menu.manage`) закрепляет и скрывает предложения: ручные настройки — `hotOfferSettingsQueryOptions`, запись — `setHotOffer` из `src/entities/dish`, хук `useSetHotOffer` перечитывает весь `hotDishKeys`; действия, отмена в сообщении и диалог — `ui/use-hot-offers.tsx` и `ui/hot-offers.tsx`, скрытие до конца дня уходит с часовым поясом браузера (`browserTimeZone` из `src/shared/lib/datetime`), отмена возвращает прежнюю настройку блюда (`revertChange`). Отметка закреплённого блюда — `PinnedChip` из `src/entities/dish`, её показывают и новый заказ, и «Сводка» и ручное оформление `/orders/new` вне вкладок. Форма заказа ограничена меню точки (`model/order-form.ts`), итог (`OrderSummary`) и отправка — в `ActionBar`; оформление — хук `usePlaceOrder` (`api/order-writes.ts`): если блюдо выключили, пока заполнялся заказ, он перечитывает меню и называет выключенные блюда. История строится на сервере с отставанием, поэтому после сигнала `orders` и своего оформления перечитывается с задержкой: склеенный отложенный `invalidateQueries` — `invalidateLater` из `src/shared/lib/query` (непрерывная серия откладывает его не дольше 3 с), им же перечитываются списки поставок. Строка истории называет автора заказа (`placed_by`) и подробности статуса: нехватку у отклонённого, кто, когда и с каким комментарием отменил — у отменённого. Принятый заказ отменяет пользователь с `orders.cancel` на работающей точке из меню строки: запись `cancelOrder`, хук `useCancelOrder` (ответ сразу заменяет заказ на страницах истории, после отказа сервера история перечитывается), подтверждение и сообщение — `ui/use-order-cancel.tsx` и `ui/order-cancel.tsx`.
- Сводка — `src/pages/dashboard`: счётчики-ссылки и короткие списки, каждый блок показывается по своему праву на точке, грузится своим запросом и падает отдельно (`blockQuery`). Запросы те же, что у разделов (`expiringBatchesQueryOptions`, `menuQueryOptions`, `hotDishesQueryOptions`, `deliveryListQueryOptions`, `deliverySummaryQueryOptions`), поэтому сигналы потока обновляют сводку без своей строки в `point-signals.ts`. Какие блоки видны, решает `dashboardBlocks`: по нему и страница, и загрузчик роута (`prefetchDashboard`). Подписи под числами — чистые функции `model/tiles.ts`, причины стоп-листа и предложений — `stopCaption` и `hotCaption`, порции — `portionsText`, горизонт предложений по умолчанию — `defaultHotHorizonHours`, всё из `src/entities/dish`.
- Поток сигналов точки (SSE) — `src/app/realtime`: `PointLayout` держит поток открытой точки через `usePointEvents` и передаёт состояние связи в оболочку. Сигнал называет категории, а `point-signals.ts` сопоставляет их с префиксами ключей разделов; аналитику (`analyticsKeys` из `src/pages/analytics`) сигналы `stock`, `expiry`, `stop-list` и `orders` перечитывают отложенно через `invalidateLater`. Новый раздел данных точки, который меняют сигналы, получает строку в этой таблице, ключи берутся из фабрик раздела (`stockKeys`, `dishKeys`). Таймеров перечитывания нет: данные точки обновляются при открытии, возврате на вкладку, после своей записи и по сигналам. Поток с токеном — `openEventStream` из `src/shared/api`. В тестах пакет `eventsource` подменён на `FakeEventSource` из `@shared/lib/test-utils` (`vitest.setup.ts`): подключением, событиями и обрывом управляет тест.
- Организация — `src/entities/organization`: сотрудники точки, сама точка (`['points', pointId, 'staff' | 'point']`), точки компании (`['companies', companyId, 'points']`) и записи организации; кого из сотрудников может менять пользователь, решает `mayManageStaff`, роли для выбора и можно ли их назначить — `roleChoices`, роли и их подписи — `roles` и `roleLabels` из `src/shared/auth`. Страницы компании живут под адресом точки и показывают компанию выбранной точки: в `nav-items.ts` первый пункт группы задаёт подпись `heading` («Компания «<название>»»), в узкой панели вместо неё черта, короткая подпись пункта для узкой панели — `shortLabel`. Точка из ответа записи кладётся в кэш через `storePoint` из `src/entities/organization`, а после записи точки или компании профиль `/me` перечитывается через `refreshProfile` из `src/entities/profile`: переключатель, навигация и плашка отключённой точки обновляются сами. Диалог новой компании из переключателя — слой `src/features` (`features/create-company`). Карточка настроек — `SettingsSection` из `src/shared/ui/settings-section`, поле названия с «Сохранить» — `RenameForm` из `src/shared/ui/rename-form` (новое название с сервера само сбрасывает черновик, `key` не нужен; без права записи `readOnlyNote` показывает название текстом с пояснением), форма в диалоге — `FormDialog` из `src/shared/ui/form-dialog` (Enter отправляет форму, ширина — `maxWidth`, `pending` только у формы с запросом; заголовок и отступы кнопок диалогов задаёт тема, `aria-labelledby` Dialog ставит сам), инициалы человека — `Avatar` из `src/shared/ui/avatar`, у `ConfirmDialog` есть `confirmDisabled` для подтверждения вводом названия. Подключение сервиса доставки Мигом к точке видит и меняет только владелец: `migomQueryOptions` (`['points', pointId, 'migom']`) и `setMigomOnPoint` (номер заведения или `null`), карточка — `pages/point-settings/ui/migom-section.tsx`, номер разбирает `parseOutletId`. Строка статуса и форма «подключить по номеру» у Мигома и Telegram общие — `ConnectionStatus` и `NumberConnectForm` (`pages/point-settings/ui/number-connection.tsx`); кнопка отключения передаётся форме дочерним элементом. Поставщики компании и их ключи — раздел «Поставщики» на «Точках и компании» (`pages/company/api/suppliers.ts`, `ui/suppliers-section.tsx`, `ui/supplier-dialogs.tsx`): ответ записи кладётся в список без ключа, ключ показывает только окно ключа, и закрыть его можно только «Готово». Поставщик как автор поставки подписывается своим названием через `actorName`.
- Раздел «Каталог» — `src/pages/catalog`, только владелец (`products.manage`), пункт открывает группу компании в `nav-items.ts`. Layout `points.$pointId.catalog.tsx` держит заголовок, вкладки «Продукты» и «Блюда» с числами (запросы с `limit: 1`) и диалоги создания; страницы получают компанию, признак «только чтение» (компания отключена) и открытие диалога нового продукта через `useCatalogScope`. Состояние списков и открытое блюдо (`dish`) — в адресе. Запись в каталог и сигнал `catalog` перечитывают одно и то же — `refreshCatalog`: весь `catalogKey` компании, склад и меню точки; ответ записи кладётся в кэш продукта или блюда и не перечитывается. Отключена ли компания — `isCompanyDisabled` из `src/entities/profile`. Черновик рецептуры и проверки количеств — `model/recipe.ts`, поля диалога продукта — `model/product-form.ts`. Содержимое списков вкладок (заготовка, ошибка, пустой список, таблица или карточки с пагинацией) — `CatalogListBody`, действия строки — `RowActions`, оба из `ui/catalog-list.tsx`.
- Экраны ошибок (`not-found`, `forbidden`, `point-unavailable`, `profile-unavailable`, `auth-unavailable`) сгруппированы в `src/pages/errors/*`: steiger разрешает не больше 20 слайсов без группы.
- Ссылки роутера в компонентах MUI — `ButtonLink`, `TextLink`, `CardLink`, `TabLink` (вкладка внутри `Tabs`) из `src/shared/ui/link`: с ними проверяются путь и параметры. Вкладки раздела (склад, заказы, каталог) — `SectionTabs` оттуда же, хлебные крошки — `Breadcrumbs` и `BreadcrumbLink` из `src/shared/ui/breadcrumbs`.

## Запуск со входом

- Приложение работает только после входа через Keycloak. Keycloak и API поднимаются по [../backend/AGENTS.md](../backend/AGENTS.md); `pnpm dev` проксирует `/api` на `localhost:8080` (другой адрес — `API_PROXY_TARGET`).
- Dev-сервер должен работать на порту 5173: клиент `goden-web` разрешает возврат только на `http://localhost:5173/*`. `pnpm preview` (порт 4173) для входа не подходит.
- Адрес Keycloak, realm и клиент задаются `VITE_KEYCLOAK_*` (см. `.env.example`); без них используется локальный стенд.
- Раздел «Генератор» у владельца скрывает `VITE_GENERATOR_ENABLED=false` (см. `.env.example`); на сервере — `GENERATOR_UI=false` в `infra/.env`.
- Тестовые пользователи: `admin`, `manager`, `approver`, `cook`, `waiter`, пароль совпадает с логином. Точки и роли у них появляются после создания демонстрационной компании (`DEMO_COMPANY=true` при миграциях, см. [../backend/AGENTS.md](../backend/AGENTS.md)): `admin` — владелец, остальные назначены на первую точку. Без неё вход ведёт на создание компании.

## Страницы входа Keycloak

- Вход, регистрацию и другие страницы Keycloak рисует тема `goden` на Keycloakify. Её код лежит в `src/app/keycloak-theme/`: `login/KcPage.tsx` выбирает страницу по `pageId`, `login/template.tsx` — общий каркас, `login/pages/` — свёрстанные страницы, `login/i18n.ts` — тексты. `kc.gen.tsx` генерирует Keycloakify, он коммитится, руками не правим.
- Тема берёт компоненты и тему только из `@shared/*`, как и остальное приложение. Текст Keycloak с разметкой вставляет только `KcHtml` (`login/components/kc-html.tsx`): он очищает его через `kcSanitize`. `src/app/main.tsx` рисует страницу входа, если Keycloak передал `window.kcContext`, иначе запускает приложение.
- Посмотреть страницу без Keycloak: `pnpm dev` и адрес `http://localhost:5173/?kcPage=login.ftl`. Параметр `kcState` выбирает состояние из `login/mocks.ts`, например `?kcPage=register.ftl&kcState=field-errors`.
- `pnpm build:keycloak-theme` собирает тему в `dist_keycloak/goden-keycloak-theme.jar`. Ему нужен Maven, поэтому обычно тему собирает образ Keycloak (`infra/keycloak/Dockerfile`, см. [../backend/AGENTS.md](../backend/AGENTS.md)).

## Комментарии и JSDoc

- Обычные inline-комментарии — только на неочевидных участках (обычно ≤2 строк), не пересказ кода.
- JSDoc у публичных и переиспользуемых компонентов, хуков и типов — одна строка: что это и как этим пользоваться. Реализацию, причины решений и крайние случаи в JSDoc не пиши (подробнее — раздел «Комментарии и JSDoc»).
- **Комментарий и JSDoc понятны с первого прочтения.** Пиши обычными предложениями:
  - одна мысль — одно предложение, в нём есть кто и что делает;
  - связи словами, а не знаками: без `=`, стрелок и цепочек тире вместо «значит», «поэтому», «потому что»;
  - простые слова вместо внутреннего жаргона: «ответа ещё нет», а не «запрос без данных»;
  - сначала что делает код, потом зачем; цель прямо («чтобы не показывать тост на каждом шаге»), без «иначе было бы…»;
  - история решения и отвергнутые варианты живут в design.md, не в коде.
  Пример: не `// тот же адрес с новым объектом = сервер пересчитал ячейку`, а `// Если сервер прислал эту ячейку заново, перезапрашиваем расшифровку.`

Код документирует себя сам: имена и структура вместо пояснений. Комментарий — исключение и отвечает «почему», а не «что».

- Комментарий читает будущий читатель файла, а не собеседник текущей задачи. Никаких отсылок к диалогу, процессу и прошлым версиям («как в старой библиотеке», «по договорённости», «раньше было», «правило посадки из соседнего компонента») — этого контекста у читателя нет. Допустима только ссылка на факт кода: имя модуля, токен, селектор.
- **Максимум 2 строки.** Хочется больше — сначала спроси себя, правильно ли написан код: длинный комментарий почти всегда кандидат на переименование или разбиение. Развёрнутое «почему так» живёт в design.md, спеке или README модуля, не в файле с кодом.
- JSDoc на публичном API — одна строка: что это и как этим пользоваться. В нём бывает контракт, который не виден из типа: что значит `undefined` или `null`, какое значение с чем обязано совпадать. `@param`/`@returns` — только у неочевидной сигнатуры, кратко. В JSDoc не пишут, как устроен код, почему так сделано, поведение, видное из нескольких строк кода, и то, что уже описано у типа или утилиты: каждый факт описан в одном месте. Внутренним компонентам и пропсам с понятным именем JSDoc не нужен. Добавляя возможность, не дописывай новые фразы в существующие JSDoc.
- Решения и крайние случаи, обговорённые с агентом, в комментарии не переносятся. Их место — тест, CHECKLIST, design.md или README модуля.
- Если устройство модуля трудно понять без описания, заводи `README.md` в корне модуля (например, `ui/controls/collections/Table/README.md`). Это крайняя мера, только когда без описания модуль правда не понять. В README — как модуль устроен и почему так, а не пересказ кода.
- Перед тем как сообщить о готовности, просмотри все добавленные комментарии. Если читатель без контекста разговора ничего не потеряет без комментария, удали его.
- Закомментированный код не оставляем; TODO — только со ссылкой на задачу.
- CSS/конфиги — короткие подписи секций, не эссе.
